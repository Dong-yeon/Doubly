# Doubly

> **둘이라서, 두 배로.** 커플 운동·식단·여행·일상 공유 앱 + 트레이너 플랫폼

Doubly는 **관계(Relation) 기반 커플 라이프 공유 앱**입니다. 커플은 운동·식단·맛집·여행·일상을
함께 기록하며 서로를 응원하고, 트레이너는 여러 회원의 운동을 관리합니다.
모든 연결은 동일한 `relations` 구조 위에서 동작합니다.

> **향후 구상 (미착수)**: 커플로 시작한 관계를 **아이가 생기면 패밀리로 확장**하는 방향을
> 검토했습니다. 커플과 패밀리는 서로를 대체하지 않고 **공존**하며, 둘만의 공간(기념일·
> 오늘의 질문·경비 반반 정산)은 그대로 유지된 채 가족 단위 기록이 그 위에 얹히는 구조입니다.
> 설계안과 착수 시 주의사항은 [관계 모델](#관계-모델--커플--패밀리아이-공존) 참고.

> **브랜드**: Duo Color System — 나=Coral·상대=Indigo·함께=Violet, 배경은 Cream, 텍스트는 Ink.
> (내부 Java 패키지는 히스토리 보존을 위해 `com.fitto` 유지, 앱 식별자는 `com.doubly.app`)

## 운동 기록 모델 — 세트 단위 로그 (전환 예정)

> **상태: 부분 착수.** V28 에서 세트별 실기록 테이블(`workout_set_entries`)과 종목 마스터
> (`exercise_catalog`)가 이미 들어갔고, 세션 화면도 세트별 무게·RPE 입력과 직전 기록
> 프리필까지 지원합니다. 다만 **운동 중 실시간 서버 저장(세션 API)·중량 추천·볼륨/1RM
> 통계**는 아직 없어 여전히 "운동을 끝내고 한 번에 저장"하는 구조입니다.
> 상세 스펙(API·화면·체크리스트)은 **[PLAN.md — Workout Log v2](PLAN.md#feature-운동-기록-고도화-workout-log-v2--짐워크형-세트-로그)** 에 있습니다.

### 지향점

운동 기록의 **정확도는 짐워크 수준**으로 올리되, 짐워크 클론이 목적은 아닙니다.
짐워크는 개인 운동일지 앱이고, Doubly 는 그 결과를 **둘이 나누는** 앱입니다.
따라서 세트 로그·볼륨·1RM 은 *수단*이고, 목적은 **볼륨·PR·성장을 커플 피드·대결·스트릭에 태우는 것**입니다.
이 구분이 흐려지면 Doubly 가 존재할 이유가 사라집니다.

### 현재 구조가 막고 있는 것

| 지점 | 현재 | 그래서 불가능한 것 |
| --- | --- | --- |
| `workout_sets` 1행 = **종목 1개** 요약, 세트별 실기록은 자식 테이블 `workout_set_entries`(V28)에 저장 | 종목당 세트별 무게·횟수는 이제 저장됨 | (해결됨 — 아래 두 항목만 남음) |
| `exercise_name` 자유 문자열 → `exercise_catalog`(V28) 종목 마스터로 대체 | 종목별 이력·PR·직전 기록 자동 로드는 이미 구현됨 | (해결됨) |
| `category` = 근력/유산소/유연성 | **운동 종류**이지 부위가 아님 (UI 라벨만 "부위") | 가슴·등·하체 **부위별 볼륨 밸런스** |
| 통계가 "운동한 날 수 / 세트 수" | 무게 정보가 집계에 안 들어감 | **총 볼륨**, 추정 1RM, 성장 그래프 |
| **운동을 다 끝내고 한 번에 저장** (`POST /workout` 1회) | 종료 전까지 서버는 세션의 존재조차 모름 | **운동 중 실시간 기록**, 중량·세트 추천, 중단 복구 |
| `workouts.total_duration_min` | 컬럼만 있고 아무도 채우지 않음 | 세션 실측 시간 |

> `WorkoutSessionScreen` 은 이미 세트별 체크·휴식 타이머까지 짐워크형으로 만들어져 있고,
> 종료 시 `entries`(세트별 무게·횟수·RPE)를 함께 보내 `workout_set_entries` 에 저장합니다 —
> 더 이상 접어서 버리지 않습니다. 다만 ① 모든 상태가 여전히 컴포넌트 로컬 state 라
> **앱을 내리거나 폰이 꺼지면 운동 전체가 사라지고**, ② 서버가 세션 진행 중에는 개입하지
> 못해 **중량 추천이 붙을 자리가 없습니다**. **화면·세트별 저장은 v2, 세션 진행 방식은
> 여전히 v1**인 상태 — 남은 격차는 여기입니다.

### 사후 저장 → 운동 중 저장

구조적으로 가장 큰 갈림은 **저장 시점**입니다. 지금은 사후 저장(post-hoc)이라
운동 중에 서버가 개입할 수 없고, 그래서 **중량 추천이 붙을 자리가 없습니다.**

```
현재  [운동 시작] ────── 전부 로컬 state ────── [종료] → POST /workout (1회)
v2    [시작] POST /session → [세트마다] PUT /session/{id}/sets/{setId}
                            [추천]     GET /session/{id}/next
                          → [종료] POST /session/{id}/finish
```

- 세션이 서버에 살아있으면 **앱이 죽어도 이어서** 할 수 있고, **다음 세트 무게를 추천**할 수 있고,
  상대에게 **"지금 운동 중"** 을 띄울 수 있습니다 (마지막 항목은 짐워크에 없는 Doubly 고유 기능)
- 추천은 AI 가 아니라 **규칙 기반 더블 프로그레션**입니다 — 목표 횟수를 다 채우고 RPE ≤ 8 이면
  다음에 +2.5kg(하체 +5kg), 2회 연속 미달이면 −10% 디로드. 세트마다 Gemini 를 부르는 건
  느리고(수 초) 일일 한도를 먹습니다

### 전환 원칙

1. ~~**세션 → 종목 → 세트** 3단 구조. `workout_sets` 를 `workout_exercises` 로 개명하고,
   그 아래에 진짜 세트 테이블을 새로 만듭니다~~ → **완료(다른 형태로)**: 개명 대신
   `workout_sets`(종목 요약)는 그대로 두고 자식 테이블 `workout_set_entries`(V28)를
   신설했습니다
2. ~~**종목 마스터(`exercises`)를 둡니다.**~~ → **완료**: `exercise_catalog`(V28)로
   부위(`body_part`) × 기구(`equipment`) 분류 + 사용자 커스텀 종목을 구현했습니다.
   `exercise_name` 은 여전히 스냅샷으로 남아 종목 이름이 바뀌어도 과거 기록은
   당시 이름을 유지합니다. 운동 기록 추가·루틴 대체 종목·세션 종목 교체 세 화면 모두
   부위→기구 순으로 좁혀 고르는 공통 모달(`ExercisePickerModal`)로 통일했고, 그 과정에서
   기록 저장 시 `exerciseCatalogId`가 payload 에서 누락돼 카탈로그 연동이 조용히 끊겨
   있던 버그를 함께 고쳤습니다
3. **볼륨·1RM 은 저장하지 않고 계산합니다.** 볼륨 `Σ(weight × reps)`, 추정 1RM 은
   Epley `w × (1 + reps/30)`. 워밍업 세트와 유산소는 볼륨 집계에서 제외합니다
4. **PR(`workout_records`)만 별도 저장**합니다. 매 조회마다 전체 스캔할 수 없기 때문
5. **운동 중 세션은 `workouts.status` 로 구분합니다.** `IN_PROGRESS` 는 히스토리·통계·스트릭·
   피드·대결에서 **전부 제외**해야 합니다. 운동을 시작만 했는데 스트릭이 오르면 안 됩니다
6. **추천은 제안일 뿐 강제하지 않습니다.** placeholder 로만 띄우고 사용자가 덮어쓸 수 있어야 합니다.
   계산은 프론트가 아니라 **서버**에서 — 규칙이 바뀔 때 앱 배포를 기다릴 수 없습니다
7. **한 번에 다 하지 않습니다.** 스키마 → 종목 마스터/직전기록(✅ 완료) → **운동 중 세션** → 추천 →
   통계 → 커플 연동 순 (남은 단계 범위는 PLAN.md)

### 착수 시 주의사항

- **마이그레이션은 H2 에서도 돌아야 합니다.** 테스트가 운영과 동일한 Flyway 를 H2 에 적용합니다
  (→ [테스트 스키마](#테스트-스키마)). 기존 요약 행을 세트 행으로 펼칠 때 `generate_series` 는
  H2 에 없으므로 `VALUES` 조인을 씁니다
- **`UserDataPurger` 를 같이 고쳐야 합니다.** 새 테이블(`workout_sets` 신규 · `workout_records` ·
  커스텀 `exercises`)이 삭제 순서에서 빠지면 **회원 탈퇴 전체가 FK 위반으로 실패**합니다
  (→ [계정 삭제](#계정-삭제))
- **`status` 필터를 빠뜨리면 조용히 망가집니다.** `WorkoutRepository` 의 조회 쿼리 6개
  (`findByUserIdAndWorkoutDate…`·`findHistory`·`findWorkoutDates`·`countDistinctWorkoutDates`·
  `findRecentForFeed`·`findLastWorkoutDate`)에 `status = 'COMPLETED'` 를 전부 넣어야 합니다
- **테스트 3종이 `workout_sets` 를 직접 씁니다** — `WorkoutFlowTest` · `StreakFlowTest` ·
  `FeedFlowTest` 픽스처를 함께 수정해야 합니다
- **헬스장은 지하가 많습니다.** 세트 확정은 오프라인 큐 + 재연결 flush 가 필요하고,
  `setId` 기준 **멱등 upsert** 여야 중복 저장이 안 생깁니다
- **대결(`couple_challenges`) 기준을 볼륨으로 바꿀 때는 절대값을 쓰지 마세요.** 체급 차이 때문에
  불공정합니다. **직전 4주 대비 증가율**이 커플 대결에 맞습니다

## 관계 모델 — 커플 · 패밀리(아이) 공존

> **상태: 보류 (미착수).** 아래는 지향하는 구조이며 현재 코드는 커플(2인) 전용입니다.
> 착수 전에 **[착수 시 주의사항](#착수-시-주의사항)** 을 먼저 읽으세요 —
> 이 문서를 처음 쓴 이후 관계(relations) 주변 코드가 크게 바뀌었습니다.

### 원칙

1. **커플은 사라지지 않습니다.** 패밀리는 커플을 대체하는 게 아니라 **동시에 존재**합니다.
   한 사용자는 `COUPLE` 관계와 `FAMILY` 관계에 **동시에 소속**될 수 있습니다.
2. **둘만의 공간은 보존합니다.** 기념일 D-day, 오늘의 질문, 경비 반반 정산, 1:1 채팅은
   커플 관계에 그대로 남습니다. 아이가 볼 수 없습니다.
3. **아이는 처음부터 계정을 갖지 않습니다.** 신생아·미취학 아동은 로그인 주체가 아니라
   **보호자가 대신 기록하는 프로필**입니다. 나이가 차면 계정으로 승격합니다.

### 아이 프로필의 3단계 수명주기

| 단계 | 구분 | 로그인 | 설명 |
| --- | --- | --- | --- |
| 1 | **관리 대상 프로필** (managed) | ✗ | 보호자가 대신 기록. 성장·수유·수면·예방접종 기록의 대상. 계정 없음 |
| 2 | **연동 계정** (linked) | ○ | 아이가 자기 계정으로 로그인. 보호자는 여전히 조회·응원 가능 |
| 3 | **독립 계정** (independent) | ○ | 성인. 보호자 열람 권한 해제, 일반 사용자와 동일 |

승격은 되돌릴 수 없으며, 2→3 전환 시 보호자의 열람 범위를 아이가 직접 통제합니다.

### 관계 유형

```
RelationType
├── COUPLE          기존 — 2인 고정. 기념일·오늘의질문·반반정산
├── TRAINER_MEMBER  기존 — 트레이너 1 : 회원 N (관계를 N개 생성)
└── FAMILY          신규 — N인. 보호자(GUARDIAN) + 아이(CHILD)
```

`FAMILY` 관계는 멤버 수 상한이 없고, 각 멤버는 `member_role`(`GUARDIAN` / `CHILD`)을 가집니다.
`GUARDIAN`만 아이 프로필을 생성·수정하고 가족 설정을 변경할 수 있습니다.

### 아이 기능 (구상)

| 영역 | 내용 |
| --- | --- |
| **성장 기록** | 키·몸무게·머리둘레 기록 + 표준 성장곡선(백분위) 대비 그래프 |
| **식사 기록** | 수유(모유/분유·양)·이유식·간식. 기존 `meals` 구조 재사용 |
| **수면 기록** | 취침/기상 시각, 낮잠 횟수, 총 수면시간 추이 |
| **예방접종** | 국가 표준 접종 일정 기반 체크리스트 + 접종일 D-day 알림 |
| **함께 운동** | 아이와 함께한 활동(산책·놀이터·자전거)을 가족 스트릭에 반영 |
| **가족 피드** | 기존 피드에 아이 태그. 커플 전용 게시물과 가족 공개 게시물 분리 |
| **가족 여행** | 인원수 기반 경비 정산(반반 → N분할), 아이 준비물 체크리스트 프리셋 |
| **성장 앨범** | 월령별 사진 자동 그룹핑, 1년 회고 카드 |

### 집계 규칙 — "함께"의 정의

커플에서 "함께"는 **두 사람 모두**를 뜻했지만, 패밀리에서는 재정의가 필요합니다.

- **가족 스트릭**: 보호자 **전원** 달성 시 인정 (아이는 집계에서 제외 — 강박 방지)
- **아이 활동**: 별도 트랙으로 기록하되 스트릭에 부담을 주지 않음
- **경비 정산**: 아이는 **분할 대상에서 제외**, 보호자끼리 N분할

> ⚠️ **아동 데이터 취급**: 아이 프로필은 미성년자 개인정보에 해당합니다.
> 보호자 동의 절차, 최소 수집 원칙, 계정 승격 시 데이터 이관·삭제 정책이
> 구현 전에 확정되어야 합니다. 국내 개인정보보호법 및 스토어 아동 정책(COPPA 등) 검토 필요.

### 착수 시 주의사항

> 이 절은 커플 기반 코드를 N인으로 넓힐 때 **실제로 발목을 잡는 지점**을 모아둔 것입니다.
> 위 설계안을 쓴 이후 관계 주변 코드가 여러 차례 바뀌었으므로, 착수 전 반드시 확인하세요.

**1. 2인 가정이 모이는 3개 지점**

| 위치 | 문제 |
| --- | --- |
| `relations.user_a_id` / `user_b_id` | 3번째 멤버가 들어갈 자리가 물리적으로 없음 |
| `Relation.partnerOf()` | "상대방"이 1명이라는 전제로 스칼라 반환 |
| `relationStore.couple` (프론트) | 활성 커플 1개만 담는 단일 객체 |

`Relation.connect(userBId)` 도 **비어있는 B 슬롯을 채우는** 방식이라, 두 번째 사람이 들어오면
첫 번째를 덮어씁니다.

**2. `relation_members` 조인 테이블로 바꾸면 함께 고쳐야 하는 곳**

관계를 N인으로 넓히면 아래가 전부 깨집니다. 모두 `user_a_id` / `user_b_id` 를 직접 참조합니다.

| 파일 | 역할 | 왜 깨지나 |
| --- | --- | --- |
| `auth/service/UserDataPurger.java` | 탈퇴 시 정리 | 관계 조회가 A/B 컬럼 기준 |
| `relation/service/RelationRecordPurger.java` | 기록 완전 삭제 | 관계 단위 삭제 — 멤버 수와 무관하나 호출부가 2인 전제 |
| `relation/service/RelationRecordRestorer.java` | 기록 불러오기 | 동일 |
| `RelationRepository.findEndedCoupleBetween` | 재회 판별 | `(A=x and B=y) or (A=y and B=x)` 양방향 매칭 |
| `relations.restore_requested_by` | 불러오기 동의 | **"다른 사람이 요청하면 실행"이 2인에서만 성립.** N인은 전원 동의 판별이 필요해 컬럼 하나로는 불가 |

**3. 조회 스코프가 "활성 관계 1개" 전제**

`activeCouple(userId)` 패턴이 8개 서비스에 복제돼 있고 모두 `findFirst()` 로 **여러 관계 중
하나를 조용히 고릅니다**. 한 사용자가 커플과 패밀리에 동시 소속되면 여기서부터 어긋납니다.
관계 목록 반환 또는 명시적 `relationId` 파라미터로 바꿔야 합니다.

**4. 재설계가 필요한 집계 로직 (치환으로 해결 안 됨)**

여행 경비 정산(`TripExpenseService.settlement` 의 `divide(2)`), 커플 스트릭(2인 AND),
식단 목표(두 집합 `retainAll`), 챌린지(`ME|PARTNER|TIE`), 주간 결산(my/partner/both 3열),
오늘의 질문(`bothAnswered`), 채팅 읽음(`senderId <> 나 = 읽음`) — 산술 자체가 2인에 묶여 있습니다.

**5. 스키마 제약**

- `streaks` 의 `UNIQUE (relation_id, streak_type)` 는 그룹 내 개인 스트릭을 표현할 수 없고,
  `UNIQUE (user_id, streak_type)` 는 개인 스트릭이 관계 스코프가 아니라 **전역**이라
  한 사용자가 여러 그룹에 속하면 즉시 깨집니다
- `relations` 참조 FK 가 두 갈래 이름(`relation_id` / `couple_id`)으로 9개 테이블에 흩어져 있습니다
- `chat_messages.is_read` 가 단일 boolean 이라 N명 읽음 상태를 담을 수 없습니다
  (`chat_message_reads` 테이블 필요)

**6. 마이그레이션 작성 시**

테스트가 운영과 동일한 Flyway 마이그레이션을 H2 에 적용하므로
(→ [테스트 스키마](#테스트-스키마)), **H2 에서 동작하는 구문만** 사용해야 합니다.
`relation_members` 도입 시 기존 `user_a_id` / `user_b_id` 에서 backfill 한 뒤 컬럼을 제거하세요.

### 착수 시 주의사항

**1. 성장 엔진은 이미 있습니다 — 없는 건 "보이는 것"입니다**

`LevelResponse` 가 이미 이렇게 돕니다. **식단·운동 등록이 그대로 성장 재료**입니다.

```
XP = 운동 기록일 × 10 + 식단 기록일 × 5
level = floor(√(XP/20)) + 1
```

매일 둘 다 기록하면 하루 15 XP — Lv2=2일, Lv3=6일, Lv5=22일, Lv10=108일.
육성 곡선으로 이미 쓸 만합니다. 문제는 이게 `GET /summary/level` 로만 있고 화면에는
**`MyScreen`(홈 헤더 프로필 → MY)에 묻혀 있다**는 것입니다. 새 시스템을 만들기 전에
**기존 레벨을 눈에 띄는 곳으로 올리는 것만으로** 상당 부분이 해결될 수 있습니다.

커플 합산으로 키우려면 엔드포인트 하나만 더하면 됩니다(`LevelResponse.of` 에 두 사람의
일수를 합쳐 넣기). 슬로건 "둘이라서, 두 배로"가 문자 그대로 구현됩니다.

**무엇이든 "추가"하면 360×640 에서 잘립니다.** 넣으려면 기존 요소(D+ 블록 ≈ 108px)를
**대체**해야 합니다. 320×568 은 육성과 무관하게 이미 넘치므로, 그 크기까지 지원하려면
D+ 글자 크기(64pt)를 화면 높이에 따라 줄이는 작업이 별도로 필요합니다.

**3. 애니메이션 수단이 없습니다**

`reanimated` · `lottie` · `skia` 모두 미설치입니다. 쓸 수 있는 건 `react-native-svg` 와
RN 내장 `Animated`(현재 `Toast` · `SplashScreen` 에서만 사용)뿐입니다.
"계속 움직이는 캐릭터"는 라이브러리 도입 + 아트 외주가 선행돼야 하고,
홈 상시 애니메이션은 배터리·발열도 고려해야 합니다.

**4. 앱 아이콘 — 버섯 두 개 안도 시도했다가 되돌렸습니다**

브랜드 마크(겹친 두 하트)를 버섯 두 개로 바꿔 아이콘까지 만들어 적용했다가,
**"둘"이라는 의미는 유지되지만 앱 톤과 맞지 않아** 원복했습니다.

다만 그 과정에서 확인한 **현재 아이콘의 문제는 그대로 남아 있습니다**:

| 문제 | 내용 |
| --- | --- |
| 여백 과다 | 마크가 캔버스의 약 60% — 홈 화면 64px 에서 작고 흐리게 보임 |
| 배경 대비 | 크림(`#FBF8F3`) 배경이라 밝은 배경화면에서 묻힘 |
| 색 불일치 | 아이콘은 Pink `#FF7EB9` / Sky `#7DD3F0`, 앱 팔레트는 Coral `#FF6A4D` / Indigo `#4A5BFF` |

색 불일치는 `DoublyLogo.tsx` 의 `PINK`/`SKY` 상수에서 오는 것이라, 아이콘만 고치면
앱 안의 마크와 어긋납니다. **손보려면 둘을 함께** 바꿔야 합니다.

**5. ⚠️ 메이플스토리 등 기존 IP 를 참조하지 말 것**

주황버섯 같은 캐릭터는 넥슨의 IP 입니다. "버섯"이라는 형태 자체는 보호 대상이 아니지만,
특정 게임의 디자인을 따라가거나 그 브랜드를 연상시키면 상표·저작권 분쟁과 스토어 심사
리스크가 생깁니다. 마스코트를 쓰려면 **독자적으로 그려야** 합니다.

**5. 시들기(역성장)는 넣지 말 것**

- 이 문서가 이미 **"강박 방지"를 원칙**으로 두고 있습니다(→ 패밀리 절의 가족 스트릭 규칙)
- 스트릭이 이미 "끊기는" 역할을 합니다. 육성까지 시들면 **이중 처벌**입니다
- 커플 공동 육성에서 시들기는 **상대 때문에 내 것이 죽는** 상황을 만듭니다 — 관계 앱에서
  이건 마찰의 원인입니다. 압박은 "같이 하면 두 배로 빨리 자란다"는 **긍정 방향으로만**

**6. 홈 배경 사진은 유지하기로 했습니다**

육성 요소 자리를 만들려고 배경 사진 기능을 없애는 안을 검토했다가 접었습니다.
홈 컴포넌트 5개에 **"배경 사진 위 흰 글씨" 전제로 하드코딩된 색이 45곳**이라
(HomeScreen 15 · CoupleHero 10 · RecentPeek 8 · MemoryPeek 8 · QuickActions 4)
배경을 없애면 전부 테마 대응으로 다시 짜야 하고, 홈에 처음으로 다크모드가 적용됩니다.
게다가 기존 커플이 올린 사진이 사라지고, 커밋 `4199fa3`(사진을 지키려고 홈을 고정 화면으로
바꾼 작업)이 무의미해집니다. **경쟁 상대는 배경 사진이 아니라 D+ 블록입니다.**

**7. 신규 테이블을 만든다면 삭제 경로도 함께**

`users` / `relations` 참조 FK 가 20개가 넘습니다. 육성 상태를 테이블로 저장하면
`UserDataPurger` · `RelationRecordPurger` · `RelationRecordRestorer` 를 **모두** 갱신해야
합니다(→ [계정 삭제](#계정-삭제)). 하나라도 빠지면 탈퇴 전체가 FK 위반으로 실패합니다.

**8. 효과를 측정할 방법이 없습니다**

이벤트 분석 도구가 없습니다(Sentry 는 에러만 수집). 육성이 실제로 기록 등록을 늘리는지
확인할 수 없으므로, 큰 투자를 하기 전에 **최소한의 이벤트 로깅**(기록 버튼 클릭·홈 진입 등)을
먼저 붙이는 편이 낫습니다.

## 친구 그룹 · 러닝 크루 · 번개 (보류)

> **상태: 보류 (미착수).** 사용자 피드백에서 나온 방향 —
> *"커플 둘만 말고 친구 그룹도. 안산 러닝 그룹 코드 공유하고 참가하면,
> 번개로 장소·시간 올리고, 조인 누른 사람이 표시되고, GPS 로 그 시간 그 장소에 오면 포인트."*

### 하려는 것

| 단계 | 내용 |
| --- | --- |
| 그룹 | 커플 외 **N인 그룹**(예: "안산 러닝 그룹"). 초대 코드로 참가 |
| 번개 | 그룹 안에 **장소·시간**을 올리면 그룹원에게 푸시 |
| 조인 | 참가 버튼 → 참가자 목록 표시 |
| 체크인 | 해당 **시간·장소에 실제로 왔는지** GPS 로 확인 → 포인트 적립 |
| 리워드 | (후순위) 포인트 → 쇼핑몰 연계 |

### 선행 조건 — 관계 모델 N인 확장이 먼저다

**트레이너 기능은 이것과 다르다.** 트레이너는 회원 N명을 **N개의 2인 관계**로 만든다
(`TrainerService.activeMemberRelations` — 트레이너를 `user_a` 로 두고 회원마다 행 하나).
그룹방이 아니라 1:1 관계의 묶음이라, 셋이 함께 있는 방을 만들 수 없다.
`chat_messages.relation_id` 도 관계 하나를 가리켜 **한 관계 = 한 대화방**이다.

즉 이 기능은 위 [패밀리 절](#관계-모델--커플--패밀리아이-공존)의 `relation_members`
확장과 **같은 작업**이다 — 요구가 다른 방향(친구 그룹)에서 왔을 뿐 스키마 변경은 동일하다.
그쪽 [착수 시 주의사항](#착수-시-주의사항)을 그대로 읽을 것. 특히:

- `relations` 는 `user_a_id` / `user_b_id` 뿐이라 **3번째 사람이 들어갈 자리가 없다**
- `findByUserAndTypeAndStatus(...).findFirst()` 가 **19개 파일**에서 "활성 관계는 1개"를 전제한다
- `chat_messages.is_read` 가 단일 boolean 이라 N명 읽음 상태를 담을 수 없다

### 초대코드 분기 설계 — 타입은 코드를 만들 때 정한다

**지금 초대코드는 구조적으로 1회용이다.** 코드가 관계 행 하나에 묶여 있고,
`Relation.connect()` 가 연결과 동시에 `inviteCode = null` 로 지우며 `PENDING → ACTIVE` 로 바꾼다.
그래서 한 명이 들어오면 코드가 소멸한다.

**분기점은 이미 코드 생성 지점에 있다.** `RelationService.createCoupleInvite` 는
`relationType(COUPLE)` 을, `createTrainerInvite` 는 `TRAINER_MEMBER` 를 하드코딩한다.
여기에 `GROUP` 을 더하는 것이 자연스러운 확장이다.

> ⚠️ **인원수로 타입을 추론하지 말 것** — "여러 명 들어오면 그냥 그룹" 은 안 된다.
>
> 1. **보안 등급이 정반대다.** 그룹 코드는 여러 번 쓰여야 하고(크루에 코드 공유),
>    커플 코드는 반드시 한 번만 쓰여야 한다. 커플 관계엔 사진·채팅·기념일이 들어 있어
>    코드가 유출되면 제3자가 전부 보게 된다. 합치면 **커플이 약한 쪽 보안을 물려받는다.**
> 2. **3번째가 들어오면 기존 데이터의 의미가 소급해서 깨진다.**
>    경비 `divide(2)` 로 이미 정산된 금액이 틀린 값이 되고, 커플 스트릭(2인 AND)·
>    오늘의 질문(`bothAnswered`)·챌린지(`ME/PARTNER/TIE`)가 성립하지 않는다. 되돌릴 수도 없다.
> 3. **2명짜리 그룹은 커플이 아니다.** 크루에 아직 둘뿐이라고 D-day 와 오늘의 질문이
>    뜨면 안 된다. 인원수는 의도를 알려주지 못한다.

대신 **메커니즘은 하나로 통합하고 타입만 명시**한다. 가입 화면과 코드 입력 흐름은 공유하고,
코드를 만들 때 "둘이서 / 여럿이서" 를 한 번 고르게 한다.

| | 커플 | 그룹 |
| --- | --- | --- |
| 코드 사용 | **1회용** (지금 그대로) | **다회용** |
| 정원 | 2 | N (무제한 또는 상한) |
| 생성 직후 상태 | `PENDING` — 혼자면 아직 관계가 아니다 | `ACTIVE` — 혼자여도 그룹은 성립한다 |
| 개수 제한 | `hasActiveCouple` 로 1개 | 여러 개 허용 |

스키마는 `relations` 에 `max_members` 와 코드 재사용 여부(`code_reusable` 또는 남은 횟수)
정도만 붙이면 된다.

**이 설계가 N인 확장의 범위를 줄이는 지렛대다.** 타입이 명시되므로 커플 전용 기능
(챌린지·경비 반반·오늘의 질문·커플 스트릭)을 `relation_type = COUPLE` 에서만 켜지게
게이팅할 수 있고, 그러면 [위에서 센 재설계 대상](#선행-조건--관계-모델-n인-확장이-먼저다)을
지금 손대지 않아도 된다.

### 새로 필요한 테이블 (개략)

```sql
group_events              -- 번개: group_id, title, place_name, lat, lng, start_at, created_by
group_event_participants  -- 조인: event_id, user_id, joined_at, checked_in_at
point_ledger              -- 포인트 적립·사용 내역 (잔액을 컬럼으로 두지 말 것 — 원장으로)
```

푸시는 기존 `NotificationService`(Expo)를 그대로 쓸 수 있다.
신규 테이블을 만들면 `UserDataPurger` · `RelationRecordPurger` · `RelationRecordRestorer`
갱신을 **반드시 함께** 해야 한다(→ [계정 삭제](#계정-삭제)). 빠지면 탈퇴가 FK 위반으로 실패한다.

### ⚠️ 착수 전에 확인해야 할 것

**1. 위치정보는 법적으로 특별 취급이다**

국내에서 개인위치정보 수집·이용은 **위치정보법** 적용 대상이다. 사업자 신고 의무 여부와
**약관과 별도인 개인위치정보 동의 절차**를 먼저 확인해야 한다. 확정되면
`frontend/src/constants/legal.ts` 개정 + `PolicyVersion` 상향(재동의 게이트 발동)이 따라온다.
법률 검토 없이 GPS 수집을 붙이지 말 것.

**2. 포인트의 성격을 먼저 정해야 한다**

현금성·환급성 포인트는 규제 대상이 될 수 있고, **쇼핑몰 연계는 특히** 그렇다.
처음부터 **환급 불가한 뱃지성 포인트**로 설계하면 위험이 크게 줄어든다.
쇼핑몰 연계는 성격이 확정되기 전에는 착수하지 말 것.

**3. GPS 체크인은 조작될 수 있다**

포인트가 걸리는 순간 위치 위조 유인이 생긴다. 서버에서 **반경·시간창**을 검증해야 하고,
그래도 완벽 방어는 불가능하다. 포인트 가치가 클수록 리스크가 커지므로 1과 2의 결론에 묶인다.

**4. 배터리·권한**

백그라운드 위치 추적은 배터리와 권한 거부율 문제가 크다. **체크인 버튼을 눌렀을 때만
단발 조회**로 제한하는 편이 현실적이다.

**5. 브랜드 결정이 포함된다**

앱 이름이 "Doubly", 슬로건이 "둘이라서, 두 배로", 로고가 두 덩굴이 얽힌 하트,
컬러 시스템이 나·상대·함께 3색이다. 그룹이 들어오면 이게 전부 흔들린다 —
기술 리팩터링이 아니라 **제품 정체성 결정**이다.

### 단계적 접근 (권장)

법적 리스크가 없는 것부터 자르면 이렇게 된다.

| 단계 | 내용 | 선행 조건 |
| --- | --- | --- |
| 1 | 그룹 + 번개 + 조인 (GPS·포인트 없음) | 관계 모델 N인 확장만 |
| 2 | GPS 체크인 | 위치정보 동의 절차·법률 검토 |
| 3 | 포인트 | 포인트 법적 성격 확정 |
| 4 | 쇼핑몰 연계 | 3 완료 + 별도 검토 |

**1단계만으로도 피드백의 핵심**("여친 말고 친구랑도, 번개 잡고 조인")**은 충족된다.**
2~4 는 법적 준비가 끝난 뒤에 붙이는 게 안전하다.

## 브랜드 결정 — "그룹이 들어오면 Doubly 가 맞나" (미결)

> **상태: 미결.** [그룹 기능](#친구-그룹--러닝-크루--번개-보류)을 붙이면 제품 정체성이
> 흔들린다는 문제 제기에서 나왔다. **출시 전에 답해야 하는 질문이다** — 아래 되돌릴 수
> 없는 항목 때문이다.

### 브랜드가 "2" 에 묶인 지점 (실측)

| 항목 | 값 | 바꾸는 비용 |
| --- | --- | --- |
| `ios.bundleIdentifier` / `android.package` | `com.doubly.app` | **출시 후 사실상 불가** |
| 앱 이름 / slug | `Doubly` / `doubly` | 스토어 등록 전이면 저렴 |
| 슬로건 "둘이라서, 두 배로" | 스플래시·로그인·MY·PWA 설명 **4곳** | 저렴 |
| `Doubly` 문자열 | **28개 파일** | 저렴 |
| 로고 | 두 덩굴이 얽혀 이루는 하트 | 저렴 |
| Duo Color System | 나·상대·함께 3색 | N인이면 인덱스 팔레트 필요 |

### ⚠️ 되돌릴 수 없는 것은 번들 ID 하나뿐이다

`com.doubly.app` 은 스토어에 한 번 올리면 바꿀 수 없다. 바꾸면 **기존 앱과 완전히 다른 앱**이
되어 사용자·리뷰·순위를 전부 잃는다. 나머지(이름·슬로건·로고·문자열)는 언제든 저렴하게 바꾼다.

**그래서 지금이 결정 비용이 가장 싼 시점이다.** 아직 스토어 미출시이므로
개명이 가능하고, 출시하는 순간 ① 외의 선택지가 닫힌다.

### 선택지

| 안 | 내용 | 비용 |
| --- | --- | --- |
| **① Doubly 유지 + 그룹은 부가 기능** | 슬로건만 "**함께**라서, 두 배로" 로 한 단어 교체. "두 배"가 인원수가 아니라 *함께 해서 생기는 효과*로 읽힌다. 로고(얽힌 덩굴)도 "연결"로 계속 통한다 | 최소 |
| ② 개명 — 그룹을 메인으로 | 번들 ID·이름·로고·슬로건 전부 교체. 제품 재정의 | 큼. **출시 후 불가** |
| ③ 그룹을 안 함 | 커플 앱으로 완성. 정체성 유지 | 성장 경로를 닫음 |

### 권장 — ①, 단 조건부

그룹이 *부가 기능*으로 남을지 *메인*이 될지는 **써봐야 안다.** 그런데 이 앱엔 이벤트 분석
도구가 없어서(Sentry 는 에러만 수집) **나중에도 알 수 없다.** 그래서 순서를 이렇게 둔다.

1. 슬로건만 "함께라서, 두 배로" 로 교체 — 이름·번들 ID 는 유지
2. 그룹 1단계(번개 + 조인)를 붙이되 **커플 기능은 `relation_type = COUPLE` 에 게이팅**
3. **최소한의 이벤트 로깅**을 먼저 붙여 그룹 사용 여부를 측정
   (→ [게임화 절](#게임화--육성-시스템-보류)의 "효과를 측정할 방법이 없다" 와 같은 문제)
4. 데이터가 "그룹이 메인" 이라고 말하면 **출시 전에** ② 를 재검토

②를 지금 결정하기엔 근거가 없다 — 피드백 한 건으로 되돌릴 수 없는 번들 ID 를 바꾸는 것은
과한 베팅이다. 반대로 ③ 은 이름 때문에 기능을 포기하는 것이라 더 아깝다.

> **판단 기한**: 스토어 등록(EAS Build → 제출) 직전. 그 이후에는 ① 만 남는다.

### 왜 지금 넣었나

한도 숫자를 정할 데이터가 없어서 제한은 켤 수 없지만, **게이팅 코드를 나중에 넣으면
컨트롤러 33개·화면 54개에 소급**해야 한다. 그래서 경로만 먼저 깔고 값은 열어뒀다.
특히 운동 v2의 세션·통계 부분이 아직 남아 있어, 새로 짜는 코드는 처음부터 플랜을 인지한 채로 태어난다.

### 과금 단위는 사람이 아니라 커플이다

공동 콘텐츠는 전부 `couple_id` 에 매달려 있다. 개인 단위로 판정하면 같은 여행·피드를
**한 명은 보고 한 명은 못 보는** 상태가 되어 커플 앱이 성립하지 않는다.

| 대상 | 판정 |
| --- | --- |
| 커플 기능 (여행·맛집·캘린더·추억·AI 데이트코스…) | **두 사람 중 높은 등급** (`Feature.isCoupleScoped()`) |
| 개인 기능 (운동/식단 통계·체중·개인 AI 코치) | 본인 등급 |

구독은 **`users` 에 붙인다.** 관계는 끊기고 다시 생기므로(REL-07) 거기에 묶으면
재회 시 결제한 사람이 자기 구독을 잃는다. 커플 등급은 조회 시점에 해석한다.

> 한쪽만 결제해도 둘 다 쓰므로 **커플당 결제 1건이 정상**이다.
> 가격은 1인 기준이 아니라 **커플 기준**으로 잡아야 한다.

### 에러 코드 — 402 와 429 를 나누는 이유

| 상황 | 코드 | 앱 동작 |
| --- | --- | --- |
| 무료에서 막힌 기능 | `PLAN_UPGRADE_REQUIRED` (402) | 업그레이드 안내 |
| 무료 한도 초과 | `PLAN_LIMIT_EXCEEDED` (402) | 업그레이드 안내 |
| **유료** 한도 초과 | `USAGE_LIMIT_EXCEEDED` (429) | "한도 소진" 안내만 |

돈 낸 사용자에게 결제를 또 권하지 않기 위해 유료 초과는 402 가 아니다.
402 는 `api/client.ts` 가 한 곳에서 가로채 `planStore.gate` 로 넘긴다 —
화면마다 분기하면 같은 코드가 60곳에 흩어진다.

### 적용된 게이팅

**핵심 규칙: 402 는 사용자가 직접 누른 동작에만 쓴다.** 화면이 자동으로 부르는 조회를
402 로 막으면 앱을 열 때마다 업그레이드 시트가 뜬다 — 그건 기능 안내가 아니라 광고다.

| 기능 | 세는 지점 | 초과 시 |
| --- | --- | --- |
| AI 7종 | `GeminiClient.requireConfiguredAndCountUsage` | 402 |
| 사진 업로드 | `POST /uploads/signature` | 402 |
| 진행 중인 여행 | `TripService.save` | 402 |
| 맛집 핀 | `PlaceService.save` | 402 |
| 내 운동 루틴 | `WorkoutRoutineService.save` · `.copy` | 402 |
| 즐겨찾는 음식 | `FavoriteFoodService.save` | 402 |
| 커플 캘린더 일정 | `CalendarService.create` | 402 |
| 여행 경비 정산 | `TripExpenseService.add` | 402 |
| 여행 준비물 | `TripChecklistService.add` | 402 |
| 커플 배경 꾸미기 | `RelationService.setCoupleBackground` | 402 |
| **추억 리마인드** | `MemoriesService.memories` | **200 + `locked: true`** (홈이 매일 부른다) |
| **주간 결산** | `SummaryService.weeklyRecap` | **200 + `locked: true`** (MY 탭이 매번 부른다) |

- **진행 중인 여행만 센다.** 지난 여행까지 세면 무료 사용자가 *추억을 지워야* 새 여행을
  만들 수 있게 된다 — 기록 앱이 해서는 안 되는 압박이다
- **추억 푸시(10시 KST)도 무료 커플에는 보내지 않는다.** 열어봐야 잠겨 있는 알림은 보내지 않는다
- 기존 하드코딩 상한(`MAX_ROUTINES=30`·`MAX_FAVORITES=50`)은 `Feature` 의 PRO 값으로
  옮겼다 — 상한의 출처를 한 곳으로 모으기 위해서다

### 잠금 UI · 업그레이드 시트

| 파일 | 역할 |
| --- | --- |
| `components/UpgradeSheet.tsx` | 402(`PLAN_UPGRADE_REQUIRED`/`PLAN_LIMIT_EXCEEDED`) 를 받으면 뜨는 전역 시트. `App.tsx` 최상단에 마운트 |
| `components/LockedCard.tsx` | 자동 조회가 잠겼을 때(`locked: true`) 그 자리에 대신 그리는 카드. 탭하면 그때 시트를 연다 |
| `store/planStore.ts` | `load()`(로그인/부팅 시 1회) · `showUpgrade()`(잠금 카드 탭 시) |
| `PURCHASE_ENABLED` (`constants/config.ts`) | `false` — 결제 미연동. 시트가 "PRO 시작하기" 대신 "준비 중" 을 보여준다 |

**두 갈래로 나뉜다** — 어느 쪽인지는 사용자가 <b>직접 누른 동작</b>인지로 정해진다.

- **사용자가 누른 동작** (여행 만들기·맛집 추가·사진 올리기…) → 서버가 402 →
  `api/client.ts` 가 가로채 `planStore.gate` 에 담음 → `UpgradeSheet` 자동 오픈
- **화면이 자동으로 부르는 조회** (홈의 추억, MY 탭의 주간 결산) → 서버는 402 를
  던지지 않고 `locked: true` 로 응답 → 화면이 원래 카드 자리에 `LockedCard` 를 끼움 →
  탭하면 `planStore.showUpgrade()` 로 그제서야 시트가 열림

이렇게 나눈 이유: 자동 조회를 402 로 막으면 **앱을 열 때마다 업그레이드 시트가 뜬다** —
기능 안내가 아니라 광고가 된다.

> ⚠️ **`WeeklyRecapCard` 를 직접 쓰는 곳이 있다면 `recap.locked` 를 먼저 확인해야
> 한다.** 잠기면 모든 수치가 0 으로 내려오므로, 확인 없이 그리면
> **"지난주에 아무것도 안 했어요"** 로 보인다. `MyScreen` 은 이미 분기돼 있다.

**의도적으로 연결하지 않은 것**

| 기능 | 왜 |
| --- | --- |
| `FULL_STATS` | 지금 "전체 기간" 값은 `totalDays` 하나뿐이다. 총 운동 일수를 가리는 건 값어치도 없고 쩨쩨하다. 이 게이트의 실제 대상은 **운동 v2 의 볼륨·1RM·부위별 밸런스**이고, 그건 아직 없다 |
| `PREMIUM_STICKER` | 프리미엄 스티커 팩이 아직 없다. 현재 16종은 전부 무료 |

> ⚠️ **`imageUpload.ts` 의 폴백 조건을 넓히지 말 것.** 예전에는 서명 발급이 실패하면
> 무조건 unsigned preset 으로 넘어갔는데, 그러면 한도 초과(402)를 받아도 조용히 우회해서
> **게이팅이 아무 일도 하지 않는다.** 폴백은 서버가 `UPLOAD_NOT_CONFIGURED` 라고
> 명시한 경우에만 한다.

**남은 구멍(의도적으로 열어둠)**: Cloudinary 서명은 `folder`+`timestamp` 만 서명해
발급 후 1시간 동안 재사용할 수 있다. 즉 앱을 고친 클라이언트는 서명 1개로 여러 장을
올릴 수 있다. 서명에 `public_id` 를 포함시키면 재사용이 같은 객체를 덮어써서 막히지만,
**운영 업로드 경로의 서명 규약을 바꾸는 일**이라 실기기 검증 없이 건드리지 않았다.
지금의 위험은 악의적 사용자가 아니라 **정상 사용량이 무료 티어를 넘기는 것**이고,
그건 서명 발급 시점 카운트로 충분히 막힌다.

### AI 한도는 두 겹이다

1. **기능별 · 플랜별** — `Feature` 의 숫자 (무료 음식사진 2회/일, PRO 30회/일 등)
2. **사용자별 총량 안전망** — `fitto.gemini.daily-limit-per-user`.
   Google AI Studio 무료 티어는 **프로젝트 단위** 일일 한도가 따로 있어서, 기능별 한도를
   아무리 잘 잡아도 사용자가 늘면 프로젝트 쿼터가 먼저 터져 **전원이** AI 를 못 쓴다

한도의 "오늘"은 **KST 기준**이다. 서버가 UTC 라 `LocalDate.now()` 를 쓰면 일일 한도가
한국 시간 **오전 9시**에 리셋된다.

## 실행 방법

전체 단계는 **[docs/RUNNING.md](docs/RUNNING.md)** 참고. 요약:

```bash
# 1) 인프라 (PostgreSQL + Redis)
docker compose up -d

# 2) 백엔드 (스키마는 Flyway 자동 생성)
cd backend && ./gradlew bootRun
#   확인: curl http://localhost:8080/api/v1/health

# 3) 프론트엔드
cd frontend && npm install && npm start   # a: Android, i: iOS, w: Web
```

- 백엔드 환경변수: `backend/.env.example` 참고 (`DB_*`, `REDIS_*`, `JWT_SECRET`, `GEMINI_*`, `CLOUDINARY_*`, `MAIL_*`, `GOOGLE_CLIENT_IDS`)
- 구글 로그인: Google Cloud Console 에서 OAuth 클라이언트(웹 + Android)를 만들고,
  같은 id 를 **프론트**(`frontend/src/constants/config.ts` 의 `GOOGLE_AUTH`)와
  **백엔드**(`GOOGLE_CLIENT_IDS`) 양쪽에 넣어야 동작합니다. 비워두면 버튼이 숨겨집니다.
- 비밀번호 재설정 메일: 미설정 시 인증코드가 **서버 로그로 출력**됩니다(개발 전용).
  운영은 **Resend(HTTP)** 를 사용합니다 — Railway 가 SMTP 아웃바운드를 막기 때문.
  `RESEND_API_KEY` 만 넣으면 되고, 절차는 [docs/RAILWAY.md](docs/RAILWAY.md) 2-1절 참고.
  (도메인 인증 전 기본 발신자 `onboarding@resend.dev` 는 본인 계정으로만 발송되는 테스트
  전용 — 실사용자 발송은 도메인 인증 필요)

### ⚠️ 약관 본문 — 출시 전 필수 작업

`frontend/src/constants/legal.ts` 의 자리 표시자는 **채워졌습니다**
(운영 주체 = 개인 개발자, 연락처 = `CONTACT_EMAIL` 단일 출처).
다만 본문은 여전히 **법률 검토를 받지 않은 초안**이므로 배포 전 검토가 필요합니다.
특히 [그룹 기능](#친구-그룹--러닝-크루--번개-보류)의 GPS 수집을 붙이면
개인위치정보 동의 조항이 새로 필요하고, 그때 `PolicyVersion` 을 올려 재동의를 받아야 합니다.

약관을 개정할 때는 **두 곳의 버전을 함께** 올려야 기존 사용자에게 재동의를 받을 수 있습니다.

| 위치 | 상수 |
| --- | --- |
| `frontend/src/constants/legal.ts` | `TERMS_VERSION` / `PRIVACY_VERSION` |
| `backend/.../common/policy/PolicyVersion.java` | `TERMS` / `PRIVACY` |

**재동의 게이트**: 버전이 올라가면(또는 V23 이전 가입자처럼 동의 이력이 `NULL` 이면)
`GET /auth/me` 의 `requiresConsent` 가 `true` 로 내려오고, 앱은 메인 대신
재동의 화면(`ConsentGateScreen`)을 띄워 동의(`PUT /auth/me/consent`) 전까지 진입을 막습니다.

### 테스트 스키마

테스트는 **운영과 동일한 Flyway 마이그레이션**을 H2(PostgreSQL 모드)에 적용하고,
`ddl-auto: validate` 로 엔티티↔스키마 불일치까지 검증합니다.

이전에는 Flyway 를 끄고 `ddl-auto: create-drop` 을 썼는데, 엔티티가 `@ManyToOne` 대신
평범한 `Long` 컬럼을 쓰는 구조라 **Hibernate 가 외래키를 생성하지 않았습니다.**
그 결과 테스트 스키마에는 FK 가 하나도 없어, 운영에서만 터지는 FK 위반을 테스트가
원천적으로 잡을 수 없었습니다 — 실제로 회원 탈퇴가 그렇게 깨져 있었습니다.

새 마이그레이션을 추가할 때는 **H2 에서도 동작하는 구문**을 써야 합니다
(`JSONB`, 부분 인덱스, `ON CONFLICT` 등은 사용 불가).

### 계정 삭제

`users` / `relations` 를 참조하는 외래키가 20개가 넘습니다. 개인 데이터 삭제 순서는
`auth/service/UserDataPurger.java`, 관계(커플) 콘텐츠 삭제 순서는
`relation/service/RelationRecordPurger.java` 한 곳에 모여 있으니 (탈퇴·지난 기록 완전
삭제가 공용으로 씀 — [지난 기록](#지난-기록--숨김--삭제--불러오기) 참고), **`relations`
를 참조하는 테이블을 추가하면 두 파일 중 해당하는 쪽도 함께 갱신**해야 합니다.
하나라도 빠지면 탈퇴·완전 삭제 전체가 FK 위반으로 실패합니다 —
`relation_members`(`V32__relation_members.sql`)가 삭제 순서에서 빠져 있던 게
실제로 그렇게 터진 사례입니다 (`relations` 삭제 전에 먼저 지워야 함).

> ⚠️ **한쪽이 탈퇴하면 커플 공동 기록(맛집·피드·여행)이 양쪽 모두에서 삭제됩니다.**
> `couple_id` 가 `NOT NULL` 이라 관계 없이는 존재할 수 없기 때문입니다.
> 상대의 개인 기록(운동·식단·체중)은 보존되며 관계 참조만 끊깁니다.

### 지난 기록 — 숨김 · 삭제 · 불러오기

연결을 끊어도 기록은 **삭제되지 않고 보이지 않는 상태**로 남습니다
(모든 커플 콘텐츠 조회가 `ACTIVE` 관계 기준이기 때문). 재회 시 불러오기 위한 설계입니다.

| 동작 | 상태 |
| --- | --- |
| 연결 끊기 → 기록 숨김 | ✅ 동작 중 |
| 지난 기록 완전 삭제 (`DELETE /relations/{id}/records`) | ✅ 완료 |
| 재연결 후 불러오기 (`POST /relations/couple/records/restore`) | ✅ 완료 |

**불러오기 규칙 (REL-07)**
- 재연결하면 **새 관계**가 생기고 기본값은 빈 상태입니다. 재연결에 동의한 것과
  옛 기록을 다시 보는 데 동의한 것은 다르므로, 자동 복원하지 않습니다
- **양쪽이 모두 요청해야** 복원됩니다. 첫 요청은 `WAITING_PARTNER` 로 접수만 되고,
  같은 사람이 두 번 눌러도 실행되지 않습니다 (`relations.restore_requested_by`)
- 행을 복사하지 않고 `couple_id` 참조만 새 관계로 옮기므로 사진·메시지 원본은 그대로입니다
- **커플 스트릭은 복원하지 않습니다.** 헤어져 있던 기간만큼 실제로 끊겼으므로,
  그대로 가져오면 공백을 건너뛴 가짜 연속 기록이 됩니다 (개인 스트릭은 영향 없음)
- 기념일·배경은 새 관계에 값이 없을 때만 승계합니다
- 다른 사람과 재연결한 경우 이전 상대와의 기록은 대상이 아닙니다

**완전 삭제 규칙**
- 연결을 끊은 관계에만 가능 (활성 관계는 `409 RELATION_STILL_ACTIVE`)
- **한쪽이 지우면 양쪽 모두에서 사라지고 되돌릴 수 없습니다.** 개인정보 삭제 요구를
  상대 동의에 묶을 수 없어 단독 삭제를 허용하되, 앱에서 2단계로 확인받습니다
- Cloudinary 이미지까지 삭제하며, **트랜잭션 커밋 이후**에 지웁니다
  (트랜잭션 안에서 지우면 롤백 시 파일만 사라진 상태가 됩니다)

> ⚠️ **Cloudinary 미설정 시 이미지가 남습니다.** `fitto.cloudinary.*` 가 비어 있으면
> DB 행만 지워지고 이미지 URL 은 계속 살아있어 "완전 삭제"가 되지 않습니다.
> 삭제하지 못한 건수는 경고 로그로 남습니다.

### 사진 보관 정책 — 구글포토와의 역할 분담

**Doubly 는 사진 창고가 아닙니다.** 갤러리 전체 자동 백업·공유는 구글포토에 맡기고,
Doubly 는 *맥락이 붙은 기록*(어느 여행 며칠차, 무엇을 먹고 어디를 갔는지, 스트릭·반응)만 담습니다.

**왜 자동 백업을 넣지 않는가**

| 이유 | 내용 |
| --- | --- |
| 용량·비용 | Cloudinary 무료 티어(≈25GB)는 커플 1~2쌍이면 소진. 동영상까지 넣으면 객체 스토리지(R2 등)로 이전 + 월 수만원대 비용이 발생 |
| **구글포토 API 제한** | 2025-03-31 부로 `photoslibrary.readonly` 등 권한이 제거되어, **서드파티 앱은 사용자의 기존 라이브러리를 읽을 수 없습니다**(403). 앱이 직접 올린 항목만 접근 가능 |
| 대체재 존재 | 구글포토 **파트너 공유**가 "내 사진을 특정 상대에게 자동 공유"를 이미 제공 |

**연동 방향 (권장)**: 구글포토 [Picker API](https://developers.google.com/photos/support/updates) 는 사용자가
직접 고르는 방식이라 기존 기기 갤러리 선택과 실질적으로 동일해 이점이 적습니다.
대신 **공유 앨범 URL 을 여행·일정에 붙이는 링크 필드**가 비용 0 으로 같은 목적을 달성합니다. (미구현)

**소스맵 업로드** — 코드 배선은 완료: `metro.config.js`(getSentryExpoConfig)가 번들에
Debug ID 를 심고, `app.json` 의 Sentry 플러그인이 빌드 시 자동 업로드합니다.
빌드 환경에 `SENTRY_ORG` / `SENTRY_PROJECT` / `SENTRY_AUTH_TOKEN`(EAS 환경변수, 최초 1회)이
있어야 실제로 업로드되며, 없으면 조용히 생략됩니다 — 등록 절차는

**개인정보처리방침**: Sentry 는 처리 위탁 대상이므로 `legal.ts` 위탁 목록에 추가했고,
`PRIVACY_VERSION` 을 1.1 로 올렸습니다(백엔드 `PolicyVersion.PRIVACY` 와 동기화).
- 앱 API 주소: `frontend/src/constants/config.ts` (iOS/웹=localhost, Android 에뮬=10.0.2.2, 실기기=PC LAN IP)
- 커플·채팅 기능 확인에는 계정 2개가 필요합니다.

### 로컬 개발 (수정 → 즉시 확인)

UI 를 고칠 때마다 빌드해서 올리지 말고 개발 서버를 켜두면 **저장하는 즉시 브라우저에 반영**됩니다.

```bash
cd frontend && npm run web      # http://localhost:8081 (Fast Refresh)
```

- 백엔드는 배포된 Railway 를 그대로 씁니다(`config.ts` 의 `USE_LOCAL_BACKEND = false`).
  단, **Railway 의 `CORS_ALLOWED_ORIGINS` 에 `http://localhost:8081` 을 추가**해야
  브라우저 요청이 통과합니다(운영은 빈 값이면 전부 차단).
- 백엔드까지 로컬로 돌리려면 `USE_LOCAL_BACKEND = true` + `docker compose up -d` + `./gradlew bootRun`.
- 같은 와이파이의 폰에서 보려면 `http://<PC-LAN-IP>:8081` — 그 주소도 CORS 목록에 넣어야 합니다.

**Netlify 배포는 검증이 끝난 뒤에만** 하면 됩니다(아래).

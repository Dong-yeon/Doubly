# 럽슐랭 — 카테고리·상태 중복 분석 (2026-08-28)

> 계기: "카테고리가 너무 많고, 가고 싶어요/다녀왔어요 기능이 중복되는 것 같다"는 지적.
> 코드(`PlaceScreen.tsx`, `placeFilters.ts`, `PlaceAddScreen.tsx`, `Place.java`)를 실제로
> 읽고 확인한 결과.

## 결론 먼저

- **카테고리 12개는 실제로 과합니다.** 화면 진입 시 상단에 모드(3)+서브뷰(2)+카테고리(13)+
  검색창+상태(3) 5단이 쌓여서, 목록이 뜨기도 전에 필터 UI만 한 화면 가까이 채웁니다.
- **"가고 싶어요/다녀왔어요" 자체는 중복 기능이 아닙니다** — 5곳에서 보이지만 그중 3곳(목록
  배지·상세 칩·지도 범례)은 같은 값을 보여주기만 하는 정상적인 표시입니다.
- **다만 진짜 중복은 따로 있습니다**: 이 상태를 **정하는 경로가 두 개**입니다 — 장소
  추가/수정 화면에서 수동으로 고르는 것과, 방문 기록을 남기면 자동으로 바뀌는 것. 이 둘이
  서로 안 맞을 수 있어서(방문 기록 0건인데 "다녀왔어요") 사용자가 느낀 "왜 두 개가 있지"는
  라벨이 아니라 이 이중 경로였을 가능성이 큽니다.

## 1. 카테고리 — 얼마나 쌓여 있나

`constants/placeCategories.ts`:

```
한식 · 중식 · 일식 · 양식 · 카페 · 디저트 · 술집 · 여행지 · 박물관·전시 · 액티비티 · 숙소 · 기타
```

12개 + "전체" = 13개 칩. 이 목록 하나를 **장소 추가 화면(선택)**과 **가이드·둘러보기 목록
(필터)** 둘 다 그대로 재사용한다(`placeFilters.ts` 주석에 명시) — 그 자체는 설계가 맞습니다
(목록이 갈라지지 않게 한 곳에서 관리). 문제는 **개수**입니다.

`PlaceScreen.tsx`를 따라가면 "둘러보기" 진입 시 쌓이는 순서:

1. 모드 칩 3개(가이드/둘러보기/콘텐츠)
2. 목록↔지도 서브 토글 2개
3. **카테고리 필터 13개** (`flexWrap`으로 3~4줄까지 접힘)
4. 검색창
5. 상태 필터 3개(전체/가고 싶어요/다녀왔어요)

지도 모드에서도 카테고리·상태 필터 두 줄이 그대로 위에 얹힌 채 지도가 시작됩니다. 커플
2인용 캐주얼 기록 앱치고는 필터 레이어가 많습니다 — 카테고리 하나 고르려면 최대 13개 중
스캔해야 합니다.

**한식/중식/일식/양식 4개**는 사실상 "음식점"이라는 같은 상위 개념을 국가별로만 쪼갠
것입니다. 이 4개를 "음식점" 하나로 합치면 12개 → 9개(음식점·카페·디저트·술집·여행지·
박물관·전시·액티비티·숙소·기타)로 줄고, 세부 구분이 필요하면 검색어나 장소 이름으로도
충분히 좁혀집니다.

### 제안 (우선순위순)

1. **한식/중식/일식/양식 → "음식점" 통합**: 카테고리 12 → 9. 가장 낮은 리스크 — DB
   마이그레이션 없이 프론트 상수 + 기존 데이터 값 매핑만 하면 됨(기존 저장된
   한식/중식/일식/양식 값을 화면 표시만 "음식점"으로 묶고 실제 카테고리 값은 유지하거나,
   원한다면 DB 값 자체를 마이그레이션).
2. **카테고리 필터를 상시 노출 칩 대신 접이식으로**: 지금은 13개가 항상 펼쳐져 있음.
   "카테고리 ▾" 버튼 하나 + 바텀시트/드롭다운으로 바꾸면 목록 화면 상단이 훨씬 가벼워짐.
   장소 추가 화면의 선택 칩은 그대로 둬도 무방(1회성 선택이라 부담이 다름).
3. **실사용 분포 확인 후 추가 정리**: 지금은 카테고리별 실제 저장 개수를 모른다 —
   `기타`/`술집`/`디저트`처럼 거의 안 쓰이는 카테고리가 있다면 그것부터 빼는 게 더 정확한
   판단. (`SELECT category, count(*) FROM places GROUP BY category`로 5분이면 확인 가능)

## 2. "가고 싶어요 / 다녀왔어요" — 어디서 왜 보이나

`status`(`PlaceStatus`: `WISHLIST`/`VISITED`)가 실제로 등장하는 5곳:

| 위치 | 역할 | 비고 |
| --- | --- | --- |
| `PlaceAddScreen.tsx` | **입력** — 추가/수정 시 수동 선택 | ⚠️ 아래 참고 |
| `placeFilters.ts` `STATUS_FILTERS` | **필터** — 둘러보기 목록·지도 좁히기 | 정상 |
| `PlaceScreen.tsx` 목록 카드 | **표시** — 배지 | 정상(단순 읽기) |
| `PlaceScreen.tsx` 지도 범례 | **표시** — "다녀옴"/"가고 싶어요" | ⚠️ 문구 불일치(아래) |
| `PlaceDetailScreen.tsx` 정보 카드 | **표시** — 칩 | 정상(단순 읽기) |

다섯 곳 중 셋(목록 배지·범례·상세 칩)은 **같은 값을 보여주기만 하는 표시**라 "기능이
중복"이라 부르기 어렵습니다 — 오히려 화면마다 상태를 안 보여주면 그게 문제입니다.

### 진짜 문제: 상태를 정하는 경로가 두 개

`Place.java`:

```java
this.status = status != null ? status : PlaceStatus.WISHLIST;  // 생성 시 수동 지정 가능
...
public void markVisited() {
    this.status = PlaceStatus.VISITED;   // 방문 기록 저장 시 자동 호출
}
```

- **경로 A**: 장소 추가/수정 화면에서 "가고 싶어요"/"다녀왔어요" 칩을 손으로 고른다.
  (`PlaceAddScreen.tsx:30-31, 44`)
- **경로 B**: 상세 화면에서 "방문 기록 남기기"로 별점·사진·메모를 남기면 서버가 자동으로
  `VISITED`로 바꾼다(`recordVisit` → `markVisited()`).

이 둘이 **서로 무관하게 같은 값을 만들 수 있습니다.** 경로 A로 "다녀왔어요"를 골라 저장한
장소는 방문 기록(`visits`)이 0건, 평균 별점도 없는 채로 목록에서는 방문 기록을 실제로 남긴
장소와 똑같이 "다녀왔어요" 배지가 붙습니다. 반대로 방문 기록을 여러 번 남겨 실제 히스토리가
쌓인 장소와 구분이 안 됩니다 — 상세 화면에 들어가야만 "어? 방문 기록이 없네"를 알 수
있습니다.

사용자가 "가고싶어요/다녀왔어요 기능이 중복되는 것 같다"고 느낀 게 정확히 이 지점일
가능성이 높습니다 — 라벨이 여러 번 보여서가 아니라, **"다녀왔다"고 선언하는 방법이 두
가지라 뭘 써야 하는지 헷갈리는 것**.

### 제안

1. **(권장) 경로 A를 없앤다**: 장소 추가 화면에서 상태 수동 선택 칩을 제거하고, 항상
   `WISHLIST`로 생성한다. "다녀왔어요"로 바뀌는 유일한 방법은 방문 기록을 남기는 것 —
   단일 진실 공급원이 되고, 목록의 "다녀왔어요" 배지는 곧 "실제 방문 기록이 있다"는 뜻으로
   확정된다. 다만 이 결정 전에 확인할 것: **"이미 오래전에 가본 곳인데 방문 기록은 안
   남기고 그냥 다녀왔다고만 표시해두고 싶다"는 실사용 케이스가 있는지.** 있다면 경로 A를
   없애는 대신, "방문 기록 없이 다녀왔다고 표시" 자체를 더 명확한 별도 UI(예: 날짜 없는
   약식 방문 기록 1건 자동 생성)로 흡수시키는 편이 낫다.
2. **지도 범례 문구 통일**: `styles.legendText`의 "다녀옴" → "다녀왔어요"로 다른 화면과
   맞춘다(`PlaceScreen.tsx:592` 근처). 사소하지만 같은 화면 안에서 다른 단어를 쓰는 건
   불필요한 인지 부하.

## 3. 더 넓게 보면 — Place 하나에 상태 개념이 3겹

이번 지적과 별개로, 분석하며 확인된 구조적 사실 하나를 남겨둔다(지금 당장 손댈 필요는
없지만, 다음에 럽슐랭을 더 단순화할 때 참고):

- `status` (WISHLIST/VISITED) — 방문 여부, 자동/수동 이중 경로(위 참고)
- `myRating`/`partnerRating` (럽슐랭 대표 평점, 1인 1개) — 등급(tier) 산정에 쓰임, 방문
  기록과 무관하게 상세 화면에서 별도 입력
- 방문 기록(`PlaceVisit`)마다의 개별 별점 — `avgRating`에 반영, 대표 평점과는 다른 숫자

한 장소에 "상태 하나 + 대표 평점 두 개(나/상대) + 방문별 평점 N개"가 동시에 존재한다. 지금
UI가 이 세 개를 각각 다른 자리(칩/별점 셀렉터/방문 카드)에 잘 분리해두긴 했지만, 처음
쓰는 사람 입장에서는 "평가를 왜 두 번 하지" 라는 지적이 나올 수 있는 구조다 — 이번 지적의
연장선에서 언젠가 함께 재검토할 만하다.

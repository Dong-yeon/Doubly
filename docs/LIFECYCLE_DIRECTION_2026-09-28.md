## 1. 결정

| 질문 | 결정 |
| --- | --- |
| 커뮤니티(불특정 다수가 모이는 앱)로 전환? | **하지 않는다.** "둘만의 닫힌 공간"이라는 핵심 가치와 반대이고, UGC 관리(신고·차단·모더레이션) 부담이 1인 개발로 감당 불가, 사용자 밀도가 없어 빈 커뮤니티가 된다. 대신 사용자 글이 없는 느슨한 층(오늘의 질문 익명 통계, 럽슐랭 데이트 코스 공개 피드)만 검토 대상 |
| 친구 그룹으로 구성원 확장? | **보류 유지.** 카톡 단톡방·밴드와 차별화가 거의 불가능하다 |
| 가족으로 구성원 확장? | **"옆으로 넓히기"가 아니라 "같은 커플을 따라가기"로 재정의한다** — 아래 |
| 방향 | **연애 → 결혼 준비 → 신혼 → 임신 → 육아.** 사용자층을 넓히는 대신 같은 커플이 오래 머문다 |

**이유**: 커플 앱은 이별 = 이탈이 구조적이다. 결혼·육아로 이어지면 관계가 끊기지 않는 사용자가 남는다.
슬로건 "둘이라서, 두 배로"와 Duo Color System(나·상대·함께)도 그대로 유효하다 — 주인공은 계속 두 사람이다.

## 2. 핵심 설계 — 아이는 "구성원"이 아니라 "커플이 기록하는 대상"

N인 확장의 큰 비용(README "착수 시 주의사항": `user_a`/`user_b` 두 자리, `partnerOf()` 스칼라,
`activeCouple().findFirst()` 8개 서비스 복제, 단일 `is_read`, Purger·Restorer·불러오기 동의의 2인 전제,
19개 파일)은 **로그인하는 사람이 3명 이상일 때** 생긴다. 이 경로는 그 조건을 최대한 늦춘다.

| 대상 | 모델 | 구조 변경 |
| --- | --- | --- |
| 결혼한 커플 | 같은 두 사람 — 기존 `relations`(COUPLE) 그대로 | 없음 |
| 아이(신생아·미취학) | 로그인 없는 **프로필**. 사진·캘린더처럼 `relation_id` 에 속하는 커플 콘텐츠 한 종류 (README 수명주기 1단계 "관리 대상 프로필") | 테이블 추가(관계 소유) — **N인 관계 아님** |
| 조부모 | 계정 없이 **읽기 전용 공유 링크** (럽슐랭 `PUBLIC_GUIDE_LINK` 와 같은 방식) | 없음 |
| 아이 본인 계정 / 조부모 직접 기록 | 이때 처음으로 `relation_members`(N인) 필요 | **큼 — 마지막 단계로 미룬다** |

아이 프로필 테이블을 만들 때도 CLAUDE.md 4절 Purger 규칙(`UserDataPurger`·`RelationRecordPurger`·
`RelationRecordRestorer`)은 그대로 적용된다.

## 4. 주의 사항

1. **각 단계에 강한 전문 앱이 있다.** 결혼 준비·육아 기록은 시장이 따로 있다. 기능 수로 경쟁하지 않는다.
   무기는 **"연애 때부터 쌓인 둘의 기록이 이어진다"** — 처음 만난 날부터 첫돌까지 한 타임라인, 가족 이모지.
   이 연결에 필요한 만큼만 넣는다.
2. **아이 데이터는 법적으로 무겁다.** 아이가 로그인하지 않아도 아이의 개인정보를 수집하는 것이고,
   성장·접종 등 건강 관련 기록은 민감정보로 볼 여지가 있다. 착수 전에 확정할 것: 개인정보처리방침 개정
   (`constants/legal.ts` + `PolicyVersion` 상향 → 재동의 게이트), 최소 수집 항목, 삭제·보관 정책, 스토어 아동 정책.
   **법률 검토 후 착수.**
3. **지금 할 일이 아니다.** 출시 직후라 사용자 대부분은 연애 중인 커플이다. 연애 단계 코어 루프가 우선.
4. **이별 이탈은 이 경로로 막지 못한다.** 그쪽은 기존 "지난 기록 숨김·삭제·불러오기" 흐름을 다듬는 것으로 대응한다.
5. **브랜드**: 육아 단계에서 "둘"이 흔들리면 README 권장안대로 슬로건만 "함께라서, 두 배로"로 바꾸는 선에서 흡수한다
   (번들 ID `com.doubly.app` 은 변경 불가).

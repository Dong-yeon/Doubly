# Dubly 커플 퍼즐 대전 — 설계 결정 (뿌요뿌요형)

작성: 2026-09-18 · 상태: **설계 확정, 미구현**

선행 문서: `docs/COUPLE_GAMES_DESIGN_2026-09-09.md`(스도쿠·오목),
`docs/COUPLE_GAMES_EXPANSION_2026-09-14.md`, `docs/CATCH_MIND_2026-09-14.md`

> 이 문서는 같은 날 작성된 **발사형(퍼즐보블) 안을 대체**한다. 발사형을 폐기한 이유와
> 초안의 재사용 자산 주장이 코드와 어긋난 지점은 §7·§8에 남긴다.

## 1. 무엇을 만드는가

뿌요뿌요 계열 **낙하형 연쇄 퍼즐의 커플 대전** 모드. 2개짜리 조각이 떨어지고, 같은 색
4개 이상이 붙으면 사라지며, 위의 조각이 내려오면서 **연쇄(rensa)** 가 일어난다. 연쇄를
터뜨리면 상대 보드에 방해 조각이 날아간다.

## 2. 확정된 결정

### 2-1. 낙하형이다 (발사형 폐기)

초안은 발사형(퍼즐보블)이었고 근거는 "한 손 엄지·세로 화면"이었다. 낙하형도 **좌우 드래그
+ 탭 회전**으로 한 손 엄지가 성립하므로 그 근거는 유지된다. 뒤집은 실질적 이유는 §7.

### 2-2. 승부 구조 — 대전 (방해 전송)

협동(보드 공유)·점수 비교 대신 대전. 협동은 게임 로직이 동일해 승패 처리만 바꾸면 되는
후순위 확장 후보로 남긴다.

### 2-3. 상쇄 시스템은 코어 (필수)

방해 조각이 대기 중일 때 내 연쇄가 터지면 상쇄되고 초과분만 반격으로 나간다.

- **근거**: 상쇄가 없으면 선(先)연쇄 측의 굳히기로 경기가 끝나 역전이 소멸한다.
  뿌요뿌요 통이 오락실에서 성립한 이유가 이 시스템이다. **원조로 오면서 이 근거가
  더 단단해졌다** — 상쇄는 이 장르의 기본 문법이고 플레이어의 기대에 맞는다.
- 구현: 받은 방해를 즉시 보드에 넣지 않고 **대기 큐**에 넣는다. 내 연쇄 발생 시 큐에서
  차감하고, 남은 잔량이 있을 때만 다음 조각 착지 후 보드에 투입한다.

### 2-4. 연쇄 규칙 — 확정됨

**낙하한 조각은 재매치를 유발한다.** 초안에서는 "착수 전 확정 필요"로 남아 있던 항목인데,
낙하형에서는 그것이 곧 연쇄의 정의이므로 자동으로 확정된다. 초안의 미결 항목 하나가
장르 변경으로 소멸했다.

### 2-5. 네트워크 — "결과 보드"를 보낸다

조작 입력만 보내 양쪽이 각자 시뮬레이션하면 부동소수점·타이밍 차이로 보드가 갈린다.

- **둔 쪽이 착지·매치·낙하·연쇄까지 전부 계산**해 최종 보드 상태를 전송한다.
- 받는 쪽은 조작을 보고 연출만 재생하고, **보드는 받은 값을 신뢰한다**.
- 커플 앱이므로 치팅 대응이 불필요 → 서버 권위와 결정론 요구사항을 통째로 제거할 수 있다.
  이것이 최대 단순화 지점이며, 낙하형이 발사형보다 결정론 요구가 큰 것도 이걸로 상쇄된다.
- 페이로드: `{ 조각색2, 착지열, 회전, 결과보드, 전송방해량, 잔여대기큐, 시퀀스 }`

### 2-6. 비동기 성립 — 고스트 대전

대전 + 실시간 방해 전송은 동시 접속을 강제한다. 초안이 플랫포머를 보류한 바로 그 이유라
그대로 두면 안 된다.

- 플레이 시 `[경과ms, 착지열, 회전, 조각색2]` 시퀀스를 기록한다(한 판 100수 기준 수 KB).
- 상대는 나중에 혼자 시작해도 그 타임라인대로 방해를 받는다 → 체감은 실시간 대전.
- **둘 다 접속 중이면 동일한 이벤트를 라이브로 흘린다. 이벤트 포맷이 같으므로 코드는 한 벌.**

### 2-7. 실력차 핸디캡 (기능 요구사항)

커플은 실력차가 큰 경우가 많고, 대전물에서 실력차는 이탈로 직결된다. 채팅 외 탭이 잘
쓰이지 않는 현 상태의 반복을 막기 위한 필수 장치다.

| 장치 | 내용 |
|---|---|
| 자동 핸디캡 | 최근 전적 기반 방해 전송 계수 조정(예: 3연패 시 피격량 70%) |
| 비대칭 시작 | 약한 쪽 시작 보드 1줄 감소 |
| 패배 보상 | 패배해도 최고 연쇄 기록을 채팅에 카드로 전송 |

핸디캡을 숨기지 않고 노출한다(커플 맥락에서는 오히려 자연스럽다).

## 3. 초안에서 틀렸던 것 — 코드 대조 결과

초안의 "재사용 자산" 5개 중 **2개는 이 저장소에 없고, 1개는 용도가 다르다.** 그래서
3일 일정이 성립하지 않는다. 확인 근거를 남긴다.

### 3-1. 똥피하기가 이 저장소에 없다

```
grep -rln "똥피하기|dodge|Dodge" → backend/.../CatchMindWords.java 뿐 (제시어 목록의 "똥")
frontend/src/screens/home/ → CatchMind · CoupleCalendar · CoupleConnect ·
                             DailyQuestion · Home · MiniGames · Omok · Sudoku
```

따라서 초안이 재사용 자산으로 적은 **① 게임 루프 원칙(SharedValue 프리미티브 분리,
dt 클램프 50ms, runOnJS 최소화) ② 화면 흔들림 감쇠 로직** 둘 다 실재하지 않는다. 다른
프로젝트에 있거나 만들어지지 않았다. **연출과 게임 루프는 0에서 시작한다.**

`react-native-reanimated@4.3.1` 은 있다(`frontend/package.json:55`). Skia 는 없다 —
캐치마인드가 `react-native-svg` 로 간 이유와 같다(웹 번들에 CanvasKit WASM 수 MB).
따라서 보드 렌더는 **Reanimated + View 또는 react-native-svg** 로 간다.

### 3-2. 오목 WebSocket 은 "전송 계층"이 아니다

```java
// common/event/CoupleEvent.java
/** 민감 데이터는 싣지 않고 타입만 보내, 수신측이 인증된 REST 로 다시 조회한다. */
public record CoupleEvent(String type) { ... }

// common/event/CoupleEventPublisher.java:18
public void publish(Long relationId, String type) {
    messagingTemplate.convertAndSend("/sub/couple/" + relationId, new CoupleEvent(type));
}
```

오목은 수를 소켓으로 보내지 않는다. `CoupleEvent.GAME` 이라는 **타입 한 개**를 보내고
클라이언트가 REST 로 재조회한다. `OmokService` 의 `convertAndSend` 는 승리 시 채팅 카드
하나뿐이다(`OmokService.java:259-260`).

그래서 §2-5 의 페이로드를 "오목 한 수와 같은 규모"로 이 채널에 실을 수 없다. 발당 재조회
왕복이 붙고 그것이 게임의 지연이 된다.

**다만 STOMP 전체가 막힌 건 아니다.** 채팅은 이미 `/sub/rooms/{relationId}` 로 전체
페이로드(`ChatMessageResponse`)를 밀어 넣는다. 즉 페이로드 채널은 아키텍처상 정상이고,
**의도적으로 페이로드가 없는 것은 `CoupleEvent` 쪽**이다. 따라서 채팅 패턴을 따라
새 채널을 만든다.

| 방향 | 경로 | 비고 |
|---|---|---|
| 발행 | `/pub/games/{relationId}` | `/pub/chat/{relationId}` 와 같은 모양 |
| 구독 | `/sub/games/{relationId}` | 클라이언트는 `chatSocket.ts` 의 `register()` 재사용 |

`common/security` 의 STOMP 채널 인터셉터가 같은 JWT 로 인증하므로 인증은 추가 작업이 없다.
클라이언트도 `subscribeRoom`(`src/api/chatSocket.ts:224`)과 같은 형태로 한 줄이다.

### 3-3. Flyway 작업이 일정에 없었다

`couple_games` 는 JPA 단일 테이블 상속이고 `game_type VARCHAR(20)` 이므로 **`GameType`
enum 값 추가는 마이그레이션이 필요 없다**. 하지만 대전은 저장할 것이 새로 있다.

기존 3게임이 `couple_games` 에 쌓이는 것과 달리 **대전은 한 판에 두 사람의 보드·기보를
들고 판 수도 훨씬 많다.** 행 크기와 증가 속도가 다르므로, 기보를 몇 판까지 보관할지
(예: 최근 N판만) 착수 시 정한다 — 무제한 누적은 `Feature.COUPLE_GAME` 이 한도가 없어서
(아래 §5) 아무도 막지 않는다.

**다음 번호는 V95 다** (2026-09-18 확인: `origin/main` 최대 94, 미병합 브랜치 선점 없음,
중복 없음). CLAUDE.md 7절 절차로 **착수 시점에 다시 센다** — 그 사이 다른 세션이 집을 수 있다.

V93(캐치마인드)의 패턴을 그대로 따른다 — 전부 `ALTER TABLE couple_games ADD COLUMN`,
**nullable**(다른 game_type 행은 이 값이 없다). V87 이 오목 때문에 스도쿠 컬럼의 NOT NULL
을 푼 것과 같은 이유다.

| 컬럼 | 용도 |
|---|---|
| 보드 2개 | 각자의 판. 문자열 1개씩(스도쿠 `board VARCHAR(81)` 과 같은 발상) |
| 대기 큐 2개 | 상쇄 잔량. `INTEGER` 2개 |
| 기보 | 고스트 재생용 `[경과ms, 열, 회전, 색2]` 시퀀스. `TEXT` (V93 `strokes` 와 같은 취급) |
| 승자 · 최고연쇄 | 결과 카드와 핸디캡 계산용 |

`JSONB` 금지(CLAUDE.md 4절)이므로 기보는 문자열로 인코딩한다 — 캐치마인드 `strokes` 와
같은 규칙(구분자 2단계, 서버는 해석하지 않고 형식만 검증).

**Purger 는 손댈 필요가 없다.** 같은 `couple_games` 테이블이라
`RelationRecordPurger.java:89` 의 `delete from couple_games where couple_id = :rid` 한 줄이
그대로 거둔다(캐치마인드가 테스트로 이미 고정: `관계_기록_삭제에_캐치마인드_판이_포함된다`).
**새 테이블을 만들면 이 면제가 사라진다** — 그것이 단일 테이블을 유지하는 이유다.

## 4. 기술적 버그 위험 지점

### 4-1. 초안에서 사라진 위험

초안이 "버그 대부분이 여기서 발생"이라 꼽은 **오프셋(육각) 그리드가 없어졌다.** 뿌요뿌요는
직사각 그리드라 이웃 계산이 `±1`, `±width` 로 끝난다. 발사형의 궤적·충돌·스냅도 통째로
빠진다. **이것이 장르를 뒤집은 가장 큰 이득이다.**

### 4-2. 남는 위험

1. **부유 클러스터 낙하 순서** — 반드시 *매치 제거 → 중력 적용 → 재매치 판정* 순서.
   역순으로 구현하면 정상 덩어리가 떨어진다. 낙하형은 열 단위 중력이라 발사형의
   flood fill 보다 단순하다.
2. **회전 킥(벽 붙은 상태 회전)** — 낙하형 고유의 새 위험. 벽·바닥에 붙은 조각을 회전할 때
   밀어낼지 거부할지 먼저 정한다. 뿌요뿌요는 밀어낸다.
3. **방해 조각의 성질** — 매치에 참여하지 않고, 인접 색이 사라질 때 함께 사라지는가.
   뿌요뿌요는 **함께 사라진다**(방해 제거가 유일한 해소 수단). 이 한 줄을 안 정하면
   난이도가 통째로 달라진다.
4. **중력 타이밍 기준** — 시간이 아니라 **수(手) 기준**으로 진행한다. 비동기/고스트 대전과
   양립하려면 필수다.
5. **동시 종료** — 둘이 동시에 K.O. 되는 경우의 승패. 시퀀스 번호로 먼저 끝난 쪽을 패배로
   확정한다(§2-5 페이로드의 `시퀀스`가 이 용도도 겸한다).

위 로직은 전부 **렌더링 없는 순수 함수**로 분리 가능하며 단위 테스트 대상이다. 프론트에는
테스트 러너가 없으므로(CLAUDE.md 6절) **순수 로직은 백엔드에 두고 Java 테스트로 고정하거나**,
프론트에 둘 경우 `scripts/verify-*.mjs` 패턴의 검증 스크립트를 함께 만든다. 후자를 택한다면
그 스크립트가 사실상의 테스트다 — `verify-spellcheck.mjs` 가 맞춤법 모듈에 하는 역할과 같다.

## 6. 진입점 — 확정

초안은 "미정, 채팅 탭 내 초대/결과 카드 유력"이었다. **`MiniGamesScreen` 카드 추가로
확정한다** — 기존 3게임이 모두 그 형태이고(`MiniGamesScreen.tsx:201-221`),
`navigation.navigate('CatchMind')` 처럼 한 줄이다. 채팅은 **결과 카드**를 받는 쪽이다
(`GAME_CARD`, 캐치마인드·스도쿠·오목과 동일). 즉 둘 중 하나가 아니라 **둘 다이고 역할이 다르다.**

## 7. 왜 뿌요뿌요인가 — 발사형을 뒤집은 근거

| | 발사형(초안) | 낙하형(확정) |
|---|---|---|
| 그리드 | 오프셋(육각). 초안이 직접 "버그 대부분" 지목 | 직사각. 이웃이 `±1`/`±width` |
| Day 1 물량 | 궤적·충돌·스냅 + 육각 이웃 | 착지·회전킥 + 직사각 이웃 |
| 상쇄 근거 | 뿌요뿌요를 인용 | 원조 그 자체 |
| 연쇄 규칙 | 미결(착수 전 확정 필요) | 장르 정의상 자동 확정 |
| 한 손 엄지 | 조준 드래그 | 좌우 드래그 + 탭 회전 (성립) |
| 새 위험 | — | 회전 킥, 방해 조각 성질 |

위험 하나가 사라지고 두 개가 생겼지만, 사라진 것이 초안 스스로 "버그 대부분"이라 꼽은
항목이고 새로 생긴 둘은 **착수 전 한 줄로 확정 가능한 규칙 선택**이다(§4-2 2·3번, 둘 다
뿌요뿌요의 기존 답이 있다). 그래서 낙하형이 기술적으로 더 안전하다.

## 8. 보류·폐기한 대안

### 발사형 퍼즐보블 (폐기)
§7 표 참고. 육각 그리드 위험과 미결 연쇄 규칙을 그대로 안고 가야 한다.

### 실시간 커플 플랫포머 (보류)
퍼즐 완료 후 재검토.
- 검토 결론: 캐릭터 간 상호작용(밟기·같이 누르기)이 **없다면** 각자 로컬 권위 + 상대 위치
  10~15Hz 보간으로 성립. 시드 기반 결정론적 맵 생성으로 맵 전송 0. 상호작용이 **있다면**
  결정론 물리 + 롤백 넷코드가 필요해 별도 프로젝트 규모.
- **보류 사유**: 실시간이라 둘 다 동시에 폰을 보고 있어야만 성립한다. 커플 앱 사용 패턴상
  성사율이 낮고, 네트워크가 실패하면 결과물이 남지 않는다.
- 되살릴 경우 필수: 3초 무패킷 시 양쪽 동시 일시정지(미구현 시 상대가 정지한 채 혼자
  달리는 상태 발생).

### 협동 모드 (후순위 확장)
보드 하나를 번갈아 두는 방식. 커플 앱 정체성에는 더 맞으나 대전을 우선. 게임 로직이
동일하므로 승패 처리만 바꾸면 된다.

### 한 폰 2인 플레이 / 점수만 비교 (미채택)
전자는 떨어져 있는 커플에게 무의미, 후자는 상호작용이 약해 대전물로 성립하지 않는다.

## 9. 개발 단계 (수정판)

초안의 3일은 §3의 세 구멍(똥피하기 부재 · 소켓 페이로드 채널 · Flyway)을 계산하지 않았다.

| 단계 | 내용 |
|---|---|
| 0 | **Flyway V95**(착수 시 번호 재확인) + `GameType` 값 추가 + 엔티티·Purger 확인 |
| 1 | 직사각 그리드·중력·매치·재매치 **순수 함수** + 단위 테스트(§4-2가 테스트 목록) |
| 2 | 상쇄 대기 큐 + 방해 투입 + 승패 판정 + 회전 킥 |
| 3 | **`/pub/games/…` · `/sub/games/…` 채널 신설**(서버 + `chatSocket.ts`) |
| 4 | 기보 기록·고스트 재생(단계 3과 같은 이벤트 포맷) |
| 5 | 게임 루프·연출 **0에서**(SharedValue 분리, dt 클램프, 화면 흔들림) + 진입점 카드 |
| 6 | 핸디캡 + 결과·패배 보상 `GAME_CARD` |

중간에 막혀도 **단계 2까지면 로컬 1인 플레이로 출시 가능하다.** 플랫포머 안은 네트워크가
실패하면 아무것도 남지 않는 구조였고, 이것이 퍼즐을 우선한 핵심 근거다 — 장르를 바꿔도
이 근거는 그대로다.

**3일은 아니다.** 단계 3·5가 초안에 없던 물량이다.

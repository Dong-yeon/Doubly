### 2-1. #1 — 단백질을 주인공으로 둔 근거와 반박

**원래 근거(인용)** — 문서는 없고 코드에만 남아 있다.
- 커밋 `7463e6db`(2026-08-10, "P0-P3 식단 기능 개선"): "P0: 단백질 중심 원형 게이지(ProteinRing) — 홈 영양 카드 최상단에 단독 배치"
- `ProteinRing.tsx:2-3`: "운동 앱 사용자는 총 칼로리보다 단백질(g) 달성률에 훨씬 민감해서 … 단독 원형 게이지로 뺐다."
- `DietScreen.tsx:509`: "운동 유저는 단백질 달성률에 가장 민감하다"
- 9/23 리뷰(§6-2)도 "운동 유저의 핵심 지표"로 유지 판정.

**반박 — 전제가 바뀌었다.**
1. **"운동 앱 사용자"가 더 이상 주 사용자가 아니다.** 근거가 쓰인 8/10 은 Fitto(운동 트래커) 시절이고,
   9/9 에 운동을 "느슨한 체크인"으로 돌렸으며(`WORKOUT_LOOSE_DIRECTION` §2), 9/27 에 운동 홈까지 가렸다.
   근거의 주어가 사라졌다.
2. **자동 분석이 믿을 만하게 채우는 건 칼로리다.** 사진만 올리면 끝(9/9) 경로의 결과는 "약 800 kcal"로
   보인다(`MealCard.tsx:78-83`). 사진 한 장으로 추정한 단백질 g 은 칼로리보다 오차가 크다 — 가장 흔한
   기록 경로가 가장 약하게 채우는 지표를 주인공으로 두고 있다.
3. **목표가 없으면 링이 빈 원이다**(`ProteinRing.tsx:38` — target 없으면 진행 호를 안 그림). 목표는 마법사·
   직접 입력으로만 생기므로 대부분의 사용자에게 링은 "23g" 숫자가 든 회색 원이다.
4. **같은 카드 안에 "남은 칼로리"가 두 개다.** `남은 칼로리 = 목표 − 섭취`(`:529`)와
   `오늘 N kcal 더 섭취 가능 = BMR + 운동 − 섭취`(`:552-554`). 기준이 달라 숫자가 다르고(목표 1,500 /
   BMR 1,400 이면 두 값이 어긋난다), 9/27 에 체크인 시간 칩으로 운동 소모를 반영하게 만든 쪽은 후자다.

**판단: 전환한다. 선택 옵션으로 두지 않는다.** 옵션은 설정 한 줄·상태 하나·두 레이아웃의 유지 비용을
낳는데, 고를 사람(고단백 식단 파워유저)은 3절 E 등급의 소수다. 단백질은 막대 첫 줄로 내려 "잃는 것"은 없다.
- 링 중심 = **남은 칼로리 = 목표 + 오늘 운동 소모 − 섭취**(9/27 시간 칩의 의미를 살린다). 아래 캡션
  "운동 +240 포함". 목표가 없으면 중심 = 섭취 kcal, 링 아래 기존 "목표 계산 권유" 행.
- 에너지 밸런스 박스(10px 수식 줄 포함)는 없앤다 — 숫자 하나로 합친다. 수식은 링을 누르면 시트로.
- 초과 시 색: 칼로리 초과는 `primary`(진한 색) 유지, 단백질 막대는 초과가 나쁜 게 아니므로 초과색을 쓰지 않는다
  (지금 링은 단백질 초과도 "초과색"으로 칠한다, `ProteinRing.tsx:43`).

**결정 수정(사용자, 2026-10-02) — 링 중심 = 목표 − 섭취. 운동 소모는 더하지 않는다.** 위 첫 안(목표 + 운동 − 섭취)을
버렸다. 체크인 시간 칩의 소모 칼로리는 "시간 × 가정 MET"로 어림한 추정치라(`EnergyBalanceService`), 링에 더하면
"오늘 이만큼 더 먹어도 된다"로 과하게 읽힌다 — 식단 앱에서 과대 추정은 과소 추정보다 해롭다는 9/27 판단과 같은 근거다.
운동은 링 아래 캡션("오늘 운동 −240 kcal")으로 **따로** 보여주고, BMR 기준 계산은 링을 누르면 여는 계산식 시트에
"참고"로만 둔다. 초과색은 위 안의 `primary` 대신 `danger` 로 했다 — 진행 호의 기본색(`primaryLight`)과 같은 계열이라
넘었는지 구별이 안 됐다. 강조는 감량·유지·미설정에서만, 증량은 목표를 채운 것이라 강조하지 않는다.

### 2-1-1. 전제 — 이 앱의 "목표"는 숫자 칸뿐이다 (사용자 지적, 2026-10-02)

> "현재 앱에 목표라는 사항이 없는 걸로 알고 있는데.."

맞다. **"몸을 어떻게 하고 싶은가"를 저장하는 곳은 없다.** 있는 건 숫자 목표뿐이고, 그것도 찾아 들어가야 생긴다.

| 있는 것 | 저장 위치 | 들어가는 길 |
| --- | --- | --- |
| 하루 영양 목표(kcal·탄·단·지) | `nutrition_goals`(V16) | 오늘 영양 카드의 작은 "목표 설정" 링크 → 모달, 또는 신체 정보가 있을 때 "목표 칼로리 계산" 권유 |
| 물 목표 ml | 물 목표 | 기본값으로 시작 |
| 커플 식단 목표(주 N일) | `relations.diet_goal_days` | 커플 목표 카드 |
| 단식 목표 시간 | 단식 세션 | 시작할 때 고름 |
| **없는 것** | — | 감량·유지·증량 같은 **방향**, 목표 체중, 목표일 |

- 마법사의 "감량/유지/증량"(`DietGoalType`)은 **계산에만 쓰고 버린다**(`NutritionService.java:119-122`,
  해당 컬럼 없음). 그래서 앱은 이 사람이 다이어트 중인지 모르고, AI 코칭·주간 레터도 그걸 모른다.
- 영향: #1 칼로리 링은 `targetCalories` 가 있어야 "남은 칼로리"가 성립하는데, 대부분은 목표가 비어 있을 것이다(지표 확인 필요).
  그러니 **목표가 없을 때의 링(중심 = 섭취 kcal, 아래에 목표 계산 권유)이 사실상 기본 화면**이고 설계도 그쪽부터 한다.
  #7 예상 도달일은 목표 체중이 없어 불가하다(§6 에 이미 보류).
- **결정(사용자, 2026-10-02)**: 방향만 저장한다 — `nutrition_goals.goal_direction`(V115, `851dcd61`). 마법사에서 계산에 쓴
  방향이 목표 저장에 함께 실리고, MY › 신체 정보에서 바꾸거나 비울 수 있다(`159c9c7a`). 본인 영양 요약에만 실리고 상대 응답에는
  없다(`PartnerPrivacyTest`). 목표 체중·목표일, AI 코칭·주간 레터 프롬프트 반영은 하지 않았다.
- (당시 질문) "목표"를 1급 개념으로 들일지. 들인다면 가장 작은 형태는 신체 정보 시트에 **방향 한 칸
  (감량·유지·증량, 선택)** 을 저장하는 것이다. 이 칸 하나로 마법사 기본값, 링 문구("오늘 400 남았어요" / 증량이면 "400 더 드세요"),
  코칭 프롬프트가 맞춰진다. 목표 체중·목표일은 그 다음 단계이고, 9/28 민감정보 원칙에 따라 **비공개로만** 둔다.
  들이지 않는다면 럽바디는 계속 "기록 일기 + 참고 숫자"로 가고, #1 링도 "섭취 kcal"을 기본으로 둔다 — 그것도 9/9
  "칼로리 트래커가 아니라 밥 사진 일기"와 맞는 일관된 선택이다.

- **데이터는 이미 계산되고 버려진다.** `MealService.coupleGoal`(`:779-803`)이 이번 주 `myDates`·`partnerDates`

- **흡수 효과**: 스트립은 "이번 주 함께 N/목표 일"의 시각화 그 자체다. 스트릭 줄(36)·커플 목표 카드(78~120)를

  흑백에서 구별이 안 된다. 그래서 **자리 + 모양**으로 말한다 — 칸 안 왼쪽 점 = 나, 오른쪽 점 = 상대(위치 고정),

  준다(`DietCalendarScreen.tsx:141-175`). 1차는 탭 없이 표시만, 날짜별 보기는 별도 판단.

### 2-4. #3 — 식사 카드 반응

- **같은 데이터다.** 럽바디 MealCard 와 우리 탭 피드 카드는 같은 `meals.id` 를 가리키고, 반응은
  `feed_reactions(target_type='MEAL', target_id=meals.id)` 에 있다(V60). 다만 `MealResponse` 에 반응 필드가 없어
  **백엔드 DTO 추가가 필요하다**(벤치마크의 "노출만 붙이면 된다(소)"는 프론트만으로는 안 된다는 점에서 정정).
  `withPlaces` 와 같은 배치 방식(`findByTargetTypeAndTargetIdIn`)이면 N+1 없음.
- **상대 식사 카드에는?** 럽바디엔 상대 식사 카드가 **존재하지 않는다**(today/history 모두 내 것만). 그래서 럽바디에서
  가능한 건 "내 식사에 상대가 남긴 ❤️ 보기"(읽기 전용)이고, 상대 식사에 반응하는 자리는 계속 우리 탭 피드다.
  럽바디에 상대 식사를 띄우는 건 "식단 탭 = 내 기록" 구조를 바꾸는 일이라 이번 범위 밖.
- **함정 — 같이 먹기 짝**: 데이트 식단은 행이 둘(`shared_group_id`)이고 피드는 **원본 id 만** 노출한다
  (`MealRepository.java:89-121`, `created_by` 필터). 상대가 등록한 데이트 식단의 내 몫(복사본)에 반응을 붙여 보여주려면
  `shared_group_id` 로 원본 id 를 찾아 그 반응을 읽어야 한다. 안 하면 "피드엔 하트가 있는데 럽바디 카드엔 없다".
- 실시간: 반응 토글 시 `CoupleEvent.FEED` 가 나가지만(`FeedService.java:434`) 럽바디는 구독하지 않는다 — 포커스 갱신으로 충분.
- "빠른 한마디"("맛있겠다")는 반응이 emoji 전용(`ReactRequest` `@Emoji`)이고 댓글 엔티티가 없어 새 테이블·Purger
  추가가 필요한 **대**다. 채팅이 이미 그 역할을 한다 — 하지 않는다.

### 2-5. #5 — 채팅 이미지 → 식단 기록

흐름(가능 여부 확인 결과):

```
채팅 IMAGE (이미 Cloudinary, PHOTO_UPLOAD 차감 끝)
  → 길게 누르기 → "식단으로 남기기" (내가 보낸 이미지만)
  → DietRecord { photoUrl } — 재업로드 없음 (ensureUploaded 가 원격 URL 이면 건너뜀, DietRecordScreen.tsx:265-281·695-729)
  → 저장 → MealPhotoAutoAnalysisService (항목·칼로리 비어 있고 설정 켜져 있으면)
  → AI_FOOD_PHOTO 차감 = 백그라운드 작업 안 GeminiClient.countUsage 시점 (GeminiClient.java:236)
```

- **같은 URL 재사용: 된다.** `SaveMealRequest.photoUrl` 은 검증 없는 문자열이고, 분석기 `CloudinaryImageFetcher` 는
  Cloudinary 호스트면 받는다(`:78-121`). 업로드 한도(`PHOTO_UPLOAD`, 커플 단위 월 60/1000)를 두 번 쓰지 않는 장점도 있다.
- **막는 문제 — 자산 공유 삭제.** 식사를 지우면 사진 자산을 Cloudinary 에서 지운다(`MealService.java:753-775`).
  채팅에서 가져온 사진이면 **채팅 원본 이미지가 깨진다.** 반대로 관계 영구 삭제(`RelationRecordPurger.java:165-166`)는
  채팅 이미지 자산을 전부 지워 그 사진을 쓰는 식사가 깨진다. **이 버그는 지금도 반대 방향으로 존재한다** — 식단 저장 후
  "채팅에 공유"한 `MEAL_CARD` 는 같은 URL 이라, 식사를 지우면 채팅 카드 이미지가 깨진다(§3 A-3).
  → 해결: 삭제 직전 "다른 행(meals.photo_url / chat_messages.image_url / feed 등)이 같은 URL 을 참조하는가"를 보고
  참조가 남으면 자산을 남긴다. #5 는 이 수정이 **선행 조건**이다.
- **차감·환불 함정**: 분석은 차감(`FoodAnalysisService.java:145`) 뒤에 이미지 다운로드(`:147`)를 하고, 다운로드 실패
  (`INVALID_PHOTO_URL`·`PHOTO_DOWNLOAD_FAILED`·`PHOTO_TOO_LARGE`)는 환불 try 밖이라 **한도만 탄다**. 채팅 이미지를
  끌어오면 오래된 URL·대용량 원본이 늘어나 이 경로를 더 자주 밟는다. 순서를 바꾸거나 환불 범위를 넓힌다.
- **기각: "음식 사진이면 자동으로 제안"** — 채팅 이미지마다 분류 호출이 필요하다(원가 + 둘만의 사진을 AI 에 보내는 사생활
  문제). 명시적 길게 누르기 액션만.
- 상대가 보낸 사진은 제외 — 남의 식사를 내 기록으로 만들 수 있게 된다(같은 끼니면 "같이 먹기"가 이미 답).
- 크로스 탭 이동(채팅 스택 → 럽바디 스택의 DietRecord)은 iOS 에서 네이티브 모달 먹통 전례가 있다
  (2026-10-01 `5acf1699`, returnTo 패턴) — 같은 처방을 따른다.

### 2-6. #7 — 체중 공개 범위 (확인 결과)

- **체중·체지방·허리·바디 사진은 상대에게 보이지 않는다.** `/body-metrics` 는 전부 `user.id()` 만 쓰고, 피드 타입에
  body 가 없으며(`FeedItemType`), 주간 레터 프롬프트는 운동·식단 일수만 넣고(`WeeklyLetterService.java:88-96`),
  트레이너 대시보드도 체중을 주지 않는다.
- **그러나 별개의 누출이 있다**: 상대(`RelationResponse.partner`)·채팅 상대(`ChatService.java:117`)·트레이너 회원

## 4. 참고 — 찌르기(nudge)를 터치와 연결할 수 있나

**사실**
- 터치는 독립 기능이 아니라 **채팅 메시지 `MessageType.TOUCH`** 다. 내용은 제스처 코드뿐(손잡기·토닥임·**콕 찌르기**
  무료 / 포옹·뽀뽀 프리미엄, `TouchGesture.java:13-18`). 맥락(예: "식단") 필드 없음, 쿨다운 없음
  (`clientMessageId` 멱등만), 푸시는 CHAT 카테고리 "[콕 찌르기]"(`ChatService.java:575-583`, `:727`),
  보내는 자리는 채팅방 ＋ 트레이뿐(홈 원탭은 9/12 에 빠졌다 — PLAN.md:354·423 은 낡은 서술).
- "상대가 오늘 안 남겼다"는 판정은 이미 있다 — `GET /meal/partner/today` 의 `completed`(`MealService.java:806-820`).
  그 위에 만든 알림은 **없다.**
- 쿨다운 있는 수동 재촉의 선례: 게임 찌르기 `POST /games/nudge/{gameId}`, 판·사람당 24시간, PARTNER 카테고리
  (`GameNudgeService.java:42-100`, `docs/GAME_NUDGE_2026-09-30.md`).

**판단: 터치에 얹지 않는다. 게임 찌르기 패턴을 식단에 복제한다.**

| | 터치(POKE) 재사용 | 식단 찌르기(게임 패턴) |
| --- | --- | --- |
| 맥락 | 없음 — 받는 쪽은 "[콕 찌르기]"만 보고 이유를 모름 | "OO님이 오늘 식단을 기다려요" + 링크 `PushLinks.DIET` |
| 채팅 기록 | 대화방에 터치 말풍선이 쌓임 — 둘만의 대화에 "재촉"이 섞인다 | 남지 않음 |
| 쿨다운 | 없음(연타 가능) | 하루 1회(KST) |
| 알림 설정 | CHAT 를 끄면 대화 알림까지 같이 꺼야 막힘 | PARTNER 카테고리 — 별도 토글 존재 |
| 비용 | 프론트만이지만 위 셋을 다 떠안음 | 백엔드 엔드포인트 + 쿨다운 저장(컬럼 1개 → 마이그레이션 1건, 또는 Redis 키로 마이그레이션 없이) |

- 자리: 홈 상대 열 식단 배지가 비어 있을 때(지금은 탭하면 내 `DietMain` 으로 감 — 상대 배지를 눌러 내 화면이 뜨는 건
  그 자체로 어색하다, `HomeScreen.tsx:841-844`) → "콕 찔러 볼까요?" 시트. 또는 #2 주간 스트립의 오늘 칸 상대 점.
- **톤 주의**: 식단 재촉은 감시로 읽히기 쉽다. 시간 창은 게임처럼 10~22시, 문구는 "기다려요"(재참여 알림의 무벌칙 톤과 같게),
  받은 쪽이 끌 수 있어야 한다. 새 클라이언트 이벤트를 남기면 `ClientAnalyticsEvent` 서버 enum 이 먼저다.
- 비용 중, 서버 + 업데이트. 우선순위는 §5 의 중 묶음 뒤.

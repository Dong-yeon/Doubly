## 1. 지금 홈 — "프로필 밑"이 어디인가

`CoupleHero`(`frontend/src/screens/home/components/CoupleHero.tsx`)의 두 열:

```
       함께한 지 / D+n / 날짜부터
  [아바타+오늘 챙김 링]   ♥   [아바타+오늘 챙김 링]
    이름 · 🌱스트릭              이름 · 🌱스트릭
    (무드 한마디)               (무드 한마디)
   (운동)(식단)  ← todayRow    (운동)(식단)
    최근 기록 한 줄              최근 기록 한 줄
```

- `todayRow` 는 44px 터치 타깃 안의 36px 원 버튼 둘(`TodayButton`). 상태는 **채움/비움**으로만 말한다(✓ 같은 기호 금지 — 9/28 결정).
- 그 아래(panelSpacer 다음)는 **한 줄 슬롯 하나**(보관함 ⓪ > 여행 > 오늘 일정 > 작년 오늘 …)와 바로가기 3칸. 바로가기 주석이 명시한다:
  "여기는 칸을 늘리는 자리가 아니다".
- 홈은 **스크롤 없는 고정 화면**이다. 새 "물 줄"(진행 막대 + 버튼)을 한 줄 더 쌓으면 작은 폰에서 히어로가 사진 자리를 더 먹는다.

→ 새 줄을 만들 이유가 없다. `todayRow` 에 원 하나를 더하면 높이가 0 늘고, "오늘 챙김" 이라는 같은 의미 묶음에 들어간다.

### 2-1. 경합 — "탭할 때마다 250"이면 연타가 기본이다
`WaterService.add` 는 `findByUserIdAndLogDate → orElseGet(save) → log.add(delta)`(JPA dirty checking) 다.

1. **하루 첫 동시 요청**: 둘 다 행이 없다고 보고 insert → 둘째가 `UNIQUE` 위반 → 500(사용자에겐 "기록에 실패" 토스트, 250 유실).
2. **둘째 이후 동시 요청**: 둘 다 750 을 읽고 1000 을 쓴다 → **lost update**(`@Version` 없음). 에러도 안 나고 조용히 사라진다.

지금 럽바디에서는 버튼이 작고 드물게 눌려 묻혀 있었지만, 홈의 "찍 차오르는" 버튼은 연타를 **부추기는** UI 라 그대로 두면 안 된다.

## 3. 권장안 — 동작

### 3-1. 탭 처리 (앱)
- **낙관적 표시**: 화면 값 = `서버 값 + 아직 안 보낸 합(pending)`. 탭 즉시 +250, 애니메이션·햅틱은 서버를 기다리지 않는다.
- **묶기(debounce 500ms)**: 마지막 탭 뒤 0.5초 조용하면 pending 합을 **한 요청**으로 보낸다. 20번 연타 = 5,000ml → 2,000 상한 때문에
  요청 3개(2000·2000·1000)로 쪼개 **순서대로** 보낸다.
- **직렬화**: 요청은 한 번에 하나만 날아간다(in-flight 중 탭은 다음 묶음으로). 한 기기 안에서는 이것만으로 §2-1 의 두 경합이 사라진다.
- **실패**: 1회 `today()` 재조회 후 같은 합을 다시 보낸다(첫 insert 충돌 회복 — 분석 문서 P1-4 와 같은 처방). 그래도 실패하면 pending 을
  되돌리고(물높이가 내려가는 애니메이션) 토스트 "물 기록을 못 했어요". `ApiError(status 0)`(오프라인)도 같은 경로.
- **오프라인 큐는 두지 않는다** — 식단 사진(보관함)과 달리 물은 다시 누르면 되는 값이고, 하루가 지나 올라가면 날짜가 틀어진다.
- **화면 떠날 때 즉시 보냄**: `useFocusEffect` 정리·AppState background 에서 debounce 를 기다리지 않고 flush. 홈에서 세 번 누르고 곧장
  럽바디로 가면 럽바디 `refreshWater` 가 낡은 값을 읽는 문제를 막는다.

### 3-2. 서버 (권장, 작음, 마이그레이션 없음)
- `add` 를 원자적 갱신으로: `UPDATE water_logs SET amount_ml = GREATEST(0, amount_ml + :d), updated_at = :now WHERE user_id = :u AND log_date = :t`
  → 0행이면 insert → `DataIntegrityViolationException` 이면 UPDATE 재시도. `GREATEST` 는 H2·PostgreSQL 공통(4절 규칙 위반 아님).
  **쿼리를 건드리므로 PostgreSQL 로도 한 번 돌린다**(CLAUDE.md 6절).
- 이것은 홈만이 아니라 **기존 럽바디 버튼·두 기기 동시 사용**의 유실도 함께 막는다. 앱 묶기만으로는 기기 두 대(폰+웹)는 못 막는다.
- `WaterSummaryResponse` 에 `partnerTargetMl` 추가(§4-3). 필드 추가뿐이라 옛 앱은 무시한다.
- 테스트: 동시 첫 요청 2개·동시 증분 10개 → 합이 정확한지(`MealFlowTest` 동시 도착 테스트와 같은 방식). 새 `@SpringBootTest` 조합은 만들지 않는다(CI 힙).

### 3-3. 실수 되돌리기
- **묶음이 서버에 들어간 뒤 토스트 하나**: "물 +500ml · 오늘 1,250ml" + [되돌리기] → 그 묶음 전체를 −. 탭마다 토스트를 띄우면 `Toast` 가
  `toast.id` 마다 spring 을 다시 시작해 연타 중 깜빡인다 — 그래서 묶음 단위.
- **길게 누르기 = −250**(햅틱 medium, 물높이 내려감). 0 아래로는 안 내려간다(서버도 `max(0, …)`).
- 스크린리더: 버튼 라벨 "물 오늘 750ml, 목표 2,000ml", `accessibilityActions` 로 "250ml 더하기/빼기"(제스처 없이도 되돌릴 수 있게).

### 3-4. 목표·넘침
- 물높이 = `min(1, consumed / target)`. target 이 0·null 이면 2000 으로 본다(API 는 500~10000 만 받지만 DB 직접 값 대비).
- 목표를 넘는 순간 **하루 한 번** `haptics.success()` + 원이 한 번 통 튀는 정도. 넘친 뒤에도 탭은 계속 된다(막지 않는다 — 정책).
- 분석 문서 방침대로 "목표까지 1,250ml 남았어요" 같은 압박 문구는 홈에 두지 않는다. 숫자는 토스트·스크린리더에만.
- 아주 큰 값(예: 하루 5L 이상)도 막지 않는다. 경고 문구는 의학적 판단이라 이번 범위 밖(필요하면 별도 논의).

### 3-5. 날짜(KST) 경계
- 홈은 자정을 넘겨도 다시 그리지 않는다(TripPeek 사례, `HOME_WIDGET_COMPLEXITY` a-2). 물 값에 `todayKst()` 키를 붙여 두고,
  탭할 때 키가 바뀌었으면 화면 값을 0 으로 리셋한 뒤 더한다. AppState active 에서도 재조회.
- 23:59:59 탭이 00:00:00.4 에 flush 되면 다음 날로 들어간다 — 0.5초 창이라 받아들인다(서버 `KstClock.today()` 가 기준).

## 4. 권장안 — 모양

### 4-1. 원 안의 물
- 기존 `TodayButton` 과 같은 36px 원. 안에 `overflow: 'hidden'` + 원 전체 크기의 채움 View 를 두고 **`translateY` 로 올린다**
  (`useNativeDriver: true` 가능 — height 애니메이션은 레이아웃 속성이라 네이티브 드라이버 불가). "찍"은 `Animated.spring`
  (friction 낮게, 살짝 넘쳤다 돌아오는 느낌) — 이미 `Toast`·`AvatarCrown` 이 쓰는 RN Animated 로 충분, reanimated 4 도 이미 있지만 필요 없다.
- 탭 지점 위로 작은 "+250" 글자가 떠오르며 사라짐(translateY+opacity, 동시 3개까지만).
- `AccessibilityInfo.isReduceMotionEnabled()` 면 출렁임 없이 바로 그 높이로(AvatarCrown 과 같은 방식).

### 4-2. 아이콘 — 새 글리프 금지
- 아이콘 서브셋(`assets/icon-glyphmap.json`, 177개)에 **물·컵 글리프가 없다**(cup/water/glass 전부 없음). 새 MDI 이름을 쓰면 서브셋 폰트를
  다시 만들어야 하고(이 기기엔 fontTools 없음), 폰트는 빌드 쪽 자산이라 OTA 로 못 나간다.
- 그래서 **💧 이모지**(Text) 또는 순수 View 로 그린 컵. 권장은 💧 — 물높이가 채워지면 그 위에 보이도록 원 가운데. 플랫폼마다 이모지
  모양이 다른 건 무드 배지와 같은 수준이라 감수.

### 4-3. 상대 열
- 상대 열에도 [물] 원을 두되 **보기 전용**(누르면 아무 이동 없이 토스트 "○○님 오늘 750ml" 정도). 내 사진을 상대 이름으로 못 남기는
  식단 칩과 같은 이유.
- 물높이 기준: 상대 목표가 응답에 없다 → 서버에 `partnerTargetMl` 추가(§3-2). 옛 서버면 2000 으로 본다.
  TodayRing 주석이 "상대의 개인 목표를 홈에 드러내지 않는다"고 했지만, 그건 칼로리·단백질 이야기다. 물 목표는 민감도가 낮고 럽바디에서
  이미 상대 마신 양을 보여준다. 그래도 **숫자는 노출하지 않고 물높이만** 보여 준다.
- 상대가 마셔도 실시간 갱신은 안 한다(포커스 때 재조회). `CoupleEventPublisher` 이벤트는 과하다.

### 4-4. 색 — 물은 파랗지만 이 앱에서 파랑은 "상대"다
- 색 규칙(2026-10-05): **나 코랄 · 상대 하늘 · 함께 라벤더**. 내 물높이를 하늘색으로 채우면 "상대 것"으로 읽힌다.
- 그래서 물높이는 **그 열의 소유자 색**(`meFill`/`partnerFill`, 글자는 `onColor`) — 운동·식단 채움과 같은 문법. 💧 가 "물"을 말한다.
- 다크 모드: `colors.surface` 원 + 소유자 fill. `npm run verify:theme` 대비 검사 대상 색은 기존 것만 쓰므로 변경 없음.

## 7. 경쟁 앱 사례 (웹 검색, 2026-10-16)
- 대부분의 물 앱(WaterMinder·Waterllama·Sip·Plant Nanny)이 **컵 아이콘 한 번 탭 = 한 컵** 을 기본으로 한다. 컵 크기는 설정에서 고른다.

## 11. 후속 — 원 대신 물컵, 1L 가 가득 (2026-10-16 같은 날, 사용자 제안)

> "물컵이 채워지는 느낌은 어때? 구현 안되나? 1L 를 최대로 보구"

**된다. 그리고 §4 의 원 안 물높이보다 낫다** — 💧 이모지가 필요 없어지고(컵 모양이 곧 "물"), 1L 를 기준으로 하면 목표 문제가 사라진다.

### 11-1. 1L = 가득 찬 컵
- 컵 하나 = 1,000ml, 한 번 탭 = 1/4 컵. 네 번이면 가득.
- **목표(2000)와 끊긴다** — 분석 문서의 "2L 를 정답처럼 말하지 않음"과 맞고, 홈이 목표 압박을 하지 않는다.
- **상대 열에 상대 목표가 필요 없어진다** → §3-2 의 `partnerTargetMl` 서버 추가가 **불필요**. 상대 컵도 같은 1L 눈금이라 숫자 노출 걱정도 줄어든다.
- 1L 를 넘으면: 컵이 가득 찬 채로 한 번 출렁이고(성공 햅틱), 다음 탭에 비우며 1/4 로 다시 시작. 컵 오른쪽 위에 작은 배지
  "2"(2잔째)를 띄운다. 계산:
  - 물높이 = `consumed == 0 ? 0 : ((consumed − 1) % 1000 + 1) / 1000` — 정확히 1000·2000 일 때 빈 컵이 아니라 **가득 찬 컵**으로 보이게.
  - 배지 = `ceil(consumed / 1000)`, 2 이상일 때만.
- 목표 달성 햅틱(§3-4)은 컵 기준이 아니라 기존 목표 기준으로 남겨도 되고, 없애도 된다(권장: 1L 마다 한 번 — 단위가 하나라 단순).

### 11-2. 그리는 법 (새 의존성·새 글리프 없음 → OTA)
- 겉은 다른 버튼과 같은 36px 원(`colors.surface`) — 줄의 리듬을 지킨다. 그 **안에** 컵을 그린다(약 18×22).
- 층 3개:
  1. 물: 컵 크기 사각 View 안에서 **`translateY` 로 올라오는** 소유자 색 채움(`meFill`/`partnerFill`) — `useNativeDriver: true` 가능.
     "찍"은 `Animated.spring`(살짝 넘쳤다 내려앉음). 수면이 기울게 하고 싶으면 `rotate` 를 ±4° 로 한 번 흔든다(역시 네이티브 드라이버).
  2. 가리개: `react-native-svg`(이미 있음 — TodayRing 이 씀)로 **컵 바깥을 원 배경색(surface)으로 칠한** 패스. 위가 넓고 아래가 좁은
     사다리꼴 컵 모양이 이걸로 나온다. View 의 `overflow: hidden` 은 사각·둥근 사각만 자르기 때문에 이 방식을 쓴다.
  3. 컵 테두리: 같은 SVG 의 선(`textMuted`, 1.5) + 오른쪽 위 짧은 하이라이트 선.
  - SVG 속성을 애니메이션하지 않으므로(움직이는 건 View 뿐) JS 스레드 부담이 없다. 가리개 색이 원 배경과 같아야 하므로 컵은 반드시
    원 **안에** 둔다(패널 뒤는 사진·그라데이션이라 색을 알 수 없다).
- 다크 모드: 가리개 = `colors.surface`, 테두리 = `colors.textMuted` — 둘 다 테마 값이라 자동.
- 줄인 움직임 설정이면 출렁임·기울임 없이 바로 그 높이.

### 11-4. 결정 — 상대 열에도 물컵, 보기 전용 (2026-10-16, 사용자)

- **눌러도 물이 늘지 않는다.** 누르면 토스트 "○○님 오늘 750ml" 한 줄만(이동 없음). 길게 누르기·되돌리기·햅틱 없음.
  내 물을 상대 이름으로 남길 수 없다는 식단 칩과 같은 이유.
- 스크린리더: "○○님 물 오늘 750ml" — 버튼이 아니라 정보로 읽히게(`accessibilityRole` 은 text, 토스트는 선택 사항).

- 갱신: 홈 포커스·AppState active 때 재조회(실시간 이벤트 없음). 상대가 방금 마신 물이 바로 안 보이는 건 받아들인다.
- 애니메이션: 상대 값이 재조회로 늘었으면 그때 한 번 "찍" 차오른다(햅틱 없이) — 상대가 마셨다는 걸 알아채는 작은 순간.

### 11-5. 결정 — 가득 찬 컵 = 2L (2026-10-16, 사용자: "하루 권장이 2L")
§11-1 의 1L 컵을 **2L 컵**으로 바꾼다. 나머지(목표와 분리·상대도 같은 눈금·서버 변경 없음)는 그대로다.

- **고정 2L 눈금**이다 — 사용자가 정한 목표(`targetMl`)를 따라가지 않는다. 목표를 따르면 상대 컵에 상대 목표가 필요해져
  `partnerTargetMl` 서버 필드가 다시 생기고, 목표를 1.5L 로 바꾼 사람과 2L 인 사람의 컵이 같은 높이에서 다른 뜻이 된다.
  목표 바꾸기는 럽바디(P1)의 일로 남긴다.
- 분석 문서의 "2L 를 정답처럼 말하지 않음"과의 관계: 컵은 **눈금**일 뿐이고 홈에 "목표까지 ○ml" 문구·경고는 두지 않는다.
  2L 는 화면 어디에도 "권장량"이라고 적지 않는다(스크린리더 문장도 "오늘 750ml" 까지만).
- **한 탭 = 1/8 컵.** 원 안 컵(약 18×22)이면 한 칸이 2.7px 라 "찍"이 약하다 → 컵을 **20×26** 으로 키우고(원 36 안에 들어감),
  "찍" 느낌은 스프링 출렁임 + 떠오르는 "+250" 글자가 같이 맡는다. 한 칸은 3.25px.
- **2L 를 넘으면 컵을 비우지 않는다.** §11-1 의 "비우고 2잔째 배지"는 1L 일 땐 흔했지만 2L 에서는 드물고, 컵이 비는 모습이
  "기록이 사라졌다"로 보일 위험이 더 크다. 가득 찬 채로 유지하고, 2L 를 넘는 순간 **하루 한 번** 출렁임 + `haptics.success()`.
  넘친 양은 토스트·스크린리더 숫자로만 보인다. 배지는 없앤다.
- 물높이 = `min(1, consumed / 2000)`. 상대 컵도 같은 식(`partnerConsumedMl`).
- 작업량 변화 없음. §11-3 표의 "잔 수 배지"만 빠진다.

## 13. 후속 — 홈↔럽바디 같은 값 + 서버 add 원자화 (2026-10-16)

### 서버 — `WaterService.add`
- 읽고-더하고-쓰기 → `WaterLogRepository.addAmount`(JPQL `UPDATE … SET amountMl = CASE WHEN amountMl + :delta < 0 THEN 0 ELSE … END`) 한 문장.
  0행이면 INSERT, 그 INSERT 가 동시 도착에 지면(unique 위반) 다시 UPDATE. **단계마다 트랜잭션을 따로** 연다 — PostgreSQL 은
  제약 위반이 난 트랜잭션을 abort 시켜 같은 트랜잭션의 다음 문장이 실패한다. ON CONFLICT·GREATEST 는 쓰지 않았다(H2 양립, CASE 는 JPQL 표준).
- 안 쓰게 된 `WaterLog.add(int)` 는 지웠다. 마이그레이션 없음, API·응답 모양 그대로.
- 테스트(`WaterFlowTest` +3): 그날 첫 요청 4개 동시 → 1000, 이미 있는 행에 10개 동시 → 정확히 2750, 행 없는 날 −250 → 0.
  **옛 코드로 돌리면 두 건 실패** — 10개 동시 +250 이 **500 만 남았고**(2,250 유실), 첫 동시 요청은 unique 위반 예외.
  H2·PostgreSQL 16 둘 다 통과(PG 로그에 duplicate key → 재시도 경로 확인). 전체 백엔드 1,520 건 통과.

### 앱 — `store/waterStore.ts` (공용)
- §12 의 `useHomeWater` 안에 있던 묶기·직렬 전송·5xx 1회 재시도·실패 되돌림·자정 리셋·2L 햅틱을 스토어로 옮겼다.
  화면 값 = 서버 값 + 날아가는 양 + 안 보낸 양. **보내는 중에 온 조회는 내 양을 덮지 않는다**(목표·상대만 받는다) — 이게 홈→럽바디 낡은 값의 해법.
- `hooks/useWaterSync` — 떠날 때·백그라운드 때 flush, 돌아올 때 재조회. 홈은 읽기까지, 럽바디는 자기 `refreshExtras` 가 읽으므로 보내기만.
- 럽바디 `DietScreen`: 물 값을 스토어에서 읽고, ±250 은 `tap`(토스트 없음 — −250 버튼이 따로 있다), 목표 저장 응답은 `absorb`.
  예전엔 매 탭 즉시 요청 + 실패 시 토스트만(되돌림 없음)이었다.
- 홈 탭만 묶음 토스트 [되돌리기]. 로그아웃 시 `reset`(authStore) — 다음 계정에 남의 물 양·안 보낸 탭이 남지 않게, 날아가던 옛 응답은 세대 번호로 버린다.

## 1. 왜 운동보다 유리한가 — 구조가 다르다

운동 문서에서 세운 **곱셈/덧셈 프레임**을 식단에 그대로 대본다.

| | 운동 | 식단 |
|---|---|---|
| 행동 발생 빈도 | 주 0~4회, **안 하는 사람은 0회** | **매일 3회, 예외 없음** |
| 기록하려면 | 없던 습관을 새로 만들어야 함 | 이미 100% 일어나는 행동에 얹음 |
| 사진 | 인증샷은 찍는 사람만 찍음 | **음식 사진은 이미 찍는다** (특히 외식·데이트) |
| 커플 성립 조건 | 둘 다 운동해야 (곱셈) | 둘 다 먹음 — 조건 자체가 참 |

운동 탭의 근본 문제였던 "확률의 곱셈"이 식단에는 거의 없다. 모수가 다르다.

### 1-1. "같이 먹기"가 곱셈을 덧셈으로 바꾸는 유일한 장치다

`sharedWithPartner` 는 한 명이 기록하면 상대 몫 Meal 을 자동 생성한다
(`MealService`, `SaveMealRequest.sharedWithPartner`). **운동에는 이에 대응하는 게 없다.**
커플 스트릭·커플 식단 목표가 식단에서만 자력으로 굴러갈 수 있는 이유가 이것이고,
현재 앱에서 가장 저평가된 기능이라고 본다.

## 2. 그런데 안 쓰이는 이유도 명확하다 — 요구하는 정확도

`frontend/src/screens/diet/DietRecordScreen.tsx` 는 **1881줄**로 운동 세션 화면보다 무겁다.
한 끼 저장에 노출되는 입력이 날짜·끼니·같이먹기·장소·별점·바코드·사진·즐겨찾기·최근음식·
음식항목(이름/양/칼로리/탄단지 ×N)·합계·메모다.

- 매크로까지 적으면 **하루 15회 이상 입력**. 다이어트 결심 후 2~4주만 유지되는 패턴이다.
- 이 영역은 **팻시크릿·다이어트신과 정면으로 붙는 자리**다. 승부는 음식 DB 규모에서 나고,
  운동 종목 카탈로그(수십 개 vs 수백~1000개)와 **똑같은 구조로 진다.**
- `Feature.AI_FOOD_PHOTO` 무료 한도가 **하루 2회**인데 끼니는 하루 3번이다
  (`backend/.../common/plan/Feature.java`). 무료 사용자는 가장 편한 경로를 매 끼니 쓸 수 없다 —
  **구조적 불일치**다. (→ 5절)

## 4. 운동과 결정적으로 다른 점 — 부품은 이미 다 있다

운동 탭에서는 느슨한 경로(원탭·사진 AI)를 **새로 만들어야** 했다. 식단은 **이미 갖고 있다** —
사진 AI 분석(`FoodAnalysisService`), 바코드(`FoodDbClient`), 즐겨찾기 원탭, 최근 음식, 공공 DB.

문제는 **메인 화면에 안 보인다**는 것이다. 진입점은 `＋ 식단 기록하기` 하나고, 들어가면
폼 전체가 펼쳐진다. 운동에서 얻은 교훈("기록의 최소 단위를 낮춰라")을 식단에 적용한다는 건
새 기능을 만드는 게 아니라 **이미 있는 가벼운 경로를 앞으로 끌어내는 일**이다.

## 5. 방향 전환 — "사진만 올리면 끝" (사용자 제안, 2026-09-09)

> "보통 음식 사진을 먹기 전에 많이 찍잖아. 그거를 찍고 AI 기록하기 버튼 또 누르고
> 이게 귀찮은 거잖아. 사진을 올리고 저장하면 알아서 백단에서 AI 계산하고 그런 게 되는 건 어때?"

### 5-1. 이 제안이 옳은 이유

1. **사진 찍는 타이밍이 분석에 유리하다.** 먹기 **전** 사진은 온전한 1인분이 다 보인다 —
   AI 추정에 가장 좋은 조건이다. 습관과 기술 요구가 처음으로 일치한다.
2. **버튼이 요구하는 건 "지금 결과를 기다리겠다"는 약속이다.** 현재 흐름은
   사진 선택 → **AI로 음식 분석** 탭 → 대기 → 결과 확인 → **완료!** 로, 사용자가 화면에
   붙들려 있어야 한다. Gemini 503 이 몇 분 지속되기도 한다는 걸 이미 알고 있으면서
   (`AiJobService` 클래스 주석) 사용자를 요청 안에 묶어두고 있다.
3. **부품이 이미 있다.** `AiJobService` 는 정확히 이 목적(요청 바깥에서 돌리고 분 단위 재시도)
   으로 만들어졌는데 식단 저장 경로가 안 쓰고 있다.

### 5-2. 지켜야 할 원칙과의 충돌 — 그리고 해소

운동 문서 4절이 못박은 원칙과 정면으로 부딪힌다:

> **AI 결과를 자동 저장하지 않는다.** 잘못 읽은 숫자가 조용히 저장되면 추이가 오염되고,
> 나중엔 무엇이 진짜였는지 알 수 없다.

**두 경우가 다르다고 판단한다.**

| | 운동 사진 | 음식 사진 |
|---|---|---|
| AI가 읽는 것 | 화면에 **인쇄된 사실**(5.2km) | **추정**(이 밥 몇 kcal) |
| 대안 입력의 성격 | 사용자가 아는 정확한 값 | 사용자도 **추정**한다 |
| 틀렸을 때 | 사실이 왜곡됨 | 추정치가 다른 추정치로 바뀜 |

운동에서 자동 저장을 막은 이유는 **사실을 훼손하기 때문**이었다. 칼로리는 애초에 사실이 아니라
추정이고, 사용자가 손으로 적는 값도 똑같이 추정이다. 그러므로 **자동 저장 금지 원칙은 식단에
그대로 적용되지 않는다.** 다만 원칙의 취지("무엇이 진짜였는지 알 수 있어야 한다")는 남기므로,
아래 설계에서 **출처 표시**로 대체한다.

### 5-3. 설계 결론

```
사진 선택 → [완료!]          ← 사용자는 여기서 끝. 화면을 떠난다
   ↓ (즉시 저장, calories=null)
Meal 저장 + AiJob 등록
   ↓ (수 초~수 분, 실패 시 재시도)
분석 결과를 그 Meal 에 채움 + estimated 플래그
   ↓
다음 진입 때 카드에 "AI 추정" 배지와 함께 보임
```

- **저장과 분석을 분리한다.** 분석이 실패해도 사진 붙은 기록은 그대로 남는다 —
  운동 인증샷과 같은 원칙("읽기 실패와 기록은 독립이다").
- **`nutrition_source` 로 출처를 남긴다**(`AI_ESTIMATED` / `USER` / `BARCODE`).
  자동 저장을 허용하는 대신 **무엇이 추정인지는 영구히 구분 가능해야** 한다.
  사용자가 그 값을 한 번이라도 고치면 `USER` 로 승격되고 배지는 사라진다.
- **확인을 강요하지 않는다.** 모달·확인 버튼 없이 카드의 배지로만 알린다.
  이 경로의 존재 이유가 "가장 낮은 마찰"이기 때문이다.
- **합계에는 포함한다.** 빼면 게이지가 0으로 남아 결국 사용자가 손대야 하고, 그러면
  이 기능이 무의미해진다.

### 5-4. 미해결 — 무료 한도 (결정 필요)

자동 분석은 사용자가 버튼을 누르지 않으므로 **한도를 조용히 태운다.** `AI_FOOD_PHOTO` 는
무료 하루 2회인데 끼니는 3번이다. 세 갈래가 있다:

1. 무료 한도를 **3회로 올린다** — 끼니 수와 일치시킨다. 원가는 flash-lite 라 무시 가능하다는
   판단이 `Feature.java` 주석에 이미 있다.
2. 자동 분석을 **설정 토글**로 두고(기본 켬), 한도 소진 시 카드에 "오늘 AI 분석 한도를
   다 썼어요"를 표시한다 → 자연스러운 PRO 유도면이 된다.
3. 자동 분석은 별도 Feature 로 분리해 한도를 따로 준다.

**1+2 조합을 권한다.** 한도를 조용히 태우는 것 자체는 사용자가 켜둔 설정이면 정당하고,
소진 사실은 반드시 보이게 해야 한다.

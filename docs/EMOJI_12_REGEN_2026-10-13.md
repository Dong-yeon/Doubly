### 1-3. 차감 시점·트랜잭션·동시성

- **요청 시 선차감.** `POST /couple-emojis/generate` → `CoupleEmojiService.prepare`(`:175`) → `GeminiClient.requireImageConfiguredAndCharge`(`GeminiClient.java:257`) →
  `PlanGuard.consumeOrCredit`. 플랜 한도(Redis 카운터)를 먼저 보고, 막히거나 넘치면 `FeatureCreditService.consumeOne`(`@Transactional`).
  결과 `Charge`(QUOTA/CREDIT/NONE)를 티켓이 들고 백그라운드 작업으로 넘어간다(`CoupleEmojiService.java:155-157`).
- **트랜잭션 경계**: 크레딧 차감은 `consumeOne` 자기 트랜잭션 하나. 생성(`generate`)은 `NOT_SUPPORTED`(`:219`)로 트랜잭션 밖이고, 장마다
  `REQUIRES_NEW` 로 저장(`:150-151`, `:268`). 차감과 생성은 **원자적이지 않다** — 되돌림으로 맞춘다(§2-5).
- **동시 요청 시 이중 차감 — 반대 방향의 위험이 있다(미확인, 테스트 없음).** `findAvailable` 은 잠금 없는 일반 조회이고
  (`FeatureCreditRepository` — `@Lock` 없음), `consumeOne` 은 메모리에서 `used++`(`FeatureCredit.java:84-90`) 후 더티 체킹으로
  UPDATE 한다. `@Version` 도 없다. 남은 크레딧이 1인데 두 요청이 동시에 읽으면 **둘 다 `used=0` 을 보고 `used=1` 로 쓴다(lost
  update)** → 1크레딧으로 2회가 나간다. 사용자에게 이중 차감이 아니라 **우리 쪽 과소 차감**이다. 플랜 쿼터 쪽은 Redis 증가라
  원자적이다(`UsageCounter`).
- **더블탭·네트워크 재시도**: 서버 멱등키 **없음**(`GenerateCoupleEmojiRequest` 에 요청 id 없음, `AiJobService.submit` 은 매번 새 UUID —
  `AiJobService.java:141-143`). 같은 요청이 두 번 오면 **두 번 차감, 두 세트 생성**이다. 앱 방어는 화면 상태뿐 —
  `generate` 첫 줄 `setGenerating(true)`(`CoupleEmojiCreateScreen.tsx:204`), 생성 중엔 버튼 영역을 그리지 않는다(`:461`).
  `apiClient` 는 401 refresh 외 자동 재시도 없음(`api/client.ts:232,270`). 원본 업로드 → 생성 요청이 한 함수라
  (`api/coupleEmoji.ts:64-73`) 생성 요청 타임아웃 후 사용자가 다시 누르면 새 업로드·새 차감이 된다.

### 1-4. 스토어에 `emoji_set_1` 이 실제 등록됐나 — **미확인**

코드·설정에서 알 수 있는 단서:
- 앱은 등록 여부를 **런타임에** 본다 — `fetchEmojiSetProduct`(`iap.ts:250-262`)가 상품을 못 받으면 가격이 null 이고 구매 버튼을
  그리지 않는다(`CoupleEmojiCreateScreen.tsx:77` `canBuySet = … && !!setPrice …`). 즉 **버튼이 보이면 등록된 것**이다.
- 문서상 마지막 상태: `PLAY_LAUNCH_AUDIT_2026-09-25.md:19` "`emoji_set_1` 은 미등록", `GROWTH_ROADMAP_2026-09-28.md:41` "남은 확인:
  … `emoji_set_1` 등록". 그 뒤 등록 기록 없음.
- 운영 데이터로 판정: `event_logs` 의 `PURCHASE_STARTED`(detail `emoji_set_1`)·`CREDIT_PURCHASED` 가 있으면 최소 한쪽 스토어에 있다.

```sql
SELECT event_type, detail, count(*), min(created_at), max(created_at)
  FROM event_logs
 WHERE detail LIKE 'emoji_set_1%' AND event_type IN ('PURCHASE_STARTED','PURCHASE_CANCELLED','PURCHASE_FAILED','CREDIT_PURCHASED')
 GROUP BY 1, 2;
SELECT store, count(*), sum(credits), sum(used) FROM feature_credits WHERE product_id = 'emoji_set_1' GROUP BY store;
```

### 3-1. 채팅 전송 시 참조 방식 → 교체 영향

`ChatService.java:335-340`: 메시지 `content` 에 **이모지 id**, `imageUrl` 에는 **행의 URL 을 복사**해 저장한다("트레이에서 숨긴 뒤에도
메시지가 조인 없이 그려지게"). 이미지 파일 복사는 없다.

→ **교체 방식이 "새 행 + 옛 행 숨김"이면 이미 보낸 메시지는 옛 그림 그대로 남는다.** 숨김은 파일을 지우지 않으므로 깨지지 않는다.
→ **"같은 행의 `image_url` 을 덮어쓰기"로 하면** 메시지는 복사본 URL 이라 옛 그림이 남지만, 옛 파일을 지우는 순간 깨진다.
배경 따내기 때는 의도적으로 메시지 URL 까지 바꿨다(`ChatMessageRepository.java:138-145` `replaceImageUrl`) — 재생성은 **다른
그림**이라 그 패턴을 쓰면 지난 대화의 표정이 바뀐다(§8-D4).

## 5. 현재 구조 요약 (단계)

1. 앱: 사진 고르기·자르기 → `POST /couple-emojis/upload-signature`(PHOTO_UPLOAD 1 차감) → Cloudinary `emoji-source/` 업로드.
2. 앱: `POST /couple-emojis/generate {sourceImageUrl, subjectUserId, emotions(1~6)}`.
3. 서버 요청 스레드 `prepare`: 폴더 검사 → 커플·대상 검사 → 감정 검사 → **차감**(전체 1000/일 → 개인 50/일 → `consumeOrCredit`: 플랜 쿼터 → 크레딧) → 티켓.
4. `AiJobService.submit` → 202 + jobId. 큐 포화면 `abandon`(차감·원본 되돌림).
5. 백그라운드 `generate`: 원본 다운로드 → **외형 추출(텍스트 1회)** → 감정마다 이미지 호출(동시 4, 장마다 재시도 최대 6) →
   컷아웃 → Cloudinary 업로드 → 장마다 `couple_emojis` 행 커밋.
6. 0장이면 `refund(charge)` 후 실패, 1장 이상이면 이벤트·상대 푸시·결과. **finally: 원본 삭제.**
7. 앱: 폴링 사이 목록을 다시 읽어 칸을 채우고, 끝나면 결과·실패 안내.
8. 채팅: 트레이에서 고르면 `content=이모지 id`, 서버가 행의 URL 을 메시지에 복사. 앱이 감정으로 모션을 입혀 재생.

## 7. 제안 스키마

### 안 A (권장) — 생성 크레딧은 `feature_credits`, 재생성은 **세트 테이블**에

생성 회차는 지금처럼 사람에게 붙는 소모성 크레딧(구매·환불·탈퇴 회수 경로를 그대로 쓴다). 재생성은 **세트에 붙는 잔량**이라
세트 테이블이 갖는다 — "그 세트 안에서만"이 스키마로 보장된다.

```sql
-- V138__couple_emoji_sets.sql  (다음 번호는 작성 직전 CLAUDE.md §7 명령으로 다시 확인)
-- 세트 단위 메타 — 누가 무엇으로 만들었나, 재생성이 몇 번 남았나.
-- (H2 호환 구문만 사용 — 테스트가 동일 마이그레이션을 적용한다)
CREATE TABLE couple_emoji_sets (
    batch_id        VARCHAR(36)  PRIMARY KEY,                     -- couple_emojis.batch_id 와 같은 값
    relation_id     BIGINT       NOT NULL REFERENCES relations (id),
    created_by      BIGINT       NOT NULL REFERENCES users (id),
    charge_source   VARCHAR(20)  NOT NULL,                        -- QUOTA | CREDIT | WELCOME | LEGACY
    credit_id       BIGINT,                                       -- CREDIT 일 때 feature_credits.id (FK 는 두지 않는다 — 탈퇴 순서)
    regen_total     INT          NOT NULL DEFAULT 0,
    regen_used      INT          NOT NULL DEFAULT 0,
    reference_emoji_id BIGINT,                                    -- 재생성 때 참조 이미지로 쓸 장(§8-D2)
    created_at      TIMESTAMP    NOT NULL DEFAULT NOW()
);
CREATE INDEX idx_couple_emoji_sets_relation ON couple_emoji_sets (relation_id);

-- 교체 이력 — 새 장이 어느 장을 대신했나(되돌리기·분쟁 확인용)
ALTER TABLE couple_emojis ADD COLUMN replaces_id BIGINT;

-- 기존 세트 백필 — 재생성 권리 없음(LEGACY, 0회). GROUP BY 만 쓰므로 H2·PostgreSQL 공통.
INSERT INTO couple_emoji_sets (batch_id, relation_id, created_by, charge_source, regen_total, regen_used, created_at)
SELECT batch_id, MIN(relation_id), MIN(created_by), 'LEGACY', 0, 0, MIN(created_at)
  FROM couple_emojis
 GROUP BY batch_id;
```

재생성 차감은 **조건부 UPDATE 한 줄**로 원자적으로(§1-3 의 lost update 를 반복하지 않는다):
`UPDATE couple_emoji_sets SET regen_used = regen_used + 1 WHERE batch_id = :b AND regen_used < regen_total` → 영향 행 0 이면 거절.
실패하면 `regen_used - 1 WHERE regen_used > 0`.

Purger: `RelationRecordPurger` 에서 `couple_emojis` 삭제(`:112`) **앞이나 뒤 어디든**(서로 FK 없음) — 단 `relations` 삭제보다 앞.
`UserDataPurger` 는 `created_by` FK 때문에 관계 정리 경로가 먼저 지우는지 확인 필요(**미확인** — 지금 `couple_emojis.created_by` 도
같은 FK 를 갖고 있어 같은 자리에 두면 된다).

### 안 B — 재생성도 `feature_credits` 에 (세트 id 칸 추가)

```sql
ALTER TABLE feature_credits ADD COLUMN batch_id VARCHAR(36);
-- 세트가 만들어질 때 서버가 한 행을 만든다: feature='AI_COUPLE_EMOJI_REGEN', store='MANUAL',
-- product_id='emoji_regen', transaction_id='regen:'||batch_id, credits=3, batch_id=<세트>
```

장점: `consumeOne`/`refundOne`/탈퇴 회수 코드를 재사용. 단점: ① `Feature` 에 상수를 하나 늘려야 해서 `PlanFeatureSyncTest`·앱
`FeatureKey` 가 같이 바뀐다 ② 크레딧이 **사람**에 붙어 있어 상대가 같은 세트를 재생성할 때 누구의 행을 쓸지 규칙이 또 필요하다
③ 세트 메타(결제 출처·참조 장)를 둘 곳은 여전히 없다. → **A 를 권한다.**

### 기존 사용자의 남은 크레딧

- 지금 `emoji_set_1` 행은 `credits=1`(=6장짜리 1회)이다. **"2회" 권리를 가진 사람은 코드상 존재하지 않는다**(§1-2). 남은 1회는
  새 규칙(12장 + 재생성 3)으로 쓰게 하면 사용자에게 유리하고 데이터 변경이 필요 없다 — 세트를 만들 때 `charge_source=CREDIT`,
  `regen_total=3` 을 주면 끝.
- 스토어 문구로 "2회"를 약속해 판 적이 있다면(콘솔 설명) 그 사람에게만 1회를 더 준다:

```sql
-- 실행 전 확인: 영향 받는 행
SELECT id, user_id, store, credits, used, created_at FROM feature_credits WHERE product_id = 'emoji_set_1' ORDER BY id;
-- (결정 시) "2회"로 판 기간의 구매에 1회 추가 — :cutover 는 콘솔 문구를 바꾼 시각
UPDATE feature_credits SET credits = credits + 1
 WHERE product_id = 'emoji_set_1' AND created_at < :cutover AND credits = 1;
```

이건 **Flyway 가 아니라 사람이 한 번 실행**한다 — 마이그레이션은 아무 배포 때나 돌아 시점 스냅샷이 틀어진다(FREE_TIER_AND_ADS.md
"Flyway 마이그레이션으로 만들지 않았습니다"와 같은 이유).

> *형태 축 진화 매트릭스와 태그 합산 로직* — 을 남기기 위한 것입니다. 저장소 어디에도
> 기록되지 않은 채 세션에만 있던 내용이라 옮겨 적습니다. 다시 꺼낼 때 참고용입니다.

## 배경 — 축이 두 개다

드롭된 프로토타입(V45)에는 **크기 축**만 있었습니다: `growth_point`가 오르면 캐릭터가
성장 단계(알 → 새싹 → …)를 올라가고, 기록이 없으면 퇴화합니다.

여기에 **형태 축**을 하나 더 얹자는 것이 이 설계입니다. 크기가 "얼마나 꾸준히 했나"라면,
형태는 "어떻게 했나"(운동 × 식단 건강도)를 나타냅니다. 두 축은 독립적입니다.

## 형태 매트릭스

|  | 식단 건강 | 식단 부실 |
| --- | --- | --- |
| **운동함** | 근육이 | 탄탄이 |
| **운동 안 함** | 말랑이 | 지방이 |

여기에 매트릭스 밖 특수 상태 3개가 붙습니다.

| 형태 | 조건 |
| --- | --- |
| **홀쭉이** | 방치 — 기존 `decay()`의 `lastActiveDate`/`graceDays` 초과 |
| **평범이** | 표본 부족(윈도우 내 기록 3일 미만) 또는 판정 모호 |
| **볼록이** | 판정이 모호하되 지방이 쪽으로 기운 경고 단계 |

### 제외한 안

체형·비율 계열, 대식이/소식이, 붓기, 종이인형, 뼈다귀는 **뺐습니다.** 몸매를 직접 평가하는
방향으로 읽힐 수 있고, 커플 앱에서 그 톤은 위험합니다. 남긴 7종도 그 기준으로 걸렀습니다.

## 판정 방식 — 자동이 아니라 태그

식사의 건강도를 **칼로리나 카테고리로 자동 판정하지 않습니다.** 사용자가 단 태그를 그대로
씁니다. 자동 판정은 오판이 잦고, 오판이 곧 "네 식사는 부실하다"는 메시지가 되기 때문입니다.

## 적용 범위 — 커플 공용

형태는 **관계당 1개**입니다. 기존 `couple_characters`가 relation당 1행인 구조를 그대로
따릅니다. 개인별 형태를 따로 두면 둘을 비교하게 되고, 그건 이 기능이 의도한 방향이 아닙니다.

## 태그 합산 로직

**윈도우: 최근 14일 롤링** (하루 단위 재계산, 스냅샷 아님)

### ① 식단 건강도 스코어 D

두 사람이 그 14일 동안 남긴 태그를 **개인 구분 없이 하나의 풀로 합산**합니다.

```
D = 건강 태그 수 / (건강 태그 수 + 부실 태그 수)
```

**태그를 안 단 식사는 분모에서 제외**합니다 — 태그 누락을 "부실"로 취급하면 억울한 케이스가
생깁니다.

### ② 운동 스코어 E

```
E = 커플이 운동한 날 수 / 14
```

"그날 운동한 날"은 **둘 중 한 명이라도 기록하면 인정**(OR 방식)입니다. 기존 `growth_point`의
"혼자=기본점수, 둘 다=보너스" 철학과 다른데, 형태 판정은 팀으로서 "우리가 이번 주 얼마나
움직였나"를 보는 것이라 OR이 자연스럽습니다.

### ③ 히스테리시스 밴드

임계값에 밴드를 둬서 경계에서 형태가 매일 왔다갔다 하는 걸 막습니다. 이전 형태를 입력으로
받아, 밴드 안이면 유지합니다.

| 스코어 | 진입 기준 | 이탈 기준 |
| --- | --- | --- |
| E (운동함) | ≥ 0.4 | < 0.3 |
| D (식단 건강) | ≥ 0.6 | < 0.45 |

> **이 네 숫자는 실측 데이터 없이 잡은 초안입니다.** 실제로 붙여보고 튜닝해야 합니다.
> 설계에서 확정되지 않은 유일한 부분입니다.

### ④ 우선순위

위에서부터 먼저 걸리는 조건이 이깁니다.

1. **방치** (`lastActiveDate` / `graceDays` 초과) → **홀쭉이** — 다른 조건 전부 무시
2. **표본 부족** (윈도우 내 기록 3일 미만) → **평범이**
3. 매트릭스 판정 (①②③)
4. 판정 모호(밴드에 걸치고 이전 형태도 없음) → **평범이**, 지방이 쪽으로 기울면 **볼록이**

## 재개한다면 — 먼저 확인할 것

1. **기반이 없습니다.** `couple_characters` 테이블(V45)과 `com.fitto.character` 패키지가
   모두 드롭된 상태라, 크기 축부터 다시 만들어야 형태 축을 얹을 수 있습니다.
2. 드롭 사유가 "도메인 레이어만 있고 서비스·컨트롤러·화면이 없는 드리프트"였습니다.
   재개한다면 **화면까지 한 번에 가는 게 아니면 시작하지 않는 편**이 낫습니다.
3. 마이그레이션 번호는 재개 시점에 반드시 다시 확인하세요 (현재 최신 `V66`).
   병렬 세션 간 Flyway 버전 충돌이 반복적으로 발생한 이력이 있습니다.

### 원래 크기 축 설계 (V45 프로토타입에서)

재개 시 참고할 만한 결정들입니다.

- `growth_point`는 파생계산이 아니라 **실제 mutable 값**입니다 — 퇴화가 값을 줄일 수 있어서
  `LevelResponse`처럼 누적 로그에서 매번 계산하는 방식이 성립하지 않습니다. 반대로 성장
  **단계**(알/새싹 등)는 저장하지 않고 조회 시점에 파생 계산합니다(저장하면 퇴화 때 드리프트).
- **"둘 다 기록" 보너스**는 하루당 dedup 날짜 + 보너스 지급 플래그로 관리해, 한쪽이 먼저
  기록해도 나중에 상대가 완성하면 보너스가 얹히게 했습니다. 예시 배점: 운동 혼자 2점,
  둘 다 하면 2+2+3=7점(단순 합의 약 2배).
- **퇴화**는 유예기간(`graceDays`)을 넘긴 유휴일만큼 차감하되, `lastDecayedDate`로 이미
  처리한 구간을 추적해 배치가 매일 돌아도 중복 차감되지 않게 했습니다.
- 정책값(유예일수·차감량·on/off)은 스키마가 아니라 `application.yml`
  (`fitto.plan.free-trial` 패턴)로 빼서 배포 후 튜닝 가능하게 했습니다.
- 적용 범위는 `COUPLE` 관계 전용(`TRAINER_MEMBER` 제외), `Streak`처럼 최초 기록 시 lazy 생성.

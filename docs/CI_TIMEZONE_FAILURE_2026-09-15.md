# CI가 매일 9시간 빨갰던 이유 — 테스트 시계와 운영 시계가 달랐다 (2026-09-15)

한국 시간 **00:00~09:00**(= 15:00~24:00 UTC)에 올린 커밋은 **전부** 빨갰다. 코드가 아니라
**시각**이 원인이라, 같은 커밋을 자정 넘겨 다시 돌리면 그대로 초록이었다.
[SCHEDULER_TEST_FLAKE_2026-09-15.md](SCHEDULER_TEST_FLAKE_2026-09-15.md)와 같은 "전체
suite 에서만/CI 에서만 깨진다" 계열이지만 원인은 전혀 다르다.

## 증상

- 최근 CI 120회를 UTC 시각별로 세면: **00~13시 91건 전부 성공**, **22시 3실패/0성공**,
  **23시 5실패/1성공**, 14시 1실패/1성공. (15~21시 UTC = 한국 자정~06시라 커밋이 없어 표본 0)
- 빨간 런(`a236cef`, 09-14 23:40Z)은 **716건 중 20건 실패**. 실패 목록이 전부
  "오늘_…" 계열이었다 — `MealFlowTest`(10건)·`WorkoutFlowTest`·`EnergyBalanceTest`·
  `CalendarFlowTest`·`MealPhotoAutoAnalysisTest`·`ReengagementNotifierTest`.

## 원인

| | "오늘"을 어디서 얻나 |
| --- | --- |
| 운영 코드 | `KstClock.today()` = `LocalDate.now(Asia/Seoul)` |
| 테스트 | 존 없는 `LocalDate.now()` = **JVM 기본 시간대** (229곳) |

개발 PC 는 KST 라 둘이 같다. CI 러너는 **UTC** 다. 한국 00:00~09:00 사이에는 UTC 날짜가
하루 이르므로, 테스트가 `LocalDate.now()` 로 만들어 저장한 기록은 서비스가 보는
`KstClock.today()` 의 "오늘"이 아니다 → `findToday()` 가 빈 목록을 돌려주고, 저장은
성공했는데 단정이 깨진다. `미래_날짜로는_수정할_수_없다` 처럼 반대 방향으로 깨지는 것도 같은 뿌리다.

재현: 테스트 JVM 기본 시간대만 UTC-12 로 돌려(= "테스트 날짜 = KST 날짜 − 1") 현재 main
(`12154d6`)에서 전체 suite 를 돌리면 **727건 중 21건 실패**, 실패 목록이 위 CI 런과 같다.
같은 커밋이 같은 날 07:27Z CI 에서는 초록이었으므로 **차이는 시간대뿐**이다.

## 고친 방법

### 1. 테스트 JVM 시간대를 KST 로 고정 (`backend/build.gradle`)

```groovy
systemProperty 'user.timezone', 'Asia/Seoul'
```

이 앱의 하루는 **정의상 KST** 다(`KstClock` 주석). 테스트 시계를 운영 시계에 맞춘 것이지
실패를 가린 게 아니다. 229곳을 `KstClock.today()` 로 바꾸는 큰 수술도 검토했지만, 시계가
한 곳에서 정해지면 나머지는 전부 따라오므로 작은 쪽을 택했다.

### 2. 그 고정이 진짜 버그를 덮지 않도록 가드 (`KstClockGuardTest`)

시간대를 고정하면 **운영 코드가 존 없는 `now()` 를 쓰는 버그가 테스트에서 안 보인다**
(개발 PC 도 KST 라 원래 안 보였다). 그래서 같은 테스트가 둘을 함께 지킨다.

- `테스트_시계는_KST_다()` — 기본 시간대와 `LocalDate.now() == KstClock.today()` 확인.
  **이 단정이 값을 갖는 자리는 CI** 다. 고정이 풀리면 UTC 러너에서 즉시 빨개지므로,
  "특정 시간대에만 깨지는" 진단하기 어려운 실패가 한 줄짜리 실패로 바뀐다.
- `운영_코드는_존_없는_LocalDate_now_를_쓰지_않는다()` — `src/main/java` 를 훑어 위반을 모은다
  (주석 줄은 제외 — `KstClock`·`Quota` 의 설명문이 자기 자신을 잡지 않도록).

`LocalDateTime.now()`(53곳)는 막지 않는다. 그쪽은 대체로 "기록된 시각"이라 순간의 문제이고
날짜 경계를 나누는 판정이 아니다. 날짜 경계만 KST 로 고정되어야 한다.

### 3. 가드가 잡아낸 운영 버그 4곳

CI 빨강과 **같은 뿌리**가 운영 코드에도 살아 있었다. 즉 이건 테스트 위생 문제만이 아니었다.

| 위치 | 증상 |
| --- | --- |
| `MealController#copyFrom` | 프런트가 `sourceDate` 를 보내지 않으므로(`diet.ts copyFromYesterday`) 서버 기본값이 실사용 경로다 → **한국 00:00~09:00 에 "어제 식단 불러오기"가 그저께를 복사**했다. 저장 대상 날짜는 `KstClock.today()` 라 맞고 원본만 하루 밀렸다 |
| `CalendarController#month` | `year`·`month` 생략 시 UTC 기준 이번 달 → **매월 1일 그 시간대에 지난달**을 돌려준다. 프런트는 항상 파라미터를 보내므로 잠재적 |
| `DateMealCalendarController#month` | 위와 같음 |
| `BmrCalculator` | 나이 계산이 생일 당일 그 시간대에 한 살 적게 나온다 |

## 다음에 같은 냄새가 나면

1. **"CI 만 빨갛다"** → 먼저 **런의 시각**을 본다. 시간대별로 갈리면 코드가 아니라 시계다.
2. 날짜 경계를 다루는 새 코드에는 `LocalDate.now()` 를 쓰지 않는다 — `KstClock.today()`.
   가드 테스트가 막지만, 막힌 뒤에 이유를 찾지 않도록 여기 적어 둔다.
3. 사용자 노출 기능에서 "새벽에만 하루가 어긋난다"는 제보가 오면 `LocalDate.now()` 를
   1순위로 의심한다. 위 표의 4곳이 전부 그 모양이었다.

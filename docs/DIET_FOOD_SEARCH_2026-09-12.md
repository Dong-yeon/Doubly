# 식단 음식 검색 — 돋보기 제거와 "칼로리 계산" 통합 (2026-09-12)

"식단쪽의 돋보기 검색이 기능이 애매하다"에서 시작한 진단과 결정입니다.
코드 변경은 `ec72fa6` 한 커밋(`DietRecordScreen.tsx`)이고, 백엔드는 손대지 않았습니다.

---

## 0. 결론 먼저

- 돋보기는 **검색이 아니라 "이미 적은 이름의 표기값 채우기"** 였습니다. 아이콘이 기능을
  잘못 말하고 있었고, 대상 데이터셋이 가공식품이라 집밥 이름은 거의 못 맞혔습니다.
- **제거하고 같은 조회를 `칼로리 계산` 버튼 앞단으로 옮겼습니다.** 표기값을 먼저 찾고,
  못 찾은 것만 AI 가 추정합니다. 전부 찾으면 AI 를 아예 호출하지 않습니다(쿼터·원가 0).
- **아직 확인되지 않은 것이 두 개 있습니다** — Railway 의 `FOOD_DB_API_KEY` 설정 여부와
  I2790 의 실제 응답 필드. 둘 중 하나라도 어긋나면 이 경로는 조용히 아무 일도 하지 않습니다
  (그래도 AI 로 이어지므로 사용자에게는 고장으로 보이지 않습니다 — 그게 이 변경의 안전망입니다).

---

## 1. 왜 애매했는가 (제거 전 상태)

| # | 문제 | 근거 |
| --- | --- | --- |
| 1 | 이 화면에서 **유일하게 라벨 없는 버튼**이었다 | `바코드로 찾기`·`AI로 칼로리 계산`·`＋ 음식 추가`는 전부 글자를 달고 있었다. 설명은 `accessibilityLabel` 뿐 — 스크린리더에만 읽힌다 |
| 2 | 이름을 **먼저 정확히 타이핑해야** 동작했다 | `onSearchDb`: 이름이 비면 "음식 이름을 먼저 적어주세요". 탐색이 아니라 채우기 |
| 3 | 대상 데이터가 **집밥이 아니다** | `FoodDbClient`가 `DESC_KOR=`로 부르는 I2790 은 `BAR_CD` 필드를 가진 가공식품 표기값 데이터셋. placeholder 가 유도하는 "공기밥"은 안 맞는다 |
| 4 | 키가 없으면 **바코드 문구로 실패** | `FOOD_DB_API_KEY` 기본값이 빈 문자열(`application.yml:157`) → `search`도 `FOOD_DB_NOT_CONFIGURED` → "바코드 조회 기능이 아직 준비되지 않았어요."(`ErrorCode:120`) |
| 5 | 채우는 값이 **검증되지 않았다** | `FoodDbClient` 클래스 주석이 스스로 밝힘 — `NUTR_CONT1~8`·`BAR_CD` 필드명은 추정치. 그런데 `pickDbResult`는 "실제 표기값으로 채웠어요"라고 확신했다 |
| 6 | AI 계산과 **역할이 겹치는데 배치가 반대** | 둘 다 `이름 → 영양값`. AI 는 항상 답하지만 유료·추정치이고 화면 맨 아래 1개, DB 는 무료·실측이지만 거의 못 맞히면서 항목마다 붙어 있었다 |

부수적으로 `FoodDbClient.isConfigured()`는 프로덕션 코드에서 아무도 호출하지 않습니다
(테스트만 씀). 즉 프론트가 "키 없음"을 미리 알고 버튼을 숨길 방법이 없었습니다.

## 1-1. 우리 DB 에는 음식 영양 데이터가 없다

혼동하기 쉬운 지점입니다. 마이그레이션의 food 관련 테이블은 전부 **사용자가 만든 데이터**입니다 —
`favorite_foods`(V12), `favorite_food_items`(V35), `favorite_food_gifts`(V51), `meal_items`(V39).
**영양성분 마스터 테이블은 없습니다.** 돋보기/바코드는 매번 외부 API(`openapi.foodsafetykorea.go.kr`)를
실시간으로 부르고, `FoodDbClient`에 캐시(`@Cacheable`)도 없습니다.

그래서 "DB 에 데이터가 있나?"는 **우리 DB 질문이 아니라 ① 키가 설정돼 있나 ② 그 공공 데이터셋이
그 이름을 갖고 있나** 두 질문입니다. ①은 Railway 변수라 코드로 확인할 수 없고, ②는 이 세션의
네트워크 정책이 해당 호스트를 막아(403 `Host not in allowlist`) 직접 조회하지 못했습니다.
**둘 다 미검증입니다.**

## 2. 바뀐 동작 (`fillCalories`)

1. 칼로리가 빈 항목의 이름으로 공공 DB 를 조회합니다. **이름 완전 일치만** 받습니다 —
   예전엔 사용자가 후보를 직접 골랐지만 지금은 자동이라, 근사 매칭은 엉뚱한 값을 조용히 넣습니다.
   이름 개수는 `MAX_FOOD_DB_LOOKUPS = 4`로 제한합니다(배치 엔드포인트가 없어 이름마다 1회 호출).
2. **전부 채워지면 AI 를 호출하지 않습니다.** 이게 유일한 실제 원가 절감 지점입니다
   (쿼터는 호출 단위라 부분 성공에는 절감이 없습니다).
3. 남으면 AI 를 부르고, **그 뒤에** 같은 이름을 표기값으로 덮습니다(실측 > 추정).
   AI 앞에서 `setItems` 하지 않는 이유: `analyzeItemsWithAi`가 "보낼 때의 목록"과 대조하는데,
   DB 가 `portion`을 채우면 그 대조가 어긋나 "음식이 바뀌어서 결과를 넣지 않았어요"가 뜹니다.
4. **조회 결과가 없으면 기존대로 AI 로 갑니다.** 값이 이미 다 차 있어도 버튼을 누르면 다시
   계산해주던 동작을 남겨야 합니다(구현 중 한 번 깨뜨렸다가 되돌린 지점).
5. 실패·키 미설정은 **조용히** 넘어갑니다 — 4번 문제(검색 버튼에서 바코드 문구)가 여기서 사라집니다.

버튼 문구도 `AI로 칼로리 계산` → **`칼로리 계산`**. 안내는 "표기값이 있는 음식은 그 값으로,
없으면 AI가 추정해요."로 바꿨습니다. AI 가 항상 도는 게 아니게 됐으니 이름이 약속을 어깁니다.

추가 영양소(당·나트륨·식이섬유)는 **모든 항목이 표기값으로 채워졌을 때만** 합계를 씁니다.
일부만 더한 값은 합계가 아닙니다. (예전 수동 선택 경로는 고른 한 항목의 값을 그대로 meal 단위
extras 에 넣었습니다 — 그건 애초에 틀린 값이었습니다.)

## 3. 폐기한 대안

| 대안 | 왜 안 했는가 |
| --- | --- |
| **B. 라벨만 달고 유지** (`표기값 찾기` 텍스트 버튼) | 최소 변경이지만 항목마다 버튼이 하나씩 늘어나는 문제가 그대로 남는다. 홈 화면 칩 축소와 반대 방향 |
| **C. 완전 제거** | 가장 단순하지만, 바코드가 안 찍히는 포장식품(지워진 라벨)은 AI 추정만 남는다. 무료·실측 경로를 버릴 이유가 없다 |
| `ErrorCode` 에 검색용 메시지 분리 | 검색 경로가 더 이상 사용자에게 에러를 보여주지 않으므로 불필요해졌다. 바코드 경로의 문구는 그 자리에서 맞다 |
| 근사(부분) 이름 매칭 | 자동 적용이라 오탐이 조용히 저장된다. 사용자가 고를 UI 를 없앤 대가로 정확도 기준을 올렸다 |

## 4. 남은 일

| 항목 | 확인 방법 |
| --- | --- |
| `FOOD_DB_API_KEY` 가 Railway 에 있는가 | Railway 변수 확인. 없으면 이 경로는 영구 no-op(식품안전나라 무료 가입 후 즉시 발급) |
| I2790 실제 응답 필드 | 키를 붙인 뒤 `FoodDbClient`의 `log.debug` 원본 응답으로 `mapRow` 대조. **매핑이 틀리면 엉뚱한 숫자가 "표기값"이라는 이름으로 들어간다** — 우선순위 높음 |
| 데이터셋에 집밥이 있는가 | 같은 조회로 "공기밥"·"김치찌개" 확인. 없다면 이 경로의 적용 범위는 포장식품뿐이라고 확정하면 된다 |
| 사진이 있는 기록의 빈 칼로리 | `칼로리 계산` 버튼은 `!photoUri` 일 때만 뜬다. 사진 분석이 이름만 주고 칼로리를 못 준 항목은 직접 입력 외 경로가 없다(기존과 동일, 이번에 만든 문제는 아니다) |
| 캐시 | 같은 이름을 반복 조회한다. 공공 API 호출량이 보이면 `@Cacheable` 검토 |

검증 상태: `npm run typecheck` 통과, `expo lint` 오류 수 변화 없음(기존 4건).
**실기기 확인은 못 했습니다** — 키 설정 여부를 모르는 상태라, 실제로 표기값이 채워지는 화면은
미검증입니다.

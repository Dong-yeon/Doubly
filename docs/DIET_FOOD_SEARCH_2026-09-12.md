# 식단 음식 검색 — 돋보기 제거와 "칼로리 계산" 통합 (2026-09-12)

"식단쪽의 돋보기 검색이 기능이 애매하다"에서 시작한 진단과 결정입니다.
코드 변경은 `ec72fa6` 한 커밋(`DietRecordScreen.tsx`)이고, 백엔드는 손대지 않았습니다.

---

## 0. 결론 먼저

- 돋보기는 **검색이 아니라 "이미 적은 이름의 표기값 채우기"** 였습니다. 아이콘이 기능을
  잘못 말하고 있었고, 대상 데이터셋이 가공식품이라 집밥 이름은 거의 못 맞혔습니다.
- **제거하고 같은 조회를 `칼로리 계산` 버튼 앞단으로 옮겼습니다.** 표기값을 먼저 찾고,
  못 찾은 것만 AI 가 추정합니다. 전부 찾으면 AI 를 아예 호출하지 않습니다(쿼터·원가 0).
- **식품 DB 조회는 동작하지 않습니다 — 바코드 스캔까지 포함해서.** 확인 과정에서 드러났습니다(§1-2).
  서비스 ID `I2790` 이 없어졌고(`ERROR-310`), 운영 키는 애초에 이 API 용 키가 아닙니다.
  이번 변경(돋보기 → AI 앞단 흡수)은 **그래도 안전합니다** — 조회 실패는 조용히 AI 로 이어지므로
  사용자에게는 고장으로 보이지 않습니다. 예전 돋보기 버튼은 같은 실패를 사용자 얼굴에
  던졌습니다("바코드 조회 기능이 아직 준비되지 않았어요").

## 1. 왜 애매했는가 (제거 전 상태)

| # | 문제 | 근거 |
| --- | --- | --- |
| 1 | 이 화면에서 **유일하게 라벨 없는 버튼**이었다 | `바코드로 찾기`·`AI로 칼로리 계산`·`＋ 음식 추가`는 전부 글자를 달고 있었다. 설명은 `accessibilityLabel` 뿐 — 스크린리더에만 읽힌다 |
| 2 | 이름을 **먼저 정확히 타이핑해야** 동작했다 | `onSearchDb`: 이름이 비면 "음식 이름을 먼저 적어주세요". 탐색이 아니라 채우기 |
| 3 | 대상 데이터가 **집밥이 아니다** | `FoodDbClient`가 `DESC_KOR=`로 부르는 I2790 은 `BAR_CD` 필드를 가진 가공식품 표기값 데이터셋. placeholder 가 유도하는 "공기밥"은 안 맞는다 |
| 4 | 키가 없으면 **바코드 문구로 실패** | `FOOD_DB_API_KEY` 기본값이 빈 문자열(`application.yml:157`) → `search`도 `FOOD_DB_NOT_CONFIGURED` → "바코드 조회 기능이 아직 준비되지 않았어요."(`ErrorCode:120`) |
| 5 | 채우는 값이 **검증되지 않았다** | `FoodDbClient` 클래스 주석이 스스로 밝힘 — `NUTR_CONT1~8`·`BAR_CD` 필드명은 추정치. 그런데 `pickDbResult`는 "실제 표기값으로 채웠어요"라고 확신했다 |
| 6 | AI 계산과 **역할이 겹치는데 배치가 반대** | 둘 다 `이름 → 영양값`. AI 는 항상 답하지만 유료·추정치이고 화면 맨 아래 1개, DB 는 무료·실측이지만 거의 못 맞히면서 항목마다 붙어 있었다 |

부수적으로 `FoodDbClient.isConfigured()`는 프로덕션 코드에서 아무도 호출하지 않습니다
(테스트만 씀). 즉 프론트가 "키 없음"을 미리 알고 버튼을 숨길 방법이 없었습니다.

## 1-2. 식품 DB 는 처음부터 죽어 있었다 (9/12 확인)

키가 설정돼 있다는 답을 받고 매핑을 대조하려다 드러났습니다. **문제가 두 개입니다.**

| # | 문제 | 증거 | 실패 모드 |
| --- | --- | --- | --- |
| 1 | **서비스 ID `I2790` 이 없다** | 아무 키(`TESTKEY123`)로 불러도 JSON `ERROR-310`("해당하는 서비스를 찾을 수 없습니다"). 인증 실패는 `INFO-100` 이므로 키와 무관한 판정 | HTTP 200 + `RESULT.CODE` |
| 2 | **운영 키가 경로에 못 들어가는 모양** | 실제 키는 `/`·`+`·`==` 를 품은 base64 64바이트 — 공공데이터포털(data.go.kr) 서비스키 형태. 식품안전나라는 키를 **경로 세그먼트**에 넣으므로 원본은 경로가 쪼개지고 `%2F` 는 Apache 가 `AllowEncodedSlashes Off` 로 거부 | Apache HTML 404 (앱에 닿지도 못함) |

두 실패 모드가 다른 게 서로의 증거입니다 — 1번은 앱이 응답을 주고, 2번은 웹서버가 먼저 끊습니다.

### 왜 여태 몰랐나

`fetchRows` 가 `RESULT.CODE` 를 읽지 않고 `row` 만 꺼냈습니다. 이 API 는 **오류도 HTTP 200** 으로
주므로, "서비스 없음"·"인증키 무효"가 전부 **데이터 없음**으로 번역됐습니다. 사용자에게는
*"등록되지 않은 바코드예요. 직접 입력해주세요."* 로 보이고, 로그에는 아무것도 남지 않았습니다.

### 이번에 넣은 것 (엔드포인트와 무관하게 유효)

- `extractRows` — `RESULT.CODE` 를 먼저 본다. `INFO-000`(정상)·`INFO-200`(데이터 없음)만 통과시키고,
  나머지는 코드·메시지와 **키를 가린 요청 URL** 을 WARN 으로 남기고 `FOOD_DB_LOOKUP_FAILED`.
- `warnIfKeyShapeUnusable` — 부팅 시 키 모양을 검사해 WARN. 2번이 조용히 반복되지 않게.
- `isConfigured()` 가 키 모양까지 본다 — 경로에 못 넣는 키는 **없는 것과 같게** 다뤄, 확정 실패할
  HTTP 를 매 조회마다 보내지 않는다. 키를 제대로 교체하면 코드 변경 없이 살아난다.
- `warnIfUnmapped` — 필드 매핑이 어긋나면 실제 응답 키를 WARN 으로 한 번(`log.debug` 는 운영에서 안 보임).

### 해결 — 공공데이터포털로 이전 (같은 날 완료)

운영 키가 data.go.kr 키 모양이라는 단서가 맞았습니다. 포털 화면에서 확인된 사실:

```
End Point : https://apis.data.go.kr/1471000/FoodNtrCpntDbInfo02
상세기능   : getFoodNtrCpntDbInq02
인증       : serviceKey 쿼리 파라미터  ← 경로가 아니라 쿼리라서 %2F 문제가 사라진다
전체 건수  : 319,060
```

응답 봉투는 포털 표준이지만 `type=json` 이라 `response` 래퍼 없이 최상위 `header`/`body` 입니다.

```json
{"header":{"resultCode":"00","resultMsg":"NORMAL SERVICE."},
 "body":{"pageNo":1,"totalCount":319060,"numOfRows":1,"items":[{...}]}}
```

**영양소 매핑은 두 가지로 교차 확인했습니다** — 실제 응답의 질량 합계가 100g 으로 닫히고
(`수분 71.60 + 단백질 6.70 + 지방 5.16 + 회분 0.63 + 탄수화물 15.94 = 100.03`), 참고문서
`출력메세지_식품영양성분DB정보.xlsx`(출력 항목 193개)의 이름과 일치합니다.

| 우리 DTO | 필드 | 이름 |
| --- | --- | --- |
| calories | `AMT_NUM1` | 에너지(kcal) |
| carbs | `AMT_NUM6` | 탄수화물(g) |
| protein | `AMT_NUM3` | 단백질(g) |
| fat | `AMT_NUM4` | 지방(g) |
| sugar | `AMT_NUM7` | 당류(g) |
| sodium | `AMT_NUM13` | 나트륨(mg) |
| fiber | `AMT_NUM8` | 식이섬유(g) |
| servingSize | `SERVING_SIZE` | 영양성분함량기준량 |
| foodName | `FOOD_NM_KR` | 식품명 |

**옛 `NUTR_CONT` 순서와 다릅니다** — 거기선 `2=탄수화물, 3=단백질` 이었지만 여기는
`3=단백질, 6=탄수화물` 입니다. 그대로 옮기면 탄단이 뒤바뀝니다(테스트로 못박아 뒀습니다).

구현에서 흡수한 응답 특성:
- 값 없는 항목은 `null` 이 아니라 **빈 문자열** — 0 으로 읽으면 안 됩니다.
- 큰 값에 **천 단위 쉼표**가 붙습니다(`"1,670.000"`).
- 인증키는 포털이 Encoding/Decoding 두 형태를 주므로, 모양을 보고 재인코딩 여부를 가릅니다
  (Encoding 키를 다시 인코딩하면 `%2F` → `%252F`, Decoding 키를 그냥 넣으면 `+` 가 공백).
- URL 은 `URI.create` 로 넘깁니다 — `uri(String)` 은 이미 인코딩된 키를 한 번 더 인코딩합니다.

### 정정 — 이 데이터셋은 가공식품 전용이 아니다

§1 표의 3번("대상 데이터가 집밥이 아니다")은 **옛 데이터셋 기준이었고 새 DB 에는 해당하지
않습니다.** 실제 응답 첫 행이 `DB_GRP_NM=음식`, `FOOD_CAT1_NM=밥류`,
`FOOD_OR_NM=가정식(분석 함량)` 입니다. 가정식·외식까지 들어 있어 이 경로의 가치가 처음 판단보다
큽니다.

### 바코드는 지원하지 않는다

새 데이터셋에 **바코드 필드가 없습니다**(옛 `I2790` 에는 `BAR_CD` 가 있었습니다). 대신
`ITEM_REPORT_NO`(품목제조보고번호)·`MAKER_NM`(업체명)이 있습니다. 그래서 `lookup(barcode)` 는
`FOOD_DB_NOT_CONFIGURED` 를 던집니다 — "준비되지 않았다"고 **정확히** 말합니다. 조회 실패를
"등록되지 않은 바코드예요"로 번역하던 예전 동작으로 되돌아가지 않도록 테스트로 고정했습니다.

살리려면 2단 구조가 필요합니다: `바코드 → I2570(유통바코드) → 제품명 → 이름 검색`. 다만
바코드연계제품정보는 **2018년 이후 갱신이 중단**됐고(유통물류진흥원 요청), 인증키 체계도 달라서
(식품안전나라 영숫자 키) 별도 판단이 필요합니다. 기능을 접는 것도 선택지입니다.

### 남은 갈림길 — 이름 매칭 규칙

식품명이 `김밥_야채` 처럼 **분류 접두어 + 언더바** 규칙입니다. 현재 프론트 정책은 **완전 일치만
자동 적용**이라 "김밥"으로는 맞지 않습니다. 아직 확인하지 않은 것은 `FOOD_NM_KR` 이 부분일치인지
완전일치인지이고, 그 답에 따라 갈립니다.

- **부분일치라면** — 후보 중 `DB_CLASS_NM=품목대표` 행을 고르는 규칙이 자연스럽습니다. 그 구분이
  "이 음식의 대표값"을 뜻하므로, 사용자가 고르는 UI(방금 없앤 돋보기) 없이도 자동 적용이 됩니다.
- **완전일치라면** — 이름 검색의 적용 범위가 매우 좁아집니다. AI 추정 경로만 사실상 남습니다.

### 기준량 주의

`SERVING_SIZE` 는 1회 제공량이 아니라 **영양성분함량기준량**(보통 `100g`)입니다. 코드가 `portion`
을 이 값으로 함께 채우므로 화면에는 "100g · 137kcal"로 정직하게 표시되지만, 사용자가 적은 1인분과
다를 수 있습니다. 환산에 쓸 값은 `NUTRI_AMOUNT_SERVING`(1회 섭취참고량)·`DISH_ONE_SERVING`
(1회분량 참고량)·`Z10500`(식품중량)입니다 — 아직 쓰지 않았습니다.

## 1-1. 우리 DB 에는 음식 영양 데이터가 없다

혼동하기 쉬운 지점입니다. 마이그레이션의 food 관련 테이블은 전부 **사용자가 만든 데이터**입니다 —
`favorite_foods`(V12), `favorite_food_items`(V35), `favorite_food_gifts`(V51), `meal_items`(V39).
**영양성분 마스터 테이블은 없습니다.** 돋보기/바코드는 매번 외부 API(`openapi.foodsafetykorea.go.kr`)를
실시간으로 부르고, `FoodDbClient`에 캐시(`@Cacheable`)도 없습니다.

그래서 "DB 에 데이터가 있나?"는 **우리 DB 질문이 아니라 ① 키가 설정돼 있나 ② 그 공공 데이터셋이
그 이름을 갖고 있나** 두 질문입니다. ①은 **있습니다**(9/12 확인). ②는 이 세션의 네트워크 정책이
해당 호스트를 막아(403 `Host not in allowlist`) 직접 조회하지 못했습니다 — 로컬에서 아래 한 줄로
확인할 수 있습니다.

```bash
curl -s "http://openapi.foodsafetykorea.go.kr/api/<키>/I2790/json/1/3/DESC_KOR=신라면" | head -c 2000
```

응답의 `row[0]` 키 이름이 `DESC_KOR`·`SERVING_SIZE`·`NUTR_CONT1~8`·`BAR_CD` 와 같은지가
확인 포인트입니다. 다르면 `FoodDbClient.map` 만 고치면 됩니다.

## 2. 바뀐 동작 (`fillCalories`)

1. 칼로리가 빈 항목의 이름으로 공공 DB 를 조회합니다. **이름 완전 일치만** 받습니다 —
   예전엔 사용자가 후보를 직접 골랐지만 지금은 자동이라, 근사 매칭은 엉뚱한 값을 조용히 넣습니다.
   이름 개수는 `MAX_FOOD_DB_LOOKUPS = 4`로 제한합니다(배치 엔드포인트가 없어 이름마다 1회 호출).
2. **전부 채워지면 AI 를 호출하지 않습니다.** 이게 유일한 실제 원가 절감 지점입니다
   (쿼터는 호출 단위라 부분 성공에는 절감이 없습니다).
3. 남으면 AI 를 부르고, **그 뒤에** 같은 이름을 표기값으로 덮습니다(실측 > 추정).
   AI 앞에서 `setItems` 하지 않는 이유: `analyzeItemsWithAi`가 "보낼 때의 목록"과 대조하는데,
   DB 가 `portion`을 채우면 그 대조가 어긋나 "음식이 바뀌어서 결과를 넣지 않았어요"가 뜹니다.
4. **조회 결과가 없으면 기존대로 AI 로 갑니다.** 값이 이미 다 차 있어도 버튼을 누르면 다시
   계산해주던 동작을 남겨야 합니다(구현 중 한 번 깨뜨렸다가 되돌린 지점).
5. 실패·키 미설정은 **조용히** 넘어갑니다 — 4번 문제(검색 버튼에서 바코드 문구)가 여기서 사라집니다.

버튼 문구도 `AI로 칼로리 계산` → **`칼로리 계산`**. 안내는 "표기값이 있는 음식은 그 값으로,
없으면 AI가 추정해요."로 바꿨습니다. AI 가 항상 도는 게 아니게 됐으니 이름이 약속을 어깁니다.

추가 영양소(당·나트륨·식이섬유)는 **모든 항목이 표기값으로 채워졌을 때만** 합계를 씁니다.
일부만 더한 값은 합계가 아닙니다. (예전 수동 선택 경로는 고른 한 항목의 값을 그대로 meal 단위
extras 에 넣었습니다 — 그건 애초에 틀린 값이었습니다.)

| **C. 완전 제거** | 가장 단순하지만, 바코드가 안 찍히는 포장식품(지워진 라벨)은 AI 추정만 남는다. 무료·실측 경로를 버릴 이유가 없다 |
| `ErrorCode` 에 검색용 메시지 분리 | 검색 경로가 더 이상 사용자에게 에러를 보여주지 않으므로 불필요해졌다. 바코드 경로의 문구는 그 자리에서 맞다 |
| 근사(부분) 이름 매칭 | 자동 적용이라 오탐이 조용히 저장된다. 사용자가 고를 UI 를 없앤 대가로 정확도 기준을 올렸다 |

## 0-1. 축이 나란한 게 아니라 곱이다

위 표가 사다리처럼 읽히지만 실제 구조는 **축 둘의 곱**이다.

| 축 | 값 | 판정 주체 |
| --- | --- | --- |
| **등급** | `FREE` / `PRO` — 둘 중 하나 | `Plan` enum · `PlanResolver` |
| **소유권** | 스티커 팩 0개 이상 — 사면 영구 | `user_sticker_purchases` |

광고는 축이 아니라 **등급의 부산물**이다 — FREE 면 뜨고 PRO 면 안 뜬다.

사용자가 실제로 놓이는 상태:

| | 팩 0개 | 팩 N개 |
| --- | --- | --- |
| **FREE** | 광고 O · 한도 O · 무료 팩만 | 광고 O · 한도 O · **산 팩 추가** |
| **PRO** | 광고 X · 한도 해제 · 기능 19개 · **유료 팩 전부** | 위와 같음(산 팩이 흡수됨) |

### PRO 가 상점을 포함한다

`StickerService.requireUsable` 의 판정 순서가 그렇게 짜여 있다.

```java
if (pack.isFreeForEveryone())            return;   // 무료 팩
if (ownedPackIds(userId).contains(packId)) return;  // 낱개 구매
planGuard.require(userId, pack.getCategory().feature());  // ← 구독으로 연다
```

즉 **낱개 구매는 "PRO 를 안 살 사람"용 상품**이다. 의도한 구조이지만 대가가 있다 —
1,200원 팩 **4개면 PRO 한 달치**라, 상점이 잘 팔릴수록 구독 전환이 줄어든다.
팩 가격과 개수를 늘릴 때 이 교환비를 봐야 한다.

### 소유권을 `Plan` 에 넣지 않는다

`Plan.java` 주석이 "중간 등급(예: PLUS)이 생겨도 호출부가 안 깨진다"며 `isAtLeast`/`max`
를 쓰라고 해뒀지만, **산 팩은 등급이 아니다.** `ordinal()` 이 곧 등급인 구조에 소유권을
끼우면 PRO 구독자가 무언가를 사는 순간 등급이 내려간다. 위 코드처럼 **소유권을 먼저 보고
마지막 갈래만 `PlanGuard` 에 위임**하는 것이 맞는 모양이다.

마지막을 `PlanGuard` 에 넘기는 이유는 402 문구, `PLAN_UPGRADE_REQUIRED` vs
`USAGE_LIMIT_EXCEEDED` 구분, `FEATURE_USED`/`FEATURE_BLOCKED` 계측이 전부 거기 있기
때문이다. 직접 던지면 그 경로에서만 지표가 조용히 사라진다.

## 1. 경계 규칙 — 원가가 가른다

축이 여럿이면 같은 기능을 두 축이 탐내게 된다. 기준은 하나다.

> **변동원가가 매달 나가는 것은 구독으로만 판다. 1회 결제(상점)에는 원가 0 인 것만 넣는다.**

**1회 결제는 매출이 한 번인데 원가는 매달 나간다.** 원가 있는 기능을 영구 소유로 팔면
사용자가 쓰면 쓸수록 적자인 상품이 된다. 비트윈 모델을 그대로 못 가져오는 지점이 정확히
여기다 — 비트윈은 스티커·테마 판매 + 광고 제거가 주 수익이고 **변동원가가 있는 구독
상품이 없다.**

원가 0 이라고 전부 1회 결제로 보내도 안 된다.

> **원가가 0 이어도 PRO 의 대표 기능은 구독에 남긴다.**

**대표 기능은 이제 코드가 정한다** — `Feature.isHero()` 가 셋을 고른다.

```java
case AI_COUPLE_EMOJI, AI_FOOD_PHOTO, WORKOUT_V2_STATS -> true;
```

`PlanCatalogEntry.hero` 로 앱에 내려가고 비교표 맨 위로 올라간다. 9/17 §6 이 제안했던
넷(영상통화 · 우리 이모지 · 추억 리마인드 · 전체 기간 통계)과 **셋이 다르다** — 그 문서는
제안이었고 이쪽이 구현이다. 규칙을 적용할 때는 `isHero()` 를 본다.

대표가 아니어도 `MEMORIES`·`FULL_STATS`·`ANNIVERSARY_RECAP` 처럼 원가 0 인 깊이형은
구독에 남는다. **"리소스를 적게 먹는다"와 "가치가 낮다"는 다른 축이다.**

광고에만 걸리는 규칙이 하나 더 있다.

> **광고로 푸는 것은 PRO 의 대체재가 아니라 FREE 한도의 완충재다.**

`Quota.blocked()` 전부를 리워드 광고로 풀면 PRO 를 결제할 이유가 사라진다(9/17 §4).
광고로 풀 수 있는 것은 **한계비용이 0 에 가까운 한도형**뿐이다.

## 3. 충돌 — "기본 제공 외에는 구매" vs 오늘의 무료화

같은 날 두 결정이 반대 방향으로 났다.

| | 내용 |
| --- | --- |
| **지시** | "기본 제공 이모티콘 외에는 스티커 상점에서 구매해서 쓰도록" |
| **구현** | 움직이는 이모티콘 **110종 8팩 전부 무료**. 예전엔 30종 중 24종이 `premium` 이었다 |

그 무료화는 **테스트로 못 박혀 있다.**

```
AnimatedStickerTest.everyStickerIsInAFreePack
PremiumContentGateTest.움직이는_이모티콘은_전부_무료다
StickerPackSyncTest.누가_무엇을_쓸_수_있는지는_그대로다   ← "무료로 준 게 다시 잠기는 것"을 막는다
```

의도적으로 세운 방어선이라, 유료 범위를 넓히려면 **이 셋을 먼저 지워야 한다.**

### 판정 — 무료화를 유지한다

1. **Noto Animated Emoji 는 어디서나 공짜로 구할 수 있다.** CC BY 4.0 이라 파는 것 자체는
   합법이지만, 무료로 구할 수 있는 그림에 값을 붙이면 상품성이 없다.
2. **이미 무료로 연 것을 다시 잠그는 것은 기능 회수다.** 반발이 가장 큰 종류이고,
   `PLAN_FREE_TRIAL=false` 전환(모두가 한꺼번에 벽에 부딪히는 시점)과 겹치면 더 나쁘다.
3. **팔 것이 유니코드에 없는 것으로 모인다.** 2026-09-14 에 `StickerPack` enum 을 지운
   근거("폰 키보드에 이미 있는 글자를 파는 모양")와 같은 잣대다.

**그래서 "기본 제공"의 정의를 이렇게 고정한다.**

> **기본 제공 = 유니코드에 이미 있는 것**(움직이는 이모티콘 110종 · 기본 무드 · 기본 터치).
> **파는 것 = 유니코드에 없는 것**(자체 캐릭터 스티커 · 우리 이모지 · 확장 무드 · 프리미엄 터치).

지시의 의도("기본 제공 외에는 판다")는 이 정의로 **그대로 성립한다.** 다른 것은 "기본
제공"의 범위뿐이다.

## 5. 폐기 — 광고 제거 영구권 (2026-09-22)

초판은 **광고 제거 영구권**을 네 번째 축으로 뒀다. **뺐다.**

검토 과정에서 나온 것들은 남긴다. 되살릴 일이 생기면 여기서부터 다시 읽으면 된다.

### 왜 넣으려 했나

PRO 와 별개로 "구독은 부담스럽지만 광고는 싫은 사람"을 받는 1회 결제 상품이다.
비트윈이 실제로 서 있는 자리다.

### 왜 뺐나

**PRO 가 광고를 제거하기로 정해지면서 영구권이 PRO 의 부분집합이 됐다.** 그러면 상품이
둘로 갈리는 게 아니라 하나가 다른 하나에 먹힌다 — 영구권을 산 사람이 나중에 PRO 를 사면
영구권 값이 죽고, 그건 환불 민원이 나오는 전형적인 자리다.

그리고 §4 에서 확인했듯 **영구권에 안전하게 넣을 수 있는 기능이 `CUSTOM_BACKGROUND`
하나뿐이었다.** 꾸미기 3종 중 둘은 이미 상점으로 갔고, 원가 있는 것은 §1 규칙에 걸리고,
원가 0 인 깊이형은 PRO 대표 기능이라 뺄 수 없다. **상품이 될 만큼의 내용물이 없었다.**

### 검토하고 뺀 반대안 — "PRO 에도 광고를 띄운다"

영구권을 살리려면 PRO 가 광고를 제거하지 않으면 된다. 그러면 두 상품이 완전히 갈리고
PRO 구독자까지 영구권을 사므로 매출 축이 둘 다 산다. **논리적으로는 일관적이다.**

**그런데 이 저장소가 이미 반대 원칙을 적어뒀다.** `PlanGuard` 클래스 주석이다.

> **유료인데 한도 초과** → `USAGE_LIMIT_EXCEEDED` — 이건 업셀이 아니라 단순 남용 방지다.
> **돈 낸 사람에게 결제를 또 권하면 안 된다**

402 와 429 를 굳이 둘로 나눈 이유가 이것이고 `CLAUDE.md` §7 에도 올라가 있다. **광고는
본질적으로 "또 권하는" 것**이고, 리워드 광고면 "돈 내고 또 광고 보기"가 된다. 그 밖에도
셋이 걸렸다.

| | |
| --- | --- |
| 가격 근거 | 4,900원은 원가 하한선을 **겨우 통과하는** 값이다(9/17 §8). 광고가 붙으면 그 가격을 못 받는다 |
| 스토어 반응 | 월 4,900원 내는 커플 앱에 광고가 뜨면 첫 리뷰가 "돈 냈는데 왜"다. 되돌리기 어렵다 |
| 동의 흐름 | AdMob 은 UMP(EU 동의)·ATT(iOS 추적)가 붙는다. PRO 도 대상이면 결제한 사람에게까지 그 화면을 태운다 |

### 남는 것

`user_sticker_purchases`(V96)의 **영구 소유 패턴**은 그대로 쓸모가 있다. 나중에 1회 결제
상품이 다시 필요해지면 이 답들이 이미 나와 있다.

| 논점 | V96 의 답 |
| --- | --- |
| 개인 소유냐 커플 소유냐 | **소유는 개인, 사용은 커플** |
| 복원·재설치 | `(user_id, pack_id)` unique 인덱스로 멱등 |
| 탈퇴 | `UserDataPurger` 가 **거둔다**(FK 가 없어 빠뜨리면 조용히 남는다) |
| 이별 | `RelationRecordPurger` 는 **일부러 안 거둔다** — "관계가 끝났다고 회수하면 환불 없는 몰수" |
| 스토어 상품 id | 컬럼이 아니라 규칙 — `sticker_pack_` + id 소문자 |

## 6. 광고 — FREE 에게만

**PRO 가 되면 광고가 사라진다.** 근거는 §5 의 `PlanGuard` 원칙이다.

선행 조건이 셋이다.

| 선행 조건 | 상태 |
| --- | --- |
| 볼 사람이 있을 것 | `PLAN_FREE_TRIAL=true` → **FREE 0명** |
| SDK 가 붙어 있을 것 | 코드 **0줄**. AdMob 은 `app.json` plugins 변경 → **EAS 빌드**(OTA 불가, `CLAUDE.md` §6) |
| 리워드면 SSV 서버 | 미착수 |

붙인다면 대상은 **한계비용이 0 에 가까운 한도형부터** — `VOICE_MESSAGE`(일 5),
`AI_FOOD_TEXT`(일 2). `AI_COUPLE_EMOJI` 는 **광고 수익 < 장당 원가($0.045)** 라 영구
제외다(9/17 §4).

> **광고 제거가 PRO 의 판매 문구가 된다.** 지금 `UpgradeSheet` 와 9/17 §6 의 플랜 화면
> 초안에는 이 항목이 없다 — 광고를 넣을 때 같이 넣어야 한다.

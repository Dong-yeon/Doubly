## 2. 캐릭터 채팅 테마 — 구현 방법

### 2-1. 얹을 자리: 사진 배경 레이어를 그대로 쓴다

지금 사진 배경은 `ChatRoomScreen.tsx:1943-1948` 에서 **SafeAreaView 의 `absoluteFill`, FlatList 바깥**에 깔린다(배경색 위 · 대화 아래, `pointerEvents="none"`). 이 자리가 캐릭터 그림에 그대로 맞는다.

- **스크롤 비용 0**: 목록 안이 아니라 고정 레이어라 스크롤·가상화와 무관하다. 그림을 `ListHeaderComponent` 나 행 배경에 넣는 안은 버린다(스크롤마다 같이 움직이고 inverted 목록에서 위치가 뒤집힌다).
- **실패해도 안전**: 그림이 안 뜨면 테마 `background` 가 보인다 — 사진 배경이 이미 이 성질에 기대고 있다(`withPhoto` 가 background 를 안 건드리는 이유).

**사진과의 우선순위**: 사진 > 캐릭터 그림 > 단색. 사진은 사용자가 직접 고른 것이고, 지금도 "테마 + 사진" 조합으로 저장된다(`chatThemeStore` 의 두 키). 캐릭터 테마를 골라도 사진이 있으면 사진이 덮고, 사진을 지우면 캐릭터 그림이 돌아온다 — 기존 동작과 같은 규칙이라 설명이 필요 없다.

### 2-2. 데이터 구조

```ts
// chatTheme.ts — CHAT_THEMES 배열 바깥에 둔다
export interface ChatThemeArt {
  /** 단색 실루엣 타일(알파만 의미). require() 로 번들 */
  tile: ImageSourcePropType;
  /** 타일을 칠할 색 — 스킴별. 대비 검증 대상 */
  pattern: { light: string; dark: string };
  /** 타일 한 칸의 화면 크기(dp) */
  tileSize: number;
  premium: boolean;
}
export const CHAT_THEME_ART: Partial<Record<ChatThemeId, ChatThemeArt>> = { … };
```

**배열 안에 `art:` 필드로 넣지 않는다.** `verify-chat-theme-contrast.mjs` 의 정규식이 `id → label → light → dark → },\s*},` 를 한 덩어리로 읽는데, `dark` 뒤에 블록이 하나 더 오면 dark 본문이 art 까지 늘어나 `pattern` 의 hex 를 팔레트 키로 오인한다. 별도 맵이면 기존 스크립트가 그대로 돌고, 새 규칙만 맵을 따로 읽으면 된다.

캐릭터 테마 자체(말풍선·meta·입력바 등 12토큰)는 **기존 10종과 똑같이 `CHAT_THEMES` 에 한 줄 더**다. 그림은 그 위에 얹는 장식일 뿐이고, 그림이 없어도 테마로 완결돼야 한다.

### 2-3. 배치 안 비교

| 기준 | **A. 타일 패턴 (단색 실루엣 + tint)** | B. 구석 고정 일러스트(풀컬러) | C. 상단/하단 띠 |
| --- | --- | --- | --- |

**권고: A 를 기본으로 낸다.** 보장 가능한 대비 · 다크 공짜 · 비율 무관 · 작은 용량이 전부 A 에만 있다. B 는 체감이 가장 크지만 "입력 중엔 가려지는 아래 구석" 과 "캡슐 모드 강제"를 같이 산다 — 낸다면 **2단계로, 위 구석 한정 + 캡슐 모드** 로 사진 배경 경로(`withPhoto`)를 일반화해 재사용한다(`currentPhotoUri` 대신 "이미지 배경 있음" 플래그). C 는 기각.

**확인 필요(미검증)**: RN `Image` 의 `resizeMode="repeat"` 와 `tintColor` 를 **동시에** 줄 때의 동작 — iOS·Android 각각, 그리고 웹(react-native-web 은 repeat 를 CSS background-repeat 로, tintColor 를 필터로 그리는데 둘의 조합은 확인하지 않았다). 안 되면 대안은 테마×스킴별로 이미 칠한 타일 PNG 를 납품받는 것(용량 2배, 검증 방식은 같음). **사진 배경은 `react-native` 의 `Image` 를 쓰고, 시트의 견본은 `expo-image` 를 쓴다** — expo-image 에는 repeat 가 없으니 타일은 RN `Image` 로.

### 2-4. 대비 검증 — `verify:chat-theme` 에 얹는 법

**"대표 색 샘플링"(평균색)은 쓰지 않는다.** meta 글자는 아무 픽셀 위에나 놓이므로 평균이 통과해도 가장 진한(또는 밝은) 픽셀 위에서 묻힌다 — 판정은 **최악값**이어야 한다.

A안이면 최악값이 계산된다: 화면의 모든 픽셀은 `background` 이거나 `pattern`(가장자리 안티앨리어싱은 그 둘의 혼합이라 둘 사이에 있다). 그래서 **배경 기준 규칙을 `pattern` 에 대해 한 번 더** 재면 된다.

| 규칙 | 대상 쌍 | 기준 |
| --- | --- | --- |
| 패턴 위 시간·날짜 | `pattern` × `meta` | ≥ 4.5 |
| 상대 말풍선 vs 패턴 | `pattern` × `bubbleTheirs` | ≥ 1.10 |
| 내 말풍선 vs 패턴 | `pattern` × `bubbleMine` | ≥ 1.20 |
| 안 읽음 하트 vs 패턴 | `pattern` × `readMark` | ≥ 3 |
| 패턴 vs 배경(보이기는 하나) | `pattern` × `background` | **1.08 ~ 1.35** — 하한은 "그림이 있다", 상한은 위 규칙들을 지키려면 어차피 걸리는 값. 상한을 따로 두는 이유는 위 4줄보다 먼저, 더 읽기 쉬운 이유로 실패하게 하려는 것 |

그리고 **타일의 알파가 이진인지**를 한 번 잰다(중간 알파 픽셀 비율이 가장자리 수준인지). 반투명 면이 있으면 그 자리 색이 `pattern` 과 `background` 사이 어딘가가 되어 위 계산은 여전히 맞지만, 디자이너가 의도한 "옅은 면"이 tint 로 사라진다 — 납품 사양(§2-5)으로 막는다. PNG 디코딩은 `node:zlib` 만으로 된다(사양이 8bit·비인터레이스로 고정되면 60줄 남짓).

**새 npm 스크립트를 만들지 말고 `verify-chat-theme-contrast.mjs` 안에 넣는다.** `package.json` 의 scripts 는 fingerprint 입력이라(10-01 메모리: 서버 스티커 팩 건) 스크립트 한 줄 추가가 JS 만 바뀐 배포를 빌드로 만든다. 같은 이유로 `pngjs`·`sharp` 같은 devDependency 도 넣지 않는다.

**빠짐 방지**: 채팅 테마 스크립트는 이미 "선언된 id 수 vs 읽은 수"를 대조한다. `CHAT_THEME_ART` 에도 같은 대조(맵의 키가 전부 `CHAT_THEMES` 에 있는가, 각 항목이 `pattern.light/dark` 를 갖는가)를 둔다.

B안(2단계)은 캡슐이 대비를 맡으므로 맨살 글자 규칙은 면제되고, 말풍선 경계(1.10)는 사진 배경과 같이 **보장하지 않는다** — 이건 지금 사진 배경이 이미 받아들인 조건이다.

### 2-5. 그림 작업자에게 넘길 사양 (A안)

**캐릭터 테마 1종당 납품물**

| 파일 | 내용 |
| --- | --- |
| `chat-tile-<캐릭터>.png` | @1x **256×256** |
| `chat-tile-<캐릭터>@2x.png` | **512×512** |
| `chat-tile-<캐릭터>@3x.png` | **768×768** |
| (원본) | 1024×1024 벡터 또는 PSD — 재출력용 |

**그림 규칙**

1. **한 가지 색(검정) 실루엣 + 투명 배경.** 색은 앱이 테마별로 입힌다. 명암·그라데이션·반투명 면을 쓰지 않는다(가장자리 안티앨리어싱만 허용). 선화는 "선 = 칠, 나머지 = 투명".
2. **이음새 없는 반복(seamless).** 칸 밖으로 넘어간 그림은 반대편에 이어지게. 한 칸에 모티프 **4~7개**, 크기·각도를 섞어 반복 격자가 눈에 띄지 않게.
3. **모티프 크기**: 화면에서 24~56dp(@1x 기준 24~56px). 이보다 작으면 노이즈, 크면 말풍선 뒤에서 형태가 잘린다.
4. **채움 면적 15~25%.** 그 이상이면 패턴이 "배경"이 아니라 "그림"이 되어 대비 상한(§2-4)을 넘긴다.
5. **선 굵기 ≥ 2px(@1x).** 그보다 가늘면 tint 후 사라진다.
6. **형식**: PNG-32(RGBA) 8bit, 비인터레이스, 색공간 sRGB. pngquant 등으로 압축해 파일당 **≤ 60 KB**.
7. 캐릭터의 **얼굴·실루엣이 한눈에 읽혀야** 한다(달걀이의 꽃, 구운이의 구운 자국처럼 윤곽에서 드러나는 특징을 살린다). 디테일은 내부 선이 아니라 윤곽으로.

**작업자가 정하지 않는 것**: 배경색·말풍선색·패턴색(개발 쪽이 캐릭터 대표색을 받아 12토큰 × 2스킴을 맞추고 검증 스크립트로 확정한다). 대신 **캐릭터별 대표색 2~3개**(hex)를 함께 넘겨 달라고 한다.

**개수**: 2~3종(달걀이·구운이 + 필요 시 더비/블리 중 하나). 설정 시트 견본은 실제 타일을 축소해 그리므로 별도 썸네일은 필요 없다.

**(2단계 B안을 할 때만)** 구석 일러스트: 풀컬러 PNG 투명 배경 **900×900(@3x, 화면 300dp)**, **라이트·다크 2벌**, 그림의 바깥 20%는 잘려도 되는 영역, 파일당 ≤ 250 KB. 위 오른쪽 구석에 붙는다는 것을 전제로 무게중심을 왼쪽 아래에.

### 2-6. 번들 vs 원격

**번들을 권한다.** 타일은 작고(1종 ≈ 100 KB 미만, 3밀도 합), 팔레트(12토큰)가 TS 에 있어야 검증 스크립트가 잴 수 있다. `require()` 한 일반 에셋은 fingerprint 입력이 아니므로(스티커 PNG 8 MB 가 이미 OTA 로 다닌다) EAS Update 로 배포된다.

원격(서버 스티커 팩처럼 `classpath:/sticker-assets/`)은 "빌드·업데이트 없이 테마 추가"가 장점이지만, 팔레트까지 서버로 옮겨야 하고 그러면 대비 검증이 백엔드 테스트로 이사 가야 한다. 테마가 수십 개가 되기 전까지는 값을 못 한다.

## 3. 캐릭터 테마 유료화 — 게이팅 최소 구성

전제: 기존 10종 + 사진 배경은 **영원히 무료**(09-21 "무료로 연 것은 되잠그지 않는다"). 캐릭터 테마만 유료.

### 3-1. 이미 있는 것

- **`Feature.CUSTOM_BACKGROUND`**("커플 배경 꾸미기", FREE blocked / PRO unlimited, DECORATION 그룹, 커플 단위) — 홈 배경 사진용이다(`RelationService.setCoupleBackground` 가 `require`, 프론트 `HomeScreen.tsx:518`). **채팅 사진 배경은 이 키를 안 지난다**(프론트 전용, 무료).
- 계측 전용 키의 선례: `COUPLE_GAME` 은 무료·PRO 모두 unlimited 이고 `require` 를 지나 `FEATURE_USED` 를 남기는 것이 목적이다.
- "설정 적용만 기록하는 가벼운 엔드포인트"는 **없다.** 가장 가까운 것이 `setCoupleBackground`(값이 있을 때만 require, 해제는 게이팅 안 함).
- 스티커 상점에는 상품 종류(kind) 축이 없다. `sticker_packs` 엔티티·DTO·`StickerPackCategory → Feature` 매핑이 전부 스티커 전용이다.

### 3-2. 세 선택지

| | (a) 새 Feature 키로 PRO 전용 | (b) 상점 상품 단위 | (c) PRO 포함 + 낱개 구매 |
| --- | --- | --- | --- |
| 백엔드 | `Feature.CHAT_THEME_PREMIUM`(blocked/unlimited) + `group()` switch(DECORATION, default 가 없어 빠뜨리면 컴파일 에러) + `isCoupleScoped()` + 엔드포인트 1개 | `sticker_packs` 에 비스티커 상품을 섞거나(카테고리 추가 → 카탈로그·미리보기·상점 화면이 스티커를 전제) 상품 테이블 신설 → Flyway·Purger | (a) + (b) |
| 스토어 | 없음(PRO 구독 그대로) | **테마 하나마다 양 스토어 상품 등록 + 애플 심사** | (b)와 같다 |
| 마이그레이션 | **0** | 1개 이상 | 1개 이상 |
| 동기화 | `PlanFeatureSyncTest` 가 `types/index.ts` `FeatureKey` 추가를 강제 | `StickerPackSyncTest.낱개로_파는_팩은_없다` 가 **일부러** 막고 있다 | 둘 다 |
| 정책 정합 | 09-22 결정 "앞으로 만드는 캐릭터 팩은 PRO 로 낸다"와 같은 자리 | 09-22 에 스티커에서 **접은 길**과 같은 비용(상품 수 ∝ 콘솔 작업·심사) | 같음 |

**권고: (a).** 근거는 09-22 문서가 이미 낸 계산 그대로다 — 유료 상품이 2~3개인 규모에서 낱개는 콘솔·심사 비용이 만드는 비용보다 크고, 캐시(지갑)는 결제 시스템 한 채다. 그 문서의 분기점("팩 10개쯤")은 스티커·테마를 **합쳐서** 세는 게 맞다 — 둘 다 "우리가 그린 것"이고, 그때 가면 같은 캐시로 판다.

`CUSTOM_BACKGROUND` 재사용은 기각: 키 하나·동기화 0 으로 가장 싸지만, 홈 배경과 채팅 테마가 같은 `FEATURE_USED` 로 섞여 "캐릭터 테마가 PRO 전환에 기여하나"를 잴 수 없다. 이 기능을 넣는 목적 중 하나가 그 측정이다.

### 3-3. 최소 구성 (a안)

1. **백엔드**: `Feature.CHAT_THEME_PREMIUM("캐릭터 채팅 테마", Quota.blocked(), Quota.unlimited())`, DECORATION, 커플 단위. 엔드포인트 `POST /api/v1/chat/theme` `{ themeId }` → 서버가 `PREMIUM_CHAT_THEMES` 에 있으면 `planGuard.require(userId, CHAT_THEME_PREMIUM)`, 아니면 통과. 저장은 하지 않는다(테마는 여전히 기기 로컬). 402 는 `api/client` 의 plan gate 핸들러가 `UpgradeSheet` 로 받으므로 프론트에 업셀 코드를 따로 안 쓴다.
   - 어떤 id 가 유료인지 서버가 알려면 목록이 백엔드에 있어야 한다 → 다른 동기화 대상들처럼 `chatTheme.ts` 의 `premium: true` 를 읽는 `ChatThemeSyncTest` 를 두고 `build.gradle` `frontendSyncSources` 에 경로를 추가한다(CLAUDE.md 7절). 이게 부담이면 **클라이언트가 유료 여부를 보내고 서버는 require 만** 하는 축소판도 된다 — 우회해서 얻는 것이 "남의 기기 로컬 배경"뿐이라 보안상 손해는 없고, 계측만 같은 값을 얻는다.
2. **프론트**: 시트에서 캐릭터 테마 견본에 `LockedCard` 와 같은 잠금 표시, 탭하면 위 호출 → 200 이면 `setTheme`. **표시 시점에도 판정**: 채팅방 진입 시 `usePlanStore.stateOf('CHAT_THEME_PREMIUM')` 가 막혀 있으면(PRO 만료) `default` 가 아니라 **같은 계열의 무료 단색 테마로** 떨어뜨린다 — 그 캐릭터 테마의 팔레트(그림 없는 버전)를 무료로 남겨 두면 만료 때 화면이 덜 깨진다.
3. **배포 순서**: 서버 먼저(엔드포인트가 없으면 402 가 아니라 404 → 프론트가 막혀야 한다). 프론트는 EAS Update.

### 3-4. 프론트 전용 게이팅이면

`usePlanStore((s) => s.plan === 'PRO')` 만으로 잠그면 백엔드·마이그레이션·동기화가 0 이다. 잃는 것:

- **`FEATURE_USED`/`FEATURE_BLOCKED` 에서 사라진다**(CLAUDE.md 7절). 그러면 "캐릭터 테마가 결제를 끌어오나"를 잴 방법이 없다 — `COUPLE_GAME` 을 계측 전용 키로 만든 바로 그 이유다.
  - 부분 보완: 클라이언트 분석 이벤트(`ClientAnalyticsEvent` — 새 이벤트는 백엔드 enum 추가 필수)로 "잠긴 테마 탭"·"적용"을 남길 수 있다. 하지만 PlanGuard 지표와 다른 표에 쌓여 퍼널을 한 줄로 못 본다.
- **커플 단위 판정이 어긋난다.** 서버는 상대가 PRO 면 나도 PRO 혜택을 주는데(`isCoupleScoped`), 프론트의 `plan === 'PRO'` 는 그걸 반영하는지 화면마다 다르다. `stateOf(feature)` 를 쓰려면 결국 Feature 키가 있어야 한다.
- 우회 가능성(로컬 저장값 조작)은 원가가 0 이라 문제 삼지 않는다.

**결론**: 프론트 전용은 "일단 내보고 지표는 포기"일 때만. (a)의 백엔드 몫이 enum 한 줄 + 엔드포인트 하나라 그 차이를 아낄 이유가 작다.

## 4. 앱 아이콘 변경

### 4-1. 현재 상태

- 대체 아이콘 플러그인·API·후보 PNG 모두 **없다**. `app.json` `icon`(1024²)·`adaptiveIcon`(432² 전경·배경·모노크롬, 배경색 `#FAF5E8`)만 있고 `ios.icon` 별도 지정 없음. 커스텀 config plugin 폴더도 없다.
- CNG 프로젝트(`/android`·`/ios` gitignore). 따라서 네이티브 변경은 전부 config plugin 경유.
- 아이콘은 fingerprint 입력(`fingerprint.config.js` 가 아이콘을 빼지 않는다) → **빌드 사안.** 1차 판단 그대로.

### 4-2. 방법

**`expo-alternate-app-icons`(pchalupa)** — Expo SDK 51+, iOS 10.3+, Android API 21+. `app.json` plugins 에 `{ name, ios: {light, dark, tinted} | path, android: { foregroundImage, backgroundColor } }` 배열을 적고, JS 에서 `setAlternateAppIcon(name | null)`.

- **iOS**: `UIApplication.setAlternateIconName`. 바꿀 때 **시스템 알림이 반드시 뜬다**(앱이 막을 수 없다). 너무 자주 부르면 에러. iOS 18 의 라이트/다크/틴트 변형을 각각 줄 수 있다.
- **Android**: 아이콘마다 activity-alias 를 만들고 `setComponentEnabledSetting(..., DONT_KILL_APP)` 로 하나만 켠다. 런처에 즉시 반영된다고 문서는 말하지만 **런처마다 다르다**(아래).

### 4-3. activity-alias 가 건드리는 곳 — 코드로 확인

| 자리 | 열기 방식 | 영향 |
| --- | --- | --- |
| 홈 위젯 클릭(`DoublyWidget.tsx:29` `OPEN_APP`) | 라이브러리 `RNWidgetProvider.openApp()` 이 `getLaunchIntentForPackage` | **안전** — 켜진 alias 를 따라간다 |
| 알림 탭(expo-notifications `ExpoHandlingDelegate`·`NotificationForwarderActivity`) | `getLaunchIntentForPackage` | **안전**. 단 런처 엔트리가 **하나도** 없으면 알림을 눌러도 안 열린다(같은 파일 :85 경고) — "현재 alias 끄고 새 alias 켜기" 사이에 실패하면 이 상태가 된다 |
| 딥링크(`doubly://`, MainActivity 의 VIEW intent-filter) | 액티비티 직접 | alias 로 옮기지 않고 MainActivity 에 두면 무관. 플러그인이 LAUNCHER 필터만 옮기는지 prebuild 산출물로 확인 |
| 앱 코드의 `MainActivity` 이름 참조·바로가기(shortcuts) | — | **0건** |

**실기기에서 볼 것**: ① 삼성 One UI 런처 — alias 전환 시 홈 화면에 놓인 아이콘이 사라졌다 다시 생기거나 폴더에서 빠지는지 ② 전환 직후 앱이 종료되는지(일부 OEM 은 DONT_KILL_APP 을 무시한다 — 그렇다면 "다음 실행 때 적용" 으로 UX 를 짜야 한다) ③ 위젯이 살아 있는지 ④ 알림 탭.

### 4-4. 스토어 정책

- **App Store**: 대체 아이콘은 바이너리에 포함되어 심사를 받는다. 다른 앱·브랜드를 흉내 내지 않고 **앱을 알아볼 수 있어야** 한다. 대체 아이콘을 IAP 혜택으로 두는 것 자체는 흔한 패턴이다.
- **Google Play**: 사칭(다른 앱처럼 보이는 아이콘) 금지. activity-alias 자체는 문제없다. 스토어 등록 아이콘은 `play_icon_512.png` 하나로 고정이다.
- 둘 다 **대체 아이콘이 "숟가락+하트" 마크를 유지하는 변주**(색·배경·캐릭터 얹기)여야 안전하다 — 09-29 확정 마크에서 벗어나는 아이콘은 정책보다 먼저 브랜드 일관성에서 걸린다.

### 4-5. 판단

다음 네이티브 빌드(K1·Pretendard 와 같이)에 묶는다 — 동의. 범위는 **2~3종, PRO 혜택**(게이팅은 §3 과 같은 패턴: `Feature.APP_ICON` 또는 `CHAT_THEME_PREMIUM` 과 묶은 "꾸미기" 키 하나 — 아이콘은 기기 설정이라 서버 저장 없음). 아이콘 후보가 아직 없으므로 작업 순서는 **그림 → 실기기(삼성) 확인 → 빌드**이고, 그림이 늦으면 빌드에서 빼도 다른 항목에 지장이 없다(플러그인을 안 넣으면 그만).

## 5. 커플 공용 vs 개인별 (열린 질문 4)

**개인별·기기별 유지.** 09-14 의 비용 계산(테이블·Flyway·실시간 이벤트·Purger)과 "상대 화면이 예고 없이 바뀐다"는 그대로다. 캐릭터 테마라고 달라지는 건 없다.

"둘이 같은 방"의 욕구는 두 가지로 싸게 채운다.
1. **PRO 판정은 커플 단위**(`isCoupleScoped` 에 넣는다) — 한 명이 결제하면 둘 다 캐릭터 테마를 고를 수 있다. "커플당 결제 1건" 모델(Feature.java 주석)과도 맞다.
2. 필요하면 나중에 **"상대에게 이 테마 보내기"**(채팅 카드 하나 → 받는 쪽이 탭해서 적용). 상대의 동의가 들어가므로 "예고 없이 바뀜"이 없고, 서버는 메시지 하나로 끝난다(테이블 없음). 지금 만들 필요는 없다.

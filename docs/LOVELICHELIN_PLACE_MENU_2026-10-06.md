# 럽슐랭 장소 — 우리가 쌓는 메뉴·사진 (2026-10-06)

> **2026-10-06 같은 날 — 메뉴판 찍기는 앱에서 뺐다(사용자 결정).** 카카오 [메뉴·정보 보기]·[네이버에서 보기]가 대부분의 가게 메뉴·가격·사진을
> 이미 보여 주고, 메뉴판 찍기가 더 나은 경우(카카오에 메뉴가 없는 작은 가게, 우리가 남기는 가격, "먹어 봤어요" 연결)는 좁은데 동선(찍기 →
> AI → 확인)과 AI 한도를 쓴다. **남긴 것**: 장소 상세 맨 위 "우리 사진" 줄. **앱에서 지운 것**: `PlaceMenuBoard.tsx`, place API 3종, 타입.
> **서버는 그대로**(V131 테이블·API 4종·Purger·StoredMediaReferences) — 비어 있어 해가 없고, 되살릴 때 앱만 되돌리면 된다(`c4ce1469`·`a144bb46`).
> 서버를 걷어낼 때는 V131 을 고치지 말고 새 마이그레이션으로 drop 한다(운영에 이미 적용됨). 아래는 만들 때의 기록이다.

`docs/LOVELICHELIN_PLACE_INFO_2026-10-06.md` §6 의 3단계. 1~2단계(세부 분류·전화·앱 안 브라우저)에 이어,
**메뉴·사진을 외부에서 가져오지 않고 둘이 남긴 기록으로 채운다.** 카카오·네이버 모두 메뉴·사진 공개 API 가 없다.

## 1. 결정

## 2. 무엇이 바뀌었나

### 서버 (`0aeba233`, V131)

- `V131__place_menu_board.sql` — `place_menu_items`(name·price·sort_order·updated_by), `place_menu_photos`(image_url·uploaded_by).
  둘 다 `places` ON DELETE CASCADE. 사람 컬럼에는 users FK 를 걸지 않는다(장소는 관계 단위로만 지워지고, UserDataPurger 가 이 표를 몰라도 되게).
- `MenuBoardService` — 분석(`analyze`, AI 작업 큐 안), 응답 정리(`toAnalysis`: 빈 이름·중복 제거, 0 이하·1천만 초과 가격은 null, 80개 상한,
  "메뉴판이라면서 한 줄도 못 읽음" = 메뉴판 아님), 저장(`save`), 사진 삭제(`deletePhoto`, 파일은 커밋 뒤 `deleteAllAfterCommit`).
  저장·삭제는 `CoupleEvent.PLACE` 를 보내 상대 화면이 다시 받는다.
- API
  - `GET /places/{id}/menu` — 기존 응답에 `board`·`boardPhotos` 를 **덧붙였다**(옛 앱은 무시).
  - `POST /places/{id}/menu-board/analyze` `{photoUrl}` → 202 + jobId(식단 사진 분석과 같은 방식). 장소 권한은 작업을 만들기 전에 본다.
  - `PUT /places/{id}/menu-board` `{items:[{name,price}], photoUrl?}` — 같은 사진은 두 번 붙지 않는다. Cloudinary 설정 시 앱 업로드 폴더 사진만.
  - `DELETE /places/{id}/menu-board/photos/{photoId}`
- 삭제 경로: `RelationRecordPurger`(places 직전에 두 표, 메뉴판 사진 URL 수집), `StoredMediaReferences`(`place_menu_photos.image_url`).
- 테스트: `MenuBoardTest`(6, 저장·재전송·10장·권한·관계 삭제), `MenuBoardAnalysisMappingTest`(5).

### 앱 (`c4ce1469`, `a144bb46`)

- `screens/place/PlaceMenuBoard.tsx` — "메뉴" 섹션(이름 왼쪽·가격 오른쪽, 6개 넘으면 "모두 보기", 메뉴판 사진 썸네일, [메뉴판 찍기]/[고치기]/[직접 적기])과
  확인·수정 시트. 메뉴판은 1600px 로 줄여 올린다(식단 1024 — 글씨가 작다).
- `PlaceDetailScreen` — 맨 위 우리 사진 줄, 메뉴 섹션. **메뉴 응답을 받기 전·실패 시 섹션을 그리지 않는다** — 저장이 통째로 바꾸기라
  모르는 상태에서 고치면 남아 있던 메뉴를 지운다.
- 분석이 실패하거나 메뉴판이 아니면 올린 사진은 `uploadApi.discard`, 시트를 취소해도 discard.

### 한글 조합 중 [저장] (웹에서 재현 → 수정 `a144bb46`)

메뉴 이름을 한글로 적다 곧장 [저장]을 누르면 마지막 입력이 빠지거나 첫 탭이 먹지 않았다(채팅 전송 2026-09-30 과 같은 계열).
- 값은 `editorRef`(편집할 때마다 같이 갱신)에서 읽는다 — onSave 가 쥔 상태가 한 박자 늦어도 최신 값이 저장된다.
- 앱은 `onPressIn` 으로 저장(+ 스크린리더 activate). **웹은 `onPress`** — react-native-web 이 이 `Pressable` 의 onPressIn 을 부르지 않았다(확인).
  웹은 조합이 blur 에서 끝나고 클릭은 그대로 와서 문제가 없다(재현 후 한 번에 저장됨을 확인).

- 서버: H2 전체 1243건 통과, PostgreSQL(postgres:16) place·관련 150건 통과.
- 앱: typecheck·lint(새 경고 없음)·verify:nested-buttons·build:web 통과. 새 아이콘 글리프 없음(`camera-outline`·`close`·`delete-outline` 기존).

  빈 상태(문구·[메뉴판 찍기]·[직접 적기]) 확인. 저장 결과는 API 로 대조.

  안드로이드/iOS 한글 키보드에서 onPressIn 저장, 메뉴판 사진 뷰어에서 지우기, 상대 화면 실시간 갱신.

## 4. 배포

서버(V131) 먼저 — Railway 가 main 푸시로 배포한다. 앱은 OTA 로 충분(네이티브·의존성 변경 없음, `expo-image-manipulator`·카메라 권한은 이미 빌드에 있음).
서버만 올라가고 앱이 옛것이면: 새 필드를 무시할 뿐 아무 일도 없다. 앱만 새것이고 서버가 옛것이면: `board` 가 없어 빈 상태가 보이고
[메뉴판 찍기]가 404 로 실패한다 — 그래서 서버가 먼저다.

## 5. 실기기 체크리스트

1. 실제 메뉴판(인쇄·벽·칠판) 촬영 → 이름·가격이 맞게 읽히는가. "9.0" 같은 천 원 단위 표기.
2. 메뉴판이 아닌 사진 → "메뉴를 읽지 못했어요" + [직접 적기].
3. 같은 장소에서 뒷면을 한 장 더 → 새 메뉴만 뒤에 붙고 표시되는가.
4. 한글 메뉴 이름을 적다 곧장 [저장] — 한 번에 저장되고 마지막 글자가 남는가(안드로이드·iOS 각각).
5. 메뉴판 썸네일 → 뷰어 → [이 사진 지우기]. 길게 눌러 지우기.
6. 상대 계정에서 메뉴가 보이고, 상대가 고치면 내 화면이 다시 받는가.
7. 식단과 연결된 방문이 있는 곳에서 "먹어 봤어요 · N번" 칩.
8. AI 한도 소진 시 안내(음식 사진 분석과 같은 한도).

# 식단 사진 "붙이자마자 분석" — 1주 계측 확인 (2026-10-12)

질문: 럽바디 기록 화면에서 사진을 붙이면 "AI로 음식 분석"을 누르지 않아도 바로 분석하는 게 낫지 않나?
10-05 기록 화면 계획서(`lovebody-record-screen-plan_2026-10-05.md` §보류)가 "한도 소모·비용 판단이 따로 필요"하다며
미뤄 둔 안이고, 그 판단용으로 넣은 `MEAL_*` 계측 1주(10-05~10-11)를 운영 `event_logs` 에서 읽기 전용으로 읽었다.

## 읽는 법의 함정

- `event_logs.created_at` 은 **날짜 단위로 잘려 저장된다**(전부 KST 자정). 같은 날 이벤트의 순서는 시각이 아니라 **`id` 순서**로 봐야 한다.
  처음 시각 기준으로 묶은 쿼리는 엉뚱한 결과를 냈다.
- 표본이 작다 — 기록 화면에서 사진을 쓴 사람은 **1명(user 1)** 뿐이다. 경향은 보이지만 일반화는 못 한다.

## 숫자 (10-05 ~ 10-11)

| 사람 | 쓰는 길 | 내용 |
|---|---|---|
| user 1 | 기록 화면 | 사진을 붙인 기록 **10건 전부** 같은 세션에서 사진 분석을 눌렀다(새 기록 9건 저장 · 1건 이탈). 사진만 붙이고 분석 없이 저장한 적은 **0건** |
| user 1 | 기록 화면 | 그중 **3건은 분석을 두 번** 눌렀다(10-08 ×2, 10-10). 원인(실패 재시도인지 다시 보기인지)은 이벤트로 구분 안 된다 |
| user 1 | 기록 화면 | 수정 화면에서 사진을 새로 붙이지 않고 분석만 다시 누른 경우 1건(10-08) |
| user 5 | 홈 빠른 기록 시트 | 사진만 저장 5건(`sheet;…;a=1`) — 서버 자동 분석에 맡김. 기록 화면에서 사진을 쓴 적 없음 |

텍스트 분석은 6건(전부 user 1), 사진 분석 14건.

## 결론

- **기록 화면에서 사진을 붙인 사람은 예외 없이 분석을 눌렀다.** 그 버튼은 선택지가 아니라 매번 거치는 한 단계다 → 붙이자마자 시작하면
  매번 한 번의 탭과 대기가 줄고, **분석 횟수는 늘지 않는다**(어차피 쓰던 1회). 늘어나는 건 잘못 고른 사진을 다시 고를 때뿐.
- 사진만 빠르게 남기는 사람은 이미 홈 시트 + 서버 자동 분석으로 버튼 없이 쓰고 있다 — 이 길은 건드릴 필요 없다.
- 그래서 **기록 화면에서 "새 사진을 붙였을 때"만** 자동 시작하는 게 맞다. 조건:
  1. 새로 붙인 사진 1장당 1회. 수정 화면을 열었을 때 이미 있던 사진으로는 돌지 않는다(그건 지금처럼 버튼).
  2. 음식 항목이 비어 있을 때만 — 이미 적어 둔 걸 덮지 않는다.
  3. 남은 사진 분석 횟수가 0 이면 돌지 않는다(버튼·안내는 지금 그대로).
  4. 설정의 "음식 사진 자동 분석"(`autoAnalyzeMealPhoto`)을 끈 사람은 돌지 않는다 — 같은 뜻의 스위치다.
  5. 분석 중에 저장하면 기다리지 않고 저장하고, 칼로리는 서버 자동 분석이 채운다(지금 사진만 저장할 때와 같은 길).
  6. 장소 힌트(10-11): 럽슐랭에서 들어와 장소를 이미 알면 그대로 싣는다. 사진 뒤에 장소를 고르면 기존 메뉴 칩으로 이름만 바꾸는 흐름(297caf3f)이 있다.
- "두 번 누른" 3건의 원인은 계측으로 알 수 없다. 자동 시작 뒤에도 같은 패턴이면 실패 재시도일 가능성이 높으니 서버 로그(`docs/STABILITY_*`)와 대조한다.

## 구현 (같은 날)

`frontend/src/screens/diet/DietRecordScreen.tsx` — `maybeAutoAnalyze`, `onAnalyze(uri, 'auto')`.

- 사진을 고른 직후(`pickFrom`)와 **채팅 사진으로 새 기록을 열었을 때** 위 조건 1~4 를 만족하면 기존 분석을 그대로 부른다.
  수정 화면의 기존 사진은 대상이 아니다.
- 플랜 상태를 아직 모르면(`stateOf('AI_FOOD_PHOTO')` 없음)·`allowed=false` 면 돌지 않는다 — 누르지도 않은 사람에게 결제 안내를 띄우지 않는다.
- 기다리는 사이 사진을 바꾸거나 지우면 늦게 온 결과(와 실패 토스트)는 버린다.
- 계측: 자동 시작은 `MEAL_ANALYZE_STARTED photo_auto`, 버튼은 그대로 `photo`. 자동 뒤에도 `photo` 가 자주 찍히면
  자동 결과가 못 미더운 것이다(또는 실패 재시도).
- **조건 5(분석 중 저장)는 바꾸지 않았다.** 저장 버튼은 분석 중 잠겨 있다(기존 결정 — 곧 올 결과를 못 받은 채 떠난다).
  풀면 앱 분석 1회 + 서버 자동 분석 1회로 **횟수를 두 번** 쓴다. 대기는 지금도 버튼을 누른 뒤 겪던 것과 같다.
- 서버 변경 없음, `app.json`·`package.json` 변경 없음 → OTA.
- 검증: typecheck 통과, eslint 는 기존 4건 그대로(새 오류 0). 실제 분석은 운영 서버·실제 횟수를 쓰므로 웹으로 돌려 보지 않았다 — 실기기 확인 필요.

## 2차 — "분석을 기다리는 게 싫다" (같은 날)

자동 시작만으로는 대기가 줄지 않았다 — 버튼을 누르는 한 번이 빠졌을 뿐 분석 시간은 그대로고, 저장 버튼이 분석 중 잠겨 있었다.

### 왜 오래 걸리나 (운영 `ai_usage_logs`, 최근 14일)

| 기능 | 모델 | 건수 | 입력/출력 토큰 평균 | thinking | 재시도 끝 성공 |
|---|---|---|---|---|---|
| AI_FOOD_PHOTO | gemini-2.5-flash-lite | 37 | 851 / 711 | 0 | 4건(11%, 최대 3회째) |
| AI_FOOD_TEXT | gemini-2.5-flash-lite | 9 | 401 / 183 | 0 | 0 |

- 이미 가장 빠른 모델이고 thinking 도 0 — 모델 쪽에서 크게 줄일 여지는 없다.
- 길어지는 건 **503 재시도**(로그: 2초 → 6초 백오프)와 **앱 폴링 간격**(`api/aiJob.ts` 0.3→0.7→1.2→2→2→3초 — 결과가 나와도 최대 3초 늦게 안다).
- 결론: 분석을 빠르게 만드는 것보다 **기다리지 않게** 하는 게 맞다.

### 수정 — 분석 중에도 저장

- **앱**: 새 기록에서 사진 분석 중에도 저장 버튼을 연다. 분석 중엔 안내가 "분석 중이에요. 기다리지 않고 저장해도 칼로리는 저장 뒤에 채워져요."로 바뀐다.
  저장하면 칼로리는 서버 자동 분석이 채운다(기존 "칼로리는 곧 채워져요" 토스트). 저장하고 떠난 뒤 늦게 온 앱 결과는 버린다(`leftScreenRef`).
  - 여는 조건(`serverTakesOverAnalysis`) = 서버가 이어받는 조건과 같다: 새 기록 · 자동 분석 설정 켜짐 · 적어 둔 음식 없음.
    수정 저장(update 는 자동 분석을 걸지 않는다)·설정 끔·음식을 적어 둔 경우엔 지금처럼 결과를 기다린다. 글로 분석은 이어받을 경로가 없어 그대로 잠근다.
- **서버**: `SharedPhotoAnalyses` — 같은 사람·같은 사진의 분석이 진행 중이면 올라타고, 끝난 지 10분 안이면 결과를 그대로 준다.
  올라탄 쪽은 한도를 쓰지 않고 Gemini 도 부르지 않는다 → **분석 중 저장해도 차감은 1회**. 같은 사진을 버튼으로 다시 누른 경우도 공짜·즉시.
  - 실패는 공유하지 않는다 — 앞선 분석이 실패하면 올라탄 쪽(자동 분석)이 직접 다시 한다.
  - 끝난 결과는 장소 힌트가 같을 때만 재사용(장소를 고르고 다시 누르면 새로 분석). 진행 중이면 힌트가 달라도 올라탄다 — 저장 때 카카오 장소가 새로 생기면 id 가 생겨 달라 보이기 때문.
  - 인스턴스 메모리다. 서버가 여러 대가 되면 대 사이에서는 공유되지 않는다(절약만 잃는다).
  - 테스트 `SharedPhotoAnalysesTest`(동시 올라타기·실패 비공유·힌트·보관 시간).

### 배포

- 서버 먼저(Railway 자동) → 앱 OTA. 순서가 바뀌면 그 사이 분석 중 저장이 한도를 두 번 쓴다.
- 계측으로 볼 것: `MEAL_RECORD_SAVED` 의 `a=1`(사진만 저장 → 서버가 채움) 비율이 기록 화면에서 늘어나는지, `photo_auto` 뒤 `photo` 재누름.

## 3차 — 글로 적은 음식도 버튼 없이 (같은 날)

사용자: "사진이 아니라 입력을 했을 때도 다시 또 버튼을 눌러야 되잖아." 계측에서도 글로 적은 새 기록 6건은 전부 "칼로리 계산"을 눌렀다.

**결정: 적는 중에 자동으로 돌리지 않고, 저장 뒤 서버가 채운다** (사진과 같은 원칙 — 저장은 바로, 칼로리는 뒤에서).
타이핑 중 자동 실행을 택하지 않은 이유: 다 적기 전에 돌면 횟수(AI_FOOD_TEXT 무료 하루 2회)를 헛쓰고, 결과가 목록을 바꿔 적던 줄이 흔들린다.

- **서버** `MealCalorieFillService` — 새 기록 저장(MealService.save → MealPhotoAutoAnalysisService.scheduleIfEligible 한 곳)에서,
  이름만 있고 칼로리가 빈 항목이 있으면 커밋 뒤 백그라운드로:
  1. 공공 DB(식약처)에서 **이름이 정확히 같은** 표기값(최대 4개 이름, 한도 안 씀)
  2. 남은 것만 AI 텍스트 분석(AI_FOOD_TEXT 1회). 보낸 개수만큼 오면 순서대로 짝짓고(이름·적은 양·적은 매크로는 유지), 다르면 빈 줄들을 AI 목록으로 바꾼다.
  - 적은 값은 건드리지 않는다. AI 가 하나라도 채웠으면 "약" 배지(AI_ESTIMATED), 표기값만이면 출처 그대로.
  - 그 사이 사용자가 기록을 고쳤으면(항목이 접수 때와 다르면) 버린다. 데이트 식단은 짝까지, 채운 값만 절반.
  - AI 한도 소진·실패면 표기값으로 찾은 것만 채우고 조용히 끝난다.
  - 사진 분석과 겹치지 않는다(사진은 항목 0개일 때만, 이쪽은 항목이 있을 때만). 수정(update)은 대상이 아니다.
  - 설정 스위치는 같은 `autoAnalyzeMealPhoto` — 앱 문구를 "사진으로 칼로리 채우기" → **"칼로리 자동으로 채우기"** 로 넓혔다.
- **앱**: "칼로리 계산" 아래 안내가 "칼로리를 비워 두고 저장해도 뒤에서 채워져요. 저장 전에 보고 고치려면 눌러 주세요."로 바뀐다(버튼은 미리 보고 고치고 싶은 사람용으로 남김).
  저장 토스트 "칼로리는 곧 채워져요"(AI 횟수 0이면 "표기값이 있는 음식은 칼로리를 곧 채워요"). 카드는 칼로리가 빈 항목이 있으면 합계 대신 "칼로리 채우는 중"(최대 10분).
  계측 `MEAL_RECORD_SAVED` 의 `a=2` 가 이 경로다.
- 테스트: `MealPhotoAutoAnalysisTest`(같은 컨텍스트에 3건 — 순서 짝짓기·개수 다를 때·대상 아님), `MealCalorieFillPlanTest`(표기값 우선·적은 값 유지·AI 실패).
- 결과는 앱에 밀어주지 않는다 — 사진 자동 분석과 같이 다음에 목록을 다시 읽을 때 보인다.

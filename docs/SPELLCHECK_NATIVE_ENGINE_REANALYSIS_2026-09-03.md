# 맞춤법 검사기 — 사전 기반 엔진 재조사 (2026-09-03)

> 전날 조사([SPELLCHECK_DICTIONARY_ENGINE_ANALYSIS_2026-09-02.md](./SPELLCHECK_DICTIONARY_ENGINE_ANALYSIS_2026-09-02.md))는
> 5개 경로를 전부 기각하고 "사전 기반 접근은 완전히 막혀 있다"로 끝났다. 맞춤법 검사기가
> Dubly의 핵심 축이라 그 결론을 다시 검증했고, **결론이 뒤집혔다.**

## 0. 결론 먼저 — 막혀 있지 않다. 전제가 틀렸다

전날 기각된 5개 경로(Kiwi / Hunspell+WASM / nspell / JSC 전환 / Polygen)는 **서로 다른
대안처럼 보이지만 사실 하나의 전제를 공유한다**:

> "사전 엔진을 **JS 엔진 안에서** 돌려야 한다 — 즉 WebAssembly로."

5개 중 4개(WASM, nspell, JSC, Polygen)가 이 전제 위에 있고, 전부 그 전제 때문에 죽었다.
Hermes에 WASM이 없고(hermes#429), jsc-android는 `--no-webassembly`로 빌드되고, Polygen은
그 벽을 우회하려다 업스트림 패키징 버그를 만났다.

**그런데 Hunspell도 Kiwi도 WASM 바이너리가 아니라 C++ 소스다.** WASM은 "C++를 JS 엔진
안으로 밀어 넣는" 우회로였을 뿐이고, React Native에는 애초에 **C++를 그냥 C++로 넣는
공식 경로**가 있다 — New Architecture의 **Pure C++ TurboModule**(JNI 불필요, RN 공식 문서).

즉 전날 조사는 "뒷문이 다 잠겨 있다"를 확인한 것이고, **정문은 열어보지 않았다.**

## 1. 이 프로젝트는 정문을 열 조건을 이미 다 갖췄다

재조사 중 확인한 사실들:

| 항목 | 상태 | 확인 방법 |
| --- | --- | --- |
| New Architecture | **켜져 있음** (`newArchEnabled: true`) | `frontend/app.json:10` |
| RN 버전 | 0.85.3 / Expo SDK ~56.0.12 | `frontend/package.json` |
| `react-native-nitro-modules` | **이미 설치돼 있음** (0.36.5, `react-native-iap`가 끌어옴) | 의존성 역추적 |
| 네이티브 디렉토리 | `android/`·`ios/` 모두 `.gitignore` → **CNG(prebuild) 프로젝트** | `frontend/.gitignore:45-46` |
| 로컬 빌드 경험 | `expo prebuild` + `expo run:android`(NDK 27.1.12297006) 이미 통과 | 전날 조사 §3-4 |

CNG라는 점이 중요하다. `android/app/src/main/jni/CMakeLists.txt`를 직접 고치는 RN 공식
튜토리얼 방식은 **`prebuild` 때마다 날아가서 이 프로젝트에선 못 쓴다.** 그래서 올바른
형태는 **로컬 Expo 모듈**(`npx create-expo-module --local` → `frontend/modules/…`, git에
추적됨, Expo autolinking이 prebuild마다 자동으로 다시 붙임)로 C++ 소스와 CMakeLists를
**모듈 안에** 넣는 것이다. 전날 조사가 이 구조적 갈림길을 안 짚었다.

## 2. 기각 사유 재검토 — 어떤 게 살아 있고 어떤 게 진짜 죽었나

사용자 확인(2026-09-03): **앱 용량 제약 없음, 개발 기간 제약 없음.** 이 두 제약이 빠지자
기각 사유의 절반이 무효가 된다.

| 경로 | 전날 기각 사유 | 재검토 결과 |
| --- | --- | --- |
| Hunspell + WASM | Hermes에 WASM 없음 | **사유는 여전히 사실. 하지만 무관해짐** — WASM을 안 쓰면 된다 |
| nspell | ko.dic이 NFD라 구조적 불일치 | **유효한 기각.** 순수 JS 재구현체 경로는 그대로 죽음 |
| JSC 전환 | jsc-android가 `--no-webassembly` | **사유는 사실. 하지만 무관해짐** — 엔진 바꿀 이유가 없어짐 |
| Polygen | 업스트림 패키징 버그 | **무관해짐** — Polygen은 "WASM을 C로 바꿔 JSI에 붙이는" 도구다. 원본이 C++인데 C++→WASM→C로 왕복할 이유가 없다 |
| Kiwi | ①용량 109MB ②LGPL 정적 링킹 컴플라이언스 | **두 사유 모두 해소.** ①용량 제약 없어짐 ②**공식 Android AAR을 배포한다**(`kiwi-android-VERSION.aar`, API 21+, ARM64) — AAR은 `.so` 동적 링킹이라 LGPL 요건을 자연스럽게 충족. "정적 링킹이라 애매하다"는 전제 자체가 틀렸다 |

정리하면 **진짜로 죽은 건 nspell 하나뿐**이고, 나머지 넷 중 셋은 "WASM을 쓴다면"이라는
조건부 기각이었으며, Kiwi는 사실 오인에 근거한 기각이었다.

## 3. 라이선스 — 상용 비공개 앱 기준 재확인

스토어 배포 앱이라 이건 따로 확인했다.

- **Hunspell 엔진**: MPL 1.1 / GPL 2.0 / LGPL 2.1 **3중 라이선스**. MPL 또는 LGPL을 택하면
  비공개 상용 앱에 넣을 수 있다. → **문제 없음**
- **hunspell-dict-ko 사전**: 결합물(ko.aff/ko.dic)은 GPL-3.0이지만, 저장소 LICENSE.md가
  명시적으로 *"이 사전은 GPLv3 비호환 소프트웨어와도 쓸 수 있다 — 실행 프로그램과 hunspell
  사전은 별개 저작물이라 라이선스가 호환될 필요가 없다"* 고 못 박아 둠. 원 데이터는
  CC-BY-SA 계열. → **문제 없음** (고지 의무는 이행 필요)
- **Kiwi**: **LGPL v3**. 동적 링킹(`.so`/AAR) + 재링크 가능 상태 유지 + 소스 제공 고지면
  비공개 앱 배포 가능. → **조건부 가능**, 다만 Hunspell보다 의무가 무겁다

## 4. 두 후보 — 무엇이 "높은 정확도"를 주는가

용량·기간 제약이 없어졌으므로 판단 기준은 **정확도 하나**로 좁혀진다.

### 4-1. Hunspell 네이티브 (권장 1순위)

- **이미 실증된 부분이 가장 크다.** 전날 Node.js에서 실제 Hunspell 코어로 돌린 결과:
  우리 규칙표의 기존 오류 5개(안되요·오랫만에·어의없어·갈께·왠일로)를 **전부 자동 검출,
  제안 문자열까지 우리 규칙표와 거의 동일**. 정상 문장은 통과(오탐 없음).
  → 엔진·사전 조합의 **동작은 검증이 끝났다.** 남은 미검증 구간은 "빌드/탑재"뿐이다.
- 크기 ko.aff 11.1MB + ko.dic 2.86MB ≈ 14MB. 제약 없음.
- 순수 C++ + CMake, 외부 의존성 없음 → Android NDK / iOS 양쪽 빌드 난이도 낮음.
- **한계**: "사전에 있나/없나" 이진 판정이다. 되/돼처럼 **둘 다 실재하는 단어**인 문맥
  의존 오류와 띄어쓰기는 원리적으로 못 잡는다. → 기존 정규식 엔진이 담당하는 영역이라
  **서로 겹치지 않고 보완된다.**

### 4-2. Kiwi 네이티브 (정확도 상한은 더 높음)

- 형태소 분석기라 천장이 높다: 0.13.0+ 내장 **오타 교정**, 미등록어 처리가 Hunspell보다
  유연(애교체 오탐에 강할 가능성), 형태소 정보가 있으니 **띄어쓰기 검사까지 확장 가능**.
- **하지만 리스크가 크다**:
  - **iOS 공식 바인딩이 아직 없다** — Swift 바인딩 "제공 예정" 상태. 안드로이드만 AAR 제공.
    크로스플랫폼 앱이라 iOS는 직접 빌드해야 한다.
  - 공식 AAR은 **ARM64 전용**.
  - LGPL v3 의무가 Hunspell보다 무겁다.
  - 전날 Node 테스트에서 **Kiwi 내장 오타 사전이 우리 타깃 케이스를 놓쳤다**(왠일로·갈께·
    오랫만에·어의없어). 즉 "Kiwi 켜면 정확도가 오른다"가 자동으로 성립하지 않고, 어떻게
    쓰느냐(내장 오타사전 vs 형태소 분석 가능 여부 판정)를 새로 설계·검증해야 한다.

### 4-3. 서버 사이드 (참고 — 권장하지 않음)

백엔드(Spring Boot, `com.fitto.chat`)에 얹으면 용량 0, 엔진 자유. 채팅 메시지는 이미
평문으로 우리 서버에 저장되므로 **"외부 모델로 보낸다"는 프라이버시 반대 논거는 자체
서버에는 해당되지 않는다**(`koreanSpellCheck.ts` 헤더의 논거는 외부 AI 기준이다).
다만 사용처가 **채팅 입력창(타이핑 중 실시간)** 이라 왕복 지연이 그대로 UX를 때리고,
오프라인에서 죽는다. 온디바이스 원칙을 깰 만큼의 이득이 없다.

## 5. 권장안 — Hunspell 네이티브 모듈, 3계층 파이프라인

기존 아키텍처 방향(전날 조사 §1-2 "권장 아키텍처")은 그대로 맞다. 전달 수단만 바꾼다.

```
1층  정규식 엔진 (koreanSpellRules.ts, ~90규칙)   ← 유지. 문맥 의존·친절한 설명 담당
2층  Hunspell 네이티브 (사전 미등재 어절 검출)      ← 신규. 일반화된 오타 담당
3층  애교체 정규화 + 예외 허용목록                  ← 신규. 2층의 오탐을 0으로 누르는 안전장치
```

3층이 핵심이다. Hunspell 단독은 "뭐했어용·사랑행·배고파용"을 전부 오탐으로 뱉는데, 이는
**오탐 제로 원칙 위반**이고 커플 채팅에서 제일 자주 쓰는 말투다. 전날 검증된 완화책
(마지막 글자 ㅇ받침을 벗기고 재검사 — 7개 중 6개가 규칙 하나로 해결)을 2층 앞에 세운다.

### 구현 순서 (각 단계가 독립적으로 검증 가능)

1. `frontend/modules/korean-spell/` 로컬 Expo 모듈 생성 (`create-expo-module --local`).
2. Hunspell C++ 소스 + CMakeLists를 모듈 안에 배치, `spell(word)` / `suggest(word)` 두
   함수만 노출하는 최소 C++ TurboModule. **먼저 영어 사전으로 왕복 성공만 확인.**
3. ko.aff/ko.dic을 모듈 에셋으로 넣고 첫 실행 시 `filesDir`로 복사(Hunspell C++ API는
   실제 파일 경로를 요구하므로 APK 내부 asset 경로로는 못 연다).
4. 로딩 시간·메모리 실측. **여기가 유일하게 남은 진짜 미지수** — 11MB짜리 aff 파싱이
   모바일에서 얼마나 걸리는지 모른다. 지연 로딩 + 타이핑 핫패스에서 분리(디바운스) 전제.
5. 3층(애교체 정규화 + 허용목록) 얹고 `scripts/verify-spellcheck.mjs` 확장 — **오탐 회귀
   테스트를 여기서 반드시 늘린다.**
6. iOS 빌드.

### 남은 리스크 (정직하게)

- **미검증**: 모바일에서의 사전 로딩 시간·메모리. 4단계에서 처음 알게 된다.
- **미검증**: 로컬 Expo 모듈에 C++ CMake를 얹는 빌드 자체. 공식 지원 경로지만 이 프로젝트에서
  해본 적은 없다.
- **설계 과제**: 2층의 오탐을 실제로 0에 수렴시키는 것. 기술 문제가 아니라 튜닝 문제이고,
  이 기능의 성패를 실제로 가르는 지점이다.

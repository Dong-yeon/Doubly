# 식단↔럽슐랭 연동 분석 (2026-09-02)

> 계기: 럽슐랭 백로그 재확인 중 사용자가 "방문 별점이 꼭 필요한가, 대표 평점이 있는데
> 매번 별점을 남기는 게 귀찮지 않을까"라는 질문을 던졌고, 그 질문을 파고들다 식단 탭과
> 럽슐랭 탭이 만나는 지점 전체를 훑게 됐다. 조사는 Explore 서브에이전트로 코드를 전수
> 확인했고(파일:줄번호 근거), 판단은 이 문서에서 직접 한다.

## 0. 결론 먼저

**"별점 두 번 받는 게 귀찮다"는 감각의 진짜 원인은 입력 횟수가 아니라 비일관성이었다.**
방문 별점은 이미 완전히 선택(스킵 가능)이고 등급 계산에도 안 쓰인다 — 강제되는 게 없다.
그런데 **같은 별 5개 위젯이 탭마다 다른 일을 한다**: 식단 탭에서는 한 번의 입력이 방문
기록과 대표 평점(등급용) 둘 다를 확정하는데, 럽슐랭 탭에서는 완전히 분리된 두 입력·두
버튼이다. 이 비일관성이 "이게 뭘 하는 입력인지" 확신을 못 주는 게 진짜 문제다.

조사하다 보니 별점보다 더 무거운 문제들이 나왔다 — **식단 탭에서 시작한 연동이 식단 탭
쪽으로는 아무것도 돌아오지 않는 단방향 구조**였다.

## 1. 적용 완료 — 식단 탭에 장소 정보 표시 ✅ 2026-09-02

**문제**: `Meal` 에 `placeId` 필드가 아예 없었다(`backend/.../MealResponse.java` 전수
확인, 0건). 식단 탭에서 장소를 붙여 저장해도(`DietRecordScreen.tsx` 의 "저장된 장소에서
고르기") 오늘 목록·히스토리 어디서도 그 사실이 안 보였다 — 럽슐랭 탭 → 그 장소 상세로
직접 찾아가야만 방문 기록으로 존재를 확인할 수 있었다.

**적용**:
- `PlaceVisitRepository.findByMealIdIn` — meal id 목록으로 방문+장소명을 배치 조회.
  `Meal.placeId` 를 따로 복제하지 않고 `PlaceVisit.mealId`(유일한 연결고리)로 역방향
  조회한다 — 복제하면 방문 기록 삭제 시 Meal 도 같이 갱신해야 해서 어긋날 여지가 생긴다.
- `MealResponse` 에 `placeId`/`placeName` 추가, `findToday`/`findHistory` 에서 배치
  조회해 채운다. `save()`/`update()` 응답에는 안 싣는다(저장 시점엔 장소 연동이 뒤이어
  오는 별도 API 콜이라 아직 없다).
- `MealCard` 에 "📍 장소명" 태그 — 카드 전체 탭(수정 화면)과 별개 터치 영역, 눌러도
  수정 화면으로 안 넘어가고 럽슐랭 탭과 공유하는 `PlaceDetail` 로 이동한다.
- `PlaceDetail` 을 `DietStackParamList` 에도 등록(크로스탭 대신 같은 스택에 쌓아 뒤로가기
  보존 — `HomeStackParamList` 가 여행에서 같은 이유로 이미 쓰는 패턴), 딥링크는
  `diet/place/:placeId` 로 별도 경로.

**검증**: 커플 생성 → 장소 없는 식단 1건 + 장소 붙인 식단 1건 저장 → `GET /meal/today`
에서 전자는 필드 자체가 안 오고(NON_NULL 직렬화) 후자만 정확히 채워지는 것을 API로 확인.
tsc/eslint 클린, 백엔드 테스트 전체 통과.

커밋: `f182039`(백엔드), `9933e03`(프론트).

## 2. 남은 마찰 지점 (미착수)

### 2-1. 별점 UX 비일관성 — 방문 별점과 대표 평점을 하나로

| | 식단 탭 (`DietRecordScreen.tsx:821-858`) | 럽슐랭 탭 (`PlaceDetailScreen.tsx`) |
|---|---|---|
| 별점 입력 | 하나 — 누르면 방문 별점 + 대표 평점 동시 반영 | 완전히 분리된 두 입력·두 버튼 |
| 다시 볼래요? | 안 물어보고 항상 `true` 하드코딩 | 체크박스, 매번 다시 물어봄(서버가 이전 값을 안 돌려줘서) |

**제안**: 방문 기록에 별점을 남기면 그게 곧 대표 평점이 되도록 통일한다(식단 탭 방식을
럽슐랭 탭에도 적용). "그날은 별로였지만 가게 자체 평가는 유지하고 싶다"는 예외적인
경우를 위해 대표 평점만 따로 조정하는 보조 진입로만 남긴다. 콘텐츠(`ContentLog.rating`
+ `ContentRating`)도 구조가 동일해 같은 방식으로 통일 가능 — 다만 콘텐츠 화면 UX는
이번에 자세히 보지 않아 화면별 차이는 별도 확인 필요.

### 2-2. 반대 방향(식단→럽슐랭)은 정상, 정보 풍부도는 비대칭

럽슐랭 탭 방문 기록 목록(`PlaceService.visits()`)이 `placeId` 기준 전체 조회라, 식단
탭에서 만든 방문 기록도 거기 정상적으로 나타난다(이 방향은 이미 괜찮았다). 다만 두
진입점으로 만든 Meal 의 데이터 풍부도가 다르다:
- 식단 탭에서 장소 붙이기: 과거 날짜 선택 가능, 품목별 이름·칼로리 입력 가능.
- 럽슐랭 탭에서 식단 같이 기록(`logMeal` 체크박스): 날짜 항상 오늘(`PlaceDetailScreen.tsx:162`
  `toDateString()` 하드코딩), 음식 이름 입력 필드 없음(memo 에 장소명만 섞여 들어감).

### 2-3. 저장이 원자적이지 않음

`DietRecordScreen.tsx:821-858`: Meal 저장 → PlaceVisit 생성 → PlaceRating upsert 가
순차 API 3콜이다. 중간에 실패하면 Meal 만 남고 장소 연동이 빠진 반쪽 기록이 생긴다
(주석이 이 트레이드오프를 이미 인지하고 있음 — "장소 연동이 실패해도 식단 기록 자체는
이미 저장됐으므로 전체 저장을 실패로 되돌리지 않는다"). 에러 토스트로만 안내되고 재시도
동선은 없다.

### 2-4. "같이 먹기" + 장소 연동 시 방문자가 한 명으로 고정

데이트 식단(같이 먹기)은 상대방 몫 Meal 을 별도 row 로 복제하지만(`MealService.java:157-160`),
장소 연동은 내가 작성한 Meal 의 id 만 넘겨서 상대방 몫은 연결되지 않는다. 결과적으로
`PlaceVisit.visitedBy` 는 폼 작성자로만 고정되고(`PlaceService.recordVisit`), 실제로
둘이 같이 갔어도 방문 기록엔 한 사람 이름만 남는다. `rate()` 가 `(placeId,userId)` 단위라
등급 계산 자체는 문제없지만("같이 갔다"는 문맥에서 방문자 표시가 한 명뿐인 건 위화감 소지.

## 3. 우선순위 판단

1번(이 문서 1절)이 가장 먼저였던 이유: 사용자가 직접 겪을 확률이 가장 높고, 스키마
변경 없이 조회 로직만으로 해결되는 명확한 버그였다. 나머지 넷은 각각 성격이 다르다:
- 2-1(별점 통일)은 UX 결정 — 구현 자체는 작지만 "기본 동작을 바꾼다"는 결정이 필요.
- 2-2(입력 폼 비대칭)는 럽슐랭 탭 쪽 폼에 필드를 추가하는 작업.
- 2-3(원자성)은 백엔드에 트랜잭션 경계를 다시 설계하는 작업(3개 API 를 하나로 합치거나,
  실패 시 보상 처리를 추가하거나).
- 2-4(같이 먹기 방문자)는 "커플이 같이 기록한다"는 약속과 직결돼 있어 성격상 가장
  무겁다 — PlaceVisit 자체가 단일 visitedBy 를 전제로 설계돼 있어 스키마 변경이 필요할
  수 있다.

다음에 이어갈 때는 이 순서 그대로 따를 필요는 없고, 그때 상황에 맞게 재우선순위할 것.

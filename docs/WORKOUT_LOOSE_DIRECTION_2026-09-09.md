# 운동 탭 방향 전환 — "느슨한 기록" (2026-09-09)

> **한 줄**: 운동 탭을 <b>정밀 트래커</b>에서 <b>느슨한 체크인</b>으로 방향을 틀었다.
> 유산소를 시간·거리로 분리하고(V83), 종목 없이 "운동 완료"만 남길 수 있게 하고(V84 함께),
> 다른 앱의 운동 완료 화면을 사진으로 올리면 AI 가 읽어 채우도록 했다.
>
> 이 문서는 **왜 그렇게 정했는지**를 남긴다. 커밋은 결과만 남기고 이유를 남기지 않으므로
> (CLAUDE.md 5절), 나중에 "왜 상급자 기능을 더 안 팠나"를 다시 묻게 될 때 여기를 본다.

---

## 1. 진단 — 운동 탭은 왜 안 쓰이는가

사용자 질문("운동쪽을 많이 사용할 것 같아? 객관적으로")에 대한 분석 결론이다.

### 1-1. 가장 강한 신호는 이미 저장소에 있었다

`docs/WORKOUT_UX_ANALYSIS_2026-09-01.md` 의 제목이 **"왜 만든 사람도 안 쓰는가"** 다.
만든 사람조차 Strong/Hevy/번핏을 쓰고 있었다는 뜻이고, 어떤 시장 자료보다 강한 신호다.
그 뒤 1~5순위 개선으로 세션 화면 자체는 좋아졌지만 **경쟁 상대가 전문 트래커라는 구조**는
그대로였다.

### 1-2. 커플 기능은 확률이 곱해진다

상대 오늘 운동 여부·음성 부스터·대결·커플 스트릭은 전부 **둘 다** 기록해야 성립한다.

```
P(둘 다 쓴다) = P(헬스장에서 루틴 운동) × P(애인도 그렇다) × P(둘 다 기존 앱의 기록 이력을 버린다)
```

채팅·사진·기념일·무드는 **이미 하는 행동에 얹는** 덧셈인데, 운동만 곱셈이다.
운동 탭이 다른 탭만큼 쓰이기 어려운 근본 이유가 여기 있다.

### 1-3. 코드 무게중심이 정반대였다

원판 계산기·RPE·e1RM·백오프 세트·근육 회복률은 전부 **1인 상급자용 정밀 도구**다.
이 영역은 Strong 과 정면으로 붙는 곳이고, 종목 카탈로그 규모(수십 개 대 수백~1000개)만 봐도
붙으면 진다. 반면 Dubly 만 할 수 있는 "같이 했다는 증거" 쪽 코드는 훨씬 얇았다.

## 2. 결정 — 느슨하게 간다 (사용자 결정, 2026-09-09)

> "너무 빡빡한 운동앱은 원하지 않아. 좀 더 느슨하게 가자"

정밀 트래커 경쟁을 포기한다는 뜻이 아니라, **기록의 최소 단위를 낮춘다**는 뜻이다.
기존 세션 화면·세트별 기록·추이는 그대로 두고(원하는 사람은 계속 쓴다), 그 아래에
훨씬 가벼운 경로를 두 개 만든다.

| 경로 | 요구하는 것 | 남는 것 |
| --- | --- | --- |
| 원탭 "운동 완료" | 탭 1번 | 스트릭·캘린더·커플 카드 (전부 동작) |
| 사진으로 기록 | 사진 1장 | 위 + 시간·거리(AI가 읽음) + 인증샷 |
| 세션 기록(기존) | 세트별 입력 | 위 + 볼륨·1RM·종목별 추이 |

**핵심 근거**: 스트릭·캘린더·커플 요일 스트립이 보는 것은 세트가 아니라 **기록의 존재**다.
그러므로 빈 기록으로도 그 목적은 100% 충족된다. 세트를 필수로 걸어둔 것은 아무것도 지켜주지
못하면서 "자세히 적을 생각이 없는 사람"을 통째로 배제하고 있었다.

## 3. 왜 사진 연동인가 (헬스 커넥트 대신)

처음 권고는 헬스 커넥트/애플 건강 자동 수집이었고, 사용자가 사진 연동을 제안해 재검토했다.
**사진 연동이 먼저**라는 결론이다.

| | 사진 연동 | 헬스 커넥트 / 애플 건강 |
| --- | --- | --- |
| 소스 범위 | 전부 — 스트라바·나이키·삼성헬스·애플워치 + **헬스장 트레드밀 직촬** | 연동된 앱/기기만, 트레드밀은 못 잡음 |
| 플랫폼 작업 | 한 경로(웹 포함) | iOS/Android 각각 + 권한 심사 |
| 재사용 | **식단 사진 분석 파이프라인 그대로** | 새로 구현 |
| 마찰 | 사용자가 올려야 함 | 0 (자동) |

결정적이었던 두 가지:

1. **새 습관을 요구하지 않는다.** 운동 후 인증샷·스크린샷은 이미 하는 행동이다.
   세트 로깅은 없던 습관을 만들라는 요구였다.
2. **이미 검증된 부품이다.** `FoodAnalysisService` 가 영양성분표의 **인쇄된 숫자를 읽는**
   경로(`NUTRITION_LABEL`)를 이미 갖고 있다. 트레드밀 LCD·앱 스크린샷 판독은 같은 난이도라
   기술 리스크가 사실상 없었다.

헬스 커넥트는 폐기가 아니라 **뒤로 미룬 것**이다. 걸음수처럼 사진이 없는 활동은 결국 자동
수집이라야 잡히고, 그때 곱셈 구조를 덧셈으로 바꾸는 지렛대가 된다.

## 4. 구현에서 지킨 원칙

- **AI 결과를 자동 저장하지 않는다.** 읽은 값은 기록 화면의 칸을 채우기만 하고, 저장은
  사용자가 확인 후 누른다. 잘못 읽은 숫자가 조용히 저장되면 추이가 오염되고, 나중엔 무엇이
  진짜였는지 알 수 없다. (음식 사진 분석과 같은 원칙)
- **0 은 "못 읽었다"로 다룬다.** 0분·0km 기록을 만들지 않는다
  (`WorkoutPhotoAnalysisService.positiveInt/positiveDecimal`).
- **모르는 카테고리는 버린다.** 앱의 칩(근력/유산소/유연성) 밖의 값이 들어오면 null 로
  떨어뜨린다 — 아니면 어느 칩도 선택되지 않은 채 유산소 판정까지 깨진다.
- **칼로리는 저장하지 않는다.** 앱마다 추정 공식이 달라 신뢰할 수 없다. 1급 데이터는
  시간·거리이고 페이스는 우리가 계산한다.
- **읽기 실패와 기록은 독립이다.** 분석이 실패해도 사진이 붙은 기록은 그대로 저장된다.
  사진 자체가 증거이기 때문이다.
- **PlanGuard 를 통과시킨다.** `AI_WORKOUT_PHOTO`(FREE 2회/일, PRO 30회/일) — 음식 사진과
  같은 급. 게이팅을 우회하면 사용량 계측(FEATURE_USED)에서도 사라진다.

### 남은 위험

- **프라이버시**: 스트라바 스크린샷에는 지도 경로(=집 위치)가 찍힌다. 지금은 사진이 기록에만
  붙지만, 커플 피드로 흐르게 만들 때는 반드시 경고나 기본 비공개가 필요하다.
- **중복 기록**: 같은 운동을 사진과 세션으로 두 번 남기는 경우를 아직 막지 않는다.
  원탭 체크인은 "오늘 이미 기록 있음" 상태로 카드가 바뀌어 자연스럽게 막힌다.

## 5. 추측 대신 측정할 것

이 방향이 맞았는지는 이미 쌓고 있는 데이터로 판정할 수 있다(`event_logs`, `workouts`).

1. **커플 양쪽 활성 비율** — 최근 30일 둘 다 기록이 있는 커플 비율. 커플 기능의 실제 성립률.
2. **주당 기록 수 분포** — 1회성인지 습관인지.
3. **경로별 비중** — 원탭 / 사진 / 세션(entries 있음). 느슨한 경로가 실제로 쓰이는지.
4. **근력 : 유산소 비중** — V83 이후의 변화.

3·4번은 이번 변경의 성패를 직접 가리키는 지표다. 배포 후 2~4주 뒤 확인한다.

# 커플 게임 방향 결정 + 협동 스도쿠 설계 (2026-09-09)

한 세션에서 "커플 미니게임을 넣을까"에서 출발해 협동 스도쿠 구현까지 내려간 결론입니다.
중간 결정(왜 A 대신 B인지)은 커밋에 남지 않으므로 여기에 둡니다. CLAUDE.md 5절 규칙.

## 0. 결론 먼저

- **미니게임은 넣는다. 단 "이기는 게임"이 아니라 "같이 푸는 게임"으로.** 승패 중심은
  2026-08-26 "운동에 대결은 톤이 안 맞는다"(`WorkoutScreen.tsx` 주석) 결정과 겹치고,
  실력 차가 관계 앱에서 마찰이 된다.
- **그래픽을 요구하는 게임은 피한다.** 육성(캐릭터·나무·섬)을 접은 이유가 그것이었고
  (README "게임화 — 육성 시스템 (보류)"), 후보 중 그래픽이 가장 많이 드는 건 오히려 육성이다.
- **첫 타자는 협동 스도쿠.** 그림 0, 콘텐츠 준비 0(생성기가 무한히 만든다), 비동기와
  실시간 둘 다 자연스럽다. 이 문서 3절부터가 그 설계다.
- 다음 순서는 사진 직소(둘의 앨범 사진 = 그래픽 비용 0) → 오목(가벼운 대결, 5분) 순.

### 1-5. 키우기는 "게임"이 아니라 "진행 표시"로

XP·레벨 계산은 이미 `GET /summary/level`에 있고 `MyScreen` 카드에 묻혀 있다. 새 시스템이
아니라 이걸 홈으로 올리고 커플 합산 + 게임 XP를 더하면, 게임·운동·식단이 한 개구리를 키우는
재료가 된다. 그림은 손그림 → `scripts/couple-emoji-experiment/sketch.mjs` →
`normalize_stickers.py` 파이프라인으로 레벨 구간 5컷. 애니메이션 없음(레벨업 순간 lottie 1회).
**시들기·역성장은 넣지 않는다** — 스트릭이 이미 끊기는 역할이라 이중 처벌이고, 커플 공동
육성에서 상대 때문에 내 것이 죽는 상황은 마찰의 원인.

## 2. 통화 중 다른 화면을 열 수 있는가 — 코드 확인 결과

**Stream SDK는 막지 않고, 막는 건 우리 오버레이 한 곳이다.**

- 통화(오디오·비디오 송수신)는 `Call` 객체에 붙어 있고 로그인 내내 살아 있는
  `StreamVideoClient`(`callStore.ts`)가 든다. 화면이 사라져도 통화는 안 끊긴다.
- `StreamCall` 프로바이더가 생명주기(안드로이드 포그라운드 서비스, 앱 상태, PiP 이벤트)를
  처리한다. 이건 마운트 유지.
- `CallContent`는 순수 UI. 언마운트 부수효과는 InCallManager 정지(스피커·근접센서 라우팅)뿐.
- `CallOverlay.tsx`가 통화가 있으면 `RootOverlayModal`을 `transparent={false}`로 띄워
  앱 전체를 가린다. 최소화 상태 없음. `PLAN.md:770` "통화 중 다른 화면 동시 사용(PIP) — 후순위".

필요 변경: `StreamCall` 유지 + `CallContent` 대신 `useCallStateHooks`로 미니 바(상대 참가
상태·마이크·끊기) + InCallManager 시작/정지를 우리 코드로. 방식은 ① 게임을 오버레이 안에
넣기(내비 안 건드림, iOS 이중 프레젠테이션 회피 — 첫 구현 권장) ② 오버레이를 플로팅 바로
줄이고 내비게이터 이동. 통화는 네이티브 전용(웹 스텁)이라 게임도 네이티브에서만 통화와 묶인다.

## 3. 협동 스도쿠 설계

### 3-1. 규칙

- 커플당 **진행 중인 판은 하나**. 누구든 새 판을 열 수 있고, 열면 상대에게 푸시.
- 같은 판을 **둘이 자유롭게** 채운다. 차례 없음. 칸마다 누가 채웠는지 색으로 남는다.
- 주어진 숫자(given)는 못 건드린다. 나머지는 누구든 쓰고 지우고 덮어쓸 수 있다
  (상대가 틀린 걸 내가 고칠 수 있어야 협동이다).
- 틀린 숫자도 **그대로 들어간다**. 화면은 정답과 다른 칸을 빨갛게 표시한다(일반 스도쿠 앱
  관행). 서버는 정답을 내려주지 않고 "틀린 칸 인덱스"만 내려준다.
- 81칸이 전부 정답이면 **완성**. 채팅에 결과 카드 한 장(누가 몇 칸), 상대에게 푸시.
- **포기** 가능(ABANDONED). 포기한 판은 기록에 남지 않는다.
- 난이도 3단계 = 주어진 숫자 개수: 쉬움 40 · 보통 32 · 어려움 26. 항상 유일해.

의도적으로 뺀 것: 메모(연필) 표기, 타이머·점수·랭킹(협동에 압박을 넣지 않는다), 힌트.

### 3-2. 데이터 (V86)

```sql
CREATE TABLE couple_games (
    id           BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    couple_id    BIGINT       NOT NULL REFERENCES relations (id),
    game_type    VARCHAR(20)  NOT NULL,   -- 'SUDOKU' (오목·직소가 같은 테이블을 쓴다)
    difficulty   VARCHAR(10)  NOT NULL,   -- EASY / NORMAL / HARD
    puzzle       VARCHAR(81)  NOT NULL,   -- 주어진 숫자. 빈칸 '0'
    solution     VARCHAR(81)  NOT NULL,   -- 정답. 클라이언트에 내려가지 않는다
    board        VARCHAR(81)  NOT NULL,   -- 현재 상태
    owner_map    VARCHAR(81)  NOT NULL,   -- '0' 없음/given, '1' 판을 연 사람, '2' 상대
    status       VARCHAR(20)  NOT NULL,   -- IN_PROGRESS / COMPLETED / ABANDONED
    created_by   BIGINT       NOT NULL REFERENCES users (id),
    created_at   TIMESTAMP    NOT NULL DEFAULT NOW(),
    updated_at   TIMESTAMP    NOT NULL DEFAULT NOW(),
    completed_at TIMESTAMP
);
CREATE INDEX idx_couple_games_couple_status ON couple_games (couple_id, status, created_at DESC);
```

- 81자 문자열 하나로 판을 든다. 칸 테이블(81행)이나 수 이력 테이블은 만들지 않는다 —
  "누가 몇 칸"은 `owner_map`으로 충분하고, 테이블이 하나면 Purger도 한 줄이다.
- `owner_map`의 '1'/'2'는 `relations.user_a_id/user_b_id`가 아니라 **`created_by` 기준**이다.
  `Relation.transferOwnership`가 A/B를 바꿀 수 있어서 A/B에 매달면 색이 뒤집힌다.
- `JSONB`·`ON CONFLICT` 없음(H2 호환). `TEXT` 대신 `VARCHAR(81)`.
- 시드는 저장하지 않는다. 생성기는 `Random`을 받으므로 나중에 "오늘의 판"(날짜 시드)을
  붙일 때 컬럼 하나만 더하면 된다.

### 3-3. 동시 입력

둘이 **다른 칸**을 동시에 쓰면 `board` 문자열 전체를 덮어써서 한쪽이 사라진다(lost update).
`findWithLockById`(`PESSIMISTIC_WRITE`)로 행을 잠그고 읽는다. H2·PostgreSQL 모두 `FOR UPDATE`.
같은 칸을 동시에 쓰면 나중 것이 이긴다 — 협동이라 문제 없다.

### 3-4. API (`/api/v1/games/sudoku`)

| 메서드 | 경로 | 동작 |
| --- | --- | --- |
| GET | `/current` | 진행 중인 판. 없으면 `data: null` |
| POST | `/` `{difficulty}` | 새 판. 진행 중인 판이 있으면 그걸 돌려준다(중복 생성 방지) |
| PUT | `/{id}/cells/{index}` `{value}` | 칸 입력. value 0 = 지우기. 응답 = 갱신된 판 |
| POST | `/{id}/give-up` | 포기 |
| GET | `/history` | 완성한 판 최근 20개 |

응답 `SudokuGameResponse`: id, difficulty, status, puzzle(81), board(81), owners(81 — 요청자
기준 `'0'|'M'|'P'`), wrongCells(int[]), filled, myCells, partnerCells, partnerName, createdAt,
completedAt. **solution은 절대 내려가지 않는다.**

### 3-5. 실시간·알림·계측

- 모든 입력 후 `CoupleEventPublisher.publish(coupleId, CoupleEvent.GAME)`. 수신측은
  `/current`를 다시 읽는다(이벤트에 데이터를 싣지 않는 기존 규칙).
- 푸시(`NotificationCategory.PARTNER`, `PushLinks.GAME_SUDOKU = "game/sudoku"`): 새 판을
  열었을 때, 완성했을 때. **칸 입력마다는 보내지 않는다.**
- 완성 시 채팅 `MessageType.GAME_CARD`. content는 `STREAK_CARD`처럼 **그대로 읽히는 문장**
  ("협동 스도쿠 완성! 동연 51칸 · 수진 4칸 (보통)") — 구버전 앱에서도 말풍선으로 읽힌다.
  화면은 가운데 배너(`ChatRoomScreen`의 STREAK_CARD 분기와 같은 모양).
- `Feature.COUPLE_GAME("협동 게임", unlimited, unlimited, 커플 스코프)`. 게이팅은 없지만
  새 판 생성 시 `planGuard.require`를 지나 `FEATURE_USED`가 남는다 — 육성을 접을 때의
  "효과를 측정할 방법이 없다"를 반복하지 않기 위해. 성공 지표: **게임한 커플의 7일
  재방문율 vs 안 한 커플**. 프론트 `FeatureKey`도 함께 추가(`PlanFeatureSyncTest`).

### 3-6. 생성기 (`SudokuGenerator`)

1. 대각선 3×3 박스 3개를 무작위로 채운다(서로 독립).
2. 후보 순서를 섞은 백트래킹으로 나머지를 채워 완성 해를 만든다.
3. 칸을 무작위 순서로 하나씩 비우되, 비울 때마다 **해가 2개 이상인지** 세는 솔버로 확인.
   유일하지 않으면 되돌린다. 목표 given 수에 닿거나 전 칸을 시도하면 멈춘다.

9×9는 밀리초 단위. `Random`을 주입받아 결정적 테스트가 된다.

### 3-7. 화면 (`SudokuScreen`, 홈 스택)

- 진입: 홈 QuickActions에 "스도쿠"(홈 세로 여백 문제와 무관 — 가로 한 칸). 딥링크 `game/sudoku`.
- 판이 없으면 난이도 3버튼. 있으면 9×9 격자 + 숫자패드(1~9, 지우기).
- 색: given = 굵은 textPrimary, 내 칸 = primary, 상대 칸 = accent, 틀림 = coral.
  선택 칸의 행·열·박스는 옅게.
- 상단: 난이도 · 채움 n/81 · "나 a칸 · 상대 b칸".
- `subscribeCouple`로 `GAME` 이벤트 → `/current` 재조회. 내 입력은 응답으로 즉시 반영.
- 완성: 축하 배너 + "새 판" 버튼. 하단에 완성 기록(최근 20).
- 순수 `View`/`Text`. SVG·Skia 불필요.

### 3-8. 삭제 경로

`RelationRecordPurger`: `couple_games`는 relations·users만 참조하고 자식이 없다.
`daily_answers` 줄 옆에 `delete from couple_games where couple_id = :rid`.
`UserDataPurger`: 관계가 먼저 지워지면 남는 행이 없지만, `created_by`가 users를 참조하므로
안전하게 `delete from couple_games where created_by = :uid`도 둔다.

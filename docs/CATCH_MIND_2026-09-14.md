# 캐치마인드 — 비동기로 (2026-09-14)

미니게임 3번째. 커넥트4·점 잇기·리버시·캐치마인드를 놓고 고른 결과와, **왜 실시간이 아니라
비동기인지**를 남긴다. 커밋은 무엇을 넣었는지만 남기므로(CLAUDE.md 5절) 판단은 여기 둔다.

## 0. 결론 먼저

- **캐치마인드를 넣는다. 단 비동기로.** A가 다 그려서 보내면 B가 아무 때나 열어서 맞힌다.
  실시간 스트로크 중계는 하지 않는다.
- **커넥트4·리버시·점 잇기는 넣지 않는다.** 이유는 3절.
- **Skia 는 쓰지 않는다.** 애초에 이 앱에 없고, `react-native-svg` 로 충분하다.

## 1. 왜 비동기인가 (이 문서의 핵심)

제안 당시의 전제는 "Skia 가 이미 있으니 캔버스는 거저, 스트로크 실시간 동기화만 필요"였다.
둘 다 사실과 달랐다.

**실시간이 문제다.** 스트로크를 중계하려면 둘이 **동시에 접속**해 있어야 한다. 그런데
`COUPLE_GAMES_DESIGN_2026-09-09.md` 1-2절이 실시간 2인 게임을 접은 이유가 정확히
"동시 접속 드묾"이었다. 이 앱의 커플은 **떨어져 있을 때** 앱을 쓴다. 같은 근거로 접은 것을
캐치마인드에서만 예외로 둘 이유가 없다.

비동기로 돌리면 전제가 통째로 사라진다.

| | 실시간 | 비동기(채택) |
| --- | --- | --- |
| 둘이 동시 접속 | 필요 | 불필요 |
| 스트로크 중계 | STOMP 로 초당 수 회 | **없음** — 완성본 한 번 |
| 서버의 "그리는 중" 상태 | 필요 | **없음** — 판은 제출되는 순간 생긴다 |
| 끊겼을 때 | 그리던 게 날아간다 | 앱 안에 남아 있다 |

그래서 서버 경로가 "다 그린 그림 제출"부터 시작한다. `GameStatus` 에 상태를 더하지 않아도
되고("그리는 중"이 없다), 기존 "커플당 진행 중인 판 하나" 규칙이 그대로 적용된다.

**나중에 실시간을 얹을 수는 있다.** 같은 획 데이터에 전송 경로만 추가하면 되고, 그건 "둘이
같이 접속해 있을 때의 보너스"지 전제가 아니다.

## 2. 왜 Skia 가 아니라 SVG 인가

`package.json` 에 `@shopify/react-native-skia` 가 **없다**(`modules/` 에도 `korean-spell` 뿐).
2026-09-09 설계 문서의 "Skia 가 Dubly 에 없다"가 그대로다.

넣을 수도 있었지만 넣지 않았다.

- 웹 번들에 **CanvasKit WASM 수 MB** 가 따라붙는다. 그러면 게임 화면을 `.web.tsx` 스텁으로
  빼야 하고(설계 1-2 가 boo 에 대해 우려한 그것), 캐치마인드는 웹에서도 돌아야 할 이유가 있다.
- 네이티브 의존성이 늘면 **EAS 빌드**가 필요해진다(`CLAUDE.md` 6절). SVG 로 하면 JS 변경이라
  `update:production` 으로 배포된다.
- 캐치마인드의 획은 폴리라인이다. Skia 의 실시간 페인팅 성능이 필요한 물건이 아니다.

`react-native-svg ^15.15.4` 와 `PanResponder` 로 그린다. 둘 다 이미 들어와 있다.

## 3. 넣지 않은 게임과 이유

1군(커넥트4·점 잇기·리버시)은 전부 **대결 게임**이다. 2026-09-09 의 기본 판정은
"이기는 게임이 아니라 같이 푸는 게임"이었고 오목은 예외로 하나 둔 것이었다. 셋을 다 넣으면
허브가 **대결 4 : 협동 1** 이 되어 방향이 뒤집힌다.

| 후보 | 판정 |
| --- | --- |
| 커넥트4 | 보류. 1군 중 가장 싸다(`OmokRules` 파라미터화 + 중력). 넣는다면 이것부터. **중력은 서버가 계산해야 한다** — 클라가 인덱스를 보내면 공중에 띄우는 치팅이 된다 |
| 점 잇기 | ✗ 재사용이 가장 적다. 상태가 "칸"이 아니라 **"변"**이라 `stones` 문자열 모델이 안 맞고(수평변·수직변 배열 둘), 추가 턴 규칙 때문에 `next_turn` 토글도 갈라진다 |
| 리버시 | ✗ 뒤집기보다 **"합법수 없으면 패스"**(양쪽 다 없으면 종료)가 진짜 비용. 실력 차가 오목보다 크게 벌어져 설계 1-4 가 바둑을 뺀 것과 같은 결이다 |
| 체스·장기 | ✗ 말별 이동 + 특수룰(캐슬링·앙파상). 비용도 톤도 안 맞는다 |

**"오목 렌더러를 그대로 쓴다"는 과대평가다.** 오목은 *교차점*에 두고 나무판에 격자선을
그리는데 커넥트4는 *칸* 안의 원형 구멍이다. 실제로 재사용되는 건 그 아래 골격이다 —
`CoupleGame` 단일 테이블 상속, 행 잠금, "판 하나" 규칙, `GAME` 소켓 이벤트, `GAME_CARD`,
허브 카드, 반응 바, 스트릭(종목 무관이라 **새 게임이 자동 편입**), `moves`+복기 패턴.

## 4. 규칙

- 그리는 사람이 **제시어를 고른다**(후보 3개) 또는 **직접 적는다**. 직접 입력을 연 이유:
  둘만 아는 단어가 이 앱에서는 제일 세다.
- 후보 3개는 **서로 다른 카테고리**에서 뽑는다. 같은 카테고리 셋이면 "동물 셋 중 하나"가
  되어 고르는 재미가 없고 난이도도 한쪽으로 쏠린다.
- 맞히기는 **시도 횟수 제한이 없다.** 횟수로 압박을 주면 "같이 하는 것"이 시험이 된다.
  막혔을 때의 출구는 **초성 힌트**와 **정답 보기(포기)** 다.
- 초성을 열어도 **실패로 치지 않는다.** 막힌 채로 끝나는 것보다 낫다.
- 정답 판정은 **띄어쓰기·문장부호를 무시**한다("고 양이!" = "고양이"). 유의어는 받지 않는다
  ("강아지"에 "개") — 거기까지 가면 무엇이 정답인지 서로 납득할 수 없다.
- **진행 중인 판이 있으면 새 문제를 거절한다.** 스도쿠·오목은 "그 판을 돌려주면" 되지만
  (둘이 같은 판을 본다) 여기서는 판마다 문제와 그림이 다르다 — 남의 문제를 돌려받으면
  방금 그린 그림이 조용히 사라진 것처럼 보인다.
- **그린 쪽도 접을 수 있다.** 상대가 며칠째 안 열면 그림 하나 때문에 다음 판을 못 낸다.
  접으면 정답이 상대에게 푸시로 공개된다.
- 맞히면 채팅 `GAME_CARD` + 그린 사람에게 푸시. 접은 판은 기록에 남지 않는다(두 게임과 같은 규칙).

## 5. 데이터 (V93)

`couple_games` 단일 테이블 상속에 얹는다(`game_type = 'CATCH_MIND'`). 테이블을 안 만들었으니
Purger 는 손대지 않는다 — 기존 `delete from couple_games where couple_id = :rid` 한 줄이
그대로 커버한다(`CatchMindFlowTest` 가 확인).

| 컬럼 | 용도 |
| --- | --- |
| `word VARCHAR(40)` | 제시어. **맞히는 사람에게 절대 안 내려간다**(스도쿠 `solution` 과 같은 취급) |
| `strokes TEXT` | 그림. `"색,굵기,x1,y1,x2,y2;..."` |
| `wrong_guesses VARCHAR(500)` | 틀린 시도, 줄바꿈 구분. 최근 10개만 |
| `guess_count INTEGER` | 시도 횟수 |
| `hint_used BOOLEAN` | 초성을 열었는가 |

### 5-1. 그림 형식

**JSON 이 아닌 이유**: (1) `CLAUDE.md` 4절이 `JSONB` 를 금지하므로 어차피 문자열이고,
(2) 같은 그림이 JSON 배열이면 2~3배 커진다.

**좌표는 0~1000 정규화 정수**다. px 로 저장하면 태블릿에서 그린 그림이 폰에서 잘린다.

**서버는 그림을 해석하지 않는다.** 그럴 이유가 없다. 다만 형식은 검사한다 —
- **용량**: 상한이 없으면 한 판이 수 MB 를 먹는다(덧칠하면 획이 계속 쌓인다). 60KB 에서 끊는다.
  앱도 획 120개에서 먼저 막는다 — 한참 그린 뒤 전송 단계에서 거절당하지 않게.
- **렌더 실패**: 값이 홀수 개면 상대 화면에서만 그림이 깨진다. 보낸 사람은 멀쩡히 그렸는데
  상대만 못 보고, 원인을 아무도 모른다.
- **점 하나짜리 획(탭)도 받는다** — 앱이 만들어내는 형식이므로. 테스트로 고정했다.

### 5-2. 틀린 시도

같은 답을 두 번 적으면 목록에는 **한 번만** 남는다(횟수는 그대로 센다). 오타를 고치다 보면
같은 답이 반복되는데, 그대로 늘어놓으면 그린 사람이 볼 목록이 그것만으로 찬다.

## 6. 화면

`CatchMindScreen` 하나가 판 상태에 따라 셋 중 하나를 그린다.

- 판 없음 → **그리기**(제시어 + 캔버스 + 전송)
- 내가 낸 판 → **기다리기**(내 그림 + 상대의 틀린 시도 — 이게 이 게임 재미의 절반이다)
- 상대가 낸 판 → **맞히기**(그림 + 입력창 + 초성)

`DrawingCanvas` 는 확정된 획과 "그리는 중인 획"을 **한 state 에 같이** 든다. 나눠 두면 손을
떼는 순간 두 번의 setState 사이에 획이 사라졌다 나타나고, PanResponder 핸들러가 최신 값을
보려면 ref 를 렌더 중에 읽어야 한다. 하나로 묶으면 전부 함수형 갱신으로 끝난다.

## 7. 남은 것

1. **실기기·웹에서 실제로 그려보지 않았다.** 이번 세션에서는 다른 세션이 웹 dev 서버 포트를
   점유하고 있어 브라우저 확인을 못 했다. `PanResponder` + SVG 경로는 typecheck 로 잡히지
   않는 종류의 문제(제스처가 스크롤뷰에 먹히는 등)가 남을 수 있는 자리다 — **첫 실행 시
   캔버스부터 만져볼 것.**
2. PostgreSQL 검증. `TEXT` 컬럼과 `findByIdForUpdate` 가 새로 들어갔다(`docs/RUNNING.md`).
3. 제시어 수가 130개 남짓이다. 많이 쓰이면 늘려야 한다 — `CatchMindWords` 한 파일이다.
4. 실시간 중계(같이 접속 중일 때의 보너스), 역할 자동 교대, 그림에 반응 남기기는 안 했다.

## 0. 결론 한 줄

**옮기지 말고 홈에도 보이게 한다. 단, 단식 중일 때만 보인다.**
자리는 사용자 제안대로 한다. 각 열의 `[운동][식단][물 알약]` 아래 **최근 기록 줄("아침 · 오늘 08:28")은 그대로 두고**,
**그 밑에 단식 중일 때만 남은 시간이 줄어드는 카운트다운 한 줄**(`⏱ 2:40 남음`)을 더한다. 목표에 닿으면 `🎉 16시간 달성`으로 바뀐다.
열 색(나 코랄·상대 하늘)의 2px 진행 막대는 선택이다. 높이는 단식 중에만 약 16px 는다.
시작·종료·설정·리포트는 럽바디에 그대로 둔다. 홈 줄을 누르면 럽바디로 간다.
상태는 DietScreen 로컬 state 를 공용 `store/fastingStore` 로 올려 두 화면이 같은 값을 보게 한다(물 `waterStore` 와 같은 이유).
**OTA 만으로 된다.** 서버는 필수 변경이 없다. 다만 이번에 찾은 **동시 시작 경합(§6-1)**은 홈과 무관하게 있는 문제라 작은 서버 수정을 같이 권한다(마이그레이션 없음).

## 2. "옮기기" vs "홈에도 보이기"

| | 옮기기(럽바디에서 뺌) | **홈에도 보이기(권장)** |
|---|---|---|
| 시작 모달·연동 설정 | 홈에 모달을 새로 둬야 한다. 홈은 스크롤 없는 고정 화면이라 설정 스위치·안전 안내를 둘 자리가 없다 | 럽바디에 그대로 |
| 리포트·지난 결과 | 진입점이 사라진다(리포트 링크는 지금 이 카드에만 있다) | 그대로 |
| 물과의 짝 | 카드가 "물만" 남아 어색하다. 물은 이미 홈과 럽바디 **두 곳에** 있다 | 물과 같은 모양: 홈 = 한눈에, 럽바디 = 자세히 |
| 저녁 제안·자동 종료 | 식사 저장에서 일어나므로 위치와 무관 | 같음 |
| 작업량 | 크다(모달 이전 + 리포트 진입 재배치) | 작다(표시 한 줄 + 공용 스토어) |

→ **옮기지 않는다.** 단식의 "조작"은 하루 두 번(시작·끝)뿐이고, 그중 대부분은 이미 식사 기록이 대신한다(저녁 제안·아침 자동 종료).
홈에 필요한 것은 조작이 아니라 **"언제 먹을 수 있는지"를 앱을 열자마자 보는 것**이다.

## 3. 홈 어디에 — 후보 비교

`CoupleHero` 한 열의 지금 모양:

```
  [아바타 + 오늘 챙김 링(68)]
    이름 · 🌱스트릭
    (무드 한마디)
   (운동)(식단)▮  ← todayRow — 물 알약이 "세 번째이자 마지막 칸"(CoupleHero.tsx:270 주석)
    아침 · 오늘 08:28   ← meta (최근 기록, 없으면 줄을 비운다)
```

| 후보 | 판단 |
|---|---|
| A. todayRow 네 번째 칸(원/알약) | **안 됨.** 물 알약을 넣을 때 "넷째를 넣으면 320 폭에서 원이 겹친다"고 적어 두었다. 원 하나에 "2:40"을 넣으면 글자가 7~8px 로 줄어든다 |
| B. meta 줄을 단식 중에만 단식 줄로 바꾸기 | 높이 0. 대신 단식하는 동안(하루의 2/3) 최근 기록이 안 보인다 — 처음 권장안이었으나 B' 로 바뀜 |
| **B'. meta 줄 아래 단식 카운트다운 한 줄 추가 (사용자 제안, 채택)** | 최근 기록을 잃지 않는다. 사람 단위 상태가 사람 열에 붙고, 나·상대가 대칭이다. 대가는 단식 중에만 높이 +16px(§9-1) |
| C. 아래 한 줄 슬롯(보관함 ⓪ > 여행 > 오늘 일정 > 작년 오늘 …) | 커플 단위 슬롯이고 하나만 보인다. 16시간 내내 단식이 자리를 차지하면 여행·일정을 밀어내고, 아래로 밀리면 정작 안 보인다 |
| D. 아바타 링을 단식 진행 링으로 | 그 링은 "오늘 챙김(아침·점심·저녁 조각)"이 이미 쓰고 있다. 두 의미가 겹친다 |
| E. 상단바 칩 | 물 알약 결정 때 상단바 안을 이미 비교하고 버렸다(§15). 배경 버튼·D-day 와 다툰다 |
| F. 바로가기 3칸 | "여기는 칸을 늘리는 자리가 아니다"(HomeScreen 주석) |

### 3-1. B' 의 모양 — 카운트다운 (텍스트 + 선택 2px 막대, 새 아이콘 없음)

```
   (운동)(식단)▮
    아침 · 오늘 08:28        ← 그대로
    ⏱ 2:40 남음              ← 단식 중에만, 1분마다 줄어든다
```

| 상태 | 내 열 | 상대 열 |
|---|---|---|
| 진행 중 | `⏱ 2:40 남음` — 줄어드는 카운트다운 (+ 막대, 코랄) | Q3 에 따라 `⏱ 2:40 남음`(권장) 또는 `⏱ 단식 중` (+ 막대, 하늘) |
| 1시간 미만 | `⏱ 38분 남음` | 같음 |
| 목표 달성(진행 중) | `🎉 16시간 달성 · 식사하면 끝나요` (막대 가득) | `🎉 16시간 달성` |
| 목표의 2배 초과(방치 의심, §6) | `⏱ 단식 38시간째 · 끝났다면 정리해 주세요` | 줄 숨김 |
| 안 하는 중 | **줄 없음** — 열은 지금과 똑같다 | 같음 |
| 오늘 끝남 | 줄 없음(결과는 끝낼 때 토스트·럽바디 결과 줄이 이미 말한다) | 같음 |

- **카운트다운 = 남은 시간**(경과가 아니라). "곧 먹을 수 있다"가 단식하는 사람이 제일 궁금한 숫자다. 경과는 럽바디 줄에 그대로 있다.
- 단위: **분 단위**(`2:40 남음` → 1분 뒤 `2:39 남음`)를 권장한다. 초 단위(`2:39:58`)는 홈이 열려 있는 동안 매초 그 줄을 다시 그려 배터리를 쓰고,
  16시간 단식에서 초는 의미가 없다. 마지막 1시간만 초 단위로 바꾸는 절충도 있다(결정 Q1-b).
- 글자: 열 폭이 122px(320 폭)라 `⏱ 2:40 남음` 처럼 짧게 쓴다. 접근성 라벨은 "16시간 단식, 2시간 40분 남음, 13시간 20분 경과"로 풀어 말한다.
- ⏱ 는 이모지(글자)다. MDI 글리프를 새로 쓰지 않는다(아이콘 폰트 = fingerprint 입력 → OTA 불가). 아이콘이 꼭 필요하면 이미 쓰고 있는 `clock-outline` 만 쓴다.
- 막대(선택): 열 색 View 두 개(바탕 = 열 색 20% 불투명도). 새 의존성 없음. "함께(라벤더)"는 둘 다 단식 중일 때도 쓰지 않는다. 각자의 줄이 이미 둘을 보여 준다.
- 단계 문구(`fastingStage`)는 홈에 넣지 않는다. 한 줄 자리이고, 몸에 대한 말은 조심스럽게 길게 해야 해서(§2-1) 럽바디 몫이다.
- 누르면: 내 줄은 `Health › DietMain`(`pop: true`, 이 파일의 다른 DietMain 이동과 같은 이유). 상대 줄은 토스트 `○○님 16시간 단식 · 2시간 40분 남았어요`(물 상대 알약과 같은 문법).
  **홈에서 종료 버튼은 두지 않는다.** 한 줄을 잘못 눌러 단식이 끝나면 되돌릴 길이 없다(`reopen` 은 MEAL 로 끝난 것만 된다).

### 3-2. 단식 안 하는 사람에게 "시작" 버튼을 매일 보일까 — 보이지 않는다

- P0 결정 "저녁 제안은 **최근 30일 안에 단식해 본 사람만**"과 같은 원칙이다. 안 하는 사람에게 매일 권하지 않는다.
- 시작은 지금도 두 길로 충분하다. ① 저녁 기록 뒤 제안(홈 사진 바로 저장에서도 뜬다) ② 럽바디 카드.
- 더 필요하면(결정 Q2) 홈 **식단 시트(QuickMealSheet)** 맨 아래에 `간헐적 단식 시작 ›` 한 줄을 두는 방안이 있다. 최근 30일 단식 이력이 있는 사람에게만 보인다.
  시트는 누를 때만 열리므로 홈 밀도를 해치지 않는다. 다만 이것도 "홈에서 시작"이 되므로 §6-1 서버 수정이 선행 조건이다.

## 4. 상태 — 공용 `fastingStore` 로 올린다

물과 같은 문제가 생긴다. 홈과 럽바디가 각자 조회하면, 홈에서 본 값과 럽바디 값이 한동안 어긋날 수 있다(물은 웹에서 7,000 vs 6,500 으로 재현됐다).
단식은 탭 연타가 없어 물만큼 위험하지는 않다. 그래도 진실의 출처를 하나로 두는 편이 단순하다.

```ts
// store/fastingStore.ts (안)
interface FastingState {
  mine: FastingStatus | null;           // null = 아직 못 읽음
  partner: (PartnerFasting & { startedAtMs?: number }) | null; // 받은 시각 - elapsedMin 으로 시작 시각을 앱이 복원
  mineState: 'loading' | 'ok' | 'error';
  load(): Promise<void>;                // active + partner 를 병렬로
  start(plan, hours?, minutesAgo?): Promise<FastingStatus>; // 진행 중 플래그로 한 번만
  end(): Promise<FastingStatus>;
  reopen(): Promise<FastingStatus>;
  reset(): void;                        // 로그아웃 — 다음 계정에 남의 단식이 보이면 안 된다
}
```

- `useFastingSignal` 은 없앤다. `mealFasting.ts` 의 `bump()` 자리를 `useFastingStore.getState().load()` 로 바꾼다. ENDED 결과는 응답 `status` 를 바로 넣을 수도 있다.
- DietScreen 의 `fasting`·`partnerFasting`·`fastingState`·`refreshFasting` 은 스토어 셀렉터로 바꾼다. 시작 모달·연동 설정·리포트는 그대로 둔다.
- 홈 `refresh()` 에 `useFastingStore.getState().load()` 를 더한다. 커플 이벤트 FASTING 은 이미 `refresh()` 를 돌리므로, 상대가 시작하거나 끝내면 홈이 따라온다.
  내 다른 기기에서 바꾼 것도 같은 커플 토픽으로 와서 따라온다.
- **조회 실패 시 기존 값을 유지한다**(스트릭과 같은 규칙, `HOME_WIDGET_COMPLEXITY` §2-1). 카운트다운은 `startedAt + 목표` 로 그리므로 낡은 값이어도 시간은 맞게 흐른다. 실패했다고 줄이 사라졌다 나타나면 더 이상하다.
- **호출 수**: 홈 진입 1회당 HTTP 가 +2건이다(지금 11~13건 수준). 서버에 `GET /fasting/couple`(내 것+상대 것 한 번에)을 두면 +1건으로 줄지만 필수는 아니다(결정 Q4).

## 5. 카운트다운 재렌더 범위

- `FastingCountdown`(가칭) 컴포넌트 **안에서만** 시계를 돌린다. `FastingActiveRow` 와 같은 패턴이다. 홈·CoupleHero·물 알약은 다시 그리지 않는다.
  두 열에 하나씩, 진행 중일 때만 마운트한다(안 하면 타이머도 0개).
- 개선 두 가지(럽바디 줄에도 같이 적용):
  1. `setInterval(60s)` 를 마운트 시점에서 시작하면 화면 숫자가 최대 59초 늦다. 카운트다운은 이게 더 눈에 띈다("2:40"이 1분 가까이 안 바뀜).
     **다음 정각 분까지 setTimeout → 그 뒤 60초 간격**으로 맞춘다. 남은 시간은 올림으로 센다(0:00:30 남았을 때 "0분 남음"이 아니라 "1분 남음").
  2. 앱이 백그라운드에 오래 있으면 타이머가 멈췄다가 돌아와도 다음 틱까지 옛 값이 보인다. `AppState` 가 `active` 가 될 때 즉시 다시 센다.
     홈 탭이 포커스를 잃으면 멈추는 것도 좋다(`useIsFocused`). 홈은 탭이라 언마운트되지 않기 때문이다.
- 0 에 닿는 순간 `🎉 달성`으로 바뀌는 것도 이 컴포넌트 안에서 판단한다(서버를 다시 부르지 않는다). 목표 도달 본인 푸시는 서버가 따로 보낸다.
- 물 알약의 물결 애니메이션은 네이티브 드라이버라 이 타이머와 섞이지 않는다.

## 6. 이상 사용 (abuse-testing A~E 에 맞춰 구현 때 검증할 것)

### 6-1. 동시 시작 — **지금도 있는 서버 경합 (홈과 무관, 수정 권장)**
`FastingService.start` 는 `existsByUserIdAndEndedAtIsNull → save` 다. 잠금이 없고, `fasting_sessions` 에 "진행 중 1개" 유일성 제약도 없다(V38·V145 는 일반 인덱스뿐).
두 요청이 동시에 들어오면 둘 다 "없다"고 보고 **진행 중 행이 2개**가 된다. 그 뒤로는 `findByUserIdAndEndedAtIsNull`(Optional)이
`IncorrectResultSizeDataAccessException` 을 던진다. 결과적으로 `/active`·`/end`·**식사 저장의 자동 종료**가 500 이 된다.
식사 저장은 try/catch 로 삼키므로 저장은 되지만, 그 뒤로 단식이 조용히 끝나지 않는다.
- 연타 경로: 지금은 시작 모달 칩(busy 로 막음)과 저녁 제안 다이얼로그(버튼 하나만 눌림)뿐이다. 하지만 두 기기, 또는 제안 다이얼로그와 모달이 겹치면 난다.
- 수정(마이그레이션 없음, H2·PG 양립): `start`·`reopen` 첫머리에서 사용자 행을 `SELECT … FOR UPDATE`(`@Lock(PESSIMISTIC_WRITE)` 로 `users` 또는 `nutrition_goals` 조회)로 잠근다.
  부분 유니크 인덱스(`WHERE ended_at IS NULL`)는 H2 에서 안 되므로 쓰지 않는다.
  읽기 쪽은 `findFirstByUserIdAndEndedAtIsNullOrderByIdDesc` 로 바꿔, 이미 생긴 중복도 500 없이 읽히게 한다. 운영 DB 에 중복이 있는지 한 번 SQL 로 확인한다.
- 앱: 스토어의 `start` 는 진행 중 플래그로 한 번만 보낸다(DietScreen 모달·저녁 제안·QuickMealSheet 모두 같은 함수를 쓴다).

### 6-2. 나머지
| 상황 | 기대 동작 |
|---|---|
| 다른 기기에서 시작/종료 | FASTING 커플 이벤트 → 홈 `refresh()` → 줄이 나타남/사라짐. 소켓이 끊겨 있으면 다음 포커스 때 반영 |
| 자정 넘김 | 남은 시간은 `startedAt + 목표 − now` 라 날짜와 무관하다. 홈 줄은 "오늘 끝난 결과"를 쓰지 않으므로 KST 경계 문제가 없다 |
| 목표 초과 수십 시간 방치 | 서버는 자동으로 닫지 않는다. 0 이후엔 `🎉 달성`, `목표 × 2` 를 넘으면 "끝났다면 정리해 주세요"(내 열), 상대 열은 줄을 숨긴다. 음수 카운트다운("−3:10")은 보이지 않는다 |
| 오프라인 | 기존 값을 유지하고 시계는 계속 흐른다. 홈에서 조작이 없으므로 실패 토스트도 없다 |
| 상대가 커플 해제 | `partner.connected=false` → 상대 열 줄을 숨긴다. CoupleHero 자체가 안 그려지는 미연결 홈에서는 단식 표시가 없다(혼자 쓰는 사람은 럽바디에서 본다) |
| 로그아웃 → 다른 계정 | `reset()` 으로 비운다. 늦게 온 옛 응답은 세대 번호로 버린다(waterStore 와 같음) |
| 기기 시각이 틀림 | 남은 시간 = 서버 startedAt + 목표 − 기기 now 라 기기 시계가 틀리면 숫자도 틀린다. 목표보다 큰 값은 목표로 자른다. 서버 시각과의 차를 보정하는 방법은 과하다 — 하지 않는다 |
| 상대 시작 시각 | `PartnerFasting` 에 `startedAt` 이 없어 "받은 시각 − elapsedMin" 으로 복원한다. 1분 이내 오차는 허용한다. 서버에 `startedAt` 을 더하면 정확해진다(선택, Q4와 함께) |
| 단식 중 식사 기록(홈 사진) | 서버가 끝내고(ENDED) 토스트가 뜬다 → 스토어 갱신 → 카운트다운 줄이 사라진다. [되돌리기] 를 누르면 다시 나타난다 |

## 7. 안드로이드 홈 위젯(`src/widget/`)에 넣는 대안

- 위젯은 `react-native-android-widget` 이고 JS(`DoublyWidget.tsx`)로 그린다. 그래서 **모양을 바꾸는 것은 JS 변경**이다.
  다만 위젯 headless task 가 OTA 로 받은 번들을 쓰는지는 이 저장소에서 확인한 기록이 없다. 실기기 확인이 필요하다.
  위젯 크기·종류를 바꾸는 것(`app.json` 플러그인 `widgets`)은 **빌드**다.
- 갱신 주기는 `updatePeriodMillis: 1800000`(30분, 안드로이드 최소값)이다. 데이터도 앱이 홈을 불러올 때 남긴 스냅샷뿐이다.
  → **카운트다운은 불가능**하다. 표시한다면 흐르지 않는 값이어야 한다. 예: `단식 중 · 오전 10:40 끝나요`(`formatFastingEnd` 재사용).
  다른 기기나 식사 기록으로 끝나도 앱을 열기 전까지는 "단식 중"으로 남는다.
- iOS 에는 위젯이 없다. 위젯이 하는 일은 "D-day 와 우리의 스트릭"이다(설명 문구).
- 판단: **후순위.** 1차는 앱 홈만 한다. 위젯은 사용자가 원하면 2차로, "끝나는 시각" 정적 표기만 한다.
  잠금화면에서 줄어드는 카운트다운은 iOS Live Activity·안드로이드 진행 알림(크로노미터)이 정답에 가깝지만, 둘 다 네이티브라 빌드가 필요하다.

## 9. 위험

1. **한 줄 추가의 대가** — 단식 중에만 열 높이가 약 16px 는다. 홈은 스크롤이 없고 남는 높이를 사진 자리(`photoArea`)가 먹으므로,
   늘어난 만큼 사진이 줄 뿐 겹치지는 않는다(`panelSpacer`·flex 구조). 320×640 에서 무드 한마디·최근 기록·단식 줄이 다 있는 열이 가장 높으므로 그 조합으로 확인한다.
   두 열 중 한쪽만 단식 중이면 열 높이가 달라진다. 열은 위쪽 정렬이라 아래쪽 끝만 들쭉날쭉하다. 거슬리면 둘 중 하나라도 단식 중일 때 양쪽에 줄 높이를 예약한다.
   최근 기록이 없는 열(meta 빈 줄)에서는 단식 줄이 그 자리로 올라간다.
2. **상대에게 보이는 것** — 단식 목표·경과는 이미 상대 럽바디 줄과 푸시로 공개된 정보라 새 노출은 아니다. 하지만 홈은 매번 보이는 자리라 체감 노출이 커진다.
   방치 상태(목표 2배 초과)만 상대 열에서 숨긴다(Q3).
3. **몸에 대한 말** — 홈 한 줄에는 단계 문구를 넣지 않는다. 오래 방치한 단식에 "대단해요" 같은 칭찬도 붙이지 않는다(장시간 단식을 부추기지 않음, 단식 분석 §2-4).
4. DietScreen 리팩터(스토어 이전)는 P0·P1 에서 다듬은 동작을 건드린다 — 설정 스위치 직렬화, 지난 결과 줄, 되돌리기 뒤 갱신. S1 뒤에 단식 분석 §7·§8 검증 항목을 다시 돌린다.

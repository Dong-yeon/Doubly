# 커플 게임 확장 — 반응·무르기·오늘의 판 (2026-09-14)

2026-09-09 에 협동 스도쿠·오목·미니게임 허브를 넣었다(`COUPLE_GAMES_DESIGN_2026-09-09.md`).
"새 게임을 더 넣을까"가 아니라 **"이 둘을 어떻게 더 쓰게 만들까"**로 출발한 세션의 결론이다.
중간 판단은 커밋에 남지 않으므로 여기 둔다(CLAUDE.md 5절).

## 0. 결론 먼저

기존 두 게임의 가장 큰 공백은 **판 위에서 아무 말도 오가지 않는다**는 것이었다. 협동 스도쿠인데
"여기 틀린 것 같아"를 할 수 없고, 오목은 대결인데 "한 수만 무르자"가 없었다. 세 가지를 넣었다.

| # | 무엇 | 왜 |
| --- | --- | --- |
| 1 | 판 위 즉석 반응 | 두 게임을 동시에 살리는 가장 싼 레버. 에셋·저장 둘 다 0 |
| 2 | 오목 수 이력(`moves`) | 컬럼 하나로 무르기·복기·최근 수 표시가 한꺼번에 열린다 |
| 3 | 오늘의 판 + 게임 스트릭 | "왜 내일 또 들어오지"에 답한다 |

검토했으나 **넣지 않은 것**과 이유는 4절.

## 1. 판 위 즉석 반응

- 화면 하단에 6개(👏 😮 🤔 😂 ❤️ 😤). 누르면 상대 화면에 떠올랐다 사라진다.
- **저장하지 않는다.** 채팅 기록도, 푸시도 없다. 상대가 지금 그 판을 보고 있을 때만 의미가 있는
  신호이고, 안 보고 있을 때까지 알림으로 따라가면 그건 반응이 아니라 재촉이다.
- 목적지를 `/sub/couple/{relationId}/game-reaction` 으로 **나눴다**. 공용 커플 채널의
  `CoupleEvent` 는 "타입만 보내고 수신측이 REST 로 다시 조회한다"가 규칙인데(설계 3-5),
  저장하지 않으니 다시 조회할 곳이 없다. 규칙을 깨는 대신 채널을 하나 더 판다.
- 이모지 목록은 **서버**(`GameReaction`)가 쥔다. `GET /games/reactions`. 앱에 박으면 버전이
  갈리고, 임의 문자열을 브로드캐스트하면 내용·길이를 통제할 수 없다. 앱에는 같은 값의
  fallback 을 둬서 목록 조회가 실패해도 바가 통째로 사라지지 않게 했다.
- 연타는 500ms 로 거르되 **200 으로 돌려준다**. 누른 사람 화면은 이미 애니메이션이 돌았는데
  거기에 실패 토스트를 얹으면 더 이상하다. 앱도 전송 실패를 알리지 않는다.
- `gameType` 을 함께 실어, 상대가 다른 게임 화면에 있으면 무시된다.

`GameReactionBar` 하나를 두 화면이 같이 쓴다. 구독·해제·애니메이션을 컴포넌트가 들고 있어서
화면은 `gameType` 만 준다.

## 2. 오목 — 수 이력(V91)

`couple_games.moves VARCHAR(1024)` (착수 인덱스를 쉼표로 이음) + `undo_requested_by VARCHAR(1)`.
225수 × 최대 4자 = 900자라 1024 로 잡았다.

**색은 저장하지 않는다.** 첫 수가 흑(선공 = 상대)이고 이후 번갈아 두므로 순번의 홀짝이 색이다.
무르기로 끝에서 하나가 빠져도 이 규칙은 유지된다. 복기 재생이 이걸 그대로 쓴다.

`undo_requested_by` 가 사용자 id 가 **아닌** 이유 두 가지:
1. `owner_map`·`next_turn`·`winner` 가 모두 `'1'`(판을 연 사람)/`'2'`(상대) 표기다.
2. `users(id)` 를 참조하면 탈퇴 삭제(`UserDataPurger`)가 `couple_games` 를 `created_by`
   기준으로만 지우므로, "상대가 연 판에 내가 걸어둔" 행이 FK 위반으로 남는다.

### 2-1. 무르기 규칙

- **직전에 둔 사람만** 걸 수 있다(= 지금 자기 차례가 아닌 쪽). 상대가 받아줘야 되돌아간다.
  서버가 바로 무르지 않는 이유: 오목에서 무르기는 규칙이 아니라 **부탁**이다. 동의 없이 판이
  바뀌면 상대는 "내가 뭘 본 거지"가 된다.
- **한 수(1 ply)만.** "내 수와 상대의 대응까지" 같은 다단 무르기는 어디까지 되돌렸는지 서로
  헷갈리기 시작하는 지점이다. 필요하면 한 번 더 요청하면 된다.
- 상대가 걸어둔 무르기를 두고 **그냥 두면 그것도 거절**이다(`place` 가 요청을 지운다).
- 이긴 수는 판이 이미 `COMPLETED` 라 무를 수 없다. 의도한 것이다 — 승부가 난 뒤의 무르기는
  결과를 뒤집는 것이지 실수 정정이 아니다.
- 요청·수락·거절 **모두 푸시**한다. 판이 멈춰 있는 쪽이 이유를 알아야 다시 흐른다.

### 2-2. 복기 · 최근 세 수

- 끝난 판을 처음부터 재생한다. 지난 판 카드를 누르거나 결과 화면에서 연다.
- 최근 세 수 중 2·3번째에 옅은 테두리. 며칠 만에 들어왔을 때 "어디까지 뒀더라"가 마지막 점
  하나로는 안 읽힌다.
- **V91 이전에 시작된 판**은 `moves` 가 비어 있다. 그래도 `last_move` 로 한 수는 무를 수 있게
  하고(배포 시점에 진행 중이던 판에서 버튼만 죽어 보이지 않게), 복기는 막는다(눌러도 빈 판이
  뜨지 않게).

## 3. 오늘의 판 + 게임 스트릭(V92)

### 3-1. 오늘의 판

`couple_games.daily_date DATE`(자유 대국은 NULL). **시드는 저장하지 않는다** — 날짜에서 매번
다시 만든다. 설계 3-2 가 이미 터놓은 길이다("생성기는 Random 을 받으므로 컬럼 하나만 더하면").

- 그날은 **모든 커플이 같은 문제**를 푼다. 다른 커플과 겨루기 위해서가 아니라 "오늘 판이 하나
  준비돼 있다"를 만들기 위해서다. **순위표는 두지 않는다.**
- 난이도는 **요일 고정**: 월·화 쉬움 / 수·목·금 보통 / 토·일 어려움. 주말에 붙어 앉을 시간이
  더 있다는 전제다. 무작위로 정하면 어제보다 쉬운지 어려운지 예측할 수 없어 오히려 피로해진다.
- `LocalDate.toEpochDay()` 를 그대로 시드로 쓰지 않는다 — 이웃한 날의 시드가 1씩만 달라
  `Random` 초기 상태가 비슷해진다. 황금비 상수를 곱해 흩뿌린다.
- **"진행 중인 판은 하나" 규칙은 그대로다.** 자유 대국이 돌고 있으면 `POST /daily` 는 그 판을
  돌려준다. 눌러보고 알게 하지 않으려고 `GET /daily` 가 `blockedByOtherGame` 을 미리 내려준다.
- 오늘 것을 **마쳤으면** 409(`GAME_DAILY_ALREADY_DONE`). **접었으면** 다시 열 수 있다 —
  문제가 그대로이므로 "다시 도전"이 된다(그래서 하루에 행이 여럿일 수 있다).

### 3-2. 스트릭

`GET /games/streak` → `{ current, best, playedToday, lastPlayedDate }`.

- **종목을 가리지 않는다.** 스도쿠를 완성했든 오목을 끝냈든 그날은 "같이 한 날"이다.
  오늘의 판에만 걸면 자유 대국을 두 판 두고도 스트릭이 끊기는데, 그건 규칙이 아니라 벌이다.
- 접은 판은 세지 않는다 — 기록에 남기지 않는다는 두 게임의 공통 규칙 그대로.
- **오늘 아직 안 했어도 어제까지 했으면 끊기지 않는다.** 하루는 자정까지 남아 있는데 낮에
  들어왔다고 "0일째"를 보여주면 이미 끊긴 것처럼 읽힌다.
- 별도 테이블을 두지 않고 `completed_at` 에서 매번 계산한다. 최근 400일만 본다 — 현재 스트릭에는
  넉넉하고, **최고 기록은 이 구간 안에서만** 본다(정확한 전체 최고치를 위해 컬럼을 두지 않았다).
- `completed_at` 은 JVM 기본 TZ 의 벽시계로 저장된다(운영 Railway = UTC). 그냥 읽으면 KST
  00~09시 기록이 전날로 잡히므로 `fitto.storage-zone` 으로 보정한다 —
  `MemoryDates.storageStartOfDay` 와 같은 문제, 같은 해법이다.

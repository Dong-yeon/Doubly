# 앱 아이콘(비개구리) 객관 평가 — 2026-09-10

> **상태: 평가만. 코드·에셋 변경 없음.**
> 대상은 커밋 `2426ea7`(비개구리로 교체) → `6bf9349`(벡터화) 이후의 현재 아이콘 5종입니다.
> 계기: "너무 장난 같은 아이콘"이라는 외부 반응. 그 반응이 타당한지, 타당하다면 원인이
> 무엇인지를 실측으로 가르기 위한 문서입니다.

## 결론

반응은 정당합니다. 다만 원인은 **"개구리를 썼다"가 아니라** 아래 세 가지입니다.

1. 마크에 개구리 신호가 없어서 종(種)이 판독되지 않는다 → 관객이 "낙서"로 기본값 처리한다
2. 유치함 신호(볼터치·혀·손그림 떨림)가 3중으로 겹치는데 상쇄할 무게추가 없다
3. 순백 배경 + 서브픽셀 윤곽이라 런처 크기에서 형태가 붕괴한다

**캐릭터를 버릴 이유는 없습니다.** 세 군데를 고치면 됩니다(§5).

## 1. 종 판독 실패

`frontend/assets/bigae-mark.svg` 에는 개구리의 형태 단서가 하나도 없습니다.

| 개구리 필수 신호 | 현재 마크 |
| --- | --- |
| 머리 윤곽 **위로 솟은** 눈 | 없음 (눈이 얼굴 안쪽 중앙에 있음) |
| 가로로 넓은 입 | 없음 (작은 원형 입 + 혀) |
| 물갈퀴·다리 | 없음 (아이콘화하며 팔다리 제거 — 커밋 `2426ea7` 의도된 결정) |
| 등 무늬 | 없음 |

남은 것은 "초록 덩어리 + 정면 얼굴"입니다. 48px 축소본에서는 완두콩·브로콜리·사과 쪽으로
읽힙니다. **설명이 필요한 아이콘은 실패한 아이콘입니다.**

### 하트 계승도 실측으로는 약하다

커밋 `2426ea7`의 핵심 근거는 "머리가 이미 하트 모양이라 커플 의미를 잃지 않는다"였습니다.
`icon.png` 실측:

```
하트 홈 깊이   = 마크 높이의 8.3%   (하트로 읽히려면 통상 12~20%)
홈 바닥 위치   = x 47.2% (중앙 이탈)
좌우 엽 높이차 = 마크 높이의 3.9%
좌우 대칭 IoU  = 0.922
```

홈이 얕고 중앙을 벗어나 **하트가 아니라 사과/복숭아 실루엣**으로 떨어집니다.
원본 스티커 `bigae_excited.png`는 전신 + 흰 스티커 테두리 덕에 하트가 살지만,
몸통만 잘라낸 아이콘에서는 그 판독이 유지되지 않습니다.

## 2. 유치함 신호 3중 중첩

| 신호 | 성격 |
| --- | --- |
| 볼터치 홍조 | 아동성 신호 중 가장 강함 |
| 혀 내민 입 | 유아 표정 코드 |
| 손그림 떨림 윤곽(비대칭·굵기 불균일) | 낙서 코드 |

각각은 문제가 아닙니다. **셋이 겹치는데 무게추가 없는 것**이 문제입니다 — 기하학적 컨테이너,
타이포, 색의 깊이 중 어느 것도 없어 상쇄가 일어나지 않습니다.

캐릭터 얼굴을 그대로 앱 아이콘에 올리는 것은 **아동·게임 카테고리 코드**입니다(핑크퐁·뽀로로).
커밋 `2426ea7`이 인용한 카카오톡은 오히려 반대 사례입니다 — 아이콘은 라이언이 아니라 말풍선
심볼이고, 캐릭터는 앱 안에 있습니다. 즉 "아이콘=마스코트 색, 인앱=무채색"이라는 그 커밋의
구조 설명은 카카오의 실제 구조와 어긋납니다. 카카오는 **아이콘=추상 심볼, 인앱=캐릭터**입니다.

## 3. 기술 측정 — 런처 크기에서 형태가 붕괴한다

```
icon.png             1024², 알파 없음(iOS 규격 적합), 마크 점유 폭 72.0% / 면적 40.5%
adaptive foreground  432²,  마크 점유 57.2%  (가시영역 66.7% 대비 86%)
adaptive background  순백 #FFFFFF  ← 색면 없음
monochrome           432²,  마크 점유 53.5%

본체 #AAD2A0 vs 흰 배경        1.69:1
본체 #AAD2A0 vs 회색 벽지      2.34:1
윤곽 #2B2B2B vs 다크 홈(#121212) 1.32:1
잉크(눈·눈썹·입·윤곽) 면적      마크의 11.7%
```

### 윤곽이 서브픽셀이다

`bigae-mark.svg`의 윤곽 두께는 viewBox 100 기준 `stroke-width="2.1"`이고, 마크가 viewBox의
약 86을 차지합니다. 48dp 런처에서 마크는 약 27.5px 로 렌더되므로 **실선 두께는 약 0.65px**입니다.

축소 렌더에서 진한 윤곽 픽셀 비율 실측:

| 렌더 크기 | 진한 윤곽 픽셀 비율 |
| --- | --- |
| 192px | 4.6% |
| 96px | 4.3% |
| 48px | 4.5% |
| **24px** | **0.3%** ← 붕괴 |

위젯·알림 크기에서 윤곽이 증발하고 **대비 1.69:1의 연녹색 얼룩**만 남습니다.

### 배경 레이어가 순백이다

Android adaptive background 가 `#FFFFFF` 단색입니다. 라이트 테마 홈/앱 서랍에서 아이콘의
바깥 경계를 전적으로 저 서브픽셀 윤곽이 지탱합니다. iOS 쪽은 흰 배경이 스퀘어클 끝까지 차서
**흰 타일 위 작은 초록 점**으로 보입니다(마크 점유 72% → 좌우 여백 각 14%).

### 모노크롬은 브랜드 회상이 0

Android 13+ 테마 아이콘에서 얼굴만 구멍 뚫린 검은 덩어리로 렌더됩니다. 실루엣만으로는
어떤 앱인지 식별되지 않습니다.

### 색 전략

`#AAD2A0` 상대휘도 0.572 — 중간 밝기 저채도. 앱 서랍의 경쟁 아이콘(카카오 노랑, 인스타
그라데이션, 당근 주황)은 전부 고채도입니다. 파스텔 녹 + 흰 배경은 홈 화면에서 **시각 무게가
가장 낮은 조합**이라 "찾기 쉬움" 싸움에서 집니다. 덧붙여 녹색은 도메인상 건강·식물·에코를
가리키므로, 커플이 1차 축인 제품에서는 축이 어긋납니다.

## 4. 공정하게 — 잘한 부분

- **커플 앱 아이콘의 중앙값(하트·핑크·그라데이션) 탈출은 성공했습니다.** 차별화는 실제로 확보됐습니다.
- 채워진 덩어리라 이전의 얇은 하트 두 개보다 실루엣이 있습니다. 커밋 `2426ea7`의 판단 자체는 타당했습니다.
- 스티커 20종(`bigae_*` 10종, `bear_*` 9종)과 IP가 실제로 연결돼 있습니다. 마스코트가 앱 안에
  진짜 존재하는 자산이라는 점은 드문 강점이며, 교체가 아니라 교정으로 가야 할 근거입니다.
- 벡터화(`6bf9349`)로 래스터 잔편·거친 모노크롬은 해소됐습니다. 남은 문제는 조형·색이지 가공 품질이 아닙니다.

### 검토하고 뺀 안

- **아이콘을 하트로 되돌린다** — 뺐습니다. `2426ea7`이 지적한 "커플 앱 중앙값 + 48px에서

## 7. 배경 색면 선정 — 측정과 결정 (2026-09-10)

### 앞 절의 오류 정정

§5 초안에 "진녹 **또는 크림** → 대비 6:1대"라고 적었는데 **크림은 틀렸습니다.**
WCAG 대비비는 밝은 색 구간에서 값이 압축되어 판단을 그르칩니다. 지각 균등한 CIE L* 로
다시 재면 크림은 현행 흰색보다 **나쁩니다.**

| 안 | 배경 L* | 본체 L* | ΔL* |
| --- | --- | --- | --- |
| 현행 흰 `#FFFFFF` | 100.0 | 80.3 | 19.7 |
| 진녹 `#3E6B4A` | 41.3 | 80.3 | 39.0 |
| **크림 `#F6EFDF`** | 94.6 | 80.3 | **14.3 ← 흰색보다 나쁨** |

본체 `#AAD2A0` 의 L* 가 80.3 이므로 **배경 L* ≤ 48 (ΔL* ≥ 32)** 이 24px 통과선입니다.
윤곽이 증발하는 구간에서 본체/배경 경계가 대신 실루엣을 잡아주는 값입니다.

### 13안 스윕 — 판단축이 ΔL* 에서 ΔC 로 넘어간다

L* 게이트는 후보 13안이 전부 통과했습니다. 그래서 실제 변별은 **색상 거리 ΔC** 였습니다.

| 계열 | ΔC | 판정 |
| --- | --- | --- |
| 녹 계열 G1~G6 (`#1F4D33`~`#4A7C59`) | 5.6 ~ 13.1 | 톤온톤. 마크가 "배경의 밝은 부분"으로 읽힘 |
| 비녹 계열 R·P·N·K·W | 30.5 ~ 61.2 | 마크가 독립된 물체로 읽힘 |

앱 서랍 시뮬레이션(카톡 노랑·인스타 핑크·당근 주황·네이버 초록 근사색 옆에 배치)에서
세 가지가 추가로 드러났습니다.

1. **현행 흰색은 이웃 사이에서 "빈 자리"로 읽힙니다.** 다크 홈에서는 반대로 눈부신 흰 사각형이 됩니다.
2. **녹계열 배경은 네이버 초록과 인접하면 묻힙니다.** 톤온톤이라 마크도 안 뜨는데 이웃과도 겹칩니다 — 녹계열 6안 공통 감점.
3. **저채도 딥톤이 고채도 이웃 사이에서 오히려 튑니다.** 채도 경쟁을 하지 않고 명도로 이깁니다.

| 의미축 | 커플(로맨스) + 미식(와인). 럽슐랭 맛집 등급 축과 겹칩니다 |

### 검토하고 뺀 안 — 2차

- **P1 플럼 `#5B3A66`** — ΔC 61.2 로 수치는 최고(보라가 초록의 보색에 가까움)지만 뷰티·판타지 카테고리 코드입니다.
- **N1 잉크 네이비 `#2C3E50`** — 조형은 되는데 금융·생산성 코드라 커플 앱과 톤이 어긋납니다.
- **G4 아주 깊은 녹 `#1F4D33`** — 마스코트 색계열을 지키는 보수안. 톤온톤 + 네이버 초록 인접 문제로 탈락.
- **T1 테라코타 `#B5563C`** — 채도가 높아 배경이 마크보다 시선을 끕니다. 배경이 주인공이 되면 안 됩니다.
- **K1 차콜 `#3A3A3A`** — 마크는 잘 뜨지만 무채색이라 브랜드 색을 하나도 싣지 못합니다.

색상값 한 줄이라 갈아타는 비용은 거의 없습니다. 재현 절차는 아래 부록과 동일하고,
`#6E2B38` 자리만 바꾸면 됩니다.

### 적용 범위

`icon.png`(1024² RGB, 알파 없음 — iOS 규격), `favicon.png`, `android-icon-background.png`(432² 단색),
`app.json` 의 `adaptiveIcon.backgroundColor`. **마크 배치는 건드리지 않았습니다** — 적용 전후
`icon.png` 의 마크 bbox 가 `(142, 149, 879, 870)` 로 동일합니다(배경색만 바뀐 diff 를 보장).
`android-icon-foreground.png`·`monochrome.png`·`splash-icon.png` 는 미변경입니다.

## 부록 — 측정 재현

```bash
python3 - <<'PY'
from PIL import Image, ImageChops
ic = Image.open('frontend/assets/icon.png').convert('RGB')
bg = Image.new('RGB', ic.size, (255, 255, 255))
mask = ImageChops.difference(ic, bg).convert('L').point(lambda v: 255 if v > 8 else 0)
print('마크 bbox', mask.getbbox())
for size in (192, 96, 48, 24):
    s = ic.resize((size, size), Image.LANCZOS)
    px = list(s.get_flattened_data())
    dark = sum(1 for p in px if sum(p) / 3 < 110)
```

개념안은 전부 아래 생성기 하나에서 나옵니다. 저장소에 에셋으로 넣지 않은 이유는
아직 채택안이 없기 때문입니다(`docs/` 는 md 전용 관례를 유지합니다).

```python
import math
GREEN='#4FBF52'; INK='#1E2B22'; WHITE='#FFFFFF'; BURG='#6E2B38'

def hp(sc, cx, cy, seg=240):
    """DoublyLogo.tsx 의 heartPoints 와 같은 파라메트릭 하트 곡선."""
    p = []
    for i in range(seg + 1):
        t = 2 * math.pi * i / seg
        p.append((cx + 16 * math.sin(t) ** 3 * sc,
                  cy - (13 * math.cos(t) - 5 * math.cos(2*t)
                        - 2 * math.cos(3*t) - math.cos(4*t)) * sc))
    return p

def hpath(sc, cx, cy):
    return 'M' + ' L'.join(f'{x:.2f},{y:.2f}' for x, y in hp(sc, cx, cy)) + ' Z'

def lobes(sc, cx, cy):
    """하트 두 엽의 정점 — 얼굴을 여기에 얹는다."""
    p = hp(sc, cx, cy)
    return (min([q for q in p if q[0] < cx], key=lambda q: q[1]),
            min([q for q in p if q[0] > cx], key=lambda q: q[1]))

def solo():
    """A — 한 마리 정면. 눈두덩이 머리 윤곽 위로 솟는 것이 개구리의 필수 신호."""
    g = [f'<ellipse cx="50" cy="58" rx="41" ry="32" fill="{GREEN}"/>']
    for ex in (-23, 23):
        g.append(f'<circle cx="{50+ex}" cy="30" r="18.5" fill="{GREEN}"/>')
        g.append(f'<circle cx="{50+ex}" cy="29" r="12" fill="{WHITE}"/>')
        g.append(f'<circle cx="{50+ex*0.93}" cy="31" r="6.8" fill="{INK}"/>')
    g.append(f'<path d="M26,66 Q50,84 74,66" fill="none" stroke="{INK}" '
             f'stroke-width="5" stroke-linecap="round"/>')
    return '\n'.join(g)

def profile(cx, cy, s, flip=False, tilt=0.0, rise=0.0):
    """E7(rise=0) / E8(rise=1) — 마주보는 옆모습. 눈이 4개에서 2개로 준다."""
    sg = -1 if flip else 1
    ex = -8 * sg
    ey = cy - (19 + 9 * rise) * s
    return (f'<g transform="rotate({tilt} {cx} {cy})">'
            f'<circle cx="{cx+ex}" cy="{ey}" r="{17*s}" fill="{GREEN}"/>'
            f'<circle cx="{cx+ex}" cy="{ey-1*s}" r="{11.5*s}" fill="{WHITE}"/>'
            f'<circle cx="{cx+ex-3.4*s*sg}" cy="{ey+1.5*s}" r="{6.6*s}" fill="{INK}"/>'
            f'<path d="M{cx-14*s*sg},{cy+9*s} Q{cx-2*s*sg},{cy+20*s} {cx+13*s*sg},{cy+11*s}" '
            f'fill="none" stroke="{INK}" stroke-width="{4.6*s}" stroke-linecap="round"/></g>')

def wrap(body, bg=BURG):
    return (f'<svg xmlns="http://www.w3.org/2000/svg" viewBox="0 0 100 100" '
            f'width="100" height="100"><rect width="100" height="100" fill="{bg}"/>{body}</svg>')

A = wrap(solo())
SC, CX, CY = 2.95, 50, 53
L, R = lobes(SC, CX, CY)
E7 = wrap(f'<path d="{hpath(SC, CX, CY)}" fill="{GREEN}"/>'
          + profile(L[0]+3, L[1]+29, 0.68, flip=True, tilt=-9)
          + profile(R[0]-3, R[1]+29, 0.68, tilt=9))
SC8, L8, R8 = 2.86, *lobes(2.86, 50, 56)
E8 = wrap(f'<path d="{hpath(SC8, 50, 56)}" fill="{GREEN}"/>'
          + profile(L8[0]+3, L8[1]+31, 0.66, flip=True, tilt=-9, rise=1)
          + profile(R8[0]-3, R8[1]+31, 0.66, tilt=9, rise=1))
```

## 9. 채택 — 까꿍 컷 + 왕관, 흰 배경 (2026-09-10)

> **상태: 적용 완료.** §8 의 듀오링고식 기하 재작도는 **폐기**했습니다.
> 방향은 "손그림 조형을 유지한 채 소스 컷만 바꾸고 왕관을 얹는다" 입니다.

### 왜 이쪽이 맞았나

§8 의 재작도는 조형은 개선되지만 **스티커 20종과 언어가 갈라지는 비용**을 안고 있었습니다
(손그림 파스텔 vs 기하학 고채도). 컷 교체는 그 비용이 **0** 입니다 — 같은 손그림, 같은 색,
같은 윤곽 언어이므로 앱을 열었을 때 다른 캐릭터가 나오지 않습니다.

그리고 §1 의 진단이 컷 선택으로 자연히 풀립니다.

| §1 에서 지적한 실패 | 까꿍 컷 |
| --- | --- |
| 눈이 점 두 개라 캐릭터가 "안 본다" | **큰 눈**을 이미 갖고 있음 |
| 잉크 면적이 마크의 11.7% 뿐 | 큰 눈·혀·입 윤곽으로 잉크 질량이 크게 늘어남 |
| 종 판독 실패 | 여전히 미해결 — 아래 "남은 것" 참조 |

### 흰 배경 복귀 — §7 의 버건디를 되돌린다

§3 에서 "순백 배경 + 서브픽셀 윤곽이라 형태가 붕괴한다"고 했고 §7 에서 버건디를 깔았습니다.
**그 근거는 이 마크에는 성립하지 않습니다.**

```
24px 진한 윤곽 픽셀 비율 (흰 배경)
excited 컷 (윤곽 2.10, 마크 점유 72.0%)    0.3%   ← 붕괴
까꿍+왕관  (윤곽 2.85, 마크 점유 93.3%)   13.0%   ← 43배
```

원인은 **채도가 아니라 잉크 질량**이었습니다. 윤곽이 두꺼워지고(2.1 → 2.85), 마크가 커지고
(72% → 93.3%), 큰 눈·혀·입이 더해지면서 얇은 선 하나에 실루엣을 의존하지 않게 됩니다.
따라서 배경 색면은 더 이상 필요 없고, `adaptiveIcon.backgroundColor` 는 `#FFFFFF` 로 돌아갑니다.

§7 의 색조 스윕(13안)과 버건디 선정 근거 자체는 폐기가 아니라 **조건부**입니다 — 파스텔 마크를
유지할 때만 유효합니다. 되살릴 일이 생기면 그 절을 그대로 씁니다.

### 파이프라인 — `6bf9349` 와 동일

색 레이어 분리 → 형태학적 열림으로 팔·다리·하트 제거 → 컨투어 리샘플 + 원형 저역통과 →
Catmull-Rom 을 3차 베지에로.

- 연결 성분 3개(몸통 + 하트 2개)로 갈려 **하트는 라벨링 단계에서 자동 제외**됩니다.
- 팔·다리는 원판 커널 R=60(@1440) 열림으로 제거. R 을 30~75 로 바꿔도 결과가 ±0.1% 라
  민감하지 않습니다.
- 눈·입은 구멍이 있는 도형이라 `fill-rule="evenodd"` 로 외곽 + 구멍을 한 패스에 담습니다.
  흰 하이라이트는 그 구멍 위에 별도 흰 패스로 덮습니다.

### 눈은 꽉 찬 검정 — 흰자를 뺀다

스티커의 반짝이는 흰자·하이라이트는 **원본 펜 그림에 없습니다.** 손그림을 이미지 모델로
스티커화하는 과정에서 덧붙은 것이고, 사용자가 종이에 그린 눈은 전부 꽉 찬 검은 타원입니다.
원본으로 되돌립니다.

걷어내는 데 두 가지가 걸렸습니다.

1. **바깥으로 열린 초승달은 구멍이 아니라 홈입니다.** 오른쪽 눈의 하이라이트는 닫힌 구멍이라
   `fill_holes` 로 메워지지만(둘레 618 불변), 왼쪽 눈은 쓸림이 테두리로 열려 있어 안 메워집니다.
   닫힘 R=24 를 먼저 걸면 봉해집니다(둘레 702 → 536).
2. **봉한 자리가 울퉁불퉁합니다.** 눈만 평활을 4.5 로 세게 겁니다(입은 2.0 그대로 — 원본 결을 남깁니다).
   볼록껍질도 재봤지만 왼쪽 눈이 각진 쐐기가 돼 **뺐습니다**.

**입만은 구멍을 남깁니다** — 혀와 몸통 초록이 비쳐야 합니다. 입의 판별은 위치 규칙이 아니라
**"혀 중심을 품는 성분"** 으로 합니다. 위치는 컷이 바뀌면 깨지지만 이 규칙은 안 깨집니다.

결과적으로 잉크 질량이 더 늘어 24px 진한 픽셀이 13.0% → **14.1%** 가 됐고, 패스 수는
14개 → 8개로 줄었습니다(하이라이트 6개 삭제).

### 실측으로 정한 세 가지

1. **윤곽 두께 2.85** — 잉크 링 면적 ÷ 실루엣 둘레 = 29.1px(@1440), viewBox 환산 2.85.
   기존 마스터의 2.1 보다 두꺼운 것은 컷이 달라서지 임의로 키운 값이 아닙니다.
2. **얼굴을 (5.4, 1.5) 평행이동** — 팔다리를 떼면 얼굴 중심이 몸통 중심에서 **왼쪽으로 5.7%**
   치우칩니다(원본은 팔다리가 균형을 잡아줬습니다). 회전 보정도 재봤지만 -18° 까지 돌려도
   -3.8% 에 그치고 몸통 자세가 훼손돼 **뺐습니다**. 평행이동은 손실이 없습니다.
3. **왕관 밑변을 V 자로** — 머리 꼭대기의 하트 홈 바닥이 y 38.44, 눈 꼭대기가 y 36.4 입니다.
   즉 **홈보다 위에 눈이 있어** 직선 밑변으로는 둘 중 하나가 반드시 깨집니다.
   밑변이 가운데(39.8)에서 양끝(33.0)으로 올라가는 V 자면 홈을 덮으면서 눈을 비켜갑니다.

### 검토하고 뺀 안 — 3차

- **왕관 밑변 y=34 직선** — 홈 아래로 흰 틈이 보입니다.
- **왕관 밑변 직선 + 얼굴 하강** — 틈은 사라지지만 밑변이 머리띠처럼 읽히고 눈을 누릅니다.
- **왕관을 머리 뒤로** — 봉우리만 삐죽 나와 뿔로 읽힙니다. 왕관 인지가 무너집니다.
- **몸통 회전 보정** — 위 2번 참조.
- **듀오링고식 기하 재작도(§8)** — 스티커 20종 정합성 비용. 조형 자체는 유효하므로 §8 은 기록으로 남깁니다.

## 10. 왕관을 떼어 띄운다 + 눈 교정 (2026-09-11)

> **상태: 적용 완료.** §9 의 "머리에 앉은 왕관"과 "잉크를 그대로 채운 눈"을 둘 다 교체합니다.

### 왕관을 머리에서 뗀다

§9 에서 왕관 밑변을 V 자로 만든 것은 **하트 홈(y 38.4)과 눈(y 36.4) 사이에 왕관을 끼워 넣기
위한 타협**이었습니다. 떼어서 띄우면 그 간섭 자체가 사라지고, 원본 손그림에 있던 **하트 두 개**가
같이 살아납니다(라벨링에서 분리해 뒀던 성분을 그대로 씁니다).

대가는 작은 크기에서의 잉크 손실입니다. 본체가 작아지고 요소가 흩어지기 때문입니다.

| 구성 | 마크 면적 | 48px 진한 | 24px 진한 |
| --- | --- | --- | --- |
| §9 왕관 붙임 | 52.6% | 15.8% | **14.1%** |
| 띄움 · 왕관 큼(본체76) | 42.0% | 13.9% | 8.0% |
| **띄움 · 채택(본체82·왕관34)** | 45.5% | 14.5% | **9.0%** |

커밋 `2426ea7` 이 팔·다리·모션선을 뺀 이유가 "48px 에서 노이즈가 된다"였고, 떠 있는 왕관·하트는
같은 성질입니다. 실측으로도 24px 잉크가 **36% 줄었습니다.** 다만 교체 전(excited 컷)의 0.3% 에
비하면 여전히 30배라 붕괴는 아닙니다. **판독성을 조금 내주고 서사를 얻는 교환**입니다.

24px 에서 왕관은 노란 얼룩, 하트는 초록 점이 됩니다. 그 크기에서 읽히는 것은 본체뿐입니다.

### 눈 — 흰자를 빼되 둥글게

§9 에서 흰자를 뺀 방식은 **잉크 윤곽을 그대로 채우는 것**이었습니다. 그러면 원본의 쉼표 모양이
그대로 남아 노려보는 인상이 됩니다. 흰자가 덩어리를 나눠주던 역할이 사라지는데 형태는 불규칙한
채로 남기 때문입니다.

교정: **모멘트로 정원을 뽑아 원본 면적의 88% 로 그립니다.**

| 안 | 판정 |
| --- | --- |
| 닫힘 24 + 평활 4.5 (§9) | 왼쪽 눈이 기울어진 타원으로 남아 노려봄 |
| 볼록껍질 | 왼쪽 눈이 각진 쐐기가 됨 |
| 모멘트 타원 | 매끈하지만 좌우 기울기 차가 남음 |
| **모멘트 정원 · 88%** | **채택.** 둥글고 가벼움 |
| 모멘트 정원 · 78% | 너무 작아 §1 의 "점 두 개라 안 본다"로 회귀 |

### 버그 수정 — 혀 주름이 초록으로 비쳤다

`a536701`·`65b3ab6` 에 있던 결함입니다. 원본에서 혀 주름은 **잉크 선**인데 렌더에서는 그 자리가
몸통 초록이었습니다.

원인: 주름은 입 성분의 **구멍(입 안) 경계로 파고든 얇은 돌기**입니다. 그 구멍을 48점으로
리샘플하면서 돌기가 뭉개져 사라졌고, 결과적으로 주름 자리까지 구멍이 됐습니다.
면적 지표로는 안 잡힙니다 — 평활 수축(-8.5%)과 돌기 소실이 서로 상쇄되기 때문입니다.
**180점 · σ0.8** 로 촘촘히 뜨면 주름이 이어집니다.

# 럽바디 사진 분석 — 럽슐랭 장소 힌트 (2026-10-11)

## 문제

사진 AI 분석이 사용자가 고른 럽슐랭 장소를 쓰지 않아, 김치찌개집에서 찍은 찌개를 부대찌개로 읽었다.

## 결정

- `POST /meal/analyze` 에 `placeId`(선택)를 받는다. 있으면 가게 이름·분류·이 가게에서 예전에 먹은
  메뉴를 사진 프롬프트 **뒤에** `[참고 정보 — 사진과 맞지 않으면 무시]` 블록으로 붙인다. "사진에 명확히
  다른 음식이 보이면 사진을 따른다"는 문장을 항상 함께 둔다.
  - 분류는 앱 분류(`category` — 음식점·카페 등)와 세부 분류(`category_detail`, V130 — 예: "한식 · 찌개,전골")를
    함께 싣는다. "음식점"만으로는 무엇을 파는지 알 수 없다.
  - 메뉴는 장소 상세 "여기서 먹은 것"과 **같은 집계**를 쓴다(`PlaceVisitRepository.countMenu` — 방문에 연결된
    식단의 음식 이름, 많이 먹은 순·같으면 최근 순, 10개). 처음엔 같은 조인을 따로 만들어 "최근 순"으로 잘랐으나,
    origin/main 병합 때 이미 있는 집계를 확인하고 그쪽으로 합쳤다 — 화면과 힌트가 같은 목록을 본다.
- 힌트는 덤이다 — 남의 장소(내 **활성** 관계의 장소가 아님)는 로그만 남기고 무시하고, 조회가 실패해도
  분석은 힌트 없이 그대로 간다. 요청을 실패시키지 않는다.
- 가게 이름(50자)·분류(30자)·세부 분류(50자)·메뉴(각 30자)는 줄바꿈·제어문자를 지우고 코드포인트 기준으로
  자른다. 사용자가 직접 입력한 장소 이름이 프롬프트에 줄을 새로 열어 지시문을 끼워 넣지 못하게 하기 위해서다.
- 찌개류 구분 힌트 한 줄("햄·소시지가 보여야 부대찌개 …")은 장소와 무관하게 사진 프롬프트에 항상 들어간다.
- 커플 장소라 상대가 남긴 방문의 메뉴도 힌트에 들어간다(같이 먹은 상이 대부분). 장소 상세 "여기서 먹은 것"이
  이미 두 사람 것을 함께 보여주므로 새로운 노출 범주는 아니다.

구현: `MealPlaceHintLoader`(조회·접근 판정), `FoodAnalysisService.buildPhotoPrompt / placeHintBlock /
sanitizeForPrompt`(조립·정리). 조회는 장소·관계·메뉴 고정 3회로, 방문 수와 무관하다.

## 서버 자동 분석 — 장소를 어디서 받나

`MealPhotoAutoAnalysisService` 는 사진만 남긴 끼니를 저장 커밋 직후 분석한다. 처음 구현은 끼니에 방문 기록으로
연결된 장소(`place_visits.meal_id`)를 역으로 찾았는데, 당시 식단 기록 화면은 **저장 응답을 받은 뒤에**
`recordVisit` 으로 방문을 따로 남겨, 작업이 돌 때 연결이 거의 없었다. 그래서 `SaveMealRequest.placeId`(선택,
**분석 힌트 전용** — 방문은 만들지 않는다)를 추가해 `scheduleIfEligible` 로 넘기게 했다.

origin/main 병합 후 사정이 바뀌었다. 장소를 고른 식단 저장은 이제 외식 기록 API 한 번(`POST /places/meal-visits`,
`MealVisitService`)으로 장소 확정 → 식단 → 방문이 한 트랜잭션에서 만들어진다. 그래서:

- `MealVisitService` 가 확정한 `placeId` 를 자신이 만드는 `SaveMealRequest` 에 실어 보낸다 — 자동 분석이 장소를
  직접 받는다. 화면 쪽 저장 요청(`dietApi.save`)은 장소가 없을 때만 쓰이므로 앱은 `placeId` 를 싣지 않는다.
- 끼니→방문 역조회 차선책은 지웠다. 장소가 있는 식단은 전부 외식 기록을 거치므로 닿을 경로가 없다.
- 카카오에서 막 고른(아직 저장 전인) 장소는 id 가 없어, 그 상태에서 누른 "AI로 음식 분석"에는 힌트가 붙지 않는다.
  저장하면 장소가 만들어지고 자동 분석에는 붙는다.

## 분석 뒤 장소를 고르면 과거 메뉴 칩으로 이름 교체 — 이제 구현 가능

처음엔 장소별 과거 메뉴 API 가 없어 보류했다. origin/main 에는 `GET /api/v1/places/{id}/menu` 가 있다 —
`items`("여기서 먹은 것", 위 집계와 같다)와 `board`(메뉴판에서 읽어 저장한 메뉴, V131)를 한 번에 준다. 남은 일은
프론트뿐이다:

- 클라이언트도 이미 있다(`placeApi.menu(placeId)`). `DietRecordScreen` 에서 분석 결과가 채워진 뒤 우리 장소를 고르면
  메뉴를 한 번 불러와, 항목 이름 옆에 칩(가로 스크롤, 현재 이름과 같은 메뉴는 제외, `items` 다음 `board`)으로
  보여준다. 탭하면 그 항목의 `name` 만 바꾸고 칼로리·탄단지는 그대로 둔다(재분석하지 않음).

같은 이유로 메뉴판 메뉴(`place_menu_items`)를 사진 프롬프트 힌트에 더하는 것도 쿼리 한 번으로 가능하다 — 처음 가는
가게라 먹은 기록이 없어도 메뉴판을 찍어 뒀다면 후보가 생긴다. 이번 범위에는 넣지 않았다.

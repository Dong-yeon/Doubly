# 럽바디 사진 분석 — 럽슐랭 장소 힌트 (2026-10-11)

## 문제

사진 AI 분석이 사용자가 고른 럽슐랭 장소를 쓰지 않아, 김치찌개집에서 찍은 찌개를 부대찌개로 읽었다.

## 결정

- `POST /meal/analyze` 에 `placeId`(선택)를 받는다. 있으면 가게 이름·분류·이 가게에서 예전에 기록한
  메뉴(`place_visits.meal_id → meal_items.name`, 중복 제거, 최근 방문순 10개)를 사진 프롬프트 **뒤에**
  `[참고 정보 — 사진과 맞지 않으면 무시]` 블록으로 붙인다. "사진에 명확히 다른 음식이 보이면 사진을
  따른다"는 문장을 항상 함께 둔다.
- 힌트는 덤이다 — 남의 장소(내 **활성** 관계의 장소가 아님)는 로그만 남기고 무시하고, 조회가 실패해도
  분석은 힌트 없이 그대로 간다. 요청을 실패시키지 않는다.
- 가게 이름(50자)·분류(30자)·메뉴(각 30자)는 줄바꿈·제어문자를 지우고 코드포인트 기준으로 자른다.
  사용자가 직접 입력한 장소 이름이 프롬프트에 줄을 새로 열어 지시문을 끼워 넣지 못하게 하기 위해서다.
- 찌개류 구분 힌트 한 줄("햄·소시지가 보여야 부대찌개 …")은 장소와 무관하게 사진 프롬프트에 항상 들어간다.
- 커플 장소라 상대가 남긴 방문의 메뉴도 힌트에 들어간다(같이 먹은 상이 대부분). 피드에서 이미 상대 끼니의
  첫 항목 이름이 보이므로 새로운 노출 범주는 아니다.

구현: `MealPlaceHintLoader`(조회·접근 판정), `FoodAnalysisService.buildPhotoPrompt / placeHintBlock /
sanitizeForPrompt`(조립·정리), `MealItemRepository.findRecentNamesAtPlace`(메뉴 조인 1쿼리).
조회는 장소·관계·메뉴 고정 3회로, 방문 수와 무관하다.

## 서버 자동 분석 — 저장 요청에 placeId 를 싣는 이유

`MealPhotoAutoAnalysisService` 는 처음엔 끼니에 방문 기록으로 연결된 장소(`place_visits.meal_id`)만
찾았는데, 지금 흐름에서는 거의 걸리지 않았다. 식단 기록 화면이 **저장 응답을 받은 뒤에** `recordVisit` 으로
방문을 따로 남기는 반면, 자동 분석 작업은 저장 커밋 직후 바로 돌아 그 시점엔 연결이 아직 없다.

그래서 `SaveMealRequest.placeId`(선택)를 추가해 `scheduleIfEligible` 로 넘긴다. **분석 힌트로만** 쓰고,
방문 기록 생성은 지금처럼 `recordVisit` 이 맡는다(저장 API 가 방문까지 만들게 하면 방문 카드·푸시·평점
흐름이 두 갈래가 된다). 접근 판정은 사용자가 직접 분석할 때와 같은 `MealPlaceHintLoader` 를 지난다.
placeId 가 없으면(이전 앱 버전 등) 예전처럼 끼니→방문 역조회를 차선책으로 시도한다.

## 보류 — 분석 뒤 장소를 고르면 과거 메뉴 칩으로 이름 교체

장소별 과거 메뉴를 돌려주는 API 가 없어 구현을 보류했다. 필요한 범위:

- 백엔드: `GET /api/v1/places/{id}/menus` → `List<String>`. `PlaceService.getCouplePlace` 로 접근 판정
  (남의 장소는 403 — 사용자 화면용이라 조용히 무시할 이유가 없다) 후
  `MealItemRepository.findRecentNamesAtPlace` 를 그대로 재사용한다.
- 프론트: `placeApi.menus(placeId)` 추가. `DietRecordScreen` 에서 분석 결과가 채워진 뒤 장소를 고르면
  메뉴를 한 번 불러와, 항목 이름 옆에 칩(가로 스크롤, 현재 이름과 같은 메뉴는 제외)으로 보여준다.
  탭하면 그 항목의 `name` 만 바꾸고 칼로리·탄단지는 그대로 둔다(재분석하지 않음).

## §1 데이터 모델

### 1-1. 엔티티 초안

```sql
-- V{n}__journal_entries.sql   (번호는 착수 시 CLAUDE.md 7절 절차로)
CREATE TABLE journal_entries (
    id             BIGINT        GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    user_id        BIGINT        NOT NULL REFERENCES users (id),
    journal_date   DATE          NOT NULL,          -- KST 하루. 서버가 KstClock.today() 이후 날짜를 거절
    mood_emoji     VARCHAR(10),                     -- 그날 무드(유니코드). 없어도 됨
    body           VARCHAR(2000),                   -- 자유 텍스트. 무드만 남겨도 됨
    photo_url      VARCHAR(500),                    -- 최대 1장
    shared_post_id BIGINT        REFERENCES feed_posts (id) ON DELETE SET NULL,  -- "우리 기록에 공유" 복사본
    created_at     TIMESTAMP     NOT NULL DEFAULT NOW(),
    updated_at     TIMESTAMP     NOT NULL DEFAULT NOW(),
    CONSTRAINT uk_journal_entries_user_date UNIQUE (user_id, journal_date)
);
```

- **`relation_id` 가 없다**(원칙 2). 그래서 `couple_id` 로 거르는 기존 조회 경로 어디에도 걸리지 않는다(§2).
- 유니크 `(user_id, journal_date)` 가 월 보기 범위 조회(`user_id = ? AND journal_date BETWEEN ? AND ?`) 인덱스를 겸하므로 별도 인덱스는 두지 않는다.
- `GENERATED BY DEFAULT AS IDENTITY`·`ON DELETE SET NULL`·`VARCHAR` 는 H2와 PostgreSQL 모두 지원하고, 기존 마이그레이션(V44 등)에서 이미 쓰는 문법이다. `JSONB`·`ON CONFLICT` 는 쓰지 않는다(CLAUDE.md 4절).
- `shared_post_id` 의 FK를 `ON DELETE SET NULL` 로 두는 이유: 피드 글은 "지난 기록 삭제"(`RelationRecordPurger`)로 지워질 수 있다. FK를 그냥 두면 그 삭제가 막히고, FK를 없애면 사라진 글을 가리키게 된다.
- 엔티티는 저장소 관례대로 `@ManyToOne` 없이 평범한 `Long userId`·`Long sharedPostId` 로 둔다.
- **구조화 필드는 넣지 않는다**(원칙 6): 체중·생리·수면·태그·날씨·위치 없음.
- 저장(upsert)은 `ON CONFLICT` 를 쓸 수 없다. `findByUserIdAndJournalDate` 로 찾아서 있으면 수정, 없으면 삽입한다. 동시 요청은 유니크 위반(`DataIntegrityViolationException`)을 잡아 한 번 다시 읽고 수정한다.

### 1-2. 하루 1개 vs 여러 개

| | 하루 1개 (권장) | 여러 개 |
| --- | --- | --- |
| 개념 | "그날의 페이지". 밑바탕(§3)이 날짜 단위라 1:1로 맞는다 | 타임라인형 메모. 밑바탕을 어느 글에 붙일지 애매하다 |
| 달력 | 칸 하나에 기록 하나. 무드 이모지를 칸에 바로 그린다 | 칸에 여러 개 → 대표값 규칙이 필요하다 |
| 무드 | 그날 무드 1개 | 글마다 무드 → "그날 기분"이 흐려진다 |
| API | `PUT /me/journals/{date}` 하나로 쓰기·수정 | 생성·수정·목록 페이지네이션 |
| 사진 한도 | 하루 1장으로 자연히 상한이 생긴다(§5-1) | 따로 상한이 필요하다 |
| 단점 | 하루에 두 번 쓰려면 이어 써야 한다 | 위 전부 |

**권장: 하루 1개.** 두 번째로 쓰러 오면 같은 기록이 열린다(이어 쓰기). 무드는 하루에도 여러 번 바뀔 수 있지만, 그 이력은 이미 `mood_statuses` 에 커플용으로 쌓인다. 기록에는 "그날 남기고 싶은 기분" 하나만 둔다.

### 1-3. 무드와의 관계

**사실**
- `mood_statuses`(V44): `couple_id NOT NULL REFERENCES relations`, `user_id`, `emoji VARCHAR(10)`, `message VARCHAR(20)`, `created_at`. V81에서 `couple_emoji_id` 가 추가됐다.
  행을 계속 쌓는 원장이고(하루 여러 행 가능), 날짜 컬럼이 없다.
- 조회 API는 "지금 무드"(최신 1행)뿐이다. 이력 API·날짜 조회 메서드는 없다.
- `MoodService.activeCouple` 이 ACTIVE 커플을 요구하므로 **미연결 사용자는 GET·POST 모두 `RELATION_NOT_FOUND`(404)** 를 받는다.
- 지워지는 경로가 둘이다. `RelationRecordPurger` 가 `mood_statuses` 를 지우고(`couple_emojis` 보다 먼저), `RelationRecordRestorer` 는 재회할 때 이를 옮긴다.
- `message`(20자)는 **상대에게 보이는 한마디**다(무드 조회에 상대 것도 내려간다). 또 COUPLE 범위 내보내기에도 양쪽 행이 들어간다.

**판단 — 참조안을 기각하고 직접 저장한다**

| 안 | 문제 |
| --- | --- |
| 기록이 `mood_statuses` 를 참조(중복 저장 없음) | ① 미연결 사용자에겐 무드 행이 생기지 않는다. ② "지난 기록 삭제" 때 내 일기의 무드가 사라진다. 원칙 2의 "이별 후에도 남는 기록"과 정면으로 충돌한다. ③ 날짜로 찾으려면 `created_at`(UTC 저장)을 KST로 환산해 "그날 마지막 행"을 고르는 규칙을 만들어야 한다 |
| **기록에 `mood_emoji` 를 직접 저장 (권장)** | 같은 이모지가 두 테이블에 있게 된다. 하지만 이는 **내 데이터**를 내 기록에 남기는 것이다. 원칙 2가 막는 것은 둘의 사진·상대 답 같은 *커플 데이터*의 복사다 |

- `couple_emoji_id` 는 저장하지 않는다. `couple_emojis` 는 관계 소유라 지난 기록 삭제 때 지워지고, FK를 걸면 그 삭제를 막는다.
  커플 이모지로 무드를 골랐다면 `MoodService.withImage` 와 같은 대응표로 **감정 → 유니코드 이모지**를 저장한다. 커플 이모지 얼굴은 일기에 남지 않는다. 대신 이별 뒤 일기에 상대가 그린 얼굴이 떠다니지 않는다.
- 무드를 고를 때의 흐름(§4-1): 연결돼 있으면 지금처럼 `POST /mood`(상대에게 보이는 현재 무드)를 보내고, 같은 값을 오늘 기록의 `mood_emoji` 에 넣는다. 미연결이면 기록에만 넣는다.
- 목록에서 바로 쓰러 들어온 경우에는 오늘 내 현재 무드(`GET /mood` 의 mine, KST 오늘 작성분)를 **미리 채우기만** 한다. 저장은 사용자가 할 때 한다.
- **두 텍스트를 섞지 않는다.** 무드 `message`(20자)는 상대에게 보이고, 기록 `body` 는 나만 본다. 같은 시트에 두 입력칸이 함께 있으면 사고가 난다. §4-1에서 화면 문구로 갈라 둔다.

### 1-4. Purger

| Purger | 할 일 | 근거 |

| `UserDataPurger.purgeFor` | ① URL 수집에 `select photo_url from journal_entries where user_id = :uid and photo_url is not null` 추가 — `body_metrics`·`meals` 의 URL 수집 옆(조사 기준 :49-54). ② `delete from journal_entries where user_id = :uid` — 개인 말단 테이블 사이, `body_metrics` 삭제(:100) 다음 | 자식 테이블이 없고, 다른 테이블이 이 테이블을 참조하지 않는다. `shared_post_id` 는 맨 앞의 RelationRecordPurger 단계에서 `feed_posts` 가 지워질 때 SET NULL 이 된다 |

### 1-5. 공유 복사본과 사진 파일 — 하나의 URL을 두 행이 가리키면 안 된다

"우리 기록에 공유"(원칙 5)가 일기의 `photo_url` 을 그대로 `feed_post_photos.url` 에 넣으면, **한쪽을 지울 때 다른 쪽의 파일까지 지워진다.**
피드 글 삭제(`FeedService`, 작성자만), 지난 기록 삭제(`collectImageUrls`), 일기 삭제가 모두 URL로 Cloudinary 파일을 지운다.
특히 "지난 기록 삭제"가 **이별 후 남겨야 할 일기 사진을 지우는** 사고가 된다.

| 안 | 내용 | 판정 |
| --- | --- | --- |
| A. 서버 측 복사 | 공유할 때 서버가 `CloudinaryImageFetcher` 로 원본을 받고 `CloudinaryImageUploader.upload(bytes, mime, "feed")` 로 새 파일을 만들어 글에 붙인다. 두 부품 모두 이미 있다 | **권장.** 삭제 경로 세 곳을 건드리지 않는다. 앱은 다시 올리지 않는다. 서버 업로드라 `PHOTO_UPLOAD` 서명을 지나지 않는다 — 공유는 하루 1회 상한(§4-3)이 있어서 괜찮다 |
| B. 참조 검사 | 삭제 경로 세 곳마다 "다른 테이블이 이 URL을 쓰는지" 확인한다(`LOVEBODY_REVIEW` A-3과 같은 계열 — **확인 필요**) | 경로가 늘 때마다 같이 고쳐야 한다. 하나라도 빠지면 조용히 사진이 사라진다 |
| C. 앱이 다시 업로드 | 공유할 때 앱이 같은 사진을 한 번 더 올린다 | 한도 차감·전송량이 두 배가 되고, 원본이 기기에 없을 수 있다 |

## §2 비공개 경로 전수표

**전제가 되는 사실**: 이 코드베이스에는 테이블을 스스로 찾아 묶는 경로가 없다.
피드·AI·알림·검색·내보내기·Purger·Restorer 모두 저장소·SQL·enum을 **명시적으로 나열**한다.
그래서 새 테이블은 누가 일부러 연결하지 않는 한 어디에도 실리지 않는다.
반대로 탈퇴 삭제와 내보내기도 **손으로 넣어야만** 들어간다. 그래서 위험은 "새는 것"보다 "나중에 누가 연결하는 것"에 있다.
테스트로 박아 두는 이유다(§2-3).

### 2-1. 경로별 판정

| 경로 | 지금 데이터를 모으는 방식 | 일기가 실리나 | 차단 방법 |

### 2-2. API 모양 자체로 막는다

- 모든 엔드포인트를 **`/api/v1/me/journals/...`** 로 두고, 대상 사용자는 토큰에서만 정한다. 경로에 `userId` 를 받지 않는다.
- 단건 수정·삭제·공유는 `{date}` 키로 한다(`/me/journals/2026-10-02`). 서버는 `findByUserIdAndJournalDate(token.userId, date)` 로 찾는다.
  다른 사람 기록을 가리킬 수단이 없으므로 "남의 id를 넣어 보는" 경로가 생기지 않는다.
- 없으면 **404**(403이 아니다). 403은 "있긴 하다"는 신호가 된다. 다만 위 구조에서는 원래 남의 기록을 지목할 수 없으니, 이는 일관성 차원의 규칙이다.

### 2-3. 테스트로 박기 — `JournalPrivacyTest`

`PartnerPrivacyTest` 처럼 **직렬화된 JSON**을 보고, 아래처럼 판정한다.
본문에 고유 표식 문자열(예: `"JOURNAL_SECRET_7f3a"`)을 넣고, 상대 계정으로 받은 응답의 원문 문자열에 그 표식이 **나오지 않는지** 확인한다.
필드 이름이 아니라 값으로 보는 이유는, 누가 나중에 다른 이름으로 실어도 잡기 위해서다.

1. A가 기록(표식 본문 + 사진) 저장 → B(상대) 토큰으로 `GET /me/journals?month=` → **B 자신의 빈 목록**(A의 것이 아님).
2. B 토큰으로 `GET /feed`, `GET /feed/photos`, `GET /feed/memories?on=`, `GET /relations/me`, `GET /mood`, `GET /meal/partner/today`, `GET /workout/partner/today` → 응답 원문에 표식·일기 사진 URL 없음.
3. B의 내보내기 `GET /export/sections/{모든 섹션}` → 표식 없음. A의 내보내기 JOURNALS 섹션에는 있음.
4. 트레이너 계정으로 `GET /trainer/members/{A}/workouts` → 표식 없음.
5. A가 공유 → B의 피드에 **복사본**이 보인다. A가 원본을 수정해도 B 쪽 글은 그대로다. A가 일기를 삭제해도 피드 글과 그 사진 파일은 남는다(§1-5 A안 검증).
6. A·B 관계에서 지난 기록 삭제 → A의 일기 행·사진 URL이 그대로 있다. 삭제 URL 목록에 일기 사진이 없다.
7. A 탈퇴 → `journal_entries` 0행, 일기 사진 URL이 삭제 목록에 있다(`WithdrawFlowTest` 쪽).
8. 저장 요청 뒤 `event_logs` 의 모든 `detail` 에 표식이 없다.

`@SpringBootTest` 조합을 새로 만들지 않고 기존 흐름 테스트와 같은 설정을 쓴다(CLAUDE.md 6절: 컨텍스트 가짓수가 늘면 CI가 OOM으로 빨개진다).

### 3-2. 기존 API 여러 번 vs 새 집계 엔드포인트

| | 기존 API 조합 | **새 `GET /me/journals/{date}` (권장)** |
| --- | --- | --- |
| 오늘 | 약 5번(`/mood`, `/meal/today`, `/workout/today`, `/daily-question`, `/feed` 후 클라이언트에서 거르기) | 1번 |
| 지난 날짜 | **불가능.** 식단·운동은 커서 페이지를 그 날짜까지 넘겨야 하고, 질문 이력은 둘 다 답한 날만 준다. 무드 이력 API는 없고, 피드도 커서로 거슬러 가야 한다 | 1번 |
| 쿼리 | 각 API가 각자 활성 커플을 다시 찾는다. `/workout/today` 는 세트까지 읽는다 | 기록 1 + 식사 1 + 운동 1 + 활성 커플 1 + 질문 1 + 피드 글 1 + 글 사진 1 ≈ **7번 고정**. 루프가 없어 N+1이 없다 |
| 변경 범위 | 날짜 조회 API를 식단·운동·질문·피드에 각각 새로 만들어야 한다(어차피 서버 작업) | 서비스 하나(`JournalDayService`)가 기존 저장소 메서드를 부른다. 프로젝션 쿼리 2개만 추가 |
| 비공개 | 일반 API를 여러 화면이 같이 쓰게 된다 | 응답 DTO가 일기 전용이고 본인 것만 담는다 |

**권장: 새 집계 엔드포인트.** `MemoriesService` 가 가장 가까운 본보기다(날짜 구간 환산, 사진 배치 로딩). 다만 그쪽은 연도마다 반복하고, 이쪽은 하루라 고정 비용이다.
월 달력은 별도의 `GET /me/journals?month=YYYY-MM` 로 **기록만**(날짜·무드·사진 유무) 1쿼리로 준다. 달력 칸마다 밑바탕을 조립하지 않는다.

### 3-3. 커플 데이터는 참조만 — 관계가 지워지면

밑바탕의 커플 부분(질문 답, 우리 기록 사진)은 **조회할 때마다 ACTIVE 커플 기준으로 읽는다.** 복사본이 없다.

| 상태 | 식사·운동·무드·본문·사진 | 질문 | 우리 기록 사진 |
| --- | --- | --- | --- |
| 연결 중 | 보임 | 보임(공개 규칙대로) | 보임 |
| 연결 끊김(ENDED, 숨김) | 보임 | 안 보임 — 행은 옛 `couple_id` 에 남아 있지만 읽는 쪽이 ACTIVE만 찾는다 | 안 보임 |
| 다른 사람과 새로 연결 | 보임 | **새 커플의 같은 날짜**만 조회된다 — 옛 날짜엔 새 커플 행이 없으니 비어 보인다 | 같은 이유로 비어 보인다 |
| 재회 후 복원 | 보임 | `RelationRecordRestorer` 가 새 관계로 옮겨 다시 보인다 | 다시 보인다 |
| 지난 기록 삭제 | 보임 | 행이 없다 | 행이 없다 |

- **빈 자리는 조용히 접는다.** "이 날의 우리 기록은 볼 수 없어요" 같은 안내를 띄우지 않는다. 이별한 사람에게 매번 그 사실을 알리는 문구가 된다. 섹션 자체를 그리지 않는다.
- 데이트 식단 복사본은 지난 기록 삭제 뒤에도 내 `meals` 에 남는다(`shared_group_id`·`created_by` 그대로). 그래서 밑바탕 식사에 "같이 먹기" 배지가 남을 수 있다. 일기 쪽에서는 배지를 그리지 않고 끼니·사진만 보여 주므로 이 화면에는 영향이 없다.
- 연결 이력 조회(ENDED 관계까지 찾아 옛 데이터를 보여주기)는 하지 않는다. 숨김은 사용자가 고른 상태다(§7).

### 3-4. 미연결 사용자

보이는 것: 무드(기록 자체의 값), 본문, 사진, 식사, 운동.
질문·우리 기록 섹션은 그리지 않는다. 서버는 활성 커플이 없으면 해당 필드를 `null` 로 주고, 404를 던지지 않는다.
기존 무드·질문·피드 API는 미연결이면 `RELATION_NOT_FOUND` 이므로, 집계 서비스는 그 서비스들을 거치지 않고 저장소를 직접 읽는다.

2. 2단계에서 "남기기"를 누르면 `PUT /me/journals/{오늘}` 에 `{ moodEmoji, body, photoUrl? }` 를 보낸다. 오늘 기록이 이미 있으면 본문을 미리 채워서 이어 쓰게 한다.
   "나중에"·바깥 누르기·뒤로 가기는 무드만 남기고 닫는다(지금 동작과 같은 결과).
3. **두 입력의 문구를 가른다**: 1단계 메모의 자리표시 문구를 "상대에게 한마디"로 바꾸고, 2단계에는 자물쇠 아이콘과 "나만 보여요"를 단다. 같은 시트에 공개·비공개 입력이 차례로 나오기 때문이다.
4. 길게 쓰고 싶으면 2단계의 "더 쓰기"가 작성 화면(§4-3)으로 이어진다.
5. 미연결: `POST /mood` 가 404이므로(§1-3) 미연결일 때는 1단계 메모칸을 숨기고 `POST /mood` 를 건너뛰고 기록에만 저장한다. 미연결 레이아웃에서 무드 버튼이 실제로 보이는지는 **확인 필요**(§0) — 안 보이면 미연결 입구는 §4-4 하나뿐이다.
6. 이참에 MoodPicker를 공용 `Sheet`(`components/Sheet.tsx`, 키보드 내리기·데스크톱 가운데 대화상자 처리 포함)로 옮긴다. 2단계에 텍스트 입력이 들어가므로 키보드 처리가 필요하고, `Sheet` 가 이미 그 처리를 한다.

**대안 — `sendMood` 성공 뒤 액션 토스트**("한 줄 남기기 →", `toast.success(msg, {label, onPress})`). 코드는 더 작다. 하지만 토스트는 몇 초 뒤 사라지고 누르기가 작다. 매일 열 이유를 만드는 입구로는 약하다. 2단계가 막히면 이쪽을 대신 쓴다.

계측: 2단계 노출 대비 저장 비율이 이 입구가 맞는지를 판정한다(§5-3).

### 4-3. 그날 페이지(작성·보기) — `JournalDay` 화면

```
 10월 2일 (목)                         [⋯ 공유 · 삭제]
 ─────────────────────────────────
 😊  ← 눌러서 바꾸기
 ┌ 🔒 나만 보는 기록 ───────────────┐
 │ (본문, 최대 2000자)              │
 └──────────────────────────────────┘
 [사진 1장 / + 사진]
 ── 이 날의 밑바탕 (2차) ──────────
 🍚 아침 · 점심(사진) · 저녁
 🏃 운동함 · 40분
 💬 오늘의 질문: "…" — 내 답 / 상대 답(공개 규칙대로)
 📷 우리 기록 사진 3장
```

- **수정**: 같은 화면에서 바로 고친다(하루 1개라 별도 수정 화면이 필요 없다). 맞춤법·띄어쓰기 바(`FeedComposeScreen` 에 있는 것)를 재사용할 수 있다. 저장 전에 나가면 dirty guard로 막는다.
- **삭제**: ⋯ 메뉴 → 확인 → `DELETE /me/journals/{date}` → 커밋 뒤 사진 삭제. 공유한 피드 글은 남는다(복사본이므로). 확인 문구에서 이를 알린다.
- **과거 날짜 쓰기**: 허용한다(오늘 이전만). 어제 못 쓴 걸 쓰는 게 일기의 기본 동작이다.
- **사진 교체**: 새 사진을 올리고 저장이 커밋된 뒤 옛 URL을 지운다.
- **"우리 기록에 공유하기"** (연결된 경우에만 메뉴에 보인다):
  1. 확인 시트를 띄운다 — 미리보기(본문·사진), 본문은 **공유본에서만** 고칠 수 있다(원본은 그대로). 안내 문구 "상대에게 알림이 가요 · 이후 고쳐도 공유된 글은 바뀌지 않아요".
  2. `POST /me/journals/{date}/share { content }` → 서버가 사진을 복사하고(§1-5 A안) `FeedService.createPost` 의 내부 경로로 글을 만든다. 그러면 푸시(앞 40자)와 `CoupleEvent.FEED` 가 기존과 똑같이 나간다. 그다음 `shared_post_id` 를 저장한다.
  3. 이미 공유했으면 메뉴가 "공유한 글 보기"로 바뀐다(`shared_post_id` 가 null이 아닐 때). 한 기록에서 공유는 한 번만 — 서버 측 사진 복사의 상한이 이것이다.
  4. 무드는 공유본에 넣지 않는다. 무드는 이미 상대에게 보이는 별도 채널(`/mood`)이 있다.
- 공유 흐름은 `FeedComposeScreen` 을 재사용하지 않는다. 그 화면은 파라미터를 받지 않고(`types.ts:29`·`:282`), 앱이 사진을 업로드하는 흐름이라 §1-5 C안이 된다.

### 4-4. 미연결 홈 "혼자서도 시작할 수 있어요"

`HomeScreen.tsx:955-971` 의 `<SettingsGroup>` 에 `<SettingsRow>` 3개(운동·식단·장소)가 하드코딩돼 있다(배열이 아니다).

## §5 한도·과금·계측

### 5-1. 사진 한도

**사실**: `PHOTO_UPLOAD`(FREE 월 60 / PRO 월 1000)는 **커플 단위**이고(`Feature.isCoupleScoped`, 커플이 없으면 본인 몫), `POST /uploads/signature` 에서 서명을 내줄 때 1장씩 차감한다.
주석(`Feature.java:356-357`)에 적힌 대로 "서명 발급 시점에 용도를 알 수 없어" 식단·체중 사진도 이미 이 커플 몫에서 나간다.
선례도 둘 있다. 용도별 폴더 서명을 따로 두고 `PHOTO_UPLOAD` 를 차감하는 `CoupleEmojiService`(:160-168), 그리고 아예 세지 않는 `CatchMindService`(:263).

| 안 | 내용 | 문제 |
| --- | --- | --- |
| a. 그대로 `PHOTO_UPLOAD` | 앱 변경 없음 | 매일 사진을 붙이면 **한 사람이 커플 FREE 한도 60장의 절반(30)을 먹는다.** 상대는 피드에 사진을 못 올리게 되고, 402 업셀이 일기 때문에 피드에서 터진다. 개인 기록이 커플 몫을 깎는 모양이 원칙 2(사람 소유)와 어긋난다 |
| b. 서명에 용도 파라미터 | 기존 엔드포인트에 `?purpose=JOURNAL` | 클라이언트가 용도를 속일 수 있다(서명은 같은 계정에 쓰인다) — c와 같은 일을 덜 깔끔하게 하는 셈 |
| **c. 전용 서명 + 전용 Feature (권장)** | `POST /me/journals/photo-signature` → 폴더 `journal/`, `Feature.JOURNAL_PHOTO("기록 사진", Quota.perDay(3), Quota.perDay(3))`, 사람 단위 | 하루 3장은 "1장 + 교체 2번"의 사고 방지선이다. FREE=PRO라 `isListed()` 가 false가 되어 결제 비교표에 안 나오고, `CSV_EXPORT` 처럼 업셀하지 않도록 `PlanGuard` 의 upsells에서 뺀다. 원가 상한은 사람당 월 약 90장, 실제로는 하루 1장 → 월 30장 × 약 300KB ≈ 9MB/인 |
| d. 세지 않음 | CatchMind처럼 | 교체를 반복하면 상한이 없다 |

`JOURNAL_PHOTO` 를 추가하면 프론트 `types/index.ts` 의 `FeatureKey` 에도 넣어야 `PlanFeatureSyncTest` 가 통과한다. 앱은 `utils/imageUpload.ts` 의 기존 `uploadImageWithSignature` 를 그대로 쓴다.

### 5-2. 기록 무료, 월간 AI 회고만 PRO

- 기록·사진·밑바탕·공유·내보내기는 **게이트 없음**(데이터 인질 금지). 기록 화면 어디에도 잠금 배지를 두지 않는다.
- 3차 `AI_JOURNAL_RECAP("한 달 회고", Quota.blocked(), Quota.perMonth(2))`:
  - 개인 판정(`isCoupleScoped` 에 넣지 않는다 — 일기는 커플 결과물이 아니다). `group()` 은 AI. `AI_TOTAL` 안전망이 그대로 걸린다.
  - 월 2회 = 생성 1 + 다시 쓰기 1. 결과는 저장한다(다시 읽는 것이 회고의 가치다) → 새 테이블 `journal_recaps(user_id, month, content, created_at, UNIQUE(user_id, month))` + `UserDataPurger` + `ExportSection`.
  - `PlanFeatureSyncTest` 는 `types/index.ts` 의 `FeatureKey` 에 같은 키를 넣어야 통과한다. 결제 화면 비교표에 자동으로 한 줄 생긴다(`isListed` = true).
  - "PRO 대표 기능"(`isHero`)에는 넣지 않는다 — 동의한 사람만 쓰는 기능이라 대표 문구가 될 수 없다.
- **동의 토글(원칙 3, 기본 꺼짐)**: `users.journal_ai_consent_at TIMESTAMP NULL`(null = 꺼짐).
  선례는 `users.auto_analyze_meal_photo`(`User.java:122`, `UserResponse` 에 노출)다. 다만 불리언이 아니라 **시각**으로 두는 것은, 동의는 "언제 켰는지"가 남아야 하기 때문이다.
  `UserResponse` 는 본인에게만 가고, 상대에게는 `PartnerUserResponse` 가 가므로 동의 여부가 새지 않는다.
  끄면 다음 회고부터 안 보낸다. 이미 만든 회고는 사용자가 지울 수 있다. 동의 없이 `AI_JOURNAL_RECAP` 을 호출하면 402가 아니라 409/400 계열의 별도 에러 코드로 막는다(결제를 권하면 안 되는 상황이다).
- 일기 본문이 Gemini(제3자)로 간다 → **개인정보처리방침 개정 가능성이 높다**(`constants/legal.ts` + `PolicyVersion` 상향 → 재동의 게이트, `PolicyVersionSyncTest`). 3차 비용에 포함한다.

## §7 하지 않을 것

- **우리 탭 게시물의 "나만 보기"** — 방향 문서 §4에서 기각. 피드 쿼리마다 필터가 필요하고, 하나라도 빠지면 노출 사고다.
- **구조화 필드**(체중·생리·수면·증상·태그·위치·날씨) — 원칙 6.
- **홈 칩 추가·탭 추가** — 원칙 4. 입구는 MoodPicker 2단계, MY 행, 미연결 홈 행뿐이다.
- **상대·트레이너에게 "오늘 일기를 썼다" 신호** — 연속 작성일을 상대 화면·주간 레터·스트릭·홈 아바타에 보이지 않는다. 내용이 아니어도 "썼다/안 썼다"는 그 자체로 사적인 정보다.
- **`mood_statuses` 참조로 무드 대체** — §1-3. 미연결에서 안 되고, 지난 기록 삭제 때 사라진다.
- **`couple_emoji_id` 저장** — 관계 소유 자산이라 지워지고, 이별 후 일기에 상대가 그린 얼굴이 남는다.
- **기존 AI 프롬프트(식단 코치 등)에 일기를 맥락으로 넣기** — 원칙 3. AI는 회고 하나, 동의한 경우에만.
- **일기 본문이 담긴 푸시·리마인더 미리보기** — 리마인더를 만들더라도 고정 문구만 쓴다.
- **공유본과 원본의 동기화** — 공유는 복사본이다. 원본을 고쳐도 피드 글은 그대로다.
- **같은 Cloudinary URL을 일기와 피드 글이 함께 가리키는 것** — §1-5.
- **끊긴 관계의 옛 커플 데이터를 밑바탕에 다시 보여주기** — 숨김은 사용자가 고른 상태다.
- **앱 잠금(비밀번호·생체인증)** — 기기 단위 잠금은 별개 기능이고 네이티브 빌드가 필요하다. 요구가 나오면 따로 본다.
- **일기 사진의 비공개 저장(authenticated delivery)** — 앱 전체 이미지 정책의 문제다(`DATA_SAFETY_INFRA`). 폴더만 분리해 여지를 남긴다.
- **기존 월 그리드 4곳의 `MonthGrid` 교체** — 이번 범위를 키우지 않는다. 일기에서 먼저 쓰고 나머지는 별도 작업.

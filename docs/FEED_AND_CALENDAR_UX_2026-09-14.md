# 우리 기록 UX + 데이트 식단 캘린더 연동 (2026-09-14)

두 가지를 다뤘다. ① 식단의 데이트 기록을 캘린더에 연동하는 방식 결정, ② "우리 기록"(피드)
화면의 UI/UX·데이터 분석과 수정. 둘 다 구현까지 끝냈고, 여기엔 **왜 그렇게 정했는지**를 남긴다.

---

## 1. 데이트 식단 ↔ 캘린더 연동

### 결론: `couple_events` 에 행을 만들지 않고 **오버레이**로 그린다

캘린더가 월 단위로 데이트 식단을 읽어 그리드에 마커를 찍는다. 여행 기간 띠가 이미 같은
방식이다([CoupleCalendarScreen.tsx](../frontend/src/screens/home/CoupleCalendarScreen.tsx) —
`tripDays`).

### 자동 일정 생성을 버린 이유

데이트 식단을 기록할 때마다 `EventType.DATE` 행을 만드는 안도 있었다. 셋이 걸린다.

| 문제 | 내용 |
|---|---|
| **플랜 한도 잠식** | `CALENDAR_EVENT` 는 FREE 월 10건([Feature.java](../backend/src/main/java/com/fitto/common/plan/Feature.java)). 자동 생성이 이걸 먹으면 진짜 일정을 못 넣고, 402 가 캘린더가 아니라 **식단 저장에서** 터진다 |
| **양방향 동기화** | 식단 수정·삭제·"같이 먹기" 해제·캘린더 일정 삭제 — 네 경로를 다 맞춰야 한다 |
| **성격 충돌** | 일정은 약속(미래), 식단은 기록(과거). 한 표에 섞이면 "다가오는 일정"이 흐려진다 |

오버레이는 셋 다 피하고, 새 테이블이 없으니 **Purger·Flyway 변경도 없다**.

### 장소가 붙은 것만 올린다 (중요)

모든 데이트 식단을 올리면 안 된다. 자주 만나거나 동거하는 커플은 "같이 먹기"를 **매일**
찍는다 — 달력이 마커로 덮여 의미를 잃는다.

장소 연결(`place_visits.meal_id`)이 **외식과 집밥을 가르는 선**이고, 마침 "어디서 먹었는지"가
캘린더에 남길 이유 그 자체다. 이 데이터는 이미 있었고 쓰이지 않고 있었을 뿐이다.

### 구현

- `GET /api/v1/calendar/date-meals?year&month` — 조회만. 고치려면 원본 식단을 고친다
- [DateMealCalendarService](../backend/src/main/java/com/fitto/calendar/service/DateMealCalendarService.java) — 쿼리 3방(끼니 / 방문+장소명 / 럽슐랭 tier), 전부 배치
- 컨트롤러를 `CalendarController` 와 분리했다 — `/calendar/events/` 아래 두면 "이벤트의 한 종류"로 오해된다
- 그리드 마커는 **속이 빈 점**: 채워진 점(앞으로 있을 일정)과 갈라 읽혀야 한다

### 남은 가능성

캘린더가 "과거 기록 레이어"를 갖게 되면서 여행 띠 + 데이트 식단 + 럽슐랭 등급이 한 화면에
모였다. 여기에 홈의 "작년 오늘"을 붙이면 **우리 연표**가 된다 — 미착수.

## 2. "우리 기록"(피드) 분석

### 문제 ① 응원이 기록보다 컸다 (사용자 지적)

상대방 자동 기록 카드(운동·식단·맛집) 한 장의 실측:

| 구성 | 높이 |
|---|---|
| 상하 패딩 | 16px |
| **기록 본문** (아이콘 34px 행) | **34px** |
| 리액션 여백 | 4px |
| **리액션 칩** (`minHeight: layout.touchTarget`) | **44px** |
| 합계 | **98px** |

리액션이 48px — **카드의 49%**, 정보를 담은 본문(34px)보다 크다. 가로로도 빈 칩 5개 +
들여쓰기 42px ≈ 218px 로 콘텐츠 폭의 **약 2/3**를 먹었다. 그 칩들은 **대부분 아무도 안 누른
빈 버튼**이다.

주범은 `minHeight: layout.touchTarget`(44px). 접근성 터치 타깃을 지키려 넣은 값이 칩 5개짜리
행에 붙으면서 카드를 두 배로 키웠다.

**수정**: 본문 행 안의 버튼 하나로 접고, 누를 때만 편다. 버튼이 행 높이 안에 들어가므로
카드가 세로로 자라지 않는다 — **98px → 60px**. 터치 타깃은 그 버튼 하나만 지키면 되니
접근성도 유지된다. 카드 롱프레스에도 같은 피커를 달아 발견성을 보완했다.

사진 포스트(`PostCard`)는 그대로 뒀다 — 카드가 크니 이모지 줄이 기록을 누르지 않는다.

### 문제 ② 제목과 내용이 뒤집혀 있었다

```
[🏋️]  운동 완료 💪            ← 굵은 16px, 모든 운동 카드가 동일
       벤치프레스 외 3개 · 40분   ← 작은 회색 13px, 1줄 자름  ← 진짜 정보
```

고정 문구가 시선을 먹고 실제 기록이 회색 부제로 밀렸다. 스크롤하면 "운동 완료 💪 / 아침
식단 🍽️"만 반복해 읽힌다. 게다가 왼쪽 색깔 아이콘이 이미 종류를 말하므로 제목의
💪🍽️📍🎬 은 **세 번째 중복**이었다.

**수정**: 제목에 실제 기록, 부제에 분량.

```
[🏋️]  벤치프레스 외 1개
       7세트 · 4,800kg · 40분      ← 총 볼륨은 새로 추가

[🍽]  삼겹살 외 2개  〔함께〕      ← 데이트 식단 배지
       점심 · 820kcal · 📍트라토리아  ← 장소는 새로 추가
```

제목의 이모지는 제거했다.

### 문제 ③ 데이트 식단이 피드에 두 번 떴다 — 버그

[FeedService.timeline](../backend/src/main/java/com/fitto/feed/service/FeedService.java) 이
`userIds = [나, 상대]` 양쪽 `meals` 를 긁는데 `shared_group_id` 중복 제거가 없었다. "같이 먹기"는
커플 양쪽에 짝을 만드는 구조라([Meal.java](../backend/src/main/java/com/fitto/diet/domain/Meal.java)),
둘이 같이 먹은 한 끼가 **똑같은 카드 두 장**으로 나왔다.

**수정**: 쿼리에서 거른다. 복제본만 `created_by`(원 등록자)가 `user_id` 와 다르므로
`(m.createdBy is null or m.createdBy = m.userId)` 한 줄로 정확히 걸러진다 — 원본과 일반 기록은
`created_by` 가 null 이다.

> **화면단에서 묶지 않은 이유**: 커서 페이징이라 짝의 한쪽만 페이지에 실리면 중복 제거가
> 페이지를 넘지 못한다. 캘린더 오버레이도 같은 규칙을 쓴다(`findSharedInPeriod`).

### 문제 ④ 있는 데이터가 안 내려갔다

- **식단**: `placeId`/`placeName` 이 `MealResponse` 엔 있는데 피드엔 없었다 → 추가
- **식단**: 데이트 식단 여부(`isSharedMeal()`) → `shared` 필드 추가, 화면은 '함께' 배지
- **운동**: `WorkoutSet` 에 `sets`/`reps`/`weightKg` 가 다 있는데 요약은 종목 수와 분뿐 → 세트 수·총 볼륨 추가
- **맛집**: 럽슐랭 tier — 피드엔 아직 미반영(캘린더 오버레이에만 들어갔다)

볼륨은 세트별 상세(`WorkoutSetEntry`)가 아니라 요약 필드로 계산한다. 한 줄 요약이라 근사치로
충분하고, 페이지마다 entries 를 훑으면 조회가 배로 는다.

## 3. 사고 기록 — 주 워크트리 동시 편집으로 작업 유실

작업 도중 **미커밋 편집분이 전부 날아갔다.** 다른 세션이 같은 주 워크트리에서
`git merge origin/main`(26건)을 실행했고, 충돌로 멈춘 그 병합이 작업 트리를 덮었다.

CLAUDE.md 5절이 "병렬 작업은 반드시 각자 워크트리에서" 라고 적어둔 바로 그 사고다.
**브랜치만 나누는 것으로는 부족하다** — 같은 워크트리를 쓰면 파일은 하나다. 이후 작업은
`.claude/worktrees/` 아래 격리된 워크트리에서 진행했다.

재작성 비용은 컸지만 설계·코드·테스트가 대화에 남아 있어 복원은 됐다. 교훈은 하나:
**세션을 시작할 때 워크트리부터 나눈다.**

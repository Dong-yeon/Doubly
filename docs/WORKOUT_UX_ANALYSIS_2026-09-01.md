# 운동 기능 사용성 분석 — "왜 만든 사람도 안 쓰는가" (2026-09-01)

> **분석 방법**: 코드 정독 + **로컬에 백엔드·앱을 실제로 띄워 자유 운동 세션을 처음부터 끝까지
> 직접 기록해봤다**(웹 빌드, 로컬 Postgres/Redis). 여기 적힌 마찰은 대부분 그 워크스루에서 나온 것이다.
> 경쟁 앱 비교는 웹 검색으로 "사람들이 실제로 칭찬하는 지점"을 모아 대조했다.
>
> **전제 하나**: 지금 쓰신다는 "다른 앱"이 뭔지 몰라서, 강점이 자주 언급되는
> Strong / Hevy / 번핏을 기준으로 잡았다. 실제로 쓰시는 앱이 다르면 3장 우선순위가 달라질 수 있다.

---

## 0. 결론 먼저

**운동 세션 화면 자체는 이미 경쟁력이 있다.** 세트별 무게·횟수·RPE, 완료 체크, 자동 휴식 타이머,
직전 기록 프리필, e1RM 실시간 표시, 세트 유형(워밍업/탑/백오프/드롭), 대체 종목, 순서 변경,
루틴 역방향 저장까지 들어 있다. 이건 Strong/Hevy 의 핵심 루프와 견줄 만하다.

**그런데 그 좋은 화면에 도달하기 전과 후가 비어 있다.** 정리하면 세 가지다.

| # | 문제 | 한 줄 요약 |
|---|---|---|
| 1 | **종목을 매번 손으로 타이핑한다** | 카탈로그가 있는데 "＋운동 추가"가 안 쓴다. 게다가 카탈로그가 34개뿐 |
| 2 | **하던 운동이 소리 없이 사라진다** | 탭 하나 잘못 누르면 진행 중 세션이 증발. "이어서 하기" 진입점이 없다 |
| 3 | **쌓인 기록이 아무것도 돌려주지 않는다** | 통계가 "며칠 했나"뿐. 무게가 늘고 있는지 볼 방법이 없다 |

3번이 가장 크다. 기록 앱을 계속 쓰는 이유는 기록 자체가 아니라 **기록이 만들어주는 그래프**인데,
지금 Dubly 는 넣기만 하고 돌려주는 게 없다.

## 1. 직접 해보며 걸린 것 (워크스루)

### 1-1. 종목 추가가 자유 입력 폼이다 — 그런데 카탈로그는 이미 로드돼 있다

`자유 운동 → ＋운동 추가` 를 누르면 나오는 건 **텍스트 입력 폼**이다.
"벤치"라고 쳐도 자동완성이 뜨지 않는다. 부위 선택지는 `근력 / 유산소 / 유연성` 셋뿐이다.

그런데 코드를 보면:

- `WorkoutSessionScreen` 은 진입 시 **전체 종목 카탈로그를 이미 받아 메모리에 들고 있다**
  (`workoutApi.exerciseCatalog()`, 486~494행)
- 부위→기구로 좁혀 고르는 **`ExercisePickerModal` 도 이미 붙어 있다**
- 다만 그게 **"⇄ 대체 종목으로 바꾸기"에만 연결돼 있다**(1352행). 정작 주 경로인 "＋운동 추가"는 안 쓴다.

즉 **좋은 부품이 있는데 주 동선에 안 꽂혀 있다.** 이건 기능 개발이 아니라 배선 문제에 가깝다.

**카탈로그 크기도 문제다.** 실제로 API 를 찔러보니 **34개**다(부위 7개 × 4~6개).
번핏·Hevy·Strong 은 수백~1000개 단위다. 34개로는 "고르기"가 성립하지 않으니
자유 입력이 남아 있는 것도 이해는 된다 — **순서가 뒤집혀 있다. 카탈로그를 채워야 피커가 의미를 갖는다.**

자유 입력이 남기는 2차 피해:

- 같은 운동을 "벤치", "벤치프레스", "벤치 프레스"로 적으면 **서로 다른 종목이 된다**
  → 직전 기록 프리필도, 종목별 추이도, PR 판정도 다 갈라진다
- `근력/유산소/유연성` 3분류로는 **"이번 달 가슴을 몇 세트 했나"를 만들 수 없다**.
  번핏 사용자들이 가장 자주 칭찬하는 "부위 빈도 리포트"가 원천적으로 불가능하다

### 1-2. 세트 2·3의 무게가 안 따라온다

1세트에 60kg 을 넣고 체크했는데 **2·3세트 무게 칸은 그대로 비어 있다**(횟수만 10으로 차 있다).
같은 무게로 3세트 하는 게 기본인데 매 세트 숫자를 다시 친다.

Strong/Hevy 는 직전 세트 값을 그대로 물려준다. 체감 차이가 큰 지점이다 —
5종목 × 4세트면 **한 세션에 20번 덜 치느냐 더 치느냐**의 문제다.

### 1-3. 하던 운동이 소리 없이 사라진다 ← **가장 치명적**

세션 중에 하단 탭바(채팅)를 눌렀더니 **경고 없이 세션에서 빠져나왔다.**
다시 운동 탭으로 돌아오니 **진행 중이라는 표시가 어디에도 없었다.** 홈에는 "자유 운동 / 맞춤 운동"
버튼만 있고 "이어서 하기"가 없다. 자유 운동을 다시 누르니 **빈 세션이 새로 시작**됐다.

코드상 복구 장치(`sessionDraft.ts`)는 있는데 조건이 좁다:

- `hasProgress()` — **체크한 세트가 하나라도 있어야** 복구 대상이다(79~81행).
  종목만 추가하고 아직 체크 전이면 그냥 버려진다
- 복구는 **세션 화면에 들어갔을 때 뜨는 다이얼로그**가 전부다. 운동 홈에는 진입점이 없다
- 스냅샷 주기는 10초 — 마지막 10초는 날아간다

경쟁 앱은 진행 중 세션을 **화면 하단에 고정 바로 붙여둔다**(Strong/Hevy 공통).
어디를 돌아다녀도 "운동 중"이 보이고, 눌러서 돌아온다. 잃어버릴 수가 없다.

> 헬스장에서 노래 바꾸고, 카톡 답하고, 다시 앱으로 오는 건 **매 세트마다 일어나는 일**이다.
> 그때마다 기록이 날아갈 수 있으면 그 앱은 못 쓴다. 이게 "나도 다른 앱 쓴다"의 가장 유력한 단일 원인이다.

### 1-4. 기록 목록에 같은 세션이 두 번 나온다

저장 후 운동 홈에 `진행한 운동` 과 `히스토리` 두 섹션에 **동일한 세션이 중복 표시**됐다.
오늘 것이 양쪽에 다 걸리는 구조로 보인다.

### 1-5. 홈의 주 버튼이 AI다

운동 탭 하단의 초록(주) 버튼이 `✨ 맞춤 운동`(AI 추천)이고, `자유 운동`이 보조다.
**매일 여는 사람에게 필요한 주 버튼은 "오늘 루틴 시작" 또는 "지난 운동 반복"이다.**
AI 추천은 한 달에 한 번 쓸까 말까 한 기능인데 가장 좋은 자리를 차지하고 있다.

## 2. 경쟁 앱이 칭찬받는 지점과의 대조

검색으로 모은 "사용자들이 실제로 좋다고 말하는 것":

| 앱 | 사람들이 꼽는 강점 | Dubly 현황 |
|---|---|---|
| **Strong** | 군더더기 없는 최소 로깅. "세트 넣고, 진행 보고, 끝". 정밀한 세트 유형·휴식 제어, CSV 내보내기 | 로깅 루프는 유사 수준 ✅ / 내보내기 ❌ |
| **Hevy** | 넉넉한 무료 티어, **소셜 피드**(팔로우·댓글), PR 추적, 차트. "불필요한 게임화·업셀 없음" | 소셜은 커플로 한정 ⚠️ / PR·차트 ❌ |
| **Jefit / Fitbod** | 방대한 종목 DB, 종목별 가이드 | 종목 34개 ❌ |
| **번핏** | **회차별 일지 + 시각화 리포트** — 루틴 수행 내역, **부위 빈도**, **기록 변화 흐름 그래프** | 전부 없음 ❌ |

그리고 리텐션 조사에서 반복적으로 나오는 두 문장:

- **"로깅 속도가 계속 쓸지 여부를 가장 잘 예측한다"** — 입력이 귀찮아지는 순간 그만둔다
- 피트니스 앱은 **3일 내 DAU 77% 이탈, 30일 잔존 8~12%** — 수동 입력 앱일수록 낙폭이 크다

Dubly 의 로깅 루프는 나쁘지 않다. **문제는 로깅 앞(종목 선택)과 뒤(보상)다.**

## 3. 그래서 뭘 해야 하나 — 순서대로

### 1순위: 세션을 잃어버릴 수 없게 만든다 — ✅ 2026-09-01 적용

> 원인은 세 겹이었다: ① 탭 누르면 popToTop 으로 세션 화면이 언마운트 ② 언마운트 정리가
> 초안을 무조건 삭제 ③ hasProgress 가 "체크한 세트"를 요구. 운동을 "끝낼 때까지 살아 있는 것"
> 으로 모델을 바꾸고, 전역 고정 바 + 재개 카드를 붙였다. "종료"는 "버리기"(명시적 확인)로 바꿨다.


- 진행 중 세션을 **앱 전역 고정 바**로 노출(어느 탭에 있든 "운동 중 12:34 · 3세트" + 탭하면 복귀)
- 운동 홈 최상단에 **"이어서 하기"** 카드
- `hasProgress` 조건 완화 — 종목만 추가한 상태도 복구 대상에 넣는다
- 스냅샷을 10초 주기 + **변경 시점**에도 저장

> 이건 기능 추가가 아니라 **신뢰 문제**다. 한 번 날려먹은 앱은 다시 안 연다.

### 2순위: 기록이 돌려주는 걸 만든다 — ✅ 2026-09-01 적용

> `GET /workout/exercises/history` + ExerciseHistoryScreen(최고 기록 3종·추이 그래프·세션 목록),
> 세션 중 실시간 신기록 배지. 집계는 요약 필드가 아니라 세트별 entries 에서 뽑는다 —
> WorkoutSet.weightKg 는 마지막 세트 값이라 백오프(80→70→60)에서 PR 세운 날이 퇴보한 날로 보인다.
> 그래프 기본 축을 e1RM 으로 둔 이유: 실제 검증 데이터에서 e1RM 은 80→88.7→93.3 으로 오르는데
> 볼륨은 1680→1560 으로 내려갔다. 같은 데이터가 축에 따라 반대 이야기를 한다.
>
> **부위별 빈도는 여전히 못 한다** — 3순위(카탈로그·부위 분류)가 선행돼야 한다.


- **종목별 상세**: 그 종목의 무게·볼륨·e1RM 추이 그래프, 전체 세트 히스토리
- **PR 배지**: 최고 무게/최고 볼륨/최고 e1RM 갱신 시 세션 중에 즉시 알려주기
  (e1RM 은 이미 계산하고 있다 — 저장·비교만 하면 된다)
- **부위별 빈도**: 단, 이건 3순위가 선행돼야 가능하다

지금 통계 화면은 `이번 주/이번 달/누적 일수` + `최근 7일 체크` + `부위별 세트 수(3분류)` 가 전부다.
**"내가 세지고 있나"에 답하지 못한다.**

### 3순위: 종목 카탈로그를 제대로 만들고 주 동선에 꽂는다 — ✅ 2026-09-01 적용

> 카탈로그 34 → **245개**(V73), `aliases` 컬럼 추가, `＋운동 추가`를 피커 + 검색으로 교체.
> SQL 은 `docs/EXERCISE_CATALOG_DRAFT.md` 의 표에서 생성했다 — 이름을 고칠 일이 생기면
> 문서를 고치고 다시 만든다.
>
> 검색 중에는 부위·기구 칩을 접고 전체를 훑는다. 검색은 "어디 있는지 모를 때" 쓰는 것이라
> 부위를 먼저 고르라고 하면 "풀오버가 등인가 가슴인가"를 사용자가 알아야 한다.
>
> **기존 기록 이름 매핑** ✅ 2026-09-01 (V74) — 아래 별도 항목 참고.
> 세부 부위(`sub_group`)는 여전히 미적용 — 초안 문서 1절 (가) 참고.

### 3순위 후속: 기존 기록 이름 매핑 — ✅ 2026-09-01 적용 (V74)

조회가 전부 `exercise_name` **문자열**로 묶이는 구조라(`WorkoutSetRepository`), 자유 입력
시절의 "벤치"/"벤치 프레스"/"Bench" 는 서로 다른 종목으로 취급됐다. 추이가 토막 나고,
PR 기준값이 그 토막 안에서만 잡혀 신기록이 아닌데 신기록으로 뜨고, 프리필도 안 걸린다.
`workout_sets.muscle_group` 이 비어 있어 그 기록들은 근육 회복에서도 통째로 빠져 있었다.

**매칭은 두 단계, 둘 다 완전 일치만 쓴다.** 기록의 이름을 바꾸는 일이라 부분 일치·유사도로
틀리면 남의 기록이 엉뚱한 종목의 추이에 섞인다.
1. 공백·대소문자만 무시한 이름 일치 (`"벤치 프레스"` → `벤치프레스`)
2. 별칭 한 칸과 통째로 일치 (`"턱걸이"` → `풀업`) — 이름 일치가 항상 우선
어느 쪽도 아니면 손대지 않는다. 카탈로그에 없는 진짜 커스텀 종목이기 때문이다.

`muscle_group` 은 카탈로그 값으로 **덮어쓰고** `equipment` 는 비어 있을 때만 채운다(V40 과 같은
처방). 기구는 사용자가 바꿔서 할 수 있지만(스쿼트를 스미스머신에서) 자극 부위는 종목의
성질이라 수행 방식에 따라 안 변하고, 카탈로그가 그 태그의 출처이기 때문이다.

**곁다리로 잡은 것**: V73 에서 `행잉 니레이즈`가 `행잉 레그레이즈`의 별칭으로 들어가 있었다.
둘은 별개 종목이다(무릎 접어 올리기 vs 다리 편 채 올리기). 245개 전수 확인 결과 별칭이 다른
종목의 이름과 겹치는 건 이 한 건뿐이었고, V74 에서 함께 고쳤다.

**남은 구멍**: 새 기록은 서버가 이름을 정규화하지 않는다 — 클라이언트가 보낸 `exerciseName`
을 그대로 저장한다. 피커의 자유 입력 폴백으로 "턱걸이"를 다시 치면 또 미연결 행이 생긴다.
피커가 주 동선이 된 지금은 재발 확률이 낮다고 보고 두었지만, 근본 해법은 `WorkoutService.save`
에서 서버가 카탈로그에 맞춰보는 것이다(모든 클라이언트를 한 곳에서 커버한다).


- 카탈로그를 34개 → **최소 200~300개**로 확장(부위·기구·한글/영문 별칭 포함)
- `＋운동 추가` 를 **`ExercisePickerModal` + 검색 + 최근/즐겨찾기**로 교체
  (부품은 이미 있다 — 연결만 하면 된다)
- 자유 입력은 "목록에 없으면 직접 추가"로 <b>후순위</b>에 두고, 추가 시에도 부위·기구를 받는다
- 기존 자유 입력 기록은 이름 정규화로 카탈로그에 매핑 시도

### 4순위: 입력 손맛 — ✅ 일부 적용 (2026-09-01)

**적용**

- **직전 세트 무게·횟수 승계** — 세트를 체크하면 다음 세트가 비어 있을 때 물려받는다.
  이미 값이 있으면 안 건드리고(루틴이 정한 램핑 무게 보호), 웜업 다음 세트에는 물려주지 않는다.
- **무게 ±2.5/±5 스테퍼** — 상시 노출이 아니라 <b>지금 만지는 세트 아래에만</b> 나타난다.
  이미 빽빽한 줄(번호·무게·×·횟수·RPE·체크)에 상시로 달면 숫자 입력이 오히려 어려워진다.
  증분이 2.5/5 인 건 원판이 양쪽에 붙어서 한쪽 1.25kg = 총 2.5kg 이 최소 실제 단위이기 때문.
- **원판 계산기** — 한쪽 기준으로 보여준다(양쪽 합은 결국 다시 반으로 나눠야 한다).
  바 무게 20/15/10/없음 선택, 만들 수 없는 무게는 숨기지 않고 "N kg 모자라요"로 알려준다.

**미적용 — 이유**

- **화면 꺼짐 방지**: `expo-keep-awake` 가 `expo` 안에 중첩 설치돼 있어 앱에서 import 가 안 된다.
  직접 의존성으로 올려야 하는데(`npx expo install expo-keep-awake`) 네이티브 재빌드가 필요하고,
  마침 App Store 제출 빌드가 도는 중이라 그 작업과 겹치지 않을 때 넣는 게 안전하다.
- **kg/lb 전환**: 저장은 전부 kg 이라 표시·입력·집계 전 구간에 환산이 들어간다. "손맛"이 아니라
  구조 변경이고, 한국 사용자 대상이라 우선순위도 낮다.
- **슈퍼세트**: 세트 그룹이라는 개념이 데이터 모델에 없다. 도메인 변경이라 별도 작업.

### 5순위: 커플이라는 차별점을 운동에서 쓴다

경쟁 앱이 못 하는 유일한 자리다. 조사에서 커플 운동 앱의 핵심으로 꼽힌 건
**"기록 공유"가 아니라 "같이 나타났다는 증거"** 였다:

- 둘의 **주간 캘린더를 나란히** — 빈칸이 서로에게 보인다
- 상대가 운동을 시작하면 실시간 알림("지금 운동 시작했어요")
- 가벼운 내기(주간 목표 미달 시 저녁 사기) — 이미 `ChallengeScreen` 이 있으니 확장
- 세트 완료 시 상대가 녹음한 음성 응원 — **이미 있다**(`VoiceClipsScreen`). 잘 만든 기능인데
  운동 홈에서 존재감이 거의 없다

### 정리: 4순위 이후 남은 작업

4순위까지는 "쓸 이유는 만들었다" 단계고, 아래는 전부 미착수다. 순서는 **막힌 이유가 풀리는 대로**
할 수 있는 것 → **도메인 변경이 필요해서 별도 작업**인 것 → **5순위(커플 차별점)** 순.

| 항목 | 막힌 이유 / 필요 작업 | 풀리는 조건 |
|---|---|---|
| 화면 꺼짐 방지 (`expo-keep-awake`) | `expo` 안에 중첩 설치라 import 불가 → 직접 의존성으로 올리고 네이티브 재빌드 필요 | **App Store 제출 빌드가 끝나면** 바로 착수 가능 — 코드 변경 자체는 이미 파악됨 |
| kg/lb 전환 | 저장이 전부 kg — 표시·입력·집계 전 구간에 환산이 들어가는 **구조 변경**(4순위 "손맛"이 아님) | 한국 사용자 대상이라 우선순위 낮음. 필요해지면 별도 작업으로 |
| 슈퍼세트 | "세트 그룹" 개념이 데이터 모델에 없음 — **도메인 변경** | 별도 설계 필요 (스키마 + 세션 화면 UI) |
| 서버 측 종목 이름 정규화 | `WorkoutService.save` 가 클라이언트가 보낸 `exerciseName` 을 그대로 저장 — 피커 우회(자유 입력)로 다시 미연결 행이 생길 수 있음 (V74 매핑 후속, 3순위 절 참고) | 재발 빈도를 보고 판단 — 지금은 피커가 주 동선이라 낮음 |
| `sub_group` 컬럼 (세부 부위) | `muscle_group` 7개론 "이번 달 팔 40세트"까지만 되고 이두/삼두 구분이 안 됨 — 카탈로그 초안 1절 (가) | 부위 빈도 리포트 같은 기능을 실제로 만들 때 |
| **5순위: 커플이라는 차별점** | 아래 4개 전부 미착수 — 코드 변경보다 **기획/UI 결정**이 먼저 필요 | — |
| ├ 둘의 주간 캘린더 나란히 (빈칸이 서로에게 보임) | 화면 신설 | |
| ├ 상대 운동 시작 시 실시간 알림 | 알림 인프라는 있음(`NotificationService`) — 트리거 지점만 추가 | |
| ├ 가벼운 내기 (주간 목표 미달 시 저녁 사기) | `ChallengeScreen` 확장 | |
| └ 세트 완료 시 음성 응원 노출 강화 | `VoiceClipsScreen` **이미 있음** — 운동 홈 진입 동선만 문제 | 코드보다 "어디에 보여줄지" 결정이 먼저 |

가장 먼저 풀리는 건 **화면 꺼짐 방지**(App Store 빌드 완료 대기 중, 그 외엔 막힌 게 없음)이고,
가장 값싼 건 **음성 응원 노출**(새 기능이 아니라 이미 있는 기능을 눈에 띄게 옮기는 일)이다.

## 4. 한 줄 정리

> Dubly 운동은 **엔진은 괜찮은데 시동 걸기가 불안하고, 달린 거리가 계기판에 안 찍힌다.**
> 1순위(세션 유실)를 막고 2순위(추이·PR)를 만들면, 최소한 "내 앱을 안 쓸 이유"는 없어진다.
> 3~5순위는 그다음 문제다.

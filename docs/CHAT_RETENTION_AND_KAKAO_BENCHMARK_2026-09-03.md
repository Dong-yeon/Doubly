# 채팅 — 보관 정책·중요 대화 저장·카톡 벤치마킹 (2026-09-03)

> 질문 세 가지: ①채팅을 언제까지 저장할 것인가 ②중요 대화를 저장하는 기능 ③카톡에서
> 가져올 만한 기능. 코드를 먼저 확인하고 답했다. **분석만 했고 구현은 하지 않았다.**

## 0. 결론 먼저

1. **텍스트 보관 기간은 두지 않는다.** 커플 앱에서 채팅은 관계의 아카이브다 — 지우는 게
   손해다. 비용도 텍스트는 무시할 수준이다(§2). **정책이 필요한 건 이미지뿐이다.**
2. **보관을 영구로 둘 거면 검색이 먼저다.** 지금은 30개씩 커서 페이징만 있어서, 반년 전
   대화를 찾으려면 끝없이 스크롤해야 한다. 영구 보관의 가치를 실제로 쓰게 만드는 건
   보관 자체가 아니라 **찾을 수 있는가**다.
3. **"중요 대화 저장"은 두 개의 다른 기능**이다 — 지금 필요한 것(공지 고정)과 나중에 볼
   것(북마크). 커플 앱에는 후자가 더 맞고, 이미 있는 「추억」과 이어붙일 수 있다(§3).
4. 카톡 기능 중 **2인 전용이라 무의미한 것이 절반**이다(§4). 가져올 만한 건 검색·갤러리·
   공지·예약 전송 정도다.
5. **곁가지 발견**: `VOICE_MESSAGE`(채팅 음성 메시지)가 `Feature.java` 에 할당량까지
   선언돼 있는데 **참조하는 코드가 0곳**이다 — 유료 설계만 끝나고 구현이 없다(§5).

## 2. 보관 기간 — 텍스트가 아니라 이미지 문제다

### 2-1. 지금은 영구 보관이고, 그게 맞다

카톡은 서버 보관 기간이 짧아서 기기를 바꾸면 과거 대화가 날아간다(그래서 「톡서랍」을
유료로 판다). Doubly 는 처음부터 서버에 다 있다 — **이건 약점이 아니라 차별점이다.**
커플 앱에서 대화 기록은 관계 그 자체의 기록이라, 보관 기간을 두는 순간 제품 가치를
스스로 깎는다.

### 2-2. 비용 — 텍스트는 걱정할 대상이 아니다

거칠게 계산하면 이렇다.

| 항목 | 가정 | 결과 |
| --- | --- | --- |
| 텍스트 행 | 하루 100통(매우 활발) × 2년, 행당 ~300B | **약 22MB / 커플 / 2년** |
| 1,000커플로 환산 | | 약 22GB — Postgres 로 감당 가능 |
| 사진 | 하루 5장 × 2MB × 1년 | **약 3.6GB / 커플 / 년** |

**두 자릿수 배 차이다.** 텍스트에 보관 기간을 걸어봐야 아끼는 건 거의 없고, 잃는 건
제품의 핵심 가치다. 반면 이미지는 Cloudinary 원가에 직결된다 — PRO 설계 문서가 이미
*"원가형(Cloudinary·Gemini·통화 분)은 PRO도 상한을 둔다"* 는 원칙을 세워 뒀다.

### 2-3. 이미지에만 정책을 두는 세 갈래

- **(a) 현행 유지 — 원본 영구.** 단순하고 사용자에게 최선. 사용자가 늘면 원가가 선형으로 는다.
- **(b) N개월 후 원본 삭제, 썸네일만 유지.** 저장 비용이 급감하지만 "추억이 흐려진다" —
  커플 앱에서 감정적 손실이 크다. 권장하지 않는다.
- **(c) FREE 는 N개월, PRO 는 영구.** 카톡 톡서랍과 같은 모델이고, PRO 설계 원칙 3번
  (*"데이터가 쌓일수록 가치가 커지는 것 = PRO"*)과 정확히 맞물린다.

**지금 결정할 필요는 없다.** Free 티어 자체가 아직 꺼져 있고(`free-trial=true` — 모두
PRO), 실사용 분포도 측정 전이다([FREE_TIER_AND_ADS.md](./FREE_TIER_AND_ADS.md)).
지금 할 일은 **사진 용량을 커플별로 관측할 수 있게 해두는 것**이지, 한도를 정하는 게 아니다.

## 3. 중요 대화 저장 — 사실은 두 개의 기능

한 덩어리로 보이지만 쓰임이 다르다. 섞으면 둘 다 어정쩡해진다.

| | 공지 고정 (pin) | 북마크 (저장) |
| --- | --- | --- |
| 언제 쓰나 | **지금 필요한 것** | **나중에 볼 것** |
| 예 | 오늘 약속 시간, 장보기 목록, 계좌번호 | 고백, 프로포즈, 웃겼던 대화 |
| 위치 | 방 상단 고정 (1개) | 별도 목록 화면 (여러 개) |
| 수명 | 짧다, 자주 교체 | 영구 |
| 카톡 | 있음(공지) | 톡서랍(유료) |

**커플 앱에는 북마크가 더 가치 있다.** 공지는 2인 관계에서 상대적으로 덜 필요하고
(어차피 바로 위에 보인다), 북마크는 **쌓일수록 가치가 커지는 종류**다.

### 3-1. 「추억」과 이어붙이면 강해진다

이미 [MemoriesScreen](../frontend/src/screens/feed/MemoriesScreen.tsx)(작년 오늘)이 있는데
**피드 기록만 본다 — 채팅은 안 들어간다.** 저장한 대화를 추억에 흘려보내면
"1년 전 오늘 이런 얘기를 했었네"가 자동으로 만들어진다. 북마크를 단독 목록으로만 두는 것보다
훨씬 큰 값이 나온다.

### 3-2. 구현 밑그림 (참고)

- 새 테이블 `chat_message_bookmarks(id, relation_id, message_id, saved_by, memo, created_at)`
  — 다음 Flyway 번호는 **V75**(현재 최신 V74).
- **커플 공용으로 본다.** 한쪽이 저장하면 둘 다 보이는 게 이 앱의 결에 맞다
  (`saved_by` 는 누가 저장했는지 표시용).
- **CLAUDE.md 4절 필수**: 테이블을 추가하면 `RelationRecordPurger` 의 삭제 순서를 같이
  고쳐야 한다 — `chat_messages` 를 지우기 **전에** 북마크를 지워야 FK 가 안 깨진다.
  (`UserDataPurger` 는 관계 쪽에 위임하므로 그쪽만 고치면 된다 — 확인함.)
- 롱프레스 메뉴에 "저장하기" 한 줄 추가(지금 4개 → 5개).

## 4. 카톡 기능 전수 검토

**2인 전용이라는 게 가장 큰 필터다.** 카톡 채팅 기능의 상당수가 그룹 전제라 여기선 의미가 없다.

### 가져올 만한 것

| 기능 | 왜 | 비고 |
| --- | --- | --- |
| **대화 검색** | 영구 보관의 짝. 없으면 보관해도 못 찾는다 | Postgres full-text 또는 `LIKE` 부터. 한국어 형태소는 **이미 Kiwi 가 앱에 있다**(띄어쓰기용) — 서버 검색이면 무관하지만, 온디바이스 검색이면 재활용 여지 |
| **사진 모아보기** | 이미지 메시지는 있는데 모아볼 방법이 없다. 코드 주석이 이미 갭으로 인정 | PRO 설계에서 *"우리 대화 갤러리"* 를 **전면 무료**로 못 박아 뒀다 — 정책은 이미 정해져 있고 구현만 없다 |
| **공지 고정** | 약속·목록. 값은 있으나 북마크보다 낮다 | §3 |
| **예약 전송** | 생일 자정 메시지 — 커플 맥락에 잘 맞는다 | 알림 인프라가 이미 있어 재활용 가능 |
| **대화 내보내기** | 백업 심리. `CSV_EXPORT` 가 이미 있어 확장하면 된다 | 원가 낮음 |

### 이미 있는 것 (가져올 필요 없음)

답장 · 이모지 리액션 · 읽음 표시 · 삭제 · 수정 · 스티커/이모티콘 · 배경 꾸미기
(`CUSTOM_BACKGROUND`).

### 2인이라 의미 없는 것

@멘션 · 투표 · 방장 위임 · 초대/내보내기 · 조용히 나가기 · 단톡방 관리 · 오픈채팅 ·
읽지 않은 사람 수 표시. **가져오지 않는다.**

### 판단 유보

- **채팅방 잠금(비밀번호)** — 커플끼리는 서로 폰을 보는 경우가 많아 오히려 덜 필요하다.
  다만 "친구가 내 폰을 볼 때"는 유효하다. 우선순위는 낮게 본다.
- **비밀 채팅(E2E 암호화)** — 프라이버시 가치는 크지만, 서버 검색·백업·다기기 동기화와
  정면으로 충돌한다(암호화하면 서버가 내용을 못 읽으니 §4의 검색이 불가능해진다).
  **영구 보관 + 검색 방향을 택하면 E2E 는 포기하는 것**이라, 둘 중 하나를 골라야 한다.
- **송금·결제** — 범위 밖.

## 5. 곁가지 발견 — 음성 메시지가 선언만 돼 있다

`Feature.java:147` 에 `VOICE_MESSAGE("채팅 음성 메시지", perDay(5), perDay(100))` 가
할당량까지 정해져 선언돼 있는데, **`Feature.VOICE_MESSAGE` 를 참조하는 코드가 0곳**이고
`MessageType` 에도 음성 타입이 없다. 유료 설계만 끝나고 구현이 통째로 없는 상태다.

같은 문서가 `PREMIUM_STICKER` 에 대해 *"이미 선언돼 있으나 어디서도 판정하지 않는"* 이라고
적은 적이 있는데, 그건 그 뒤 연결됐고(참조 3곳) **`VOICE_MESSAGE` 만 남았다.**

음성 메시지는 카톡에도 있고 커플 앱과 궁합이 좋다(목소리는 텍스트로 안 되는 걸 한다).
다만 원가형(저장·전송)이라 이미 상한이 설계돼 있으니, 구현할 거면 그 설계를 그대로 쓰면 된다.

## 6. 권장 순서

근거는 "지금 있는 것의 가치를 실제로 꺼내 쓰게 만드는가"다.

1. **대화 검색** — 영구 보관을 이미 하고 있는데 쓸 방법이 없다. 새 데이터를 만들지 않고
   기존 자산의 가치를 여는 유일한 항목이라 1순위다.
2. **사진 모아보기** — 정책(무료)까지 정해져 있고 구현만 없다. 검색과 화면을 공유할 수 있다.
3. **중요 대화 북마크** (+ 추억 연결) — 새 테이블이 필요하지만 커플 앱의 결에 가장 맞는다.
4. **음성 메시지** — 설계가 끝나 있어 착수 비용이 낮다. 다만 원가형이라 Free 티어 정책과
   함께 봐야 한다.
5. **예약 전송 · 대화 내보내기 · 공지 고정** — 있으면 좋지만 위 넷보다 뒤.

**보관 기간 정책은 목록에 없다.** 지금 정할 이유가 없고(§2-3), 정해야 할 때가 오면
그건 텍스트가 아니라 사진에 대한 결정이다.

## 7. 추가 발견 — 사진 다운로드/저장 기능이 아예 없다 (2026-09-03, 분석만)

사진 모아보기(§6-2, 이번에 구현)를 실기기에서 확인하던 중 발견. **분석만 했고 구현은
하지 않았다.**

### 현재 상태

- `expo-media-library`(갤러리 저장), `expo-sharing`(공유 시트) **둘 다 미설치**
  (`frontend/package.json` 확인).
- [ImageViewer.tsx](../frontend/src/components/ImageViewer.tsx) — 채팅·사진 모아보기·
  피드 사진첩이 **공용으로 쓰는** 전체화면 뷰어인데, 닫기(X) 버튼만 있고 저장·공유
  버튼이 없다. 카톡·인스타그램 등엔 당연히 있는 "길게 눌러 저장" 또는 저장 아이콘이
  이 앱엔 아예 없다.
- 영향 범위 — ImageViewer 하나만 고치면 채팅 사진·피드 사진(PhotoAlbumScreen)·
  방문 인증샷(럽슐랭)·여행 커버 이미지 등 앱이 보여주는 **모든 사진에 한 번에 적용**된다
  (공용 컴포넌트라는 게 여기선 장점).

### 필요한 것

1. `expo-media-library` 추가 — 저장 권한 요청 + `MediaLibrary.saveToLibraryAsync(uri)`.
2. 이미지가 원격 URL(Cloudinary)이라 먼저 로컬로 받아야 한다 — `expo-file-system`
   (이미 설치돼 있음, 새 의존성 아님)의 `FileSystem.downloadAsync` 로 임시 파일을
   만든 뒤 ①에 넘긴다.
3. ImageViewer 의 닫기 버튼 옆에 저장 아이콘 추가, 저장 중 로딩·성공/실패 토스트.
4. (보완) `expo-sharing` 으로 "공유하기"(카톡 등으로 바로 전달)도 같이 넣으면
   카톡의 "전달하기"에 대응하는 값이 생긴다 — §4 표의 "가져올 만한 것"에 없던 항목이지만
   같은 성격이라 여기 붙여도 자연스럽다.

### 난이도·우선순위

새 패키지 1개(`expo-media-library`) + ImageViewer 버튼 1개로 **전체 화면에 한 번에
적용**되는, 착수 비용이 낮은 항목이다. §6 순서에 넣는다면 "사진 모아보기" 바로 다음이
자연스럽다 — 모아보기를 만들어 놓고 저장을 못 하면 절반짜리 기능이기 때문.
